📊 数据库选型指南

根据需求选择最适合的数据库，避免技术选型踩坑

数据库类型概览

类比：选择数据库就像选择交通工具——去近的地方骑自行车（简单快速），去远的地方开车（功能强大），运大量货物用货车（高吞吐）。不同的场景需要不同的工具。

主流数据库分类

类型代表产品数据模型适用场景
关系型数据库MySQL, PostgreSQL, Oracle表格、行、列结构化数据，复杂查询，事务
文档数据库MongoDB, CouchDBJSON文档灵活的数据结构，快速开发
键值数据库Redis, MemcachedKey-Value缓存、会话管理、配置存储
列族数据库Cassandra, HBase列族海量数据写入，时间序列
图数据库Neo4j, ArangoDB节点、边社交网络、推荐系统、知识图谱
时序数据库InfluxDB, TimescaleDB时间戳+值监控、IoT、日志
向量数据库Milvus, FAISS, Pinecone向量相似度搜索、RAG、推荐
向量扩展pgvector (PostgreSQL), MySQL 9.x VECTOR向量（嵌入关系型）已有PG/MySQL团队、中小规模向量检索

扩展知识：现代应用往往需要多种数据库协同工作（多库架构）。例如：MySQL存用户数据 + Milvus存向量 + Redis做缓存。此外，越来越多的数据库开始原生支持混合搜索（向量+全文检索），如 PostgreSQL 的 pgvector + tsvector 组合、Milvus 2.5+ 内置的 BM25 全文检索等，使得单库即可完成多种检索任务。

选型决策

✅ 选择Milvus

  • 需要分布式支持
  • 数据量超过1亿向量
  • 需要高可用和容灾
  • 愿意投入运维成本

✅ 选择FAISS/Chroma

  • 数据量较小（<1000万）
  • 快速原型开发
  • 不需要分布式
  • 学习和实验

pgvector：已有PostgreSQL团队的最佳选择

  • pgvector 是 PostgreSQL 的向量检索扩展，安装后即可在熟悉的 PG 实例中存储和查询向量
  • 无需额外部署和运维独立的向量数据库，降低架构复杂度
  • 支持 IVFFlat、HNSW 索引，千万级向量数据性能表现良好
  • 可与 PostgreSQL 的 SQL 能力无缝结合——在同一查询中同时做向量检索和结构化过滤
  • 适合中小规模 RAG 项目、需要向量+关系数据联合查询的场景

MySQL 9.x VECTOR 类型（实验性）

MySQL 9.0+ 开始引入原生 VECTOR 数据类型和向量距离函数，标志着 MySQL 也在向量检索领域发力。目前该特性仍处于实验性阶段，功能和索引支持远不如 pgvector 成熟。如果你的团队使用 MySQL 且对向量检索需求较轻，可以持续关注其演进；生产环境仍建议搭配 Milvus 或 pgvector。

混合数据库架构

类比：混合数据库架构就像一个完整的公司——MySQL是财务部（处理结构化交易数据），Milvus是市场部（处理用户行为向量），Redis是前台（快速响应请求）。每个部门专注自己的领域，通过协作完成整体目标。

数据分片策略

策略说明适用场景
水平分片同一表的数据分散到多个数据库数据量超大，单机无法存储
垂直分片不同业务的表放在不同数据库业务逻辑清晰分离
功能分片不同类型的数据用不同数据库关系数据 + 向量数据 + 缓存

数据一致性方案

方案一致性延迟复杂度适用场景
强一致最高高高金融交易
最终一致中低中大多数Web应用
弱一致低最低低非关键数据

实践建议：大多数RAG应用采用最终一致性方案即可。用户数据存MySQL，向量数据存Milvus，通过CDC或双写保持同步，允许几秒钟的延迟。

混合搜索新趋势：传统架构需要 MySQL + Milvus 两套系统分别负责关键词检索和向量检索。随着技术演进，混合搜索正逐渐走向原生化：PostgreSQL 通过 pgvector + tsvector 可在单库内同时完成语义搜索和全文搜索；Milvus 2.5+ 内置了 BM25 全文检索能力，不再需要为关键词搜索单独维护一个 MySQL。对于新建项目，简化架构、减少数据同步复杂度是一个值得考虑的方向。
