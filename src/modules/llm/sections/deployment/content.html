推理核心概念

理解这些概念对于选择和优化推理方案至关重要。

连续批处理（Continuous Batching）

类比：传统批处理像公交车——必须等所有人到齐才发车。连续批处理像地铁——每到一站都有人上下车，不用等所有人一起。vLLM的核心创新就在于此。

文本
# 连续批处理 vs 静态批处理

静态批处理（传统方式）：
  - 一个batch中所有请求必须同时完成
  - 短请求完成后空等长请求，GPU空闲浪费
  - 吞吐量低

连续批处理（vLLM/SGLang核心）：
  - 某个请求完成后立即插入新请求
  - GPU始终保持忙碌，无空闲等待
  - 吞吐量提升2-10倍

PagedAttention与KV Cache优化

文本
# KV Cache是推理时最大的显存消耗者

问题：每个请求需要缓存所有已生成token的Key和Value
  - 长上下文请求（如32K tokens）会占用大量显存
  - 传统方式为每个请求预分配最大长度的显存，造成浪费

PagedAttention（vLLM的解决方案）：
  - 借鉴操作系统虚拟内存的分页思想
  - 将KV Cache分成固定大小的"页"
  - 按需分配，不需要连续内存
  - 显存利用率从约20-40%提升到>95%

RadixAttention（SGLang的方案）：
  - 使用Radix Tree（基数树）管理KV Cache
  - 自动复用相同前缀的KV Cache
  - 特别适合多轮对话和few-shot场景

推测解码（Speculative Decoding）

文本
# 推测解码：用小模型加速大模型推理

原理：
  1. 小模型（Draft Model，如1B）快速生成N个候选token
  2. 大模型（Target Model，如70B）一次性验证这N个token
  3. 接受正确前缀，拒绝后面的错误token
  4. 输出质量与大模型完全一致，但速度快2-3倍

适用场景：
  - 延迟敏感的应用（如实时聊天）
  - 有合适的小模型可作为Draft Model
  - GPU算力充足，大模型推理是瓶颈

vLLM使用：
  vllm serve your-model --speculative-model draft-model --num-speculative-tokens 5

结构化输出（Structured Output）

文本
# 结构化输出 / 引导生成（Guided Generation）

服务化部署

FastAPI服务

Python
from fastapi import FastAPI
from pydantic import BaseModel
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

app = FastAPI()

# 加载模型
model_name = "./my_model"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name).to("cuda")

class GenerateRequest(BaseModel):
    prompt: str
    max_length: int = 512
    temperature: float = 0.7

@app.post("/generate")
def generate(request: GenerateRequest):
    # 注意：同步推理函数用def，不要用async def
    # torch推理是同步阻塞操作，用async会阻塞事件循环
    inputs = tokenizer(request.prompt, return_tensors="pt").to("cuda")

    with torch.no_grad():
        outputs = model.generate(
            **inputs,
            max_length=request.max_length,
            temperature=request.temperature,
            do_sample=True
        )

    response = tokenizer.decode(outputs[0], skip_special_tokens=True)
    return {"response": response}

# 如果确实需要async，使用run_in_executor避免阻塞事件循环：

#     loop = asyncio.get_event_loop()
#     result = await loop.run_in_executor(None, sync_generate, request)
#     return result

SGLang部署

SGLang（v0.5.10）：2025-2026年快速崛起的推理框架，与vLLM形成双雄竞争。其RadixAttention技术在多轮对话和结构化输出场景下表现优异。

Bash 
# 安装SGLang
pip install sglang[all]

# 启动SGLang服务
python -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --port 30000 \
    --tp 1

# 客户端调用（兼容OpenAI API）
curl http://localhost:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "meta-llama/Llama-3.1-8B-Instruct",
    "messages": [{"role": "user", "content": "Hello"}]
  }'

vLLM vs SGLang选择建议：

  • 通用推理服务：两者都很好，vLLM社区更大
  • 多轮对话/Agent：SGLang的RadixAttention有天然优势
  • 结构化输出：SGLang原生支持更好
  • 大规模部署：两者都支持TP/PP分布式，看具体硬件兼容性

TensorRT-LLM部署

TensorRT-LLM（v1.2.1）：NVIDIA官方的LLM推理优化引擎。通过算子融合、量化优化、自定义CUDA内核等技术，在NVIDIA GPU上实现极致推理性能。适合对延迟和吞吐量有严格要求的生产环境。

Bash
# 安装TensorRT-LLM
pip install tensorrt-llm

# 转换模型（HuggingFace → TensorRT-LLM格式）
python convert_checkpoint.py \
    --model_dir ./your-hf-model \
    --output_dir ./trt-llm-ckpt \
    --dtype float16

# 构建TensorRT引擎
trtllm-build \
    --checkpoint_dir ./trt-llm-ckpt \
    --output_dir ./trt-engine \
    --gemm_plugin float16 \
    --max_batch_size 8 \
    --max_input_len 2048 \
    --max_seq_len 4096

# 运行推理
python run.py \
    --engine_dir ./trt-engine \
    --max_output_len 256 \
    --input_text "Hello, how are you?"

注意事项：TensorRT-LLM需要为特定的模型架构和GPU型号构建引擎，不具有跨平台通用性。适合固定模型、固定硬件的大规模部署场景。

本地部署：GGUF + Ollama

GGUF格式：llama.cpp项目定义的模型格式，专为高效CPU/GPU混合推理设计。支持多种量化方案（Q4_K_M、Q5_K_M、Q8_0等），是本地部署LLM的事实标准格式。Ollama让本地部署变得极其简单。

Bash 
# Ollama：最简单的本地LLM部署方案
# 1. 安装Ollama：https://ollama.com

# 2. 一行命令运行模型
ollama run llama3.1:8b

# 3. Ollama也提供API服务（默认端口11434）
curl http://localhost:11434/api/generate \
  -d '{"model": "llama3.1:8b", "prompt": "Hello"}'

# 常见量化级别：
# Q4_K_M  → 4-bit量化，显存约4-5GB（7B模型），推荐日常使用
# Q5_K_M  → 5-bit量化，显存约5-6GB，质量更好
# Q8_0    → 8-bit量化，显存约8-9GB，几乎无质量损失

# llama.cpp直接使用GGUF：
# ./llama-cli -m model.gguf -p "Hello" -n 128

Ollama适用场景：

  • 本地开发和测试（无需GPU服务器）
  • 隐私敏感场景（数据不离开本机）
  • 快速原型验证
  • 在Apple Silicon（M系列芯片）上运行效果尤佳

多LoRA服务

多LoRA服务：一个基座模型同时服务多个LoRA适配器。比如一个7B基座模型同时服务"法律助手""医疗助手""编程助手"三个不同LoRA，共享基座权重，大幅降低部署成本。

Bash
# vLLM多LoRA服务
vllm serve meta-llama/Llama-3.1-8B-Instruct \
    --enable-lora \
    --lora-modules legal_lora=./lora_legal medical_lora=./lora_medical \
    --max-lora-rank 16

# 请求时指定LoRA适配器
curl http://localhost:8000/v1/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "legal_lora",
    "prompt": "解释合同法中的要约与承诺",
    "max_tokens": 256
  }'

# SGLang同样支持多LoRA
python -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --lora-paths legal=./lora_legal medical=./lora_medical \
    --enable-lora

多LoRA的优势：基座模型的显存只需加载一次（约14GB for 7B FP16），每个LoRA适配器仅额外占用几十MB。一个GPU即可服务多个专业领域模型，显著降低部署成本。
