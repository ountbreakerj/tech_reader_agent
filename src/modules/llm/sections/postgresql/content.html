PostgreSQL vs MySQL

类比：如果把MySQL比作一辆经济型轿车（简单、实用、省油），那么PostgreSQL就像一辆豪华SUV（功能丰富、性能强大、适合复杂场景）。两者都是好车，但适用于不同的驾驶需求。

选型建议

✅ 选择MySQL

  • 简单的CRUD应用
  • 读密集型场景
  • 快速开发和原型
  • 已有MySQL生态
  • 团队MySQL经验丰富

✅ 选择PostgreSQL

  • 复杂的查询和分析
  • 地理空间数据（PostGIS）
  • JSON文档存储
  • 需要高数据完整性
  • 未来可能需要扩展功能

我的建议：如果是新项目且团队愿意学习，推荐PostgreSQL。它的功能更强大，扩展性更好，社区活跃。很多云服务（AWS RDS、Google Cloud SQL）都支持PostgreSQL。

maintenance_work_mem = 64MB         # 维护操作内存
effective_cache_size = 4GB          # 操作系统缓存大小（建议物理内存的50%）

# WAL配置（写前日志）

checkpoint_completion_target = 0.9
max_wal_size = 1GB

# 查询优化
random_page_cost = 1.1              # SSD硬盘设为1.1，HDD设为4
effective_io_concurrency = 200     # SSD设为200

# 日志
logging_collector = on
log_directory = 'log'
log_filename = 'postgresql-%Y-%m-%d.log'
log_min_duration_statement = 1000  # 慢查询阈值（毫秒）

# 字符集
client_encoding = UTF8

性能调优原则：PostgreSQL的性能主要由shared_buffers、work_mem和effective_cache_size三个参数决定。生产环境中，shared_buffers设为物理内存的25%，effective_cache_size设为50%。

高级SQL特性

窗口函数

类比：普通聚合函数（GROUP BY）会把多行数据压缩成一行。窗口函数则在保留所有行的同时，对周围的行进行计算。就像在Excel中计算滑动平均值。

窗口函数的基本语法：

SQL 
函数() OVER (
    PARTITION BY 分组字段   -- 可选，按什么分组
    ORDER BY 排序字段       -- 可选，按什么排序
    ROWS BETWEEN ... AND ... -- 可选，窗口范围
)

排名函数

SQL 
# ROW_NUMBER：行号（没有并列，1,2,3,4,5）
SELECT
    name,
    score,
    ROW_NUMBER() OVER (ORDER BY score DESC) AS rank
FROM students;

# RANK：排名（有并列，1,2,2,4,5）
SELECT
    name,
    score,
    RANK() OVER (ORDER BY score DESC) AS rank
FROM students;

# DENSE_RANK：密集排名（有并列，1,2,2,3,4）
SELECT
    name,
    score,
    DENSE_RANK() OVER (ORDER BY score DESC) AS rank
FROM students;

PARTITION BY分组

SQL 
# 每个部门内部的员工薪资排名
SELECT
    department,
    name,
    salary,
    RANK() OVER (
        PARTITION BY department   # 按部门分组
        ORDER BY salary DESC      # 组内按薪资降序
    ) AS dept_rank
FROM employees;

LAG/LEAD：前一行/后一行

SQL 
# 计算每天的销售额变化
SELECT
    date,
    amount,
    LAG(amount, 1) OVER (ORDER BY date) AS prev_amount,
    amount - LAG(amount, 1) OVER (ORDER BY date) AS change
FROM daily_sales;

# 计算移动平均值
SELECT
    date,
    amount,
    AVG(amount) OVER (
        ORDER BY date
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW  # 前2行到当前行
    ) AS moving_avg_3days
FROM daily_sales;

窗口函数使用场景：排名、滑动平均、环比同比计算、累计求和、分组内排名等。是数据分析和报表开发的利器。

CTE（Common Table Expressions）

类比：CTE就像是临时视图，让你在查询中定义一个临时的结果集，然后在主查询中引用它。递归CTE则可以处理层次结构数据（如组织架构、产品分类）。

基础CTE

SQL 
# 使用CTE提高查询可读性
WITH active_users AS (
    SELECT id, username, email
    FROM users
    WHERE status = 'active'
),
user_orders AS (
    SELECT
        user_id,
        COUNT(*) AS order_count,
        SUM(total_amount) AS total_spent
    FROM orders
    GROUP BY user_id
)
SELECT
    au.username,
    au.email,
    COALESCE(uo.order_count, 0) AS orders,
    COALESCE(uo.total_spent, 0) AS spent
FROM active_users au
LEFT JOIN user_orders uo ON au.id = uo.user_id;

递归CTE（层次结构查询）

SQL 
# 查询组织架构的所有层级
WITH RECURSIVE org_tree AS (
    # 锚点成员：根节点
    SELECT
        id,
        name,
        manager_id,
        0 AS level,
        name::TEXT AS path
    FROM employees
    WHERE manager_id IS NULL  # CEO

    UNION ALL

    # 递归成员：下属
    SELECT
        e.id,
        e.name,
        e.manager_id,
        ot.level + 1,
        ot.path || ' -> ' || e.name
    FROM employees e
    INNER JOIN org_tree ot ON e.manager_id = ot.id
)
SELECT
    REPEAT('  ', level) || name AS org_chart,
    path
FROM org_tree
ORDER BY path;

递归CTE应用场景：组织架构、产品分类、评论嵌套、文件夹结构、物料清单（BOM）等任何层次结构数据。

JSON/JSONB数据类型

类比：如果关系型数据库是结构化的Excel表格，那么JSONB就像是Excel中的单元格可以存储任意JSON文档。你可以像查询关系型数据一样查询JSON内部的数据，还能建立索引。

JSON vs JSONB

类型特点使用场景
JSON存储原始JSON文本，保留格式写入频繁，查询少
JSONB二进制存储，查询快，支持索引查询频繁（推荐）

创建带JSONB的表

SQL 
# 创建产品表，使用JSONB存储灵活的属性
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    category VARCHAR(50),
    attributes JSONB DEFAULT '{}'::JSONB,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

# 插入JSONB数据
INSERT INTO products (name, category, attributes)
VALUES (
    'iPhone 15',
    '手机',
    '{"brand": "Apple", "storage": 256, "color": "黑色", "specs": {"screen": "6.1寸", "battery": "3349mAh"}}'::JSONB
);

查询JSONB

SQL 
# 查询JSONB字段
SELECT
    name,
    attributes->'brand' AS brand,
    attributes->>'storage' AS storage_gb
FROM products;

# 查询嵌套字段
SELECT
    name,
    attributes#>> '{specs, screen}' AS screen_size
FROM products;

# 条件过滤JSONB
SELECT * FROM products
WHERE attributes->>'brand' = 'Apple';

# 检查JSONB是否包含某个键
SELECT * FROM products
WHERE attributes @> '{"color": "黑色"}'::JSONB;

# 展开JSONB数组
SELECT
    name,
    value
FROM products,
    jsonb_array_elements_text(attributes->'tags') AS value;

JSONB索引

SQL 
# GIN索引：支持@>、?、?|、?&操作符
CREATE INDEX idx_attrs ON products USING GIN (attributes);

# B-tree索引：针对特定字段
CREATE INDEX idx_brand ON products ((attributes->>'brand'));

# 复合索引
CREATE INDEX idx_category_brand ON products (category, (attributes->>'brand'));

JSONB最佳实践：

  • 固定字段用列存储，灵活字段用JSONB
  • JSONB字段务必建立GIN索引
  • 频繁查询的JSONB字段可以单独建B-tree索引
  • 考虑使用物化视图预计算JSONB查询结果

高级索引

PostgreSQL支持多种索引类型，针对不同数据类型和查询模式：

索引类型数据类型适用场景
B-tree所有类型等值查询、范围查询（默认，最常用）
Hash所有类型只用于等值查询（PostgreSQL 10+）
GiST几何、全文搜索、JSONB范围查询、相似度搜索
SP-GiST电话号码、IP地址不平衡数据结构
GIN数组、JSONB、全文搜索包含查询、全文搜索
BRIN时间序列、自增ID物理顺序与逻辑顺序相关的大表

部分索引

SQL 
# 只为未处理的订单建立索引（节省空间）
CREATE INDEX idx_pending_orders ON orders (created_at)
WHERE status = 'pending';

# 只为高分记录建立索引
CREATE INDEX idx_high_scores ON players (score)
WHERE score > 1000;

表达式索引

SQL 
# 不区分大小写的索引
CREATE INDEX idx_email_lower ON users (LOWER(email));

# 使用该索引的查询
SELECT * FROM users
WHERE LOWER(email) = 'john@example.com';

EXPLAIN ANALYZE详解

SQL 
# 分析查询执行计划（实际执行）
EXPLAIN ANALYZE
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.created_at > '2024-01-01'
GROUP BY u.id
ORDER BY order_count DESC
LIMIT 10;

关键指标解读：

  • Seq Scan：全表扫描（可能需要索引）
  • Index Scan：索引扫描（好）
  • Bitmap Index Scan：位图索引扫描（好）
  • rows：预估行数 vs 实际行数差距大时需要ANALYZE
  • actual time：实际执行时间（毫秒）

性能优化

连接池（PgBouncer）

PostgreSQL每个连接都会启动一个后端进程，连接数过多会消耗大量资源。PgBouncer是一个轻量级连接池，可以显著提升性能。

Bash 
# 安装PgBouncer
sudo apt install pgbouncer -y

# 配置 /etc/pgbouncer/pgbouncer.ini
[databases]
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction  # 事务级连接池（推荐）
max_client_conn = 1000
default_pool_size = 20

VACUUM和ANALYZE

SQL 
# VACUUM：清理死元组，回收空间
VACUUM users;

# VACUUM FULL：完全清理（会锁表）
VACUUM FULL users;

# ANALYZE：更新统计信息，帮助优化器选择更好的执行计划
ANALYZE users;

# 同时执行VACUUM和ANALYZE
VACUUM ANALYZE users;

VACUUM策略：PostgreSQL默认开启autovacuum，会自动清理。但对更新频繁的表，建议手动定期执行 VACUUM ANALYZE。

分区表

SQL 
# 创建分区表（按时间范围）
CREATE TABLE events (
    id SERIAL,
    event_type VARCHAR(50),
    payload JSONB,
    created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

# 创建分区
CREATE TABLE events_2024_01 PARTITION OF events
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE events_2024_02 PARTITION OF events
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

# 查询会自动只扫描相关分区
SELECT * FROM events
WHERE created_at >= '2024-01-15'
AND created_at < '2024-02-01';

分区优势：对大表（千万级以上）按时间或其他字段分区，可以显著提升查询性能和维护效率。PostgreSQL 10+支持声明式分区。

pgvector：PostgreSQL的向量扩展

类比：pgvector 就像是给 PostgreSQL 装上了一个"语义搜索引擎"。原本只能用关键词精确匹配的数据库，现在可以直接存储和搜索 AI 模型生成的向量嵌入，让你在同一个数据库中同时管理结构化数据和向量数据。

pgvector 是 PostgreSQL 的向量检索扩展，在 LLM/RAG 应用中极为重要。它让你无需引入独立的向量数据库，直接在 PostgreSQL 中完成向量存储和相似度搜索。

安装与基本使用

SQL 
# 安装pgvector扩展
CREATE EXTENSION vector;

# 创建带向量列的表
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    content TEXT,
    metadata JSONB,
    embedding vector(768)  # 768维向量（对应常用Embedding模型输出维度）
);

# 插入向量数据
INSERT INTO documents (content, embedding)
VALUES (
    '机器学习是人工智能的一个分支',
    '[0.1, 0.2, -0.3, ...]'::vector
);

索引类型

索引类型原理特点适用场景
IVFFlat倒排文件索引 + 聚类构建快，内存适中中等规模数据（百万级）
HNSW分层可导航小世界图查询快，召回率高，内存较大频繁查询，低延迟要求（推荐）
SQL 
# HNSW索引（推荐，查询性能最好）
CREATE INDEX idx_embedding_hnsw ON documents
USING hnsw (embedding vector_cosine_ops);

# IVFFlat索引（构建更快，适合批量导入场景）
CREATE INDEX idx_embedding_ivf ON documents
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

相似度搜索操作符

操作符距离类型说明索引操作类
<->L2（欧氏距离）两点间的直线距离vector_l2_ops
<#>内积负内积（值越小越相似）vector_ip_ops
<=>余弦距离1 - 余弦相似度（最常用）vector_cosine_ops

RAG 文档检索完整示例

SQL 
# 创建Embeddings表
CREATE TABLE knowledge_base (
    id SERIAL PRIMARY KEY,
    title TEXT,
    content TEXT,
    source TEXT,
    embedding vector(768)
);

# 创建HNSW索引（余弦距离）
CREATE INDEX idx_kb_embedding ON knowledge_base
USING hnsw (embedding vector_cosine_ops);

# 查询与给定问题最相关的文档（余弦相似度 Top 5）
SELECT
    title,
    content,
    1 - (embedding <=> '[0.1, 0.2, -0.3, ...]'::vector) AS similarity
FROM knowledge_base
ORDER BY embedding <=> '[0.1, 0.2, -0.3, ...]'::vector
LIMIT 5;

pgvector vs 独立向量数据库：pgvector 最大的优势是与 PostgreSQL 生态无缝集成——你可以在同一个事务中完成向量搜索和关系型查询，无需维护额外基础设施。对于中小规模 RAG 应用（百万级文档），pgvector 是绝佳选择。超大规模场景仍推荐 Milvus 等专用向量数据库。

动手练习

✏️ 动手练习（进阶）

目标：用窗口函数实现一个销售排行榜和移动平均分析。

数据准备：

① 创建 sales 表（id、product_id、sale_date、amount）

② 插入至少30天的销售数据（可以随机生成）

要求：

① 计算每个产品的累计销售额（SUM OVER）

② 计算每日销售额的7天移动平均（AVG OVER ROWS）

③ 计算每个产品的销售额排名（RANK）

④ 计算与前一天的销售额差异（LAG）

✏️ 动手练习（进阶）

目标：用递归CTE查询组织架构的所有层级。

数据准备：

① 创建 employees 表（id、name、manager_id、department）

② 插入一个至少5层的组织架构（CEO → VP → Director → Manager → Employee）

要求：

① 查询从CEO到每个员工的完整路径

② 计算每个员工的层级深度

③ 统计每个管理层级的直接下属数量

④ 查询某个VP下的所有下属（递归）

✏️ 动手练习（进阶）

目标：用JSONB存储和查询灵活的用户配置数据。

数据准备：

① 创建 user_profiles 表（id、username、profile JSONB）

② profile字段包含：基本信息（name、age、email）、偏好设置（theme、language、notifications）、社交链接（github、twitter）

要求：

① 插入5个用户的配置数据

② 查询所有使用暗黑模式的用户

③ 查询有GitHub链接的用户

④ 为JSONB字段创建GIN索引

⑤ 对比有索引和无索引的查询性能
