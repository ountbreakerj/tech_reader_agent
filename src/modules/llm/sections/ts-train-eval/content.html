Agent 评估：任务解剖与轨迹指标

评估 Agent 和评估单轮 QA 有本质区别：正确的最终答案不等于正确的执行过程，而错误的执行过程即使碰巧得到正确答案，也是不可靠的 Agent。

评估任务的四个组成部分

  • 初始状态：环境可重置到特定状态（沙箱、数据库快照）。
  • 用户目标：任务描述，可以是自然语言或结构化 spec。
  • 可用工具：工具集合及其行为定义。
  • 验证条件：程序化验证器（检查文件状态、测试通过率）或 LLM-as-a-Judge。

Pass@k 与 Pass^k

这两个指标测量不同的东西：

  • Pass@k：k 次独立运行里至少一次成功的概率。衡量能力上限——模型在最好情况下能做到什么。Pass@k = 1 - (1-p)^k
  • Pass^k（也叫 Mean Pass@k）：k 次独立运行全部成功的概率。衡量业务可靠性——用户每次都能得到正确结果的概率。Pass^k = p^k

数字说话：单次成功率 90% 看起来很高，但 Pass^5 = 0.9^5 ≈ 59%——意味着 5 次任务里有 2 次会失败。生产系统应看 Pass^k，而不是 Pass@k。

LLM-as-a-Judge 与失败归因

LLM-as-a-Judge 的设计要点

  • Rubric 设计：让模型按 1–5 打分几乎没有意义，分数的含义没有锚定。更可靠的方式：成对比较（A vs B 哪个更好），或二分类（这个答案是否满足了用户的核心需求）。
  • 位置偏差：在成对比较中，模型倾向于偏向列在前面的答案。缓解：随机化顺序，分两次比较（A vs B 和 B vs A）取平均。
  • 长度偏差：模型倾向于认为更长的回复更好。缓解：在 rubric 里明确说明评价的是质量而非长度。
  • 一致性校验：用 Cohen's Kappa 或 Krippendorff's Alpha 衡量 judge 与人工标注的一致性，通常需要 κ > 0.6 才能信任。

失败归因：定位第一个出错的步骤

只看最终结果失败，无法指导改进——模型是在哪一步出错的？工具调用参数写错了？检索到的文档不相关？规划步骤遗漏了？

归因方法：对每一步的输入输出独立评分，找到第一个得分异常的步骤。这要求记录完整轨迹（每次工具调用的入参、返回值、模型的思考链），这也是为什么可观测性是评估基础设施的核心组件。

SFT vs RL 的本质区别：SFT 是模仿——模型学习复制示范轨迹，容易学到正确的表面格式，但不能泛化到训练集之外的场景。RL 是探索——模型从自己的输出中获得反馈信号，可以发现新的策略，但需要可靠的奖励来源。

什么时候先做 Mid-training：当目标任务的知识完全不在预训练数据里时（小众语言、专有领域知识、最新事件），直接做 SFT/RL 会发现模型根本「不知道」正确答案，强化正确的格式没有意义。先用领域数据继续预训练，补充底层知识，再做 SFT/RL 对齐格式与偏好。

偏好优化家族：DPO、GRPO 与 ORPO

DPO（直接偏好优化）

DPO 把「学习偏好」的问题重构成一个分类问题——不需要训练单独的 reward model，直接从 (chosen, rejected) 对的对数似然比中提取训练信号。直觉：如果模型对 chosen 的对数概率比 rejected 高 β 倍以上，就认为已经对齐了。实践中 DPO 训练稳定，是目前最常用的偏好优化基线。

GRPO（组内相对偏好优化）

GRPO 适合有可验证奖励的场景（代码是否通过测试、答案是否正确）。做法：对同一个 prompt 采样 G 个响应，计算每个响应相对于组内均值的优势，用这个相对优势训练模型。优势是 GRPO 省掉了 value model（PPO 需要的），训练代价更低，且天然适合二元可验证奖励（对/错）而不需要连续分值。

ORPO

ORPO 把 SFT 损失和偏好对齐损失合并成一步，OR（Odds Ratio）损失的正确公式带负号：

L_OR = -log σ(log(odds_θ(chosen) / odds_θ(rejected)))

注意负号不可省略，去掉后优化方向反了。

PPO 的现状

PPO 已移入 TRL 的 trl.experimental.ppo，官方标注将从 trl.trainer 移除。新版参数名改为 processing_class（不是 tokenizer），训练由 trainer.train() 驱动而非手动 step() 循环。生产场景更常用 DPO 或 GRPO。

LoRA 与参数高效微调

LoRA（Low-Rank Adaptation）的核心思想：微调时不修改原始权重 W，而是学习一个低秩分解的增量 ΔW = AB，其中 A ∈ R^{d_in × r}，B ∈ R^{r × d_out}，r 远小于 d_in 和 d_out。

可训练参数量计算

每个 LoRA 层的参数量：r × (d_in + d_out)。对 Llama-3.1-8B（GQA 结构），q_proj 是 4096×4096，o_proj 是 4096×4096，k/v_proj 由于 GQA 是 4096×1024，r=8：

q_proj: 8 × (4096+4096) × 32层 = 2,097,152
k_proj: 8 × (4096+1024) × 32层 = 1,310,720
v_proj: 8 × (4096+1024) × 32层 = 1,310,720
o_proj: 8 × (4096+4096) × 32层 = 2,097,152
总计 ≈ 6,815,744 ≈ 6.8M 参数，占全模型约 0.085%。

这就是为什么 LoRA 可以在单 24GB GPU 上微调 8B 模型——可训练参数只有约 7M，梯度和优化器状态的显存消耗微乎其微。

r 和 alpha 的取值

  • r（秩）：常用 8、16、32、64。r 越大表达能力越强，但可训练参数更多。对于格式和风格的对齐，r=8 通常足够；对于需要学习新知识的任务，r=32 或 64 更稳妥。
  • alpha（缩放因子）：实际学习率缩放为 alpha/r，常见做法 alpha=2r（即 alpha=16 对 r=8）保持缩放比例不变，或固定 alpha=16/32。
  • QLoRA：用 4-bit NF4 量化冻结原始权重，再在量化基础上做 LoRA，可以把 8B 模型的总显存需求压到 6–8GB，但训练速度比 bf16 LoRA 慢约 20–30%。

多 Agent 协作：拓扑与失败模式

什么时候多 Agent 真的有价值

多 Agent 不是免费的——协调开销、错误传播、调试复杂度都是真实代价。多 Agent 真正优于单 Agent 的条件：

  • 子任务可以真正并行（不共享可变状态，彼此不依赖）
  • 每个子任务的上下文可以完全隔离（子 Agent 不需要整个主任务的历史）
  • 任务规模超出单个上下文窗口的处理能力

六种失败模式（附根因）

  • 并发写冲突：多个 Agent 同时修改同一文件。根因：共享可变状态没有加锁。修复：每个 Agent 只写自己的工作区，最后由合并者负责整合。
  • 错误级联放大：Agent A 的错误输出被 Agent B 当作事实，被 Agent C 放大。根因：下游 Agent 没有独立验证输入。修复：关键信息在传递前做格式和语义验证。
  • 同质趋同：让多个「独立」Agent 交叉审查，但它们用相同的提示词和模型，给出相同的错误。根因：没有真正的多样性。修复：用不同模型、不同提示词、不同解题角度。
  • 互相扯皮：两个 Agent 在循环里互相把锅推给对方，都不作为。根因：没有定义谁有最终决策权。修复：明确所有权边界，陷入循环时升级到管理者或人类。
  • 循环失控：Agent 陷入无限循环，没有终止条件。根因：缺少步数上限和进度检测。修复：强制步数预算 + 进度验证（每步之后检查是否比上一步更接近目标）。
  • 理解债：系统变复杂后，没有人（包括设计者）能说清楚单次失败是哪个 Agent 的问题。根因：可观测性不够，各 Agent 的输入输出没有记录。修复：在设计阶段就规划 trace 和 span，而不是等出了问题再加日志。

可观测性与统计显著性

结构化 Trace

Agent 的可观测性不是打日志，而是结构化的 span 树：每个工具调用是一个 span，包含入参、出参、耗时、token 消耗；多个 span 组成一次任务的 trace；trace 上附加任务结果（成功/失败/部分成功）和失败原因分类。这样才能做「哪个工具调用最慢」「哪类任务的失败率最高」的聚合分析。

工程实践：成本核算要在 span 级别（每个工具调用消耗多少 token，折合多少费用），而不只是任务级别——这样才能找到成本最高的瓶颈并优化。

统计显著性

小样本上的差异可能是噪声。假设两个版本的 Agent，A 成功率 72%，B 成功率 75%，差了 3 个百分点——在 100 个测试任务上这个差异通不过显著性检验（p > 0.05）。需要多少样本？以 80% 统计功效、p<0.05 显著性检验 5% 差异为例，大约需要 500 个任务。

Bootstrap 置信区间：对测试集有放回抽样 1000 次，每次计算成功率，取 2.5%–97.5% 分位数作为 95% 置信区间。比 Z 检验更稳健，不依赖正态假设，适合 Agent 评估这种小样本高方差的场景。
