为什么需要数据库？

类比：想象你有一个巨大的图书馆。如果所有书都堆在地上（文件存储），想找到一本特定的书会非常困难。但如果你有图书管理系统（数据库），按照类别、作者、书名等分类存放，就能快速找到需要的书。

文件存储的问题

在早期的应用程序中，数据通常存储在文件中。但这种方式存在很多问题：

  • 数据冗余：同一份数据可能在多个文件中重复存储
  • 数据不一致：更新一个数据需要修改多个文件，容易遗漏
  • 数据孤立：不同文件中的数据难以关联和查询
  • 安全性差：难以控制不同用户对数据的访问权限
  • 并发问题：多个用户同时修改文件会冲突

数据库的优势

📁 文件存储

  • 数据分散在多个文件中
  • 查询需要遍历整个文件
  • 没有事务支持
  • 并发控制困难
  • 数据安全性低

🗄️ 数据库存储

  • 数据集中管理，结构化存储
  • 通过索引快速查询
  • 完整的事务支持（ACID）
  • 内置并发控制
  • 细粒度的权限管理

关系型数据库的核心概念

概念说明类比
表（Table）数据的集合，类似Excel表格图书馆的书架
行（Row）一条具体的记录书架上的一本书
列（Column）数据的字段书的属性（书名、作者、出版日期）
主键（Primary Key）唯一标识一条记录图书的ISBN编号
外键（Foreign Key）关联其他表的字段图书分类ID关联到分类表

MySQL简介

MySQL是最流行的关系型数据库之一，由Oracle公司维护。它的特点包括：

  • 开源免费：社区版完全免费
  • 性能优秀：处理大规模数据效率高
  • 易于使用：SQL语法简单直观
  • 生态完善：大量工具和框架支持
  • 稳定可靠：经过20多年生产验证
💡 典型应用场景：Web应用（WordPress、Laravel）、电商平台、内容管理系统、日志系统、企业应用等。

SQL基础语法

类比：SQL（Structured Query Language）就像是和数据库对话的语言。你用SQL告诉数据库"创建一个表"、"插入数据"、"查询数据"等操作。

创建数据库和表

SQL 
# 创建数据库
CREATE DATABASE my_database
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;

# 使用数据库
USE my_database;

# 创建用户表
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

数据类型

类型说明使用场景
INT整数，4字节ID、计数等
BIGINT大整数，8字节大范围的ID
VARCHAR(n)可变长度字符串，最多n个字符用户名、标题等
TEXT长文本，最多65535字节文章内容、描述等
DECIMAL(m,n)精确小数，m位数字，n位小数金额、价格等
FLOAT浮点数，4字节科学计算（不建议用于金额）
DOUBLE双精度浮点数，8字节科学计算（不建议用于金额）
DATETIME日期时间，'1000-01-01' 到 '9999-12-31'时间戳
TIMESTAMP时间戳，'1970-01-01' 到 '2038-01-19'记录时间
BOOLEAN布尔值，实际是TINYINT(1)开关、标志位
关键点：金额等精确数值务必使用 DECIMAL 类型，不要使用 FLOAT 或 DOUBLE，因为浮点数有精度问题。

约束条件

SQL 
# 创建订单表（演示各种约束）
CREATE TABLE orders (
    id INT AUTO_INCREMENT PRIMARY KEY,           # 主键，自动递增
    user_id INT NOT NULL,                          # 非空约束
    order_number VARCHAR(20) UNIQUE NOT NULL,      # 唯一约束
    total_amount DECIMAL(10, 2) NOT NULL,           # 精确小数
    status ENUM('pending', 'completed', 'cancelled') DEFAULT 'pending',  # 枚举类型
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE  # 外键约束
);

CRUD操作

创建数据（INSERT）

SQL 
# 插入单条数据
INSERT INTO users (username, email, password_hash)
VALUES ('john_doe', 'john@example.com', 'hashed_password_123');

# 插入多条数据
INSERT INTO users (username, email, password_hash)
VALUES
    ('jane_doe', 'jane@example.com', 'hashed_password_456'),
    ('bob_smith', 'bob@example.com', 'hashed_password_789');

VALUES ('alice_wonder', 'alice@example.com', 'hashed_password_abc');
SELECT LAST_INSERT_ID();  # 获取刚插入的ID

查询数据（SELECT）

SQL 
# 查询所有用户
SELECT * FROM users;

# 查询特定列
SELECT username, email FROM users;

# 条件查询
SELECT * FROM users
WHERE username = 'john_doe';

# 多条件查询
SELECT * FROM users
WHERE created_at >= '2024-01-01'
AND username LIKE '%john%';

# 排序和分页
SELECT * FROM users
ORDER BY created_at DESC  # 降序排列
LIMIT 10 OFFSET 0;        # 分页：从第0条开始，取10条

更新数据（UPDATE）

SQL 
# 更新单个用户
UPDATE users
SET email = 'john_new@example.com'
WHERE id = 1;

# 批量更新
UPDATE orders
SET status = 'completed'
WHERE created_at < '2024-01-01';

# ⚠️ 危险：不带WHERE条件会更新所有行！
UPDATE users SET status = 'active';  # 不要这样做！
⚠️ 警告：执行 UPDATE 或 DELETE 操作前，一定要先用 SELECT 确认WHERE条件是否正确，避免误操作导致数据丢失！

删除数据（DELETE）

SQL 
# 删除单条记录
DELETE FROM users
WHERE id = 1;

# ⚠️ 危险：删除所有数据
DELETE FROM users;  # 不要这样做！

# 更好的方式：使用TRUNCATE（快速清空表）
TRUNCATE TABLE users;

SQL进阶

聚合函数

类比：聚合函数就像是统计员，帮你计算"总数"、"平均值"、"最大值"等统计数据。
SQL 
# 统计用户总数
SELECT COUNT(*) AS total_users FROM users;

# 计算订单总金额
SELECT SUM(total_amount) AS total_revenue FROM orders;

# 计算平均订单金额
SELECT AVG(total_amount) AS avg_amount FROM orders;

# 查找最高和最低订单金额
SELECT
    MAX(total_amount) AS max_amount,
    MIN(total_amount) AS min_amount
FROM orders;

# 分组统计（GROUP BY）
SELECT
    status,
    COUNT(*) AS count,
    SUM(total_amount) AS total
FROM orders
GROUP BY status;

# HAVING过滤分组结果
SELECT
    user_id,
    COUNT(*) AS order_count
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 5;  # 只显示订单数大于5的用户
💡 WHERE vs HAVING：WHERE 在分组前过滤行，HAVING 在分组后过滤组。聚合函数的结果只能用 HAVING 过滤。

多表连接（JOIN）

类比：JOIN就像是把两个表格按照某个共同字段合并在一起。比如，把"用户表"和"订单表"通过 user_id 关联起来，就能看到每个用户的订单信息。
SQL 
# INNER JOIN：只返回两个表都有的数据
SELECT
    u.username,
    o.order_number,
    o.total_amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

# LEFT JOIN：返回左表所有数据，右表没有的显示NULL
SELECT
    u.username,
    COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id;

# 多表连接示例
SELECT
    u.username,
    o.order_number,
    p.product_name,
    oi.quantity
FROM users u
INNER JOIN orders o ON u.id = o.user_id
INNER JOIN order_items oi ON o.id = oi.order_id
INNER JOIN products p ON oi.product_id = p.id;
JOIN类型说明使用场景
INNER JOIN只返回两个表都有的数据查询有关联的数据
LEFT JOIN返回左表所有数据，右表没有的显示NULL查询所有用户及其订单（包括没有订单的用户）
RIGHT JOIN返回右表所有数据，左表没有的显示NULL较少使用
CROSS JOIN返回两个表的笛卡尔积生成组合数据

子查询

SQL 
# IN子查询：查找下过订单的用户
SELECT * FROM users
WHERE id IN (
    SELECT DISTINCT user_id FROM orders
);

# EXISTS子查询：查找有订单的用户（通常比IN更快）
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.user_id = u.id
);

# 标量子查询：查询每个用户的订单数
SELECT
    username,
    (
        SELECT COUNT(*)
        FROM orders o
        WHERE o.user_id = u.id
    ) AS order_count
FROM users u;

索引优化

类比：索引就像书的目录。没有目录的书，找某一页需要从头翻到尾（全表扫描）。有了目录，直接翻到对应页码（索引查找）。

索引原理

MySQL默认使用B+树作为索引结构。B+树的特点：

  • 所有数据都存储在叶子节点
  • 叶子节点通过指针连接，支持范围查询
  • 树的高度通常只有3-4层，查询效率高

创建索引

SQL 
# 创建普通索引
CREATE INDEX idx_username ON users(username);

# 创建唯一索引
CREATE UNIQUE INDEX idx_email ON users(email);

# 创建复合索引（多字段）
CREATE INDEX idx_user_status ON orders(user_id, status);

# 创建全文索引（用于全文搜索）
CREATE FULLTEXT INDEX idx_content ON articles(title, content);

# 查看表的索引
SHOW INDEX FROM users;

索引失效场景

🚨 常见索引失效场景：
  • 对索引列使用函数：WHERE YEAR(created_at) = 2024
  • 对索引列进行计算：WHERE id + 1 = 10
  • 使用 LIKE '%abc'（前导通配符）
  • 使用 OR 连接非索引列
  • 类型隐式转换：WHERE varchar_column = 123

EXPLAIN执行计划

SQL 
# 分析查询执行计划
EXPLAIN SELECT * FROM users
WHERE username = 'john_doe';

# 输出字段说明：
# type: 访问类型（system > const > eq_ref > ref > range > index > ALL）
# key: 实际使用的索引
# rows: 预估扫描行数
# Extra: 额外信息（Using index表示使用了覆盖索引）
💡 索引优化原则：
  • 在WHERE、JOIN、ORDER BY的字段上创建索引
  • 选择性高的字段更适合建索引（如用户名、邮箱）
  • 复合索引遵循最左前缀原则
  • 不要过度索引，索引会占用存储空间并降低写入性能

事务与锁

类比：事务就像银行转账。从A账户扣钱和给B账户加钱必须作为一个整体完成——要么都成功，要么都失败，不能只完成一半。

事务ACID特性

特性说明类比
原子性（Atomicity）事务是不可分割的最小单位转账要么全成功，要么全失败
一致性（Consistency）事务前后，数据保持一致转账前后，两个账户的总金额不变
隔离性（Isolation）并发事务互不干扰两个人同时转账，互不影响
持久性（Durability）事务提交后永久保存转账成功后，即使断电也不会丢失

事务控制

SQL 
# 开启事务
START TRANSACTION;

# 转账操作
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;

# 检查余额是否足够
SELECT balance INTO @balance FROM accounts WHERE id = 1;
IF @balance < 0 THEN
    ROLLBACK;  # 余额不足，回滚
ELSE
    COMMIT;    # 成功，提交
END IF;

并发问题

问题说明解决方法
脏读读到其他事务未提交的数据READ COMMITTED隔离级别
不可重复读同一事务内，两次读取结果不同REPEATABLE READ隔离级别
幻读同一事务内，查询结果行数不同SERIALIZABLE隔离级别

事务隔离级别

隔离级别脏读不可重复读幻读性能
READ UNCOMMITTED✓✓✓最高
READ COMMITTED✗✓✓较高
REPEATABLE READ✗✗✓*一般（MySQL默认）
SERIALIZABLE✗✗✗最低
📖 InnoDB 与幻读：上表中标 * 的幻读列是 SQL 标准的定义。但实际上，MySQL 默认引擎 InnoDB 在 REPEATABLE READ 级别下通过 MVCC（多版本并发控制）+ Next-Key Locking 已经能防止大部分幻读场景，其行为比 SQL 标准定义的更加严格。这也是为什么 MySQL 官方文档推荐使用默认的 REPEATABLE READ 而非 SERIALIZABLE。
💡 选择建议：大多数Web应用使用 READ COMMITTED 或 REPEATABLE READ 即可。金融等高一致性要求的场景使用 SERIALIZABLE。

数据库设计

范式（Normalization）

范式是数据库设计的规范，用于减少数据冗余和提高数据一致性。

范式要求示例
第一范式（1NF）字段不可再分不要把多个电话号码存在一个字段
第二范式（2NF）消除部分依赖订单商品表应该拆分为订单表和订单明细表
第三范式（3NF）消除传递依赖用户表不应该存储城市名称，应该存储城市ID

反范式设计

有时候为了查询性能，会故意增加数据冗余（反范式）：

SQL 
# 冗余字段示例：在订单表中冗余用户名
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    username VARCHAR(50),  # 冗余字段，避免每次JOIN用户表
    total_amount DECIMAL(10, 2),
    # ...
);
⚠️ 反范式原则：只在读取频率远高于写入频率的场景使用反范式，并确保数据同步机制（如触发器、应用层同步）。

常见设计模式

树形结构（组织架构、分类）

SQL 
# 邻接表模型（最常用）
CREATE TABLE categories (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    parent_id INT NULL,
    FOREIGN KEY (parent_id) REFERENCES categories(id)
);

# 查询某个节点的所有子节点（递归CTE）
WITH RECURSIVE category_tree AS (
    SELECT id, name, parent_id
    FROM categories
    WHERE id = 1  # 根节点

    UNION ALL

    SELECT c.id, c.name, c.parent_id
    FROM categories c
    INNER JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT * FROM category_tree;
