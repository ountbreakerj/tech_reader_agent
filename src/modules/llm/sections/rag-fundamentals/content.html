理解检索增强生成的核心概念和架构

什么是RAG

类比：RAG（Retrieval-Augmented Generation）就像是给LLM配了一个"图书管理员"——当你问问题时，图书管理员先帮你从图书馆找到最相关的几本书（检索），然后你再根据这些书来回答问题（生成）。这样就解决了LLM知识过时和幻觉的问题。

RAG vs Fine-Tuning vs Prompt Engineering

方法优点缺点适用场景
RAG知识实时更新，可溯源检索质量影响效果知识库问答、文档助手
Fine-Tuning特定任务效果好需要训练数据，知识固化领域适配、风格迁移
Prompt Engineering简单快速上下文长度限制简单任务、原型验证

RAG核心架构

三个阶段

graph LR

    subgraph Retrieval["检索阶段"]

    subgraph Generation["生成阶段"]
        H --> I[构建Prompt]
        I --> J[LLM生成回答]
        J --> K[返回结果]
    end

完整流程

Python 
from langchain_milvus import Milvus
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

# 1. 初始化Embedding模型
embeddings = HuggingFaceEmbeddings(
    model_name="BAAI/bge-base-zh-v1.5"
)

# 2. 连接向量数据库
vectorstore = Milvus(
    embedding_function=embeddings,
    collection_name="documents",
    connection_args={"host": "localhost", "port": 19530}
)

# 3. 创建检索器
retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 3}  # 返回3个最相关的文档
)

# 4. 创建RAG链（LCEL风格）
template = """根据以下上下文回答问题：
{context}

问题：{question}
"""
prompt = ChatPromptTemplate.from_template(template)
llm = ChatOpenAI(model="gpt-4o")

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

# 5. 查询
result = rag_chain.invoke("什么是机器学习？")
print(result)

文档处理

文本分割策略

Python
from langchain_text_splitters import RecursiveCharacterTextSplitter

# 递归字符分割（推荐）
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,       # 每个chunk的最大字符数
    chunk_overlap=50,     # chunk之间的重叠
    length_function=len,
    separators=["\n\n", "\n", "。", " "]  # 分割符优先级
)

# 分割文档
docs = text_splitter.split_documents(documents)
print(f"分割成 {len(docs)} 个chunk")

# chunk大小选择指南（以token为单位）
# - 太小（<128 tokens）：上下文不完整，语义信息不足
# - 太大（>1024 tokens）：检索不精确，噪声过多
# - 推荐：256-1024 tokens（具体取决于embedding模型的最大输入长度）
# - 例如BGE模型最大512 tokens，text-embedding-3系列最大8191 tokens

进阶分块策略

除了基础的递归字符分割，现代RAG系统采用更智能的分块方法，能显著提升检索质量：

策略原理优点适用场景
语义分块（Semantic Chunking）计算相邻句子的embedding相似度，在相似度骤降处切分保持语义完整性段落结构清晰的文档
智能体分块（Agentic Chunking）使用LLM判断最佳切分点，理解文档语义结构最智能的切分方式复杂结构文档、高质量需求
延迟分块（Late Chunking）先对完整文档生成token级embedding，再切分embedding向量保留全局上下文信息长文档、跨段落依赖
上下文分块（Contextual Chunking）用LLM为每个chunk生成上下文摘要，附加到chunk前面提升独立chunk的可理解性孤立chunk难以理解的场景
父子分块（Parent-Child Chunking）小chunk用于精确检索，返回其所属的大chunk提供完整上下文兼顾检索精度和上下文完整性大多数生产RAG系统（推荐）

父子分块实践建议：小chunk通常为128-256 tokens用于embedding检索，父chunk为512-1024 tokens用于提供上下文。检索命中小chunk后，返回其对应的父chunk给LLM，这样既保证检索精度又不丢失上下文。

查询转换技术

用户查询往往不够精确或表述方式单一，查询转换技术在检索前对查询进行优化，能显著提升召回率：

HyDE（假设性文档嵌入）

先让LLM生成一个"假设性回答"，再用这个回答的embedding去检索。假设性回答虽然可能包含错误事实，但其语义分布更接近真实文档，能有效弥合查询与文档之间的语义鸿沟。

多查询扩展（Multi-Query Expansion）

将原始查询改写为多个不同表述方式的子查询，分别进行检索后合并结果。例如"Python如何读取Excel"可扩展为："Python读取xlsx文件方法"、"openpyxl库使用教程"、"pandas读取Excel数据"等，大幅提高召回率。

查询分解（Query Decomposition）

将复杂的多跳问题分解为多个简单子问题，分别检索后综合回答。例如"对比BERT和GPT在文本分类上的优劣"可分解为："BERT在文本分类上的表现"和"GPT在文本分类上的表现"两个子查询。

选择建议：HyDE实现最简单，适合作为查询优化的起点；多查询扩展在大多数场景下能稳定提升召回率；查询分解适合处理复杂多跳问题。三者可以组合使用。
