第 21 章

Hooks

主线故事 · 第 21 章（虚构）

阿青的三个需求，林舟一开始打算直接写进橘子里：工具执行完，如果是 edit_file，就调一下客户的格式化脚本；如果是 deploy，执行前先发一条消息到值班群。

老唐拦住了他：“你写进去之后，下一个客户要的是 prettier 而不是 black，值班群在飞书而不是钉钉。你打算给每个客户发一个不一样的橘子？”

他们改成了 hooks：橘子在几个固定的时刻——收到用户输入时、执行工具前、执行工具后、准备停下前——去调用客户自己配置的脚本。脚本通过标准输入拿到一段 JSON，告诉橘子“放行”“拒绝”还是“补充一点信息”。阿青第二天就把三个需求都接上了，没有动橘子一行代码。

一周后出了第一个事故。阿青写了一个 Stop hook：“如果测试没过，就别停，继续修。”有一次测试环境本身坏了，测试永远过不了，橘子在 Stop hook 的催促下修了两个小时，烧掉了一整天的预算。

第二个事故更隐蔽。值班群的通知脚本有一天因为网络问题报错退出，林舟的实现把“hook 出错”当成“没有意见”，于是那天下午的部署全部绕过了通知，直接执行了。

“扩展点是给别人用的门，”老唐说，“门开在哪、开多大、门坏了怎么办，都得你来定。别人的代码总会出问题，你的 harness 不能跟着一起出问题。”

这一章要把这些门定下来：开在哪几个时刻（事件词表）、每扇门允许做什么（观察、修改、拦截、要求继续）、hook 自己出错时怎么办，以及“要求继续”为什么必须有上限。

到第 20 章为止，harness 能做的每件事都写在它自己的代码里。这对一个团队自用的工具足够了，对一个要交给不同用户、不同团队使用的 harness 就不够了：每个人都有自己的格式化工具、自己的通知渠道、自己的合规检查。把这些都写进 harness，它会变成一堆针对特定客户的分支。

Hooks 是第一种“不改 harness 代码就能改变它行为”的扩展方式。接下来两章是另外两种：Skills 与 MCP（第 22 章）扩展的是知识和能力，子代理与 PTC（第 23 章）扩展的是执行方式。

先看全貌：Hooks 是什么、管哪些事

一句话：hooks 是 harness 在循环的几个固定时刻调用的外部函数或外部命令，用来观察正在发生的事、修改它、拒绝它，或者在模型准备停下时要求它继续。

这一层要管的事：

  • 事件词表：有哪些时刻可以挂 hook。这张表就是 harness 对外承诺的接口。
  • 能力：每个事件允许 hook 做什么——观察、修改、拦截、要求继续。
  • 顺序与合并：多个 hook 挂在同一个事件上时，谁先谁后、结果怎么合并。
  • 失败处理：hook 自己抛异常、超时、退出码不对时怎么办。
  • 形式：进程内函数，还是外部命令（通过标准输入输出通信）。
  • 防失控：“要求继续”这种会延长运行的能力，必须有上限。

四个决定，先给结论：

决定看起来省事的做法本章的结论
事件有哪些每个需求加一个新事件一张小而固定的词表；改词表等于改 API
hook 能做什么任何事件上都能做任何事按事件声明能力：执行后的事件不能“拦截”（已经发生了），只有 Stop 能“要求继续”
hook 自己出错当作“没有意见”按事件定策略：拦截类事件失败关闭（当成拒绝），观察类事件忽略并记录
要求继续hook 说继续就继续必须有次数上限；用户有新输入时重新计数

三个仓库在这一层分别是什么水平

DSH（TypeScript）：整个 harness 都建立在扩展点之上（第 01 章的 agent/pre-step、agent/turn-stopping，第 13 章的 tools/pre-execute，第 18 章的 agent/request-error）。在这之上，它有一个实验性的包，把 Claude Code 和 Codex 风格的外部命令 hook 桥接到这些扩展点上：例如外部的 PreToolUse hook 被接到 tools/pre-execute，返回拒绝时调用被拦截。这个包里还留着一条 TODO：连续的强制继续需要设上限，在那之前 hook 必须自己限制自己。

OpenHarness（Python）：有独立的 hook 执行引擎。pre_tool_use 钩子在参数校验之前运行，拿到的是工具名和未校验的原始参数，可以拦截并给出理由；循环在模型不再调用工具时触发一次 STOP 钩子，载荷里的停止原因是固定字符串 tool_uses_empty。

事件词表与能力表

hooks 的第一个设计决定，是“在哪些时刻开门”。labs 定义了五个事件，和 learn-claude-code 的四个基本一致，多了一个会话开始：

CAPABILITIES: dict[str, frozenset[str]] = {
    USER_PROMPT: frozenset({"observe", "modify", "block"}),
    PRE_TOOL: frozenset({"observe", "modify", "block"}),
    POST_TOOL: frozenset({"observe", "modify"}),
    STOP: frozenset({"observe", "continue"}),
    SESSION_START: frozenset({"observe", "modify"}),
}

每个事件后面跟着它允许的能力。这张能力表比事件本身更重要，因为它决定了 hook 的权力边界：

事件时刻观察修改拦截要求继续典型用途
user_prompt_submit用户输入进入上下文之前✓✓✓补充当前分支、工单号；拦截含密钥的输入
pre_tool_use工具执行之前✓✓✓部署前通知、冻结期拦截、参数规范化
post_tool_use工具执行之后✓✓改完代码跑格式化、把 lint 结果追加给模型
stop模型准备停下时✓✓（有上限）测试没过就让它继续修
session_start会话开始✓追加上下文注入项目状态、今日值班人

有两个格子值得解释。

执行后不能拦截。工具已经执行过了，副作用已经发生。如果允许 post_tool_use 返回“拒绝”，实现者会面临一个无解的问题：拒绝什么？撤销文件写入？撤回已经发出的消息？大多数副作用是撤不回的。所以 labs 在 post_tool_use 上忽略“拦截”，并把它记进 ignored，让写 hook 的人知道自己写错了地方：

    def test_post_tool_cannot_block(self) -> None:
        bus = HookBus()
        bus.on(POST_TOOL, "late-veto", lambda e, p: HookResult(block=True, reason="太晚了"))
        outcome = bus.dispatch(POST_TOOL, {"tool_name": "write_file", "tool_output": "ok"})
        self.assertFalse(outcome.blocked)
        self.assertTrue(any("不能拦截" in msg for msg in outcome.ignored))

只有 Stop 能要求继续。“继续”会让循环多跑一轮或多轮，是成本最高的一种能力。把它限制在一个事件上，就能在一个地方集中管理它的上限（第 4 节）。

事件词表本身要小而稳定。每增加一个事件，就增加了一个用户可能依赖的接口，以后很难删掉。新需求出现时，先看能不能用现有事件加上过滤条件（matcher）满足。比如“只在 deploy 工具执行前通知”，不需要一个新的 pre_deploy 事件，用 pre_tool_use 加 matcher="deploy" 就够了。

多个 hook 的顺序与合并

一个事件上可以挂多个 hook。它们按注册顺序依次调用，结果按下面的规则合并：

    def dispatch(self, event: str, payload: dict[str, Any]) -> DispatchOutcome:
        """按注册顺序调用 hook。修改会传递给下一个；拦截立刻结束；继续有上限。"""
        import fnmatch

        allowed = CAPABILITIES[event]
        outcome = DispatchOutcome(event, dict(payload))
        for reg in [r for r in self._hooks if r.event == event]:
            tool = str(outcome.payload.get("tool_name", ""))
            if reg.matcher and not fnmatch.fnmatchcase(tool, reg.matcher):
                continue
            try:
                result = reg.fn(event, dict(outcome.payload))
            except Exception as exc:  # noqa: BLE001 — 外部代码，什么都可能抛
                message = f"{reg.name}: {type(exc).__name__}: {exc}"
                outcome.errors.append(message)
                self.log.append((event, reg.name, f"error {exc}"))
                if ON_ERROR[event] == "block":
                    outcome.blocked = True
                    outcome.blocked_by = reg.name
                    outcome.reason = f"安全检查 {reg.name} 自身出错，按拒绝处理：{exc}"
                    return outcome
                continue
            if result is None:
                continue
            if result.block:
                if "block" not in allowed:
                    outcome.ignored.append(f"{reg.name}: {event} 不能拦截（事情已经发生了）")
                else:
                    outcome.blocked, outcome.reason, outcome.blocked_by = True, result.reason, reg.name
                    self.log.append((event, reg.name, f"block {result.reason}"))
                    return outcome
            if result.payload is not None:
                if "modify" in allowed:
                    outcome.payload = dict(result.payload)
                    self.log.append((event, reg.name, "modify"))
                else:
                    outcome.ignored.append(f"{reg.name}: {event} 不能修改载荷")
            if result.context:
                if "modify" in allowed or event == SESSION_START:
                    outcome.contexts.append(result.context)
                else:
                    outcome.ignored.append(f"{reg.name}: {event} 不能追加上下文")
            if result.keep_going:
                if "continue" not in allowed:
                    outcome.ignored.append(f"{reg.name}: 只有 stop 事件能要求继续")
                elif self._forced_continues >= self.max_forced_continues:
                    outcome.ignored.append(
                        f"{reg.name}: 已经连续强制继续 {self._forced_continues} 次，达到上限，这次按停止处理")
                    self.log.append((event, reg.name, "continue refused (cap)"))
                elif not outcome.keep_going:
                    self._forced_continues += 1
                    outcome.keep_going, outcome.continue_reason = True, result.reason
                    self.log.append((event, reg.name, f"continue {result.reason}"))
        return outcome
  • 修改是链式的：第一个 hook 修改后的载荷，作为第二个 hook 的输入。测试 test_modifications_chain_in_order 里，两个 hook 依次在文本后面追加 A 和 B，最终结果是 “hi A B”。
  • 拦截是单调的：任何一个 hook 拒绝，分发立刻结束，后面的 hook 不再调用，也没有 hook 能推翻这个拒绝。这和第 13 章权限规则、第 02 章执行前钩子是同一条规则——DSH 把它写成了明确的契约：任何匹配的 guard 都可以拒绝，没有 guard 能强行放行另一个 guard 已经拒绝的调用。
  • 追加的上下文累积：每个 hook 追加的上下文都保留，按顺序排列。
  • 继续只采纳一次：多个 Stop hook 都要求继续时，只算一次（只消耗一次上限）。

拦截必须带理由，这一点在构造 HookResult 时就强制检查：理由会作为错误结果喂回模型，没有理由，模型只会原样重试（第 13 章第 6 节）。

@dataclass(frozen=True)
class HookResult:
    """hook 的返回值。字段都可选，含义由事件决定。

    block      拒绝这件事（必须带 reason，会喂回模型）
    payload    修改后的载荷（替换原载荷传给下一个 hook）
    context    追加给模型的一段上下文（例如格式化脚本的输出）
    keep_going Stop 事件里要求继续，并给出继续的理由
    """

    block: bool = False
    reason: str = ""
    payload: dict[str, Any] | None = None
    context: str = ""
    keep_going: bool = False

    def __post_init__(self) -> None:
        if self.block and not self.reason:
            raise HookError("拦截必须给出理由：模型看不到理由就只会原样重试")
        if self.keep_going and not self.reason:
            raise HookError("要求继续必须给出理由：它会作为下一轮的输入")

hook 追加的上下文放在哪里，也有讲究。labs 的组装版（第 25 章）把它放在工具结果所在的同一条 user 消息里、排在工具结果之后。这样既不会把 tool_use 和 tool_result 隔开（第 01 章坑一），模型也能在下一轮同时看到工具结果和 hook 的补充信息。DSH 的做法类似：工具执行期间产生的额外上下文排进“下一步”的队列，总是在工具结果之后提交。

hook 自己出错时怎么办

hook 是外部代码，什么都可能发生：抛异常、超时、退出码不对、输出不是合法的 JSON。故事里第二个事故的原因是：通知脚本出错时被当成“没有意见”，于是部署绕过了通知。

正确的处理取决于这个 hook 在做什么。labs 按事件定了一张失败策略表：

ON_ERROR: dict[str, str] = {
    USER_PROMPT: "ignore",
    PRE_TOOL: "block",
    POST_TOOL: "ignore",
    STOP: "ignore",
    SESSION_START: "ignore",
}
事件hook 出错时理由
pre_tool_use当成拒绝（失败关闭）这里的 hook 往往是安全检查。一个坏掉的安全检查不能变成放行
其他事件忽略并记录这些 hook 主要在观察或补充信息。日志 hook 写失败，不应该让 agent 停下来

这张表是一个保守的默认值。真实项目里可以让每个 hook 自己声明失败策略：一个“部署前必须通知”的 hook 应该失败关闭，一个“顺便记一下工具耗时”的 hook 应该失败忽略，哪怕它们挂在同一个事件上。

失败关闭时的拒绝理由要写清楚“是检查本身出错”，而不是“检查不通过”：

    def test_pre_tool_error_fails_closed(self) -> None:
        bus = HookBus()
        bus.on(PRE_TOOL, "broken-guard", lambda e, p: 1 / 0)
        outcome = bus.dispatch(PRE_TOOL, {"tool_name": "rm"})
        self.assertTrue(outcome.blocked)
        self.assertIn("自身出错", outcome.reason)

这两种情况对模型和用户的意义完全不同：“检查不通过”意味着这个操作本身有问题，模型应该换做法；“检查出错”意味着检查工具坏了，应该告诉用户去修 hook，而不是让模型绕过去。

超时也属于 hook 出错。外部命令形式的 hook 必须有超时（第 19 章），否则一个卡住的通知脚本会让整个 agent 卡住。

Stop hook 与“要求继续”的上限

Stop hook 是最强大、也最危险的一种 hook。它在模型准备结束时运行，可以说“还没完，继续”。用得好，它能实现“测试没过就接着修”这样的质量门；用得不好，就是故事里那个修了两小时的会话。

问题出在“继续”的条件可能永远不满足：测试环境坏了，测试永远过不了；hook 的检查逻辑有 bug，永远返回“没完”；或者任务本身就超出了模型的能力。这时 Stop hook 会一直把模型拉回来，每一轮都要重发整段历史（第 05 章），成本线性增长。

DSH 自己在代码里承认了这个问题：它的外部 hook 桥接包里有一条 TODO，写着连续的强制继续需要设上限，在那之前 hook 必须自己限制自己。labs 直接把上限做进了分发器：

    def test_continue_is_capped(self) -> None:
        bus = HookBus(max_forced_continues=2)
        bus.on(STOP, "never-done", lambda e, p: HookResult(keep_going=True, reason="测试还没过"))
        results = [bus.dispatch(STOP, {}).keep_going for _ in range(4)]
        self.assertEqual(results, [True, True, False, False])

上限的计数在用户有新输入时清零（reset_turn()）。理由是：用户的新输入意味着人重新介入了，前面的“继续”已经得到了人的认可或者纠正。如果计数整个会话累计，长会话后面的 Stop hook 就永远不会生效了——这和第 18 章“重试计数按步清零”是同一个道理。

上限达到后，这次“继续”被忽略，模型正常停下。被忽略这件事要记下来，并且最好告诉用户：“质量检查仍未通过，已达到自动继续的上限”。否则用户会以为任务已经完成。

外部命令形式的 hook

阿青写的 hook 不是 Python 函数，而是脚本。外部命令是 hooks 最常见的形式，因为它不要求写 hook 的人使用和 harness 相同的语言。约定通常是：

方向内容
输入（标准输入）一段 JSON：事件名、工具名、参数、输出等
退出码 0通过；标准输出如果是 JSON，可以带修改后的载荷或要追加的上下文
退出码 2拦截；标准错误的内容作为拒绝理由
其他退出码、超时hook 自身出错，按事件的失败策略处理
def command_hook(argv: Sequence[str], *, timeout: float = 10.0) -> Hook:
    """把一条外部命令包装成 hook：载荷以 JSON 写进 stdin。

    约定（与常见的 CLI agent 一致的简化版）：
    - 退出码 0：通过。stdout 若是 JSON，可带 {"context": ...} 或 {"payload": ...}
    - 退出码 2：拦截，stderr 作为理由
    - 其他退出码或超时：视为 hook 自身出错（由事件的 ON_ERROR 策略处理）
    """

    def hook(event: str, payload: dict[str, Any]) -> HookResult | None:
        data = json.dumps({"event": event, **payload}, ensure_ascii=False)
        proc = subprocess.run(
            list(argv), input=data, capture_output=True, text=True,
            encoding="utf-8", errors="replace", timeout=timeout,
        )
        if proc.returncode == 2:
            return HookResult(block=True, reason=proc.stderr.strip() or f"{argv[0]} 拒绝了这次操作")
        if proc.returncode != 0:
            raise HookError(f"hook 命令退出码 {proc.returncode}: {proc.stderr.strip()[:200]}")
        out = proc.stdout.strip()
        if not out:
            return None
        try:
            reply = json.loads(out)
        except json.JSONDecodeError:
            return HookResult(context=out)
        return HookResult(context=str(reply.get("context", "")), payload=reply.get("payload"))

    return hook

这个约定是常见 CLI agent 采用的形式的简化版；DSH 的外部 hook 桥接包就是在适配 Claude Code 和 Codex 的这类约定。把“拦截”和“出错”用不同的退出码区分开很重要：如果任何非零退出都算拦截，一个有 bug 的脚本就会被当成在主动拒绝，给模型的理由是一段崩溃信息；如果任何非零退出都算出错，脚本就没有办法明确表示“我拒绝”。

外部命令 hook 还有两个要注意的地方：

  • 它在沙箱之外运行。hook 是用户（或者团队）配置的，代表用户的意志，通常有比 agent 更大的权限——它要能发通知、要能读配置。这意味着 hook 的配置文件本身需要保护：如果 agent 能修改 hook 配置，它就能给自己开后门。hook 配置应该和指令文件一样，修改时总是需要人工确认（第 17 章第 6 节）。
  • 它会拖慢每一次工具调用。pre_tool_use 和 post_tool_use 在每次工具调用时都要启动一个进程。用 matcher 把 hook 限制在需要的工具上，可以避免给所有调用增加启动开销。

hooks 和前面几章的关系

回头看会发现，前面很多章的机制都可以用 hooks 实现：

机制用哪个事件前面在哪一章

这引出了一个架构上的选择：harness 自己的核心功能，要不要也通过 hooks 实现？

DSH 选择了“是”：它的核心循环几乎只负责调度扩展点，超时、重试、压缩、权限都是挂在扩展点上的插件。好处是每个功能都可以单独替换、单独测试，第三方插件和内置功能享受同样的能力。代价是理解一个完整的行为需要跨好几个包，而且插件之间的顺序和交互变得重要（第 01 章说过“读懂一个 turn 要跨好几个包”）。

OpenHarness 和 labs 选择了“部分是”：核心功能写在循环里，hooks 作为对外的扩展接口。好处是核心流程一眼能看懂；代价是用户能扩展的范围受限于事件词表。

两种选择都成立。一个实用的判断标准是：如果某个功能有可能被用户替换成别的实现，就把它做成扩展点上的插件；如果它是 harness 正确性的一部分（比如“每个 tool_use 都要有结果”），就写在核心里，不要让 hook 有机会破坏它。

坑与失败案例

坑一：Stop hook 无限要求继续

  • 触发条件：Stop hook 的继续条件永远不满足（测试环境坏了、检查逻辑有 bug、任务超出能力）。
  • 后果：模型被一次次拉回来，每一轮都重发整段历史，成本线性增长，直到撞上其他上限或者有人发现。
  • 怎么防：强制继续的次数上限做在 harness 里，而不是寄希望于 hook 自律；用户新输入时清零；达到上限时告诉用户。

坑二：安全 hook 出错被当成放行

  • 触发条件：hook 抛异常、超时或退出码异常时，实现选择“忽略这个 hook”。
  • 后果：通知、合规检查、冻结期拦截在出错时全部失效，而出错的时候往往正是系统不稳定、最需要检查的时候。
  • 怎么防：拦截类事件失败关闭；拒绝理由写明“检查本身出错”。

坑三：执行后的 hook 试图“拒绝”

  • 触发条件：在 post_tool_use 上写了一个“发现问题就拒绝”的 hook。
  • 后果：如果 harness 支持这种返回，就要面对“怎么撤销已经发生的副作用”这个无解的问题；如果 harness 默默忽略，写 hook 的人会以为检查生效了。
  • 怎么防：按事件声明能力，不允许的能力被忽略时记录下来。执行前的检查放在 pre_tool_use；执行后能做的是追加上下文，让模型知道刚才的结果有问题。

坑四：hook 改坏了 harness 的不变量

  • 触发条件：允许 hook 任意修改消息历史，比如在 post_tool_use 里删掉工具结果，或者在 tool_result 前面插一条文本。
  • 后果：tool_use 失去配对的结果，下一次请求被拒绝；或者 tool_result 不再紧跟 tool_use，模型厂商拒绝请求。
  • 怎么防：hook 只能修改它所在事件的载荷（工具参数、工具输出、用户输入），不能直接操作消息历史；追加的上下文由 harness 放在合法的位置。

坑五：agent 可以修改自己的 hook 配置

  • 触发条件：hook 配置文件在工作区里，而 agent 有写工作区的权限。
  • 后果：一次注入（第 17 章）让 agent 修改 hook 配置，删掉安全检查，或者加一个在沙箱外运行的恶意命令。
  • 怎么防：hook 配置和指令文件一样，修改需要人工确认；或者把 hook 配置放在工作区之外，agent 没有写权限。

坑六：每个 hook 都在每次工具调用时运行

  • 触发条件：外部命令 hook 没有用 matcher 过滤。
  • 后果：每次 read_file 都要启动一个格式化脚本的进程，几十毫秒到几百毫秒的开销乘以每轮几十次工具调用。
  • 怎么防：用 matcher 把 hook 限制在相关工具上；需要对所有工具生效的 hook，用进程内函数而不是外部命令。

小结

  • hooks 是在固定时刻调用外部代码的扩展方式；事件词表要小而稳定，它就是 harness 的对外接口。
  • 每个事件声明允许的能力：执行后不能拦截，只有 Stop 能要求继续。
  • 多个 hook 按顺序调用：修改链式传递，拦截单调且立刻结束，拦截与继续都必须带理由。
  • hook 出错时按事件处理：拦截类失败关闭，观察类忽略并记录。
  • 强制继续必须有上限，由 harness 而不是 hook 自己来保证。
  • 外部命令 hook 用退出码区分“拦截”和“出错”，必须有超时；hook 配置本身需要保护，不能让 agent 修改。

hooks 让别人能在 harness 的固定时刻插入行为。下一章讲另外两种扩展：让模型多知道一些事（Skills），让模型多能做一些事（MCP）。继续读：Skills 与 MCP。

Stop hook 加了上限（连续三次），通知 hook 改成失败关闭之后，阿青那边一个月没再出事。有一次通知脚本又挂了，部署被拦下，橘子收到的理由是“安全检查 notify-oncall 自身出错，按拒绝处理”，它停下来告诉用户“部署前的值班通知脚本出错了，需要先修好它”。阿青说这是她见过最礼貌的事故报告。

阿青的第二批需求来了：“我们有一套内部的代码规范，四十多页。还有一个内部的文档搜索服务、一个工单系统。能不能让橘子知道这些规范，也能用这些服务？”

林舟的第一反应是把四十页规范塞进系统提示。他试了一下：系统提示从三千 token 涨到了四万 token，每一轮请求都要带上；橘子在写一个简单的工具函数时，引用了规范里关于数据库迁移的一条，完全不相干。

“它不需要每时每刻都背着四十页规范，”老唐说，“它需要的是：知道有这么一份规范，需要的时候能翻到对的那一页。”
