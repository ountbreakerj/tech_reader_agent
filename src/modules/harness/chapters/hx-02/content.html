第 2 章

工具定义与注册

一个工具在协议层其实只有三个字段：name、description、参数 schema。模型看不到你的 Python 函数，只看得到这三件套，然后凭它们猜测你的系统能做什么、该传什么参数。于是“工具定义与注册”这一层要解决的问题不是“怎么调函数”，而是三件容易搞砸的事：定义怎么变成模型看得懂的东西、名字怎么保证唯一、模型写的参数谁来查、查出来错了怎么告诉它。

本章先给出 labs 里的完整实现（labs/harness/tools.py），再逐段对照 DSH 的 ctx.tools、OpenHarness 的 ToolRegistry 和 learn-claude-code 的 TOOLS / TOOL_HANDLERS 两张表，最后列出这一层最常见的失败方式。

前置：本章假定你已经知道 agent loop 长什么样（工具结果是怎样回填进历史的），如果还没有，先看 第 01 章 Agent Loop 与停止条件；工具执行里的并发调度细节属于 第 00 章全景图 划出的范围，本章只讲到“只读标记怎样影响调度决策”为止。

1. 协议层的三件套：模型到底看到什么

先看 DSH 的协议定义。真正发给模型的那个形状不叫 ToolDefinition，而是一个只有四个字段的小接口，而且它被刻意声明在 LLM 适配层而不是工具包里：

/**
 * JSON-schema description of a tool, as sent to the model.
 *
 * Declared here (not in dsh-tools) because it is part of {@link GenerateOptions};
 * dsh-tools' ToolDefinition and dsh-system-prompt's PromptAssembly both import
 * it from this package.
 */
export interface ToolSchema {
  /**
   * Requests deferred loading of the tool definition into model context,
   * independently of whether a tool-addition block records the tool.
   * Uses Anthropic's defer_loading terminology.
   */
  deferLoading?: true
  name: string
  description: string
  /** JSON Schema object for the arguments. */
  parameters: Record<string, unknown>
}

types.ts:467-484

四点值得注意。第一，注释直说这是 as sent to the model，而 ToolSchema 声明在 llm 包里（types.ts:469），因为模型请求的入参类型要用它，工具包和系统提示包都 import 它——协议形状归协议层，不归实现层。第二，字段名是 parameters 而不是 input_schema，parameters 的值仍然是一份 JSON Schema 对象（types.ts:482-483）。第三，这三个字段是普通可写字段，而注册表里的 ToolDefinition 用 readonly 修饰（index.ts:334）——投影出去的是副本，注册表内部的不许改。第四，唯一多出来的模型可见开关是 deferLoading（types.ts:479），用来请求厂商延迟把这个工具的定义放进上下文；它借用的是 Anthropic 的 defer_loading 术语。

OpenHarness 走的是另一条路：它不定义“协议层形状”这个中间类型，而是让每个工具自己吐出一个字典，并且注释里明说目标是 Anthropic Messages API：base.py:52。三键是硬写的（base.py:53-57），键名用 input_schema。

learn-claude-code 更直接：把五份定义写成模块级列表的字面量，code.py:138，每行一个工具（code.py:139-140）。整个约束词汇只有 type、properties、required，没有 enum，没有嵌套对象，也没有 additionalProperties。

取舍：三件套的内容越丰富，模型第一次就写对参数的概率越高，但每一轮请求都要把这些 schema 重新发一遍，token 成本随工具数线性上升。DSH 的做法是两头发力——向上提供 deferLoading 让厂商按需加载，向下用 enum/const 把取值收紧（见 第 3 节）。教学示意：工具数量在 10～20 个之间时，schema 本身通常占系统提示的 20%～40%，超过这个数量就该考虑分组或延迟加载了（这个比例是本教程的经验估计，不是任何仓库里的常量）。

2. 从一个 ToolSpec 出发

labs 的起点是一个冻结的 dataclass。它把“模型可见的部分”和“执行侧的部分”放在同一个类型里，但只让前者出圈：

@dataclass(frozen=True)
class ToolSpec:
    """一个工具的全部定义。模型只看得到前三个字段，handler 永远不出圈。"""

    name: str
    description: str
    input_schema: dict[str, Any]
    handler: Callable[[dict[str, Any]], str]
    # 只读工具可以并发；写工具是屏障。默认发 false 是 fail-safe：
    # 忘了标就退化成串行，不会把两个写操作并到一起。
    read_only: bool = False
    # 与 read_only 分开：只读也可能不可并发（例如共享一个游标）。
    parallel_safe: bool = False
    # 秒。None 表示不设时限，交给上层钩子处理。
    timeout: float | None = None

    def schema(self) -> dict[str, Any]:
        """投影成模型可见的定义。执行相关字段一律不进这个字典。"""
        return {
            "name": self.name,
            "description": self.description,
            "input_schema": self.input_schema,
        }

注意 schema() 是白名单而不是黑名单：它新建一个字典逐个写入三个键，所以以后往 ToolSpec 上加任何执行侧字段（比如重试次数、审计标签），都不会意外漏给模型。DSH 在同一个位置用同样的手法，而且把这件事写进了注释——timeoutMs 那段明说 it is NEVER sent to the model，理由是 index.ts:263。它的投影函数确实只解构四个字段：

    const { name, description, parameters, deferLoading } = definition

index.ts:1289

整个方法的契约写在 docstring 里：index.ts:1261，返回值是 每个工具一份深拷贝。深拷贝这一条容易被忽略：如果导出的是同一个对象引用，某个调用方为了给特定 agent 加一句提示而就地改 description，就会污染所有 agent 看到的定义。

入口本身带一个可选的 scope 参数，因为 DSH 允许每个 agent 看到不同的工具子集（index.ts:1266）。OH 的对应方法不接受参数，直接遍历注册顺序（base.py:80）。顺序这件事在 OH 里是隐式的——Python 的 dict 保序，所以工具在提示里的排列就等于注册顺序，而注册顺序取决于插件初始化顺序，没有显式排序。

2.1 重名注册：为什么不能静默覆盖

labs 的选择是直接报错：

    def register(self, tool: ToolSpec) -> ToolSpec:
        """注册一个工具。重名直接报错，不覆盖。"""
        if tool.name in self._tools:
            raise ToolError(
                f"工具 {tool.name!r} 已经注册过了。"
                f"不能静默覆盖：覆盖会让运行时行为取决于插件的安装顺序，"
                f"而排错时看到的日志和实际生效的实现对不上。"
                f"要换实现请先 unregister，或者换一个名字。"
            )
        problems = check_schema(tool.input_schema)
        if problems:
            raise ToolError(f"工具 {tool.name!r} 的 input_schema 不合法：{'；'.join(problems)}")
        if not callable(tool.handler):
            raise ToolError(f"工具 {tool.name!r} 的 handler 不可调用")
        self._tools[tool.name] = tool
        return tool

理由在错误信息里写全了：静默覆盖会让行为取决于安装顺序。插件 A 注册 read_file，插件 B 也注册 read_file，最后谁生效完全看谁后初始化；而出问题时你看到的日志里写着 A 的实现，实际跑的是 B 的。这类 bug 排查成本极高，报错成本几乎为零。

但“报错”这个选择有一个必须同时决定的细节：报错的范围是什么。OH 的做法是最宽松的一种，注册就是一次纯赋值：

    def register(self, tool: BaseTool) -> None:
        """Register a tool instance."""
        self._tools[tool.name] = tool

base.py:66-68

没有检查、没有日志，同名后注册的赢。这是有意的权衡：OH 的注册表由 tools/__init__.py 集中装配，作者假定装配表本身是可信的，多一道检查只是浪费。代价是任何一次插件式扩展都可能踩到它。

DSH 把这个问题拆得更细，因为它的注册天生就是“可撤销的 effect”（每个包在挂载时注册、卸载时自动撤销），所以它必须区分两种情况：同层重名要失败，跨层同门是遮蔽。这条规则写在 register 的 docstring 里：index.ts:1064-1065。具体的报错文案分了两句，一句给全局：

? `tool "${name}" is already registered (for a per-agent variant, register through that agent's `agent.ctx` instead)`

index.ts:748

另一句给作用域内：index.ts:749。第一句的括号里顺手给了替代方案——想给某个 agent 换实现，就注册到那个 agent 的 agent.ctx 上，让它去遮蔽全局的版本。

还有一件事值得抄：注册时就把定义本身验一遍。DSH 在 register 开头检查 output 的形状（index.ts:1075）、检查 timeoutMs 是正有限数（index.ts:1080-1081）、并且调用 assertSupportedJsonSchema 把超集的 schema 关键字当场拒掉（index.ts:1077）。labs 对应的是 check_schema()：它在注册时递归走一遍 input_schema，遇到不认识的 keyword（比如 minLength、anyOf）直接失败，而不是留到运行期静默忽略。DSH 的报错文案把这个子集列全了（json-schema.ts:267），失败信息里带着子集清单，作者看一眼就知道该改写什么。

保留名是最后一道。DSH 禁止任何人注册或遮蔽 run_code，理由是注释里写的：任何 agent 都可能给自己选 code 模式，如果部署默认配置下这个名字是空着的，一旦某个 preset 挂上来就会碰撞（index.ts:1083-1087）。“当前没人用”不等于“可以随便用”，因为工具集是运行时可变的——这一点在你自己写 harness 时同样成立：凡是名字会被运行时机制保留的，注册期就要挡。

3. 参数校验：由 harness 做，还是由模型做

先回答一个问题：既然 schema 已经发给模型了，为什么还要校验？因为 schema 是提示，不是约束。模型可以少给一个必填字段、把一个数组塞进字符串字段、多带一个没声明的字段——这些都不是异常行为，是正常行为。所以校验必须在 harness 侧做，而且失败的产物必须是一条喂回模型的错误信息，不能是一个抛到循环外层的异常。

DSH 的注释把这件事说得很直白：README.md:34（参数在执行前校验，非法输入变成一条普通错误结果）。它的错误类型也专门为“模型写错了参数”开了一个：

/** Invalid model-generated arguments for a typed tool. */
export class ToolArgsError extends HarnessError {
  /** Individual violations in schema-walk order. */
  readonly violations: string[]

  constructor(violations: string[]) {
    super(`invalid arguments: ${violations.join('; ')}`, 'INVALID_ARGS')
    this.name = 'ToolArgsError'
    this.violations = violations
  }
}

schema.ts:460-470

两个细节：violations 是一个数组而不是一个字符串，且拼进 message 时用 '; ' 连接——一次把所有问题都给模型，而不是遇到第一个就返回；错误带的 code 是 'INVALID_ARGS'，让上层的策略代码能把“参数错”和“工具自己抛的错”区分开。

校验发生在哪里？DSH 把它塞进了 defineTool 产出的 execute 里，也就是说：调用方拿到的是一个永远不会因为参数错而返回垃圾的函数。

    async execute(args: unknown, exec: ToolRunContext): Promise<JsonValue> {
      const violations = validate(args)
      if (violations.length > 0) throw new ToolArgsError(violations)
      return userExecute(args as InferArgs<S>, exec) as Promise<JsonValue>
    },

schema.ts:597-601，其中 validate 在定义时就闭包捕获了编译好的 schema（schema.ts:579），所以每个工具只在注册时编译一次。

抛出的这个 ToolArgsError 最终会到哪里去？到 dispatchToolBody 的 catch 里，被统一转成错误结果：index.ts:1592-1593。循环不会因为一次参数写错而中断，模型会在下一轮看到 invalid arguments: ... 然后自己纠正。

OH 的校验点在循环里而不是工具类里，这是两者最大的结构差异：

它校验的是“原始 dict”，校验器由 tool.input_model（一个 pydantic 模型）提供。回给模型的是 str(exc)，也就是 pydantic 自己生成的错误报告，带字段路径。这有个实际好处：你不需要自己写错误文案；坏处是文案是 pydantic 的措辞，可能很长（一个嵌套模型会打印好几十行），而且换了 pydantic 大版本措辞会变，靠文字匹配做断言/回放会脆。labs 的取舍是自己写一个短校验器，错误文案完全可控，代价是只支持 JSON Schema 的一个很小的子集。

子集校验器的核心在处理对象类型时就能看清。下面这段是 DSH 手写的、不依赖任何 JSON Schema 库的递归下降实现，用显式栈而不是递归调用（避免深层 schema 爆栈）：

            if (!Object.hasOwn(frame.value, key) || frame.value[key] === undefined) {
              violations.push(`missing required property "${propertyPath(frame.path, key)}"`)
            }
          }

json-schema.ts:561-566，接着是多余字段：

            for (const key of Object.keys(frame.value)) {

json-schema.ts:573-579

三处值得抄的细节：

  • 用 Object.hasOwn 而不是 in 或 node.required 直接取值。模型可能传一个 {"__proto__": ...} 或者 {"constructor": ...}，用 in 会把原型链上的东西也当字段。labs 在 Python 侧对应的是“只遍历 properties 里显式列出的键”，不做任何动态属性查找。
  • required 同时检查 !Object.hasOwn(...) 和 === undefined：JSON 里没有 undefined，但反序列化中间产物里可能有，显式写键值为 undefined 和完全没写这个键在语义上都是“缺”
  • 多余字段单独收进 tailViolations，最后才合并——这个技巧的作用是让错误列表的顺序稳定（先必填、后多余），方便测试断言

labs 的校验器把同样的规则写成了 Python，核心是“积累问题而不是首错返回”：

def validate_value(schema: Mapping[str, Any], value: Any, path: str = "arguments") -> list[str]:
    """按 schema 校验一个值，返回全部问题（不是遇到第一个就返回）。

    一次报全，模型一次就能改对；只报第一个问题往往要来回好几轮。
    """
    problems: list[str] = []

    if "enum" in schema:
        allowed = schema["enum"]
        if value not in allowed:
            problems.append(f"{path}: 取值 {value!r} 不在 enum {allowed!r} 中")
        # enum 已经限定了取值，不再叠加类型检查，避免同一处报两条。
        return problems

    expected = schema.get("type")
    if expected is None:
        # 没写 type 就只做结构性检查，不做类型约束（JSON Schema 的宽松语义）。
        if isinstance(value, dict) and "properties" in schema:
            expected = "object"
        else:
            return problems

    if expected == "object":
        if not isinstance(value, dict):
            return _check_scalar_type(value, "object", path)
        properties: dict[str, Any] = schema.get("properties") or {}
        for key in schema.get("required") or []:
            if key not in value:
                problems.append(f"{path}.{key}: 缺少必填字段")
        for key, sub in properties.items():
            if key in value:
                problems.extend(validate_value(sub, value[key], f"{path}.{key}"))
        if schema.get("additionalProperties") is False:
            for key in value:
                if key not in properties:
                    problems.append(f"{path}.{key}: 不是已声明的字段（additionalProperties 为 false）")
        return problems

    if expected == "array":
        if not isinstance(value, list):
            return _check_scalar_type(value, "array", path)
        items = schema.get("items")
        if isinstance(items, dict):
            for index, entry in enumerate(value):
                problems.extend(validate_value(items, entry, f"{path}[{index}]"))
        return problems

    return _check_scalar_type(value, expected, path)

整数与数字的区分是这一层最容易写错的地方，需要单独一段：

def _check_scalar_type(value: Any, expected: str, path: str) -> list[str]:
    """单值类型检查。返回问题列表，空列表表示通过。"""
    if expected == "integer":
        # bool 是 int 的子类，得先排掉；3.0 在 JSON 里等价于 3，按整数收下。
        if isinstance(value, bool):
            return [f"{path}: 期望 integer，收到 boolean"]
        if isinstance(value, float) and not value.is_integer():
            return [f"{path}: 期望 integer，收到带小数的 {value!r}"]
        if not isinstance(value, (int, float)):
            return [f"{path}: 期望 integer，收到 {type(value).__name__}"]
        return []
    checker = _TYPE_CHECKS.get(expected)
    if checker is None:
        return [f"{path}: 不支持的 type {expected!r}"]
    if expected in ("number",) and isinstance(value, bool):
        return [f"{path}: 期望 number，收到 boolean"]
    if not isinstance(value, checker):
        return [f"{path}: 期望 {expected}，收到 {type(value).__name__}"]
    return []

这里有两个语言级别的坑。第一，Python 里 True 是 int 的实例（isinstance(True, int) 为真），如果直接 isinstance(value, int)，模型传 {"limit": true} 会被当成 1 收下，然后在 file[:limit] 这种地方产生一个没人想得到的结果。第二，JSON 只有一种数字类型，3.0 和 3 在网络上完全无法区分（很多序列化器会把 3.0 写成 3），所以 integer 的正确语义是“值是整数”，而不是“Python 类型是 int”：3.0 应该通过，3.5 应该被拒。labs 的测试把这两条都钉住了。

校验顺序也很重要：labs 的 call() 先校验参数、后跑钩子。反过来的话，钩子里的路径判断会拿到一份畸形参数——一个检查 args["path"].startswith(...) 的钩子会因为 path 类型不对而抛 AttributeError，而钩子抛异常的后果通常比参数错严重得多。OH 的顺序是相反的：pre_tool_use 钩子在 query.py:893 就先跑了，载荷是未校验的原始参数（query.py:896），到 917 行才校验。这个顺序有它的道理（钩子要能拦截畸形调用，甚至要在校验前就把调用挡掉），但写钩子的人必须知道自己拿到的是不可信数据。

4. 执行前钩子：allow / deny / reason

校验解决“参数写得对不对”，钩子解决“这次调用该不该发生”。labs 把钩子建模成一个返回决策对象的函数列表：

    def run_hooks(self, name: str, args: dict[str, Any]) -> HookDecision:
        for hook in self._hooks:
            decision = hook(name, args)
            if not decision.allowed:
                return decision
        return HookDecision.allow()
@dataclass(frozen=True)
class HookDecision:
    """执行前钩子的返回值。allowed=False 时必须给 reason：拒绝理由会原样喂回模型。"""

    allowed: bool
    reason: str = ""

    @staticmethod
    def allow() -> "HookDecision":
        return HookDecision(True)

    @staticmethod
    def deny(reason: str) -> "HookDecision":
        if not reason:
            raise ToolError("拒绝工具调用必须给出理由：模型看不到理由就只会重试同样的调用")
        return HookDecision(False, reason)

三个设计决定：

  1. 顺序执行，任一拒绝即终止。后面的钩子不再跑（测试 test_hooks_are_ordered_and_first_denial_wins 钉住了这一点）。串行执行意味着钩子必须是廉价的，别在里面做网络请求。
  2. 拒绝必须带理由，deny("") 直接抛 ToolError。这是被真实失败逼出来的约束：模型看不到理由，就只会原样重试同一个调用，然后被反复拒绝，直到轮数耗尽。理由本身是喂给模型的输入，写“被拒绝了”等于没写，写“路径 /etc 在只读区，请改用工作目录下的文件”才是有效信息。
  3. 钩子只能拒绝，不能强制放行。这是 DSH 明确写进文档的单调性契约：index.ts:1135-1137（任何匹配的 guard 都可以拒绝，但没有 guard 能强行放行另一个 guard 已拒绝的调用）。单调性的价值在于策略可以被推理：你要判断“这个调用能不能出去”，只需要看有没有任何一个策略拒绝了它，不需要考虑策略之间的相对顺序或谁先谁后。如果允许强制放行，你就得为每一对策略分别推理，策略数一多就无法维护。

DSH 把这条规则实现成两层，位置在 pre-execute 之后。第一层是可扩展的 waterfall 事件，listener 可以返回 allow / deny / cancel / ask 四种决策，语义写在事件声明上方：

     * Allow, deny, cancel, or ask before dispatch. `next()` delegates to allow;
     * `cancel` selects the canonical pre-dispatch cancellation result, and missing
     * approval support turns `ask` into denial. Async gates must observe
     * `exec.signal`; the registry rechecks cancellation after they settle but

index.ts:145-148。注意 missing approval support turns ask into denial：没有审批通道时 ask 降级为拒绝，也就是 fail-closed——一个需要人确认的调用，在没人能确认的场景下必须失败而不是放行。这个默认值选错方向（fail-open）在很多部署里就是安全事故。

第二层是 guard，它单调且同步，返回值就是拒绝理由（index.ts:1139）。两层的调用点在同一段代码里，顺序写得很清楚：

      const askResolution = gate.kind === 'ask'
        ? await this.serviceAsk(exec, gate)
        : { decision: gate, approvalCancelled: false }
      const { decision } = askResolution
      if (this.callerCancelled(exec) && askResolution.approvalCancelled) {
        return await next({ kind: 'post-result', exec, result: toolAbortedBeforeDispatchResult() })
      }
      if (decision.kind === 'cancel') {
        return await next({ kind: 'post-result', exec, result: toolAbortedBeforeDispatchResult() })
      }
      const denialReason = decision.kind === 'allow' ? this.guardReason(exec) : decision.reason

index.ts:1515-1525。这一行是整个钩子层的浓缩：decision.kind === 'allow' ? this.guardReason(exec) : decision.reason——如果 pre-execute 已经拒绝了，就直接用它的理由；只有它放行时，才去问 guard。guard 永远跑在 pre-execute 之后，永远不能推翻它。

拒绝最后长什么样？它和工具体自己抛错走同一个出口，都是一条 isError 的文本结果：

          result: this.materializeFinalResult({
            content: [{ type: 'text', text: `Error: ${denialReason}` }],
            isError: true,

index.ts:1531-1533。前缀是 Error: 。这个前缀不是装饰：模型见过的训练数据里，工具结果的 Error: 前缀和“这条路走不通，换一条”是稳定关联的。labs 用了同样的前缀（Error: 工具 'x' 被拒绝：...），OH 用的是 is_error=True 加一句自然语言（query.py:901），lcc 什么都没有——它的结果块里根本没有 is_error 字段（code.py:183），所以模型只能从文本内容自己猜这次调用成功了没有。

labs 的钩子接在调用链里的位置是这样：

    def call(self, name: str, args: Any) -> str:
        """执行一次模型请求的调用。任何失败都返回字符串错误，不抛异常。"""
        tool = self._tools.get(name)
        if tool is None:
            known = ", ".join(sorted(self._tools)) or "（一个都没有）"
            return f"Error: 未知工具 {name!r}；可用工具：{known}"

        if not isinstance(args, dict):
            return f"Error: 工具 {name!r} 的参数必须是对象，收到 {type(args).__name__}"

        problems = validate_value(tool.input_schema, args)
        if problems:
            return f"Error: 工具 {name!r} 的参数不合法：\n- " + "\n- ".join(problems)

        decision = self.run_hooks(name, args)
        if not decision.allowed:
            return f"Error: 工具 {name!r} 被拒绝：{decision.reason}"

        try:
            return str(tool.handler(args))
        except Exception as exc:  # noqa: BLE001 — 工具是用户代码，什么异常都可能有
            # 异常转成错误文本而不是上抛：一次工具失败不该结束整个循环。
            return f"Error: 工具 {name!r} 执行失败：{type(exc).__name__}: {exc}"

整个 call() 的返回类型是 str，没有 raise 分支。这是刻意的：这个方法就是“模型调用”和“内部实现”之间的边界，边界上一旦有异常泄漏，循环就多了一条崩溃路径，而循环的调用方（下一章的调度器）通常并不准备处理它。

未知工具单独说一下。labs 返回 Error: 未知工具 'x'；可用工具：a, b——把可用工具列出来。这不是可有可无的礼貌：模型拼错工具名时，看到列表就能自己纠正；看不到列表就只会换一个同样错的名字再试。DSH 在未知工具的报错里做了同类的“给出路”处理：如果一个名字可见但被呈现模式挡住（比如 PTC 模式下只有 run_code 能直接调），报错会带上路怎么走，注释解释了这个决定的理由——否则模型读到的是一个光秃秃的 unknown tool，而它记得提示里刚声明过这个工具，就会得出“部署坏了”的结论，而不是“我调错了”（index.ts:1469-1473）。OH 的未知工具分支同样给了名字但没给列表（query.py:912）。

5. 只读标记如何影响后续调度

“只读”这个标记之所以必须放在工具定义里，是因为它决定了循环能不能把一批调用并发发出去。OH 让它成为一个方法而不是字段，因为只读与否可能取决于参数：

    def is_read_only(self, arguments: BaseModel) -> bool:
        """Return whether the invocation is read-only."""
        del arguments
        return False

base.py:46-49。基类默认返回 False，也就是 fail-safe：忘了覆盖就当写操作，宁可串行。具体工具覆盖它，例如文件读取工具恒为真（file_read_tool.py:27-29）。这个标记在权限层直接被消费：只读调用无条件放行（checker.py:132-134）。

但要注意，OH 的执行调度并不看这个标记：多个调用一律并发（query.py:853），只有单个调用时才走顺序分支，理由是事件要即时发出去（query.py:821-822）。这意味着两个写文件调用会被同时发出去。它为什么还能用？因为并发写同一个文件在多数场景下不出现，而且它用 return_exceptions=True 保证一个失败不会把兄弟调用取消掉，理由是保住 tool_use/tool_result 的配对（query.py:849-852）。配对这件事是硬约束，后面第 6 节会展开。

DSH 把“能不能并发”抽成一个独立的、更严格的概念：isConcurrencySafe。它的三条规则值得背下来：

   * Pure synchronous classifier for overlap with sibling tool calls. Only
   * `true` opts in; omission, exceptions, non-`true` returns, and invalid
   * `defineTool` arguments are exclusive. This metadata is never model-visible.

index.ts:269-271。规则是“只有显式返回 true 才算”，异常、返回非 true、甚至参数没通过校验都算独占。最后这一条在 defineTool 里实现：

    tool.isConcurrencySafe = (args: unknown): boolean => {
      if (validate(args).length > 0) return false
      return userIsConcurrencySafe(args as InferArgs<S>)
    }

schema.ts:626-629。为什么要先校验参数？因为作者写的分类函数假定参数是合法的（它拿到的是 InferArgs<S>），你把一份缺字段的参数喂进去，它可能抛也可能返回一个错误的 true。先校验，就保证了分类函数只在合法输入上被调用。

查询方在同一份源码里，每次调用现查一次，不缓存：

  executionMode(exec: ToolExecutionInput): ToolExecutionMode {
    const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
    if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
    try {
      const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
      return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
    } catch {
      return { kind: 'exclusive' }
    }
  }

index.ts:1309-1318。三处 fail-safe：!tool?.isConcurrencySafe（未知工具或未声明 = 独占）、concurrencySafe === true（严格全等，返回 1 或 "yes" 都不算）、catch { return exclusive }（分类函数抛异常也独占）。模式语义很短：parallel 可以和兄弟调用重叠，exclusive 单独跑并形成一个顺序屏障（index.ts:356-357）。

labs 把这两个概念拆成了两个字段而不是一个：read_only（能否只读地访问系统，影响权限判定）和 parallel_safe（能否与兄弟调用重叠，影响调度）。它们可以不一致：一个只读但需要独占某个共享游标的工具，read_only=True, parallel_safe=False。DSH 只有 isConcurrencySafe 一个（权限由 pre-execute 钩子处理，不需要工具自报只读），OH 只有 is_read_only 一个（且不参与执行调度）。分组逻辑在 labs 里是一个纯函数：

def group_calls(registry: ToolRegistry, calls: Iterable[tuple[str, Any]]) -> list[list[tuple[str, Any]]]:
    """把一次模型回复里的多个调用切成执行组：连续可并发的合成一组，独占的各自成组。"""
    groups: list[list[tuple[str, Any]]] = []
    current: list[tuple[str, Any]] = []
    for name, args in calls:
        if execution_mode(registry.get(name)) == "parallel":
            current.append((name, args))
        else:
            if current:
                groups.append(current)
                current = []
            groups.append([(name, args)])
    if current:
        groups.append(current)
    return groups
def execution_mode(tool: ToolSpec | None) -> str:
    """按工具的并行标记返回 'parallel' 或 'exclusive'。

    未知工具按 exclusive 处理：宁可让一个坏名字挡住后面的调用，
    也不要让它混进一批并发调用里。
    """
    return "parallel" if tool is not None and tool.parallel_safe else "exclusive"

结果是一个组列表：[读, 读, 写, 读] 切成 [[读, 读], [写], [读]]（三条组，长度 2/1/1）。写工具是屏障——它前面的读必须先跑完，它后面的读不能和它同时跑。这个“屏障”语义和 DSH 的调度器完全一致，那部分的实现细节在第 01 章已经讲过（tool-calls.ts 里的滚动池与重新分类），这里只强调它依赖上报的元数据：分类错一个工具，屏障就是假的。

教学示意：并发能省多少时间取决于工具本身的耗时结构。教学示意：五个各耗时 1 秒的只读工具，串行是 5 秒，全并发是 1 秒多一点；但如果其中两个工具是 90% 时间在等网络、10% 时间在占 CPU，并发收益会小得多，因为真正的瓶颈不在等待而在本机。别把“并行安全”当成性能保证，它只是“允许重叠”。

6. 坑与失败案例

下面五条是这一层最常见的翻车方式，每条都尽量指到具体行为。

坑 1：注册与定义分成两张表，忘同步就静默降级

lcc 的 s02 是教科书式的反例。它有两张必须手工保持同步的结构：TOOLS（code.py:138）让模型知道有什么工具，TOOL_HANDLERS（code.py:153-156）让 harness 知道怎么执行。README 自己把流程写成两步：定义工具、注册处理函数（README.zh.md:29）。

忘同步的后果分两种。只加在 TOOLS 里：模型看到工具、调它、拿到 "Unknown: xxx"（code.py:181）——而且因为结果里没有 is_error，模型会把这句 Unknown: xxx 当作一次成功的工具输出。只加在 TOOL_HANDLERS 里：多了个永远不会被调用的函数，无害但也无用。真正的问题是这两种错误都是静默的——循环会一直转下去，直到轮数用完或用户放弃。

防御方式就是 labs 的做法：让定义和实现在同一个对象里（ToolSpec 同时持有 input_schema 和 handler），注册时一次性收下，两张表在结构上不可能不同步。OH 的 BaseTool 是同一个思路：name / description / input_model 是类属性，和 execute 同属一个类（base.py:38-40）。

坑 2：不校验参数，直接把模型的 dict 展开成关键字参数

lcc 的 s02 用 handler(**block.input) 直接展开（code.py:181）。这一行有四种坏结局：字段缺失 → TypeError: missing required positional argument；多余字段 → TypeError: unexpected keyword argument；类型不对 → 要看具体实现，多数情况变成一个更难懂的错误（比如 len() of unsized object）；名字撞上保留参数 → 调用了一个你没打算调用的东西。

更糟的是这些异常发生在循环里而不是工具边界上：s02 的循环体没有 try/except，一个 TypeError 会直接冲出 agent_loop，整个会话结束。labs 用 call() 那一层 try/except 把工具异常转成错误文本（见第 4 节代码），OH 用 _execute_tool_call 里更早的 model_validate 把那四类问题在展开之前就拦下来。

坑 3：错误结果没有标记成错误

Anthropic 的 tool_result 块有一个可选布尔字段 is_error。漏掉它的后果比看起来严重：模型分不清“工具说没找到文件”和“工具执行失败了”。前者应该换路径重试，后者应该放弃这个方案或修参数——如果两种情况在模型眼里长得一样，它就只好靠猜。lcc 的 s02 全程没有这个字段（code.py:183），OH 和 DSH 都设了（query.py:923，index.ts:1533）。写自己的 harness 时，把“工具失败”和“工具有效地报告了一个否定结果”分开建模，是省下大量调试时间的一件事。

坑 4：结果截断位置不当，切断了结构化内容

工具输出必须截断（否则一次 cat 大文件就能把上下文塞满），但在哪里切很有讲究。lcc 直接切前 50000 字符（code.py:88），既不落盘也不加省略标记——模型完全不知道后面还有内容，也不知道自己看到的是一份被裁过的证据。用这份假证据做决策，就是幻觉的来源。

OH 的处理更完整：超过阈值就把全文落盘，上下文里只留一段说明、文件路径和预览（query.py:542）。三个阈值是可配的常量：内联 16000 字符、预览 3000、微压缩准入 4000（tool_outputs.py:10-12）。DSH 把这件事交给插件而不是工具：tools/post-execute 之后的 spill 策略决定什么时候把超长结果换成定位符（相关包在第 08 章展开），工具体只要保证自己的返回值是合法的 JSON 值就行。

教训：截断策略要有可逆性。宁可给模型一个能取回全文的句柄，也不要给它一段被悄悄裁过的文本。

坑 5：schema 里写了子集外的关键字，以为它会生效

很多人第一反应是在 input_schema 里写 minimum、minLength、pattern、anyOf。这些模型看得懂（它们会照着提示尽量遵守），但你的校验器如果不支持，就等于没写——模型偶发的违规会一路走到工具函数里。DSH 的做法是双向封死：作者向的 DSL 只允许一个很窄的子集，而且不认识的 keyword 直接拒绝，而不是忽略（json-schema.ts:267）。报错里带子集清单，作者一眼就能看出该用什么替代。

labs 抄了这一条：check_schema() 在注册时递归检查关键字，不认识的当场失败。这样做的额外好处是——模型看到的 schema 和 harness 校验用的 schema 是同一份，两者不可能漂移。lcc 反过来的问题更严重：它的 schema 里只有 type/properties/required，而 harness 侧一行校验都没有，所以 schema 完全是给模型看的提示，没有任何强制力。

8. 小结

  • 模型的全部认知来自三件套；执行侧的字段要主动用白名单挡住，别靠“记得不要传出去”。
  • 重名注册必须报错，并且要想清楚报错的范围（同层 vs 跨层）；保留名在“当前没人用”的时候就要挡。
  • 参数校验由 harness 做，位置在工具执行体之外；一次报全所有问题；失败以错误结果回给模型，不以异常打断循环。
  • 钩子只能拒绝，不能强制放行。拒绝必须带理由，否则模型只会重试。没有审批通道时，ask 要降级为拒绝（fail-closed）。
  • 只读 / 并行标记的默认值必须是“不安全的那一边”；分类函数抛异常要兜底成独占。
  • 结果截断要可逆：给句柄和说明，不要给一段没有痕迹的裁剪文本。
