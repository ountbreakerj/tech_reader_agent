第 14 章

Shell 命令解析

主线故事 · 第 14 章（虚构）

老唐把那两周的 run_bash 日志导成一份文件，用橙色的荧光笔在上面划。划到第十七行的时候他停下来，把屏幕转给林舟。

那一行是：grep -rn "timeout" . > /tmp/scan.log。

“这条命令没有写 rm，没有写 mv，它唯一的动作是把结果写到一个文件里。”老唐说，“你的规则放它过了，因为它只看工具名。”

后面还有更隐蔽的。有一条 git checkout -- src/，把三个文件的未提交修改丢掉了；有一条 find . -name "*.pyc" -delete，程序名是白名单里的 find，动作是删除；还有一条 sed -i "s/DEBUG = True/DEBUG = False/" config.py，程序名是 sed，一个参数就把它变成了写操作。

林舟的第一版补救是加关键词：命令里出现 >、-delete、-i 就拦。当天下午橘子用 cat $(ls /tmp/*.sql) 绕过去了——参数里的 $(...) 会在执行时被 shell 展开成别的东西，而这条命令的字面文本里既没有重定向也没有危险参数。第二天又出了一条误报：echo "use > to redirect"，引号里的那个 > 被当成了真的重定向。

“你在拿字符串做语法分析。”老唐把荧光笔盖上，“要做就正经做：先把它拆成片段，再看每个片段的第一段程序是什么。”

这一章要做的事就是拆：按 shell 的规则切开 ;、&&、|、换行，但不切开引号里的；给每个片段取出程序名和参数；把“重定向写文件”“命令替换”“子 shell”“解释器内联代码”这些让命令变得不可静态判定的东西标出来；最后只给三种结论——只读、需要人看、无法判定。目标不是“识别危险命令”，而是把不确定的地方暴露出来，因为一个能确定说“我判定不了”的解析器，比一个猜测的规则安全得多。

权限规则遇到 run_bash 时会卡住，因为它的参数只有一个键 command，值是一条字符串。模型在这条字符串里能表达的东西，比任何工具 schema 都多：管道、逻辑连接、重定向、命令替换、子 shell、变量展开、把一段代码作为参数交给解释器。规则要做出参数级判定，前提是先把这条字符串变成结构。

这一章只做一件事：把命令字符串解析成可判定的结构，然后给出保守的结论。至于结论出来之后是放行、问人还是拒绝，属于第 13 章和第 16 章。

先看全貌：Shell 命令解析是什么、管哪些事

一句话：把 run_bash 那一条字符串拆成若干片段，判断每个片段在跑什么程序、会不会改动文件系统，然后把无法静态判定的部分标出来。

它管四件事：

  • 切分：按 shell 的语法切开连接符（;、&&、||、|、换行、&），引号和转义内部不切。
  • 分词：每个片段取出 argv，程序名就是第一段。
  • 分类：程序是否在只读白名单里；参数里有没有把只读程序变成写操作（sed -i、sort -o、git checkout）。
  • 标记不可判定：重定向、命令替换、变量展开、子 shell、解释器内联代码、通配符。

四个决定，先给结论：

决定看起来省事的做法本章的结论
判定方式在原始字符串上找关键词先按 shell 语法切分，再逐段判断；字符串匹配两头都错（漏 /bin/rm、误报引号里的关键词）
白名单还是黑名单列一串危险命令拦住用只读白名单：命中的放行，其余按需要人看处理。黑名单永远在补漏
遇到看不懂的部分猜一个大概率的结果标成不可判定，按最坏情况处理（拒绝或强制问人）
多条片段混合看第一条命令取所有片段里最严的结论：一段要写，整条就不能自动放行

三个仓库在这一层分别是什么水平

第一步是切分，而切分的关键是引号

切分的目标是把一条命令变成若干片段，每个片段对应一个进程（大致上）。分隔符有六种，其中三种是“顺序执行”（;、&&、||），两种是“管道”（|、|&），一种是把整条命令放到后台（&）。判定时它们的区别不大——不管用什么连接，每一段都会被执行——但记录连接符有额外用途：&& 后面的片段只在前面成功时执行，这对“这条命令会不会真的删东西”的判断有影响，虽然保守起见我们会忽略这个区别。

真正麻烦的是引号。下面四条命令看起来相似，判定结果完全不同：

命令片段数正确的判定
grep a file.txt; rm b.txt2第二段是删除，不是只读
grep "a; rm b.txt" file.txt1只读：; 在被搜索的字符串里
echo 'a | b'1只读：单引号里不做任何展开
echo a\;b1只读：反斜杠转义了分隔符

切分函数是一个字符一个字符往前走的循环，维护三个状态：当前是否在某种引号里、上一个字符是否是转义符、当前正在积累的片段。它不解释语义，只负责“在正确的位置断开”：

def split_segments(command: str) -> list[tuple[str, str]]:
    """按 shell 分隔符切分，返回 [(连接符, 片段)]。引号与转义内部不切。

    这是本模块最容易出错的地方：`echo "a; b"` 是一段，`echo a; b` 是两段；
    `2>&1` 和 `&>` 里的 & 是重定向的一部分，不是「放到后台」。
    """
    pieces: list[tuple[str, str]] = []
    buffer: list[str] = []
    separator = ""
    quote = ""
    escaped = False
    index = 0
    while index < len(command):
        char = command[index]
        if escaped:
            buffer.append(char)
            escaped = False
            index += 1
            continue
        if char == "\\" and quote != "'":
            buffer.append(char)
            escaped = True
            index += 1
            continue
        if quote:
            buffer.append(char)
            if char == quote:
                quote = ""
            index += 1
            continue
        if char in ('"', "'"):
            quote = char
            buffer.append(char)
            index += 1
            continue
        matched = next((sep for sep in SPLITTERS if command.startswith(sep, index)), "")
        if matched == "&" and _is_redirect_ampersand(command, index):
            matched = ""
        if matched:
            pieces.append((separator, "".join(buffer).strip()))
            separator = matched
            buffer = []
            index += len(matched)
            continue
        buffer.append(char)
        index += 1
    pieces.append((separator, "".join(buffer).strip()))
    return [(sep, text) for sep, text in pieces if text]

这段代码有四处值得注意：

  • 双引号里的反斜杠仍然有转义作用，单引号里的没有。所以判断转义时要看 quote != "'"。"a\"b" 是一个片段，'a\'b' 里那个反斜杠是普通字符。
  • 切分只做切分，不解释。$VAR、$(cmd) 在这里被当作普通文本原样保留，交给第 4 节的标记步骤处理。
  • 分隔符按长度优先匹配：&& 必须比 & 先试，否则 a && b 会被切成 a & 和 & b。labs 把 &&、|| 放在分隔符列表前面。
  • 保留连接符：返回的是 (连接符, 片段) 对，连接符记在片段上，后面判定和给模型的理由都用得到。

分词交给标准库的 shlex——它已经正确处理了引号、转义和 Windows 之外的常见情形。切不出来（引号没闭合）时返回空列表，让上游把整条命令标成不可判定，而不是丢掉这段继续判。

只读白名单：判的是程序加参数，不是命令名

分类的核心是一份只读白名单。选它的理由很直接：能自动放行的命令是少数，而“所有其他命令”是一个无限集合，没法枚举。白名单漏掉的是灵活性（多问几次），黑名单漏掉的是安全性。

READ_ONLY_COMMANDS = frozenset({
    "cat", "head", "tail", "wc", "ls", "find", "grep", "rg", "awk", "sed", "cut", "sort",
    "uniq", "diff", "file", "stat", "du", "df", "echo", "printf", "pwd", "which",
    "whoami", "date", "basename", "dirname", "realpath", "jq", "md5sum",
    "sha256sum", "od", "nl", "tr", "type", "git",
})

白名单只是第一层。同一个程序名，参数一变性质就变，所以分类还要看参数：

程序看起来只读实际会写怎么判
sedsed -n 1,10p a.txtsed -i s/a/b/ a.txt参数含 -i / --in-place
sortsort a.txtsort -o out.txt a.txt参数含 -o / --output
gitgit statusgit checkout / git reset / git push子命令在只读子命令集合里
findfind . -name "*.py"find . -delete / find . -exec rm {} \;参数含 -delete 算会写（需要人看）；含 -exec 算不可判定，因为它会对每个结果执行任意命令
awkawk '{print $1}' a.txtawk '{print > "out.txt"}' a.txt脚本参数里含重定向算会写；含 system( 或管道算不可判定

这类“参数改变语义”的判断不可能穷尽。git 尤其麻烦：它的子命令有一百多个，其中一部分既读又写（git stash、git clean），还有一部分取决于参数（git branch -D）。labs 的做法是给 git 单独一张只读子命令表，其余一律按“需要人看”处理：

READ_ONLY_GIT = frozenset({"status", "log", "diff", "show", "branch", "rev-parse", "describe", "blame", "ls-files"})

branch 在只读表里，但它要再看参数：不带参数是列出分支，带 -D 或一个新名字就是删除或创建。所有“白名单程序 + 参数改变性质”的判断集中在一个函数里，新增规则时只改这一处：

def _program_risk(argv: list[str]) -> tuple[str, str] | None:
    """白名单程序里，参数会改变性质的那几个。返回 (结论, 理由)；None 表示参数没问题。

    sed 和 awk 本身是完整的语言，这里只覆盖最常见的写法；拿不准的交给沙箱兜底（hx-15）。
    """
    program, args = argv[0], argv[1:]
    positional = [arg for arg in args if not arg.startswith("-")]
    if program == "find":
        if any(arg in ("-exec", "-execdir", "-ok", "-okdir") for arg in args):
            return "opaque", "find -exec 会对每个结果执行任意命令"
        if any(arg in ("-delete", "-fprint", "-fprintf", "-fls") for arg in args):
            return "needs_review", "find 带 -delete / -fprint，会删除或写文件"
    elif program == "sed":
        if any(arg.startswith("-i") or arg.startswith("--in-place") for arg in args):
            return "needs_review", "sed -i 会原地修改文件"
        script = positional[0] if positional else ""
        if re.search(r"(^|[;}/])\s*[we]\b", script):
            return "needs_review", "sed 脚本里有 w（写文件）或 e（执行命令）"
    elif program == "awk":
        script = positional[0] if positional else ""
        if "system(" in script or "|" in script:
            return "opaque", "awk 脚本里调用了 system() 或管道，会执行别的命令"
        if ">" in script:
            return "needs_review", "awk 脚本里有重定向，会写文件"
    elif program == "sort":
        if any(arg in ("-o", "--output") or arg.startswith("--output=") for arg in args):
            return "needs_review", "sort -o 会写文件"
    elif program == "uniq":
        if len(positional) >= 2:
            return "needs_review", "uniq 的第二个参数是输出文件"
    elif program == "date":
        if any(arg in ("-s", "--set") or arg.startswith("--set=") for arg in args):
            return "needs_review", "date -s 会修改系统时间"
    elif program == "git":
        sub = positional[0] if positional else ""
        if sub not in READ_ONLY_GIT:
            return "needs_review", f"git {sub or '（无子命令）'} 不是只读子命令"
        if sub == "branch":
            rest = args[args.index("branch") + 1:]
            if any(arg in ("-d", "-D", "-m", "-M", "-c", "-C", "--delete", "--move", "--copy") for arg in rest) \
                    or any(not arg.startswith("-") for arg in rest):
                return "needs_review", "git branch 带参数会创建、删除或重命名分支"
    return None

注意这里判的是具体的写出选项，而不是“带 -o 或 -i 就算写”：grep -i 是忽略大小写，grep -o 是只输出匹配部分，它们都不写文件。一刀切的写出选项列表会让 grep -i todo 这种最常见的只读命令每次都停下来问人，用户很快就会去把审批关掉。

经验：白名单的条目应当由“最近用到过、而且明确只读”的命令逐步积累，而不是一次性抄一份 shell 命令大全。清单越长，误放行的概率越大，而每一条都需要有人真的审过。labs 的清单里故意没有 tee、xargs、install、cp / mv——它们看起来无害，但都是写操作；也没有 env（env rm -rf build 会执行后面的命令）、xxd（xxd a b 会写 b）和 tree（tree -o 会写文件）。

三种结论，而不是一个布尔值

解析的产物不是“安全 / 不安全”，而是三种状态：

结论含义建议动作典型例子
readonly全部片段都是只读程序，参数里没有写出选项，也没有重定向或替换自动放行cat a.txt | grep -n todo | wc -l
needs_review能判定它会做什么，而且其中有一段会写问人（或按规则拒绝）ls > out.txt、sed -i ...、git checkout -- src/
opaque无法静态判定它到底会做什么默认拒绝；明确知道风险并配置过时降级为问人sh -c "..."、cat $(find . -name x)、python -c "..."

把 opaque 单列出来是这套设计的关键。很多实现只有“危险 / 安全”两档，于是所有看不懂的命令都被塞进“安全”那一档（因为看起来没有危险词），或者被塞进“危险”那一档（于是 cat $(ls) 和 rm -rf / 得到同样的处理，用户很快就不再认真读提示了）。

判定顺序是：先算每一段的结论，再取最严的一个。最严的顺序是 opaque > needs_review > readonly：

def analyze(command: str) -> CommandAnalysis:
    """解析一条 shell 命令，给出判定与理由。"""
    analysis = CommandAnalysis(command=command)
    if not command.strip():
        analysis.verdict = "opaque"
        analysis.reasons.append("空命令")
        return analysis

    for separator, text in split_segments(command):
        segment = Segment(text=text, separator_before=separator, argv=_tokenize(text))
        if redirect_targets(text):
            segment.flags.append("write-redirect")
        if SUBSTITUTION.search(strip_quoted(text, double=False)):
            segment.flags.append("substitution")
        if GLOB.search(strip_quoted(text, double=True)):
            segment.flags.append("glob")
        analysis.segments.append(segment)

    reasons: list[str] = []
    verdict = "readonly"
    for segment in analysis.segments:
        program = segment.program
        if not program:
            verdict = _worse(verdict, "opaque")
            reasons.append(f"无法解析片段 {segment.text[:40]!r}（引号未闭合或语法不完整）")
            continue
        if "substitution" in segment.flags:
            verdict = _worse(verdict, "opaque")
            reasons.append(f"{program}: 含命令替换或变量展开，实际执行的命令在解析阶段无法确定")
        if "write-redirect" in segment.flags:
            verdict = _worse(verdict, "needs_review")
            targets = ", ".join(redirect_targets(segment.text))
            reasons.append(f"{program}: 重定向会写入 {targets}")
        if program in SHELL_INTERPRETERS or (program in CODE_RUNNERS and _runs_inline_code(segment.argv)):
            verdict = _worse(verdict, "opaque")
            reasons.append(f"{program}: 直接把代码当参数执行，内容无法静态判定")
        elif program not in READ_ONLY_COMMANDS:
            verdict = _worse(verdict, "needs_review")
            reasons.append(f"{program}: 不在只读白名单里")
        else:
            risk = _program_risk(segment.argv)
            if risk:
                verdict = _worse(verdict, risk[0])
                reasons.append(f"{program}: {risk[1]}")

    analysis.reasons = reasons or ["全部片段都是白名单里的只读命令，且没有写文件的重定向"]
    analysis.verdict = verdict
    return analysis

和权限引擎同构：局部结论先算出来，合成时取最严，理由逐条累积。这样的好处是判定结果永远可以说清楚——你能告诉用户“因为第三段含命令替换，所以整条按不可判定处理”。

不可判定：这四类东西让命令不再是一段静态文本

有四类语法让命令的实际行为在解析阶段无法确定。它们不是“危险”，而是“无法判定”，处理方式应该和危险区别开。

命令替换与变量展开。$(...)、反引号、${VAR} 的值在执行时才确定。攻击者可以用它绕过任何字符串判断：c\at /etc/shadow 里那个反斜杠会被 shell 吃掉。更常见的是无害用法（cat $(find . -name "*.log")），但你无法从文本上区分两者。

子 shell 与进程替换。(...) 里可以是一整条命令，<(cmd) 把命令输出当成文件描述符传给程序。

解释器内联代码。sh -c "..."、bash -lc "..."、python -c "..."、perl -e "..."、node -e "..."。注意这里的判据是程序名 + 参数形态，不是“程序名在黑名单里”：python setup.py install 是未知程序（会写），python -c "..." 是不可判定。两者结论不同，处置也不同。

通配符与重定向。*、? 展开成哪些文件取决于磁盘状态；>、>>、&> 会写文件（<<< 是把字符串当输入，不写文件）。前者 labs 只做标记（不放行也不拒绝，由别的规则决定），后者算“需要人看”——它确定会写，只是不知道写什么。

重定向有两个容易误判的地方。一是引号里的符号是字面量：echo "a > b" 不写文件，所以找重定向之前要先把引号里的内容去掉。二是有些重定向不写文件：2>/dev/null 把错误丢掉，2>&1 合并两个输出流，它们出现在大量只读命令的末尾。把它们也当成写操作，grep -rn todo . 2>/dev/null 就要问人，误报会多到没人愿意读提示。labs 用同一个函数处理这两件事：

def redirect_targets(text: str) -> list[str]:
    """片段里会写入的重定向目标。`>/dev/null`、`2>&1` 不算；目标被引号包住时记作 '?'。"""
    bare = strip_quoted(text, double=True)
    targets: list[str] = []
    for match in REDIRECT.finditer(bare):
        target = match.group(1)
        if target not in HARMLESS_TARGETS:
            targets.append(target or "?")
    return targets

还有一个连带的细节：2>&1 和 &>out.txt 里的 & 是重定向的一部分，不是“放到后台”的连接符。切分函数遇到 & 时要看它前后的字符，否则 ls 2>&1 会被切成两段。

这四类的判定结果统一往 opaque 或 needs_review 走，然后转成权限决策：

def to_hook_decision(analysis: CommandAnalysis, *, allow_opaque: bool = False) -> tuple[str, str]:
    """把分析结果映射成权限引擎的判定（allow / ask / deny）与理由。"""
    if analysis.verdict == "readonly":
        return "allow", "命令的每一段都是只读的，且没有写文件的重定向"
    if analysis.verdict == "needs_review":
        return "ask", "命令里有会写入的片段：" + "；".join(analysis.reasons)
    return ("ask" if allow_opaque else "deny"), "无法判定这条命令会做什么：" + "；".join(analysis.reasons) \
        + "。请把要执行的命令直接写出来，不要用替换、变量或内联代码"

一个真实的边界：解析器不能用来做安全保证。它可以被绕过（换编码、用未列入的语法、把命令放进脚本文件里执行），所以它的定位是“把明显只读的放行、把明显要写的交给审批”，而不是“识别所有攻击”。真正的防线是第 15 章的沙箱——即使解析漏放了一条 rm，沙箱的路径边界和只读挂载仍然限制它能删什么。这句话在很多实现里被搞反了：它们把解析当成安全边界，于是规则一漏，损失就没有上限。

把解析结果接回权限引擎

解析器输出的是结构，权限引擎需要的是 allow / deny / ask。两者之间用一个适配函数连接，规则只写一条：

解析结论权限引擎的动作理由文案（喂回模型）
readonlyallow（不需要）
needs_reviewask“命令里有一段会写：sed -i 会原地修改文件；请确认，或改用 write_file 工具”
opaquedeny（默认）或 ask（配置过时）“这条命令含命令替换，实际执行的命令无法确定；请把展开后的命令直接写出来”

最后一行的那句理由是有讲究的。橘子出问题的那条命令是 cat $(ls /tmp/*.sql)，直接拒绝之后它收到的是“无法确定你执行什么”。它下一轮改成先跑 ls /tmp/*.sql，拿到文件名列表，再逐条 cat——两轮之后任务完成，全程没有人工介入。这就是把不可判定转成一次有效纠正，而不是一次空转。

有一条边界要提醒：解析只覆盖通过 run_bash 这一条路径进来的命令。如果某个工具内部会拼命令（比如“模糊查找文件”工具自己调 grep），那条命令不经过解析器，规则的覆盖就出现了缺口。真实项目里的做法是：所有执行外部程序的工具都必须经过同一个执行入口，解析与沙箱挂在这个入口上，而不是挂在某一个工具上。

哪些命令该进白名单：一份可维护的清单

白名单的维护比写解析器更花时间。三条经验：

  1. 按用途分组，而不是按字母：读文本（cat/head/sed -n/awk）、查目录（ls/find/du）、查内容（grep/rg）、看状态（git status/git diff/stat）。审清单时按组过，比一条条看快得多。
  2. 每个条目都要有一个“它为什么只读”的说法。sed 只读是因为不加 -i 就只输出到标准输出；git 只读是因为子命令在白名单里。写不出这个说法的条目，就该从清单里去掉。
  3. 把清单做成配置，而不是代码常量。项目不同，需要的命令不同；做成配置之后，用户可以在自己的项目里加规则（并承担后果），而不是来改 harness 的源码。

反面清单同样有用：明确列出一批“看起来只读、其实会写”的命令，命中就进 needs_review，不依赖白名单遗漏。tee、xargs、install、truncate、dd、patch、unzip -o 都属于这一类。

坑与失败案例

坑一：在原始字符串上做关键词匹配

  • 触发条件：规则写成 ">" in command 或 "rm" in command。
  • 后果：漏报与误报同时发生。grep "rm" notes.md 被拦；/bin/rm、rm\t-rf、find . -delete 放行；echo "a > b" 被当成重定向拦住。
  • 怎么防：切分 + 分词 + 按程序名分类；把“引号里的符号不是分隔符”写成测试。

坑二：只看第一个片段的程序名

  • 触发条件：cat a.txt && rm -rf build，判定只看 cat。
  • 后果：一条命令里后半段做什么完全不受约束；模型（或注入的指令）只要把危险动作接在只读命令后面就能过。
  • 怎么防：所有片段都判，取最严。labs 的 test_mixed_chain_takes_worst 覆盖三种组合。

坑三：把不可判定的命令当成安全

  • 触发条件：解析遇到看不懂的语法时返回“没发现问题”。
  • 后果：cat $(printf 'rm -rf /') 这类命令自动放行。所有基于解析的防护都被这一条归类错误一次性绕过。
  • 怎么防：解析结果三种状态，看不懂就是 opaque，默认拒绝；要降级成问人必须显式配置。

坑四：把解析当成安全边界

  • 触发条件：系统里只有解析层，没有沙箱和审批。
  • 后果：一次漏判就等于全部权限。典型的漏判路径是把命令写进脚本文件再执行（bash ./setup.sh 里是什么，解析器看不到），或者用程序拼命令（python -c 之外的一切解释器）。
  • 怎么防：解析负责“少问几次”，能力边界（沙箱的工作目录、只读挂载、超时）负责“少损失”。两者叠加，缺一个都会让另一个变得关键。

坑五：白名单里混进写命令

  • 触发条件：为了减少询问，把常用命令一股脑加进白名单。tee、cp、mv、sed -i、git stash。
  • 后果：白名单从此等于“全部放行”，而且因为攻击面转移，没人再去审它。更麻烦的是这些条目往往由“加一条就能少弹一次窗”这种动机驱动，一次一条，不知不觉。
  • 怎么防：每条白名单条目都要有“为什么只读”的理由；git 这种多子命令的程序拆开判；把白名单的变更纳入代码评审。

坑六：忽略重定向的目标

  • 触发条件：命令 cat a.txt > b.txt 被判成“读文件”。
  • 后果：目标文件被截断为零字节（> 会覆盖），而日志里只看到一次 cat。如果目标是配置文件或测试文件，损失往往在很久之后才体现。
  • 怎么防：任何重定向都算写操作，进 needs_review；如果解析器要更进一步，就把重定向的目标路径提取出来交给沙箱做路径校验。

值得注意的对比是 DSH 的选择：它没有把精力投在解析命令上，而是把边界放在权限钩子与沙箱。这个取舍有道理——命令语法是开放集合，解析永远落后一步；而沙箱的能力边界是封闭的，一旦设好就不会因为一条新语法而失效。实践中的推荐组合是：解析用来决定“要不要问人”，沙箱用来决定“问了也最多能怎样”。

小结

  • 判定前先切分：连接符分片段，引号与转义不切。切错的后果比判断错更严重。
  • 分类用只读白名单，程序名之外还要看参数（sed -i、sort -o、git checkout、find -delete）。
  • 结论是三态：只读、需要人看、无法判定。能说“我看不懂”是这一层最有价值的性质。
  • 命令替换、变量展开、子 shell、解释器内联代码让命令不再是静态文本，一律按最坏情况处理。
  • 多段命令取最严的一条；解析只覆盖经过统一执行入口的命令。
  • 解析不是安全边界；“问了也最多能怎样”由下一章的沙箱回答。

下一章把最后一道关补上：假设权限放行了、命令也看懂了，这条命令跑起来之后，它还能碰到什么。继续读：沙箱。
