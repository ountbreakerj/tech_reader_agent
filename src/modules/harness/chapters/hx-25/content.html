第 25 章

组装 mini-harness 与长任务连续性

主线故事 · 第 25 章（虚构）

阿青的问题是这样的：周五下班前她让橘子改一个模块，改到一半，改了三个文件，测试还没跑，她关掉终端走了。周一早上她重新打开，橘子问她：“有什么可以帮你的吗？”

日志里什么都有。但那是一份记录，不是一份交接。记录回答“发生过什么”，交接回答“现在是什么状态、接下来该做什么”。

林舟的第一版答案是“把上周的历史加载进来”。试了一次就放弃了：那个任务的历史有六万多 token，加载进来要花二十多秒和一笔不小的钱，而且模型读完之后还是会问“你想让我做什么”。

老唐让他换一个角度想：“人是怎么交接的？下班前你在群里说一句：今天改了哪三个文件、改到哪一步、下一步跑那个模块的测试、有个地方拿不准。周一早上接手的人先跑一遍测试看看当前状态，然后接着干。”

他们把橘子改成：一天结束前（或者任务告一段落时），写一份交接——目标、已完成、下一步、拿不准的地方、开工前该跑哪些验证命令；周一早上新会话开始时，读这份交接，并且先跑验证命令确认当前状态和交接里写的一致，再动手。

第一次试用就抓住了一个问题：交接里写“已改 a17、a18、a19，测试通过”，但验证命令跑下来发现 a18 的测试是失败的——因为周五下班后有人从主干合了一个改动进来。如果没有那一步验证，橘子会从“全都通过了”这个错误前提上继续往下做。

这一章做两件事：把前面二十四章的部件装成一台能跑的机器，以及回答“一个任务跑不完怎么办”——答案是让状态活在仓库里，而不是活在对话历史里。

前面每一章都只实现了一个部件，而且刻意让它能单独读懂：循环、注册表、执行管线、日志、预算、缓存、压缩、卸载、记忆、检索、权限、解析、沙箱、审批、注入、重试、超时、熔断、hooks、Skill 与 MCP、委派与 PTC、可观测性。这一章把它们接起来，重点是顺序：每一层放在哪、谁包着谁、谁在谁之前。

然后是最后一件没解决的事：连续性。一个要跑几天的任务，不可能一口气跑完；会话会结束、进程会被杀、用户会去睡觉。恢复靠什么？

先看全貌：组装与连续性是什么、管哪些事

一句话：组装是按正确的顺序把各章的部件串成一个能跑的整体；长任务连续性是指一个跨多个会话的任务，靠仓库里的工件（进度、决策、交接）而不是靠对话历史接上。

这一层的重点：

  • 顺序：一次工具调用和一次模型调用分别经过哪些层，谁包着谁。
  • 停止原因：一次运行为什么结束，每种原因对应什么处置。
  • 工件：进度文件、决策文件、交接文件分别记什么，谁写谁读。
  • 开工验证：新会话开始时先验证状态，再干活。
  • 压缩与重置的取舍：什么时候压缩现有历史，什么时候干脆从头开始。

四个决定，先给结论：

决定看起来省事的做法本章的结论
层与层的顺序按写的顺序随手嵌套熔断在重试外面、重试在模型外面、整轮截止时刻在最外面；hooks 在执行前后、权限在校验之后
停止原因一个布尔值“成功 / 失败”区分完成、轮数上限、时间超限、熔断、模型错误、错误预算、被拦截；每种给不同的下一步
跨会话恢复加载上一次的完整历史写一份交接：目标、已完成、下一步、未决问题、验证命令；新会话读交接并先跑验证
状态放哪放在对话历史里放在仓库里的文件里：历史会被压缩、会被截断、会随进程消失，文件不会

三个仓库在这一层分别是什么水平

DSH（TypeScript）：整份 harness 就是以“组装”的形式存在的——每个能力都是一个包，由若干装配文件把它们组合起来（基础的、headless 的、各运行形态各一套）。会话日志是唯一的事实来源，投影从日志里算出来，子代理结束时主线会等待它们，恢复靠日志重放。

OpenHarness（Python）：单体工程，各部件在同一个进程里按调用顺序串起来；恢复靠会话文件。

learn-harness-engineering（讲义）：这一层讲得最清楚。它的第五讲讲长任务为什么会失去连续性，列出三个具体的失效模式——重建成本、上下文焦虑、漂移（Drift）；给出的对策是仓库里的工件：进度文件、决策文件，以及“上班 / 下班”两套固定动作（会话开始时读状态并验证，会话结束前写进度和决策）。讲义里明确标注它的数字是教学默认值。

labs（本章要写的）：labs/harness/assembly.py，MiniHarness 把第 01–24 章的部件按顺序串起来，外加交接文件的读写与校验，14 条测试。

本章怎么读：

  1. 第 1 节给出完整的调用顺序，这是本章的骨架，值得对照 labs 的代码读一遍。
  2. 第 2 节讲停止原因；第 3 节讲组装版为什么故意做得小（它的用途是看清接口）。
  3. 第 4–6 节讲连续性：三个失效模式、三类工件、开工与收工的动作。第 6 节最重要。
  4. 第 8 节的坑可以当自查清单；第 9 节是全书的收束。

本章的源码描述来自前面章节已经核对过的笔记；不再逐条标注 文件:行号。

    def _run_tool(self, call_id: str, name: str, args: dict[str, Any]) -> tuple[str, bool, list[str]]:
        with self.tracer.span(f"tool.{name}", tool=name):
            pre = self.hooks.dispatch(PRE_TOOL, {"tool_name": name, "tool_input": args})
            if pre.blocked:
                return f"Error: 被 hook {pre.blocked_by} 拒绝：{pre.reason}", True, pre.contexts
            args = pre.payload.get("tool_input", args)
            if self.permissions is not None:
                decision = self.permissions.decide(name, args)
                if decision.outcome != ALLOW:
                    # 组装版没有审批界面：ask 按无通道处理（hx-16 的 fail-closed）
                    verb = "拒绝" if decision.outcome == DENY else "需要人工确认，当前无审批通道，按拒绝处理"
                    return f"Error: 权限规则 {decision.rule or '默认策略'} {verb}：{decision.reason}", True, pre.contexts
            output = self.registry.call(name, args)      # 内部做参数校验，失败返回 Error 文本
            is_error = output.startswith("Error:")
            post = self.hooks.dispatch(POST_TOOL, {"tool_name": name, "tool_input": args,
                                                   "tool_output": output, "is_error": is_error})
            return str(post.payload.get("tool_output", output)), is_error, pre.contexts + post.contexts

两条容易搞反的顺序，在组装时值得专门确认一次：

  • hooks 在权限之前还是之后？labs 放在之前，理由是 hook 可以修改参数（比如规范化路径），权限应该对最终参数做判断。如果放在之后，一个 hook 把 ../etc/passwd 改成别的路径，权限判定就基于了一个过期的值。反过来的考虑也有道理：先让权限拒绝掉明显不该做的调用，省掉一次 hook 启动开销。两种都成立，关键是写清楚，并且不要在同一层既改参数又依赖参数。
  • 审批在权限之前还是之后？必须在之后（第 16 章）：规则拒绝的调用不应该交给人去特批，否则规则就不再是边界。

组装版里还有一处是刻意简化的：ask 被当成“无审批通道”处理，直接拒绝。这是第 16 章的 fail-closed 默认值，也提醒了一件事——一个没有审批界面的 harness，它的权限规则实际上只有 allow 和 deny 两种结果。

停止原因

循环为什么停下来，比“成功还是失败”丰富得多。组装版区分七种：

停止原因含义合理的下一步
completed模型给出最终回答，且没有 hook 要求继续结束
max_turns撞上轮数上限多半是任务太大或模型在打转；让人看一眼
timeout整轮时间预算用完停下来总结已完成的部分和剩下的工作
circuit_open模型依赖已熔断不要重试，等冷却或换模型（第 20 章的降级链）
llm_error重试耗尽后仍失败告诉用户失败类型和尝试次数
error_budget工具连续失败达到上限检查工具或参数；这也是“打转”的信号
blocked用户输入或某个调用被 hook 拦截把拦截理由给用户
max_tokens / refusal模型自己的停止原因前者要续写（第 01 章），后者要换问法或告诉用户

把它们分开的价值，在可观测性那一章已经说过一次：一个笼统的“成功率 82%”没有信息量，拆成“12% 撞上轮数上限、4% 撞上错误预算”就能直接指向原因。这里加一句：停止原因也是给用户的。用户看到“橘子跑完了但只做了一半”，和看到“橘子跑到了 20 轮上限，通常意味着任务太大，建议拆成几步”，两种体验完全不同。

组装版的价值是看清接口：你能在一个文件里看到模型调用怎么被熔断包住、工具调用怎么被 hooks 包住、以及每一步怎么写日志和 span。真实项目不会用这个组装版，但可以拿它对照自己的顺序。

如果要往一个真实项目迁移，建议的顺序是：先照组装版把顺序理清，再把并行（第 03 章）加回来，然后加压缩与卸载，最后加委派。反过来做（先上子代理和并行）最常见，也最容易把顺序问题埋进去——出问题时你分不清是并行导致的还是层序导致的。

长任务为什么会失去连续性

阿青的问题不是橘子特有的。learn-harness-engineering 的讲义把它拆成三个具体的失效模式：

失效模式表现根因
重建成本新会话要花很久才进入状态：重新读文件、重新理解代码结构、重新发现上次的结论状态只存在于上一个会话的对话历史里，新会话拿不到
上下文焦虑任务快做完时，历史越来越长，模型开始担心放不下，于是草草收尾或者反复压缩把所有细节都堆在同一个上下文里
漂移做了几步之后方向偏了，而且没人（包括模型自己）注意到缺少一份显式的“目标与当前进度”，只有一长串对话

讲义还指出一个关键的区别：压缩与重置不是一回事。压缩（第 07 章）保留历史的形状，丢掉细节；重置丢掉全部历史，从头开始，只依赖仓库里的工件。压缩丢的是“为什么”——为什么当初这么选、哪些方案试过不行；如果这些没有写进决策文件，压缩之后就永久丢失了。所以：

  • 能写进文件的不留在对话里：目标、进度、决策、未决问题。
  • 需要推理过程的才留在对话里：当前的探索、正在写的代码、刚读到的内容。
  • 压缩之后要重建的：把任务表和进度重新放回运行时上下文（第 09 章的做法），而不是指望摘要记得住。

三类工件

状态要有地方放。labs 用了三个文件：

文件写什么谁写谁读
PROGRESS.md每个阶段的进度：做了什么、下一步每次收工追加一段新会话开始时读
DECISIONS.md每个设计决策：决定了什么、为什么做出决策时追加后人（包括未来的模型）需要知道“为什么”时
.harness/handoff.json结构化交接：目标、已完成、下一步、未决问题、验证命令会话结束前写下一个会话开始时读
@dataclass
class Handoff:
    """一次会话结束时留给下一次会话的东西。字段刻意少：多了没人写，也没人读。"""

    goal: str
    done: list[str]
    next_steps: list[str]
    open_questions: list[str] = field(default_factory=list)
    verify: list[str] = field(default_factory=list)        # 下一次开工前先跑的验证命令
    updated_at: str = ""

    def validate(self) -> list[str]:
        problems = []
        if not self.goal.strip():
            problems.append("缺少目标")
        if not self.next_steps:
            problems.append("没有写下一步：下一个会话会从头摸索")
        if not self.verify:
            problems.append("没有写验证命令：下一个会话无法确认当前状态是不是好的")
        return problems

字段刻意少。交接文件最怕的是字段太多：字段一多，写的时候会挑几个填，读的时候要处理缺字段，最后没人相信它。labs 的校验只强制三件事：有目标、有下一步、有验证命令。第三项是最容易被省、也最有价值的一项：没有验证命令，下一个会话就只能相信交接里写的“测试通过”。

原子替换这一个细节值得说明：写交接的时机恰好是“会话要结束了”，进程随时可能被杀。直接覆盖写，一旦在写的中途被杀，留下的是一个坏掉的交接文件，下一个会话读它的时候会崩。先写临时文件再原子替换，保证读到的要么是旧的完整版，要么是新的完整版。

为什么交接要写进仓库，而不是只存在会话日志里？因为接手的不一定是同一个 harness：可能是另一个 CLI、另一个模型、或者是周一早上的阿青本人。放在仓库里、格式是普通文本和 JSON，谁都能读。

上班与下班

把这件事做成两个固定动作，比“记得写交接”可靠得多。

收工（会话结束前）：

  1. 跑一遍验证命令，确认真实状态（而不是凭记忆写“测试通过”）。
  2. 写交接：目标、已完成、下一步、未决问题、验证命令。
  3. 把“为什么这么选”写进决策文件。
  4. 清理：临时文件、没用的分支、后台进程。

开工（新会话开始时）：

  1. 读交接和进度文件。
  2. 先跑验证命令，确认当前状态和交接描述一致。
  3. 不一致就先解决差异，再继续下一步（差异本身就是重要信息：可能是别人动了代码，也可能是上次的交接写错了）。
def resume_prompt(handoff: Handoff | None) -> str:
    """把交接渲染成新会话的第一段上下文。先验证，再干活。"""
    if handoff is None:
        return "这是一个新任务，没有上一次的交接记录。"
    parts = [f"上一次会话（{handoff.updated_at}）留下的交接：", f"目标：{handoff.goal}"]
    if handoff.done:
        parts.append("已完成：" + "；".join(handoff.done))
    parts.append("下一步：" + "；".join(handoff.next_steps))
    if handoff.open_questions:
        parts.append("未决问题：" + "；".join(handoff.open_questions))
    if handoff.verify:
        parts.append("开工前先运行这些命令，确认当前状态和交接描述一致：" + "；".join(handoff.verify))
    return "\n".join(parts)

第二步是整套机制里最关键的。故事里那次“有人合了主干改动进来导致 a18 的测试其实是失败的”，如果没有开工验证，橘子会从错误的前提出发继续干活——而且它的每一次判断都是基于“a18 已经改好了”。

和 hooks 的关系：这两个动作可以用第 21 章的 hook 来保证。“下班”可以做成会话结束时的 hook，“开工”可以做成会话开始时的 hook。区别是：hook 保证它会发生，但内容仍然要模型（或者人）来写。用 hook 强制“写交接”，再用校验函数检查必填项，这套机制就不依赖当事人记性好不好了。

什么时候压缩，什么时候重置

历史变长时有两个选择，取舍如下：

压缩（第 07 章）重置（新会话 + 交接）
保留对话的形状与一部分细节只有仓库里的工件
丢失细节、部分“为什么”全部对话，包括正在写的东西
成本一次摘要调用重新读取需要的文件
适合任务还需要当前的探索上下文任务阶段之间；上下文里已经堆了很多无关内容

实践中的组合是：任务进行中压缩，阶段之间重置。判断依据是“上下文里有多少东西是这一步还需要用的”：如果超过一半已经无关，重置比压缩划算——重置后的上下文干净、便宜，而且能从工件里重建出需要的信息；如果大部分还在用，压缩更划算。

重置还有一个副作用值得记住：它会丢掉缓存命中（第 06 章）。新会话的前缀和旧会话不同，第一次请求全是缓存写。所以频繁重置的成本不只是重读文件，还包括重新建立缓存。

坑与失败案例

坑一：靠上一个会话的历史恢复

  • 触发条件：新会话把上一次的完整历史加载进来当上下文。
  • 后果：重建成本高（几万 token、几十秒），而且模型读完还是会问“你想让我做什么”——历史里没有“下一步是什么”这个信息。
  • 怎么防：交接文件 + 开工验证。历史用来查证，不用来恢复。

坑二：交接里只有“已完成”，没有“下一步”

  • 触发条件：交接模板里“已完成”是必填，“下一步”靠自觉。
  • 后果：新会话要重新分析一遍才敢动手，交接的价值减半。
  • 怎么防：把“下一步”和“验证命令”做成必填项，缺了就在收工时报警（labs 的 validate() 就是干这个的）。

坑三：不验证就相信交接

  • 触发条件：新会话直接按交接里的描述继续做事。
  • 后果：交接写的是几小时甚至几天前的状态；代码可能被合了别人的改动、依赖可能升级了、临时文件可能被清理了。从错误前提上继续做，比从头做更糟。
  • 怎么防：开工先跑验证命令；不一致就先把差异讲清楚。

坑四：交接文件写一半被杀

  • 触发条件：直接覆盖写交接文件，写入过程中进程被杀。
  • 后果：留下一个语法不全的 JSON，下一个会话读它时崩溃，而且旧的那份已经被覆盖掉了。
  • 怎么防：先写临时文件再原子替换；读取时对解析失败做兜底（当作没有交接，而不是崩掉）。

坑五：决策的“为什么”没留下来

  • 触发条件：只记“改成了什么”，不记“为什么这么改”。
  • 后果：压缩一次之后，“为什么”永久丢失。后面的会话（或者人）会重新提出已经被否决的方案，甚至推翻一个有理由的决定。
  • 怎么防：决策文件里写“决定 + 原因”两行；把“试过但不行”的方案也记下来，它和“选了哪个”一样有价值。

坑六：把所有东西都记进工件

  • 触发条件：进度文件每做一步就追加一大段，交接文件字段越来越多。
  • 后果：工件本身变成需要压缩的东西；读它的人和模型都会跳过它。
  • 怎么防：工件只记“下一个会话需要知道的”。判据是：这条信息如果不说，下一个会话会不会做错事？不会就别记。

回到全局：这个 harness 由什么组成

把二十五章放在一起看，一个 harness 可以分成六类部件：

类别部件章它回答的问题
骨架循环与停止条件、工具定义、执行管线、会话日志01–04下一步做什么、怎么执行、怎么记录
上下文预算、缓存、压缩、卸载05–08什么东西现在能进模型的窗口
记忆工作记忆、长期记忆与指令、检索、生命周期09–12什么东西值得跨轮、跨会话留下来
安全权限、命令解析、沙箱、审批、注入13–17能不能做、做的是什么、最多能造成什么损失
韧性重试、超时、熔断与降级18–20外部世界不可靠时怎么继续
扩展与运维hooks、Skill 与 MCP、委派与 PTC、可观测性、组装与连续性21–25谁能往里加东西、跑起来之后怎么看

这六类里，最容易被低估的是骨架和连续性：前者看起来只是几十行循环，后者看起来只是几个文件。但真正让一个 agent 从“能跑”变成“好用”的，往往不是多了一个工具或者多了一个模型，而是“它知道自己做到哪了”和“它停下来的时候状态是清楚的”。

小结

  • 组装的关键是顺序：整轮截止时刻在最外，熔断在重试外，重试包住单次请求；hooks 在执行前后，权限在参数校验之后。
  • 停止原因是结构化的，不是布尔值：每种原因对应不同的下一步，也要分别统计。
  • 组装版刻意不做并行、插话、压缩、委派，它的价值是让你看清接口和顺序。
  • 长任务失去连续性有三个原因：重建成本、上下文焦虑、漂移。对策是把状态放进仓库的工件里，而不是对话历史里。
  • 三类工件：进度（做了什么、下一步）、决策（决定了什么、为什么）、交接（目标、已完成、下一步、未决问题、验证命令）。
  • 收工先验证再写交接；开工先读交接再跑验证，不一致就先解决差异。写交接要原子替换。
  • 任务进行中压缩，阶段之间重置；重置会丢掉缓存命中。

到这里，一个完整的、能跑长任务的 harness 已经组装完成。最后一章换一个角度：前面二十五章讲的都是“怎么造”，最后看看“怎么用”——同一个 harness，按不同的控制流去解任务，效果可能差好几倍。继续读：Agent 范式。

主线故事 · 白板的最后一页（虚构）

周一早上，橘子读了交接，跑了四条验证命令，发现 a18 的测试失败，于是先没说“继续改 a20”，而是说：“交接里写 a18 测试通过，但现在失败了；差异出现在 logging.py 的一个新签名，可能是周末有人合了改动。要我先修 a18 吗？”

阿青回了一个字：“修。”橘子改完 a18，重新跑验证，确认全绿之后接着做 a20。

那天下午，老唐把四页白板从墙上取下来，钉在一起。第一页是“谁说了算”（规则、解析、院子、审批、来源），第二页是“它会出事”（再试一次、别等太久、别撞同一堵墙），第三页是“别人怎么往里加东西”（门、说明书、外部能力、派活），第四页只有一行字：状态放在仓库里，不放在脑子里。

阿青看着第四页说：“那要是任务本身，我们不知道该按什么思路去做呢？”

老唐把白板翻过去，背面还空着。

“那就是另一件事了，”他说，“同一套零件，怎么摆，能决定它做得好不好。先想清楚这件活适合一次做完、还是先列计划、还是拆开并行、还是做完让人验收——这些摆法，比多写一个工具重要得多。”
