第 1 章

Agent Loop 与停止条件

主线故事 · 第 1 章（虚构）

周一下午，林舟给橘子的循环加了一行：if turns > 50: break。老唐看了一眼：“行，至少不会烧一个周末了。”

周二，翻车了三次，每次都不一样。

第一次。演示前彩排，橘子跑到一半，林舟觉得它方向不对，按了 Ctrl+C，然后输入“换个思路，先看日志”。结果 API 直接报错，说历史里有一个工具调用找不到对应的结果。原来按下 Ctrl+C 的那一刻，模型刚说完“我要读 config.py”，工具还没来得及跑。历史里留下了一个只有问、没有答的调用，之后每次请求都被拒，这个会话就这么废了。

第二次。林舟让橘子写一个长一点的迁移脚本。橘子写到一半，回复戛然而止，最后一句是“接下来我们把所有的 user_id 改成”。循环检查了一下：没有工具调用，于是判断“任务完成”，在终端里打出一个绿色的勾。半截脚本就这么被当成了成品。

第三次。某个工具抛了个异常，异常一路冒泡，把整个循环带走了。终端里只剩一屏 Python 调用栈，橘子之前十几轮的工作上下文全没了。

老唐总结：“你只装了一种刹车，就是撞墙。”

这一章就是给循环补齐刹车：先看清楚“停”有哪几种，每一种由谁来喊，喊停的那一刻怎么保证历史还是完整的。下面的正文会反复回到这三次翻车，它们对应的正是 坑与失败案例 里的几条。

Agent loop 的骨架只有几行：调模型，看回复，跑工具，把结果喂回去，再调模型。真正决定一个 harness 能不能放心交给它跑的，是它怎么停：谁有权说“到此为止”，停的依据是什么，停下那一刻的消息历史还能不能原样发出下一次请求。本章先画出全貌，再按从简单到复杂的顺序逐个看 learn-claude-code、OpenHarness 和 DSH 的循环，然后给出 labs 里的完整实现，把“采样后决定下一步”单独抽成纯函数，最后列出这一层最常见的失败方式。

先看全貌：Agent Loop 是什么、管哪些事

一句话：Agent Loop 是 harness 最外层的那个循环。它反复做同一件事：把历史发给模型，看模型想干什么，替它去干，把结果记进历史，再问一次模型。直到某个条件成立，它才停下来。

收到用户的任务后，循环每一轮做五步：

  1. 先检查该不该停：用户按了中断，或者轮数已经用完，就停。
  2. 调模型：把系统提示和全部历史发出去，拿回一条回复。
  3. 判定这条回复：被截断或拒答，就停（或者让模型接着写）；没有工具调用，就停，任务完成；有工具调用，进入第 4 步。
  4. 执行工具：把这一批的全部结果作为一条消息写回历史。
  5. 记账：工具连续失败太多次，就停；否则回到第 1 步。

五步里只有第 2 步是模型在干活，其余四步全是 harness 的事。这个循环要管的事情可以归成四类：

  • 驱动：让模型和工具轮流说话，采样、执行、回填，周而复始。
  • 判定：每拿到一条回复，决定是继续、停下，还是让模型接着写完。
  • 刹车：模型自己不停的时候，harness 要能主动喊停，比如轮数上限、错误预算、用户中断。
  • 保持历史合法：不管从哪个出口停下，留下的消息历史都必须能原样发出下一次请求，否则这个会话就废了。

不管哪个仓库，循环能停下的出口大体就是下面这几种。表里“labs 里的名字”是本章自己实现时用的停止原因：

出口谁喊的停什么时候发生labs 里的名字

有的仓库还有第四方能喊停：插件。DSH 的插件可以拒绝下一步、提前结束一轮，也可以反过来让本该停下的循环继续跑。

全章反复出现的两条规则，先记住：

  1. 先判截断，再看工具调用。被截断的回复里，工具调用的参数可能只有半截，不能执行。橘子把半截迁移脚本当成“完成”，就是没先判截断。
  2. 任何一个停止点上，每个工具调用都要有结果。历史里只要留下一个“只有问、没有答”的调用，下一次请求就会被拒。橘子按 Ctrl+C 后整个会话报废，就是这条被破坏了。

本章怎么读：

  1. 本节是全貌，必读。
  2. 然后逐个看三个仓库，从最简单的三十行版本读到生产级实现，每个仓库单独一节。第一遍可以只挑一个：想看骨架，读 learn-claude-code；想看完整的 Python 写法，读 OpenHarness；想看生产级的细节，读 DSH。
  3. 看完别人的写法，再读 labs 的实现：自己写一个循环，必须掌握的就是这一部分，代码可以直接运行。
  4. 坑与失败案例按问题列出，每条里再分仓库说明怎么防，适合遇到问题时回来查。最后的对比表用来复习。

正文里蓝色的 文件:行号 是源码出处，第一遍读可以跳过，不影响理解。

逐个仓库看：从三十行到生产级

三个仓库按从简单到复杂的顺序排：learn-claude-code 只有骨架，OpenHarness 在骨架上加了上限和错误处理，DSH 把截断、插话、中断都做全了。每个仓库自成一节，可以只读你关心的那一个；对照上一节的五步，看它在每一步做了什么、少做了什么。

术语：三个仓库对“轮”的叫法不一样。DSH 把处理一条用户输入的全过程叫 turn（agent.ts:298），把其中每一次模型调用叫 step（agent.ts:400）。OpenHarness 的 turn_count 每调一次模型加一（query.py:699-701），相当于 DSH 的 step。labs 沿用 OpenHarness 的口径：LoopResult.turns 是模型调用次数。下文说“一轮”都指一次模型调用。

learn-claude-code s01：最小版本

先知道：learn-claude-code 是一个教程仓库，每一课讲一个机制，第一课 s01 就是一个最小循环。读它是为了看清骨架长什么样；后面两个仓库多出来的代码，基本都是在防这个骨架没防住的情况。

learn-claude-code 的第一课把循环压到三十行，README 的说法是“模型调用工具就继续，不调用就停”（README.zh.md:28）：

def agent_loop(messages: list):
    while True:
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=messages,
            tools=TOOLS, max_tokens=8000,
        )

        # Append assistant turn
        messages.append({"role": "assistant", "content": response.content})

        # If the model didn't call a tool, we're done
        tool_calls = [
            block for block in response.content if block.type == "tool_use"
        ]
        if not tool_calls:
            return

        # Execute each tool call, collect results
        results = []
        for block in tool_calls:
            print(f"\033[33m$ {block.input['command']}\033[0m")
            output = run_bash(block.input["command"])
            print(output[:200])
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": output,
            })

        # Feed tool results back, loop continues
        messages.append({"role": "user", "content": results})

出处：code.py:96-126。它做对了两件事：没有 tool_use 块就返回（code.py:110），一批调用的结果放进同一条 user 消息（code.py:126）。其余都没做：while True 没有上限（code.py:97）；max_tokens 写死 8000 且不看 stop_reason（code.py:100）；不检查工具名，所有 tool_use 都当 bash 执行；run_bash 只接住超时和两类系统错误（code.py:89-92）；没有插话，也没有中断。这是有意的教学取舍，README 自己说后面 16 章都在这个循环上叠机制（README.zh.md:116）。

后面的章节补上了一部分。s15 把“只看块、不信 stop_reason”写成了注释（code.py:1924），仓库测试专门验证：stop_reason 说 end_turn 但回复里有真实的 tool_use 时，工具照样执行（test_agent_loop_boundaries.py:244）。s15 也处理了截断：第一次截断丢弃整个回复、把 max_tokens 从 8000 提到 16000 重试；再截断就把回复写进历史、追加续写提示，最多两次（code.py:3185-3197，常量见 code.py:69 和 code.py:72）。

OpenHarness：一个 while 加一个异常

先知道：OpenHarness 是用 Python 写的完整 harness，循环集中在 engine/query.py 的 run_query 一个函数里。它和 learn-claude-code 的骨架几乎一样，只是多了轮数上限、错误处理和中断后的修补。读的时候对照开头的五步看三件事：停止只看什么，截断防没防，上限用什么方式表达。

OpenHarness 的循环集中在 run_query 一个函数里，文档字符串就是它的停止条件：“运行对话循环，直到模型不再请求工具”（query.py:637）。与停止有关的三段：

    turn_count = 0
    while context.max_turns is None or turn_count < context.max_turns:
        turn_count += 1
        # …
        if not final_message.tool_uses:
            if context.hook_executor is not None:
                await context.hook_executor.execute(
                    HookEvent.STOP,
                    {
                        "event": HookEvent.STOP.value,
                        "stop_reason": "tool_uses_empty",
                    },
                )
            return
        # …
        messages.append(ConversationMessage(role="user", content=tool_results))

    if context.max_turns is not None:
        raise MaxTurnsExceeded(context.max_turns)
    raise RuntimeError("Query loop exited without a max_turns limit or final response")

出处：query.py:699-884。逐项看：

  • 停止判定：只看 final_message.tool_uses 是否为空（query.py:808）。API 客户端其实把 stop_reason 带回来了（ None = None，client.py:261），但循环只取走 message 和 usage（query.py:750-752），STOP 钩子收到的 stop_reason 是一个固定字符串 tool_uses_empty。
  • 截断：没有处理输出截断。它处理的是请求侧的 max_tokens：先夹到 128000 和上下文窗口以内（query.py:90），厂商仍嫌太大时从错误信息里解析上限、重试，并把这一轮的计数退回去（query.py:766）。如果输出在 tool_use 中间被截断，这个块照样被转成 ToolUseBlock（messages.py:205）并执行，唯一的保护是参数的 pydantic 校验（query.py:917）。
  • 插话：run_query 里没有收件箱，用户的新输入只能等这次循环结束、下一次 submit_message。
  • 上限：max_turns 写在 while 条件里，检查发生在调模型之前。默认值有三处且不一致：QueryContext 是 200（ None = 200），QueryEngine 构造参数是 8（ None = 8,），设置文件是 200（settings.py:581）。可以设成 None 表示不设限（test_query_engine.py:375）。超限时抛 MaxTurnsExceeded 而不是返回，由 UI 捕获后提示（runtime.py:681），再由 /continue 走 continue_pending 接着跑（ None = None)）。
  • 错误：模型调用失败时发一个 ErrorEvent 后返回（query.py:781），提示过长时先做一次反应式压缩再重试（query.py:768）；模型回了空消息就丢掉并返回（query.py:792）。工具侧：未知工具（query.py:912）、参数非法、工具抛异常都变成 is_error=True 的结果。
  • 中断：循环内没有取消信号。悬空的 tool_use 在下一次进入时修补：sanitize_conversation_messages 把没有配对结果的 tool_use 所在的 assistant 消息整条删掉（messages.py:119-127），submit_message 和 continue_pending 开头都会调用（query_engine.py:237）。

DSH：三层循环和一张出口表

先知道：DSH（DeepSeek Harness）是用 TypeScript 写的生产级 harness，循环在 packages/core/agent-loop/src/agent.ts，拆成三层：kick() 一直开新的 turn，turn() 处理一条用户输入，step() 调一次模型。不熟 TypeScript 也没关系，抓住两件事就够了：turn() 有哪些出口（下面的出口表），step() 怎么判定一条回复的结局（第二段代码）。截断、插话、上限和中断放在下一小节单独讲。

DSH 的循环拆在三个方法里。最外层 kick() 只做一件事：只要 turn() 返回 true 就再开一个 turn（agent.ts:254）；turn() 结束时只要收件箱里还有待处理的输入就返回 true（agent.ts:392）。中间层 turn() 是驱动 step 的 while (true)（agent.ts:315）。最内层 step() 里还有一个 while (true)（agent.ts:409），只服务于“请求失败后重试同一步”。

turn 内部驱动 step 的部分（省略了失败恢复，下面单独讲）：

      while (true) {
        signal.throwIfAborted()
        const step = phase.step + 1
        const decision = await this.preStep(target, { turn, step })
        if (decision.kind === 'reject') {
          turnEnds = { kind: 'blocked' }
          return false
        }
        if (turnEnds && decision.messages.length === 0) break
        // A removed waking message or an enter decision rewritten to empty
        // still owns the initial turn boundary, but it spends no model call.
        if (phase.step === 0 && decision.messages.length === 0) {
          turnEnds = { kind: 'completed' }
          return false
        }
        signal.throwIfAborted()
        this.session.append('step/start', { turn, step })
        phase.step = step
        const toolRecovery = new ToolCallRecovery()
        const stopRecovery = this.ctx.on('session/event', (session, event) => {
          if (session === this.session) toolRecovery.observe(event)
        })
        try {
          // max-tokens is sticky: once any step hits the ceiling, later steps
          // that complete normally must not downgrade the turn outcome.
          const stepEnd = await this.step(decision)
          // max-tokens stays sticky: a later completed step must not
          // downgrade the turn outcome.
          if (turnEnds === null || turnEnds.kind !== 'max-tokens') turnEnds = stepEnd
        // …
        signal.throwIfAborted()
        if (turnEnds && this.inbox.nextStep.length === 0) {
          await this.dispatch.serial('agent/turn-stopping', { turn, signal })
          signal.throwIfAborted()
        }
        if (turnEnds && this.inbox.nextStep.length === 0) break
        target = 'next-step'

DSH：截断、插话、上限与中断

截断。DSH 在两层防半截工具调用。组装层：结束原因是 max-tokens 时，BlockAssembler 从回复里丢掉所有 tool-call 块，只保留文本，回放元数据也同步裁剪，“写进日志的内容”和“回放时发给厂商的内容”不会对不上（assembler.ts:131-140）。循环层：step() 先判截断再找工具调用（上面的 547 行）。两层叠加的效果由测试钉住：截断回复里的工具调用不会被执行，日志里也没有 tool/call 事件（loop.spec.ts:1530）；文本部分保留，下一次请求照常回放（loop.spec.ts:1665）。

DSH 默认不自动续写：单步被截断，turn 就以 max-tokens 结束，只调用一次模型（loop.spec.ts:1439）。要续写，由插件在 agent/turn-stopping 钩子里 steer 一条消息，测试里正是这么做的（loop.spec.ts:1459）。这个测试还说明了第二个设计：max-tokens 是粘滞的，后面的步骤正常结束也不会把 turn 的结局改回 completed（；类型注释写得很直白：types.ts:213）。

插话（inbox）。DSH 的待处理输入是持久化在会话日志里的两个队列：next-turn 和 next-step（inbox.ts:22-23）。三个入口分别是 followup（排到下一个 turn 并唤醒，agent.ts:164）、steer（排到下一步并唤醒，agent.ts:168）和 inject（排到下一步但不唤醒，agent.ts:172）。并入时机是每一步开始前的认领：先取走全部 next-step 消息，新 turn 的第一步再额外取一条 next-turn（inbox.ts:109-111）。认领到的消息只在本步第一次请求时写入会话，失败重试不会重复写（agent.ts:426）。

工具执行期间产生的上下文也走 next-step 队列（agent.ts:553），所以它们总是排在工具结果之后，不会把 tool_use 和 tool_result 隔开（loop.spec.ts:1155）。工具执行时用户 steer 的消息，会进入同一 turn 的下一步（loop.spec.ts:1018）。最关键的一点在出口表的“正常停止”一行：即使模型已经不再调用工具，只要 next-step 队列里还有消息，turn 就不会停，而是再跑一步。换句话说，DSH 的停止条件是“模型不欠回应并且没有待处理的转向”，钩子文档把这个规则写成“数据决定，监听器的顺序改变不了结果”（runtime-types.ts:365）。

上限。DSH 的核心循环里没有 step 数或 turn 数上限。agent-loop 插件的配置只有一个并发上限 maxParallelToolCalls，默认 10（index.ts:346，constants.ts:6）。能让循环提前停下的都是插件手段：agent/pre-step 拒绝下一步（runtime-types.ts:310）、以 hook 为原因取消（agent.ts:89-90）、工具 concludeTurn()。反方向的“强制继续”目前没有上限，仓库里自己留了 TODO：index.ts:275。实验插件 tool-ralph 的 maxRounds 默认 256（index.ts:35），限的是“新开子 agent 跑多少轮”，不是单个 turn 的 step 数。

中断。cancel() 中止当前 turn 的 AbortController，默认同时清空收件箱（agent.ts:175-181），循环在各个 await 之后用 signal.throwIfAborted() 检查。流式输出被打断时，已经显示给用户的文本前缀会作为 interrupted 消息落盘，工具调用一律不保留，“因为中断发生在派发之前，保留它就得伪造一个结果”（assembler.ts:165；落盘见 agent.ts:465-466）。工具执行到一半被取消时，没开始的调用会补一对 call/result，结果是 isError 的“aborted before dispatch”（tool-calls.ts:250-253）。如果一步因异常失败，ToolCallRecovery 会给所有还没结果的调用补上错误结果，再关闭这一步（agent.ts:344-355），注释写明了原因：repair.ts:164。

小结：停止信号到底看什么

可用的信号有两个：厂商返回的 stop_reason，以及回复里有没有工具调用块。三个仓库判断“正常完成”时都看后者，没有一个只凭 stop_reason == "tool_use" 决定继续。差别在于截断是否先于工具调用检查：DSH 先判截断，而且在组装层就把截断的工具调用丢掉；labs 同样先判截断；OpenHarness 和 learn-claude-code s01 不看截断，s15 看了但续写路径有配对风险（4.2）。

谁有权决定停：模型（不再调用工具）、harness 自身（上限、预算、错误）、用户（取消）。DSH 多了第四方：插件，可以拒绝一步、结束一个 turn，也可以通过 steer 让本该停的 turn 继续。

最小循环：run_agent 每一行在防什么

看完三个仓库的写法，现在自己写一个。下面的实现对照本章开头的五步：第 1、2、5 步在 run_agent 里，第 3 步是 next_step（第 3 节单独讲），第 4 步是 execute_tools。

labs 的循环在 labs/harness/loop.py，只用标准库，模型通过 harness.llm 的适配器调用，测试里换成按脚本回放的 FakeLLM。先看配置：三个字段对应三种由 harness 主动发起的停止。

@dataclass
class LoopConfig:
    max_turns: int = 20               # 模型调用次数上限（默认值是教学示意）
    max_consecutive_errors: int = 3   # 连续失败的工具调用数上限（默认值是教学示意）
    max_continuations: int = 0        # 被 max_tokens 截断后最多自动续写几次；0 表示像 DSH 默认那样直接停

max_turns 的默认值 20 和 max_consecutive_errors 的默认值 3 都是教学示意，不来自任何仓库。max_continuations 默认 0，意思是输出被截断就停，和 DSH 的默认行为一致（见 2.2）。

循环的返回值永远是一个 LoopResult，不靠异常表达“停了”：

@dataclass
class LoopResult:
    final_text: str
    stop: StopReason
    turns: int
    messages: list[dict]
    truncated: bool = False
    usage: dict[str, int] = field(default_factory=dict)
    error: str | None = None

stop 是一个字面量：completed、max_turns、max_tokens、refusal、error_budget、interrupted、llm_error。truncated 单独成字段，因为“截断过”和“最后怎么停的”是两件事：续写成功后 stop 是 completed，但调用方仍需要知道中间被截断过。

核心循环：

def run_agent(
    llm: LLM,
    system: str,
    task: str,
    tools: dict[str, Tool],
    tool_schemas: list[dict],
    config: LoopConfig | None = None,
    should_stop: Callable[[], bool] | None = None,
) -> LoopResult:
    """跑一个任务直到停止条件成立。"""
    state = LoopState(config or LoopConfig())
    stop_requested = should_stop or (lambda: False)
    messages: list[dict] = [user(task)]
    while True:
        # 边界检查放在采样之前：此时上一批工具结果已经入史，停在这里历史是完整的
        if stop_requested():
            return _finish(state, messages, "interrupted")
        if state.turns >= state.config.max_turns:
            return _finish(state, messages, "max_turns")
        try:
            turn = llm.complete(system, messages, tool_schemas)
        except Exception as exc:  # 网络、鉴权、脚本耗尽：结构化地停下，不让调用方去猜
            return _finish(state, messages, "llm_error", f"{type(exc).__name__}: {exc}")
        state.turns += 1
        state.last_text = turn.text
        _add_usage(state.usage, turn.usage)

        step = next_step(turn, state)
        if step != "run_tools":
            _record_without_tools(messages, turn)
            if step in ("continue", "max_tokens"):
                state.truncated = True
            if step != "continue":
                return _finish(state, messages, step)  # completed / max_tokens / refusal 同名即停止原因
            state.continuations += 1
            messages.append(user(CONTINUE_PROMPT))
            continue

        messages.append(assistant_from_turn(turn))
        results, interrupted = execute_tools(turn.tool_calls, tools, stop_requested)
        messages.append(tool_results(results))  # 一批调用的全部结果放进同一条 user 消息
        if interrupted:
            return _finish(state, messages, "interrupted")
        _update_error_streak(state, results)
        if state.consecutive_errors >= state.config.max_consecutive_errors:
            return _finish(state, messages, "error_budget")

按出现顺序，每一段在防的问题：

  1. 中断和轮数检查放在采样之前。走到这里时，上一批工具结果已经写进历史，所以从这两个出口返回的 messages 一定以 user 消息结尾，可以原样续跑。如果把轮数检查放在“执行完工具、还没追加结果”的位置，就会留下没有 tool_result 的 tool_use；OpenHarness 在另一个层次上踩到了这个问题，见 4.6。
  2. 模型调用包在 try 里。网络、鉴权、脚本耗尽都变成 stop="llm_error" 加 error 字段，调用方永远拿到一个历史完整的结果。这是教学取舍：生产实现会在这里重试，例如 DSH 的 agent/request-error 钩子可以要求重试同一步（agent.ts:523-526）。
  3. 先判定，再动历史。next_step 只读不写，返回五种动作之一；计数器加一、写历史这些副作用全部留在 run_agent 里（第 3 节）。
  4. 不执行工具的分支只写安全前缀。完成、截断、拒答三种情况都走 _record_without_tools：去掉 tool_use 块，去完为空就不写。截断时的 tool_use 参数可能只有半截；就算参数完整，一个不打算执行的 tool_use 写进历史也会让下一次请求因为缺结果而被拒。
  5. 执行分支先写 assistant，再执行，再把全部结果一次性写成一条 user 消息。结果顺序与模型给出的调用顺序一致。
  6. 批内中断也要补结果。execute_tools 在每个工具开始前检查 should_stop，没执行的调用补一条 is_error 结果，再返回 interrupted。
  7. 连续错误预算。同一个失败的命令被模型反复重试，是最常见的空转方式；连续失败的工具调用数达到上限就停，中间任何一次成功都清零。

单个工具和一批工具的执行：

def run_tool(call: ToolCall, tools: dict[str, Tool]) -> tuple[str, str, bool]:
    """执行单个调用。未知工具和工具异常都变成 is_error 结果，交给模型自己纠正。"""
    fn = tools.get(call.name)
    if fn is None:
        return call.id, f"Error: unknown tool {call.name!r}", True
    try:
        return call.id, str(fn(call.args)), False
    except Exception as exc:  # 工具的 bug 不能打断循环；KeyboardInterrupt 之类仍然上抛
        return call.id, f"Error: {type(exc).__name__}: {exc}", True
def execute_tools(
    calls: list[ToolCall],
    tools: dict[str, Tool],
    should_stop: Callable[[], bool],
) -> tuple[list[tuple[str, str, bool]], bool]:
    """按模型给出的顺序执行一批调用。返回 (结果列表, 是否被中断)。"""
    results: list[tuple[str, str, bool]] = []
    interrupted = False
    for call in calls:
        if interrupted or should_stop():
            interrupted = True
            # 中断后没执行的调用也要配一个错误结果：每个 tool_use 都必须有对应的 tool_result
            results.append((call.id, INTERRUPTED_RESULT, True))
            continue
        results.append(run_tool(call, tools))
    return results, interrupted

未知工具和工具异常都变成 is_error=True 的结果交还给模型，让它自己改正；只捕获 Exception，KeyboardInterrupt 照常上抛。

不变量：run_agent 的每一个返回点上，messages 都能原样作为下一次请求的历史。测试 labs/tests/test_loop.py 里的 assertHistoryValid 在每种停止原因下检查三件事：首条是 user 消息；没有空的 assistant 消息；每条带 tool_use 的 assistant 消息后面紧跟一条 user 消息，里面的 tool_result 与 tool_use 一一对应且顺序相同。运行：py -m unittest discover -s labs/tests -t labs。

next_step：把“下一步做什么”写成纯函数

def next_step(turn: AssistantTurn, state: LoopState) -> Step:
    """采样之后决定下一步。纯函数：只读 turn 和 state，不改任何东西。"""
    if turn.stop_reason == "refusal":
        return "refusal"  # 拒答可能截在工具参数中间，这一轮的工具一律不执行
    if turn.stop_reason == "max_tokens":
        # 先看截断再看工具调用：被截断的 tool_use 参数可能只有半截
        if state.continuations < state.config.max_continuations:
            return "continue"
        return "max_tokens"
    if not turn.tool_calls:
        return "completed"
    return "run_tools"

四个分支的顺序就是本章的核心结论，对应 DSH 里 step() 的判定：

  1. refusal 最先。DSH 的结束原因里没有拒答这一项（types.ts:156），这张表是可合并扩展的，适配器要用得自己加（types.ts:154）；Anthropic 的 Messages API 会返回 refusal，而拒答可能截在工具参数中间，所以和截断一样不执行这一轮的工具，并且直接停。
  2. max_tokens 先于工具调用检查。对应 agent.ts:547 排在 agent.ts:549 之前。还有续写预算就返回 continue，否则 max_tokens。默认预算 0 与 DSH 默认一致；把预算交给配置，相当于把 DSH 里“插件在 turn-stopping 时 steer 一条续写消息”的做法内置成一个开关。
  3. 没有工具调用就完成。对应 agent.ts:550、OpenHarness 的 query.py:808 和 learn-claude-code 的 code.py:110。stop_sequence 也落到这一支。
  4. 否则执行工具。对应 agent.ts:551。labs 没有 concludeTurn 这种“工具宣布结束”的机制。

写成纯函数的好处是判定逻辑可以脱离模型和工具单独测试。NextStepTests.test_decision_table 用一张六行的表覆盖所有组合，不需要 FakeLLM；test_continuation_budget_is_read_not_spent 确认它只读预算、不扣预算。扣预算、置 truncated、写历史都在 run_agent 里，与 DSH 把 max-tokens 粘滞逻辑放在 turn() 而不是 step() 的分工一致（agent.ts:338）。

不执行工具的三个分支共用一个写历史的函数：

def _record_without_tools(messages: list[dict], turn: AssistantTurn) -> None:
    """不执行工具的回复只留安全前缀：去掉 tool_use 块，去完为空就不入史。

    截断/拒答时 tool_use 的参数可能只有半截，而且没有结果的 tool_use 会让下一次请求被拒；
    空的 assistant 消息同样会被 API 拒绝。按块过滤而不只是清空 tool_calls，
    是因为适配器可能把厂商原始块（含 tool_use）放在 turn.blocks 里原样写回。
    """
    message = assistant_from_turn(replace(turn, tool_calls=[]))
    message["content"] = [b for b in message["content"] if b.get("type") != "tool_use"]
    if message["content"]:
        messages.append(message)

它按块过滤，而不只是把 tool_calls 清空：真实的 Anthropic 适配器会把厂商原始块放进 turn.blocks，assistant_from_turn 优先原样写回原始块，只清空 tool_calls 的话，半截 tool_use 会从原始块里漏进历史。测试 test_raw_blocks_from_adapter_are_filtered_too 专门覆盖这一点。这和 DSH 在组装层统一做“保留哪些块”的决定是同一个思路：只在一个地方决定，写进历史的和回放出去的就不会不一致。

没覆盖的情况：pause_turn 只在使用服务端工具时出现，含义是“服务端暂停了，请原样再发一次”。next_step 会把它当成没有工具调用的完成。如果要接服务端工具，需要加一个分支：写入回复，不追加 user 消息，直接再采样一次。

坑与失败案例

工具结果拆成多条消息，或者中间夹了别的消息

  • 触发条件：每执行完一个工具就追加一条 user 消息；或者在工具执行期间把提醒、用户插话、后台通知直接追加进历史。
  • 后果：Anthropic 的 API 会把相邻的同角色消息合并，所以单纯拆开不一定报错，但官方文档提醒这会让模型逐渐不再并行调用工具。一旦中间夹进了文本，tool_result 就不再紧跟 tool_use、也不再位于 user 消息开头，请求会被拒绝。
  • 各仓库怎么防：OpenHarness 和 learn-claude-code 都在一批执行完后一次性追加（query.py:880，code.py:126）；learn-claude-code s15 把后台通知放在同一条消息里、排在结果后面（code.py:3111）。DSH 的日志里每个结果是独立事件，但插话和工具上下文都排进 next-step 队列，提交在结果之后（loop.spec.ts:1155）；结果按模型给出的顺序提交，哪怕后一个工具先完成（tool-calls.spec.ts:230）。序列化成 Anthropic 风格请求时，DeepSeek 适配器把 tool 角色映射成 user 并合并相邻同角色消息（serialize.ts:124-127），发现调用缺结果就在本地报错，再把 tool_result 挪到消息最前（serialize.ts:141-142）。labs 由 tool_results() 一次构造整批结果，测试 test_parallel_results_share_one_user_message_in_model_order。

只看“有没有工具调用”，忽略 max_tokens

  • 触发条件：输出在 tool_use 内部触到 max_tokens，循环只检查回复里有没有工具调用。
  • 后果：参数缺字段时工具报参数错误，还算幸运；参数字段齐全但内容被截短（比如写文件的正文只到一半）时，工具照常执行，把半截内容写进磁盘。另一种失败是把截断回复原样写回历史，再追加一条“请继续”的文本，下一次请求就带着一个没有结果的 tool_use。
  • 各仓库怎么防：DSH 两层都防（assembler.ts:137，agent.ts:547）。OpenHarness 没防，只有 pydantic 校验能拦住缺字段的情况（query.py:917）。learn-claude-code s01 没防。s15 第一次截断时丢弃回复、调大 max_tokens 重试，这是安全的；第二次起把 response.content 原样写回（code.py:3191）再追加续写提示（code.py:3193），如果被截断的内容里已经有 tool_use 块，下一次请求就会出现缺结果的调用。labs 由 next_step 先判截断，_record_without_tools 只写安全前缀，测试 test_truncated_tool_call_is_dropped_not_executed。

工具异常冒泡，打断循环

  • 触发条件：工具函数抛异常（参数取不到键、网络超时、第三方库的 bug）；或者并行执行时一个失败导致整批失败。
  • 后果：循环崩溃。此时 assistant 消息往往已经写进历史而结果还没写，历史停在一个悬空的 tool_use 上；并行时兄弟任务被取消，副作用执行到哪一步也不清楚。
  • 各仓库怎么防：OpenHarness 单个工具用 try 包住（query.py:827），并行时用 return_exceptions=True，注释把原因写得很清楚（query.py:849-852），并有回归测试检查两个结果仍在同一条消息里（test_query_engine.py:1351）。DSH 在工具运行时里捕获工具本体的异常，转成错误结果，未知工具也走这条路（index.ts:1585，index.ts:1593）；调度器本身出错时先等已开始的调用全部结束（tool-calls.ts:234），再由 step 补齐结果。learn-claude-code s01 先把 assistant 消息写进历史（code.py:104），再取 block.input["command"]（code.py:117），模型漏写这个参数就是一个没人接的 KeyError。labs 的 run_tool 捕获 Exception，测试 test_tool_exception_becomes_error_result 同时检查兄弟调用不受影响。

没有上限的循环

  • 触发条件：模型反复重试同一个失败的命令；Stop 类钩子每次都要求“继续”；上限被设成 None。
  • 后果：每一轮都要重发整段历史，输入 token 随轮数累加，上下文膨胀到触发压缩或超窗，费用不可控。
  • 各仓库怎么防：OpenHarness 有 max_turns（query.py:700），但三处默认值 200、8、200 不一致，且允许 None。DSH 核心循环没有 step 上限，强制继续的钩子也还没有上限（index.ts:275）。learn-claude-code s01 是裸 while True，s15 的子 agent 用 for _ in range(30) 兜底（code.py:1932）。三个仓库都没有“连续工具失败”的预算；learn-claude-code s15 的 MAX_CONSECUTIVE_529 管的是 API 过载重试，不是工具失败（code.py:71）。labs 用两个预算：max_turns 限总轮数，max_consecutive_errors 专门抓“卡在同一个失败上”的空转（默认 20 和 3 均为教学示意），测试 test_max_turns_stops_with_complete_history、test_error_budget_counts_consecutive_failures。

中断后留下没有结果的 tool_use

  • 触发条件：用户在工具执行期间按下中断；进程崩溃；上层取消了任务。
  • 后果：历史停在带 tool_use 的 assistant 消息上，下一次请求会被拒绝。DSH 的注释（repair.ts:164）和 OpenHarness 的注释（query.py:851）说的是同一件事。
  • 各仓库怎么防：两种相反的策略。DSH 补结果：没开始的调用补一条“派发前已中止”（tool-calls.ts:253）；已记录开始、但结果没落盘的调用，补的错误结果明确告诉模型“结果未知，有副作用的操作先核实再决定是否重试”（repair.ts:34）。测试 cancel.spec.ts:494 验证补上的结果会在下一次请求里回放。OpenHarness 删调用：下次进入时把悬空 tool_use 所在的消息整条删掉（messages.py:169），测试 test_query_engine.py:1418。删除更简单，代价是模型不知道这个调用发生过，而它的副作用可能已经发生。labs 采用补结果：execute_tools 给没执行的调用补 INTERRUPTED_RESULT，测试 test_interrupt_mid_batch_still_answers_every_tool_use。

OpenHarness：max_turns 停下时，最后一批工具结果没进历史

  • 触发条件：通过 submit_message 运行，并且到第 max_turns 轮时模型仍在调用工具。
  • 过程：submit_message 把历史复制成 query_messages 交给 run_query（query_engine.py:264），只在收到 AssistantTurnComplete 事件时把副本同步回 self._messages（query_engine.py:270-271）。这个事件在执行工具之前发出；最后一批工具执行完、结果追加到副本后，while 条件不再成立，直接抛出 MaxTurnsExceeded（query.py:880-883），不会再有新的同步。于是 engine.messages 停在带 tool_use 的 assistant 消息上。
  • 后果：UI 的待续提示只认“最后一条是带 tool_result 的 user 消息”（runtime.py:522-524），这里不显示；/continue 回答没有可继续的内容（registry.py:1317）；下一次 submit_message 开头的清洗会把这条 assistant 消息删掉（上一条的 messages.py:169）。工具已经执行过，模型却看不到自己调用过它们。
  • 证据：这是我们读源码后在本地复现的结果（伪造的 API 客户端，max_turns=2，两轮都返回 tool_use）：engine.messages 依次是 user、assistant(tool_use)、user(tool_result)、assistant(tool_use)；has_pending_continuation() 返回 False；下一次 submit_message 时模型收到的历史里，第二个 tool_use 已经不见了。continue_pending 直接在 self._messages 上运行（query_engine.py:301），不受影响。
  • labs 怎么避免：上限在采样之前检查；只有一份 messages，不复制、不靠事件同步；用返回值而不是异常表达停止，测试 test_max_turns_stops_with_complete_history 断言停下时最后一条是工具结果。
