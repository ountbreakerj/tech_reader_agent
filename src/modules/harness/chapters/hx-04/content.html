第 4 章

会话日志与回放

到这里为止，我们一直把 messages 当成历史本身：循环拿到一个列表，往里追加，再把它整个发给模型。这一章要把这个前提翻过来。历史不是那个列表——历史是一份只追加的日志，列表只是它此刻的一种投影。看起来只是换个数据结构，但它决定了三件事：进程被杀之后能不能接着跑、一次失败的运行能不能被逐字复现、以及「模型当时到底看见了什么」这种问题有没有答案。

为什么日志是事实来源，内存里的数组不是

一个内存里的消息数组只记录结果，不记录过程。它丢掉了这些信息：这次请求是在什么配置下发出的、某条消息是模型一次尝试的产物还是最终产物、工具调用有没有真的发生过、上一次运行到哪一步。这些信息在正常运行时不重要，因为没人回头看；但只要出现下面任何一种情况，它们立刻变成必需：进程崩溃后想接着跑、想复现一次线上失败、想知道「为什么这次模型的行为和昨天不同」。

DSH 把这条原则写成了明确的架构约束，措辞很硬：

Model-visible means logged.每次模型请求都必须能从日志重建；任何新的模型可见输入，都必须有对应的 session 事件。其余的一切——缓存、投影、界面状态——都只能是日志的导数。

这条约束的出处是 docs/architecture.md:124。它不是一句口号，因为它后面跟着一条可以机械检查的性质：给定一份日志，任何人都能算出「第 N 次请求时模型看到的消息列表是什么」。这就是回放。

seq 就是下标

DSH 的 Session 首先是一份只追加的日志（index.ts:515），内部就是一个数组（index.ts:523）。append 的签名和实现同样朴素：

    this.commit(event as SessionEvent, entry)
    return event

出处：index.ts:816-826（方法签名在 index.ts:798）。

注意 seq: SessionSeq(this.log.length) 这一行：序号不是单独维护的计数器，它就是事件在日志里的下标。这个选择带来两个直接后果。

好的一面是「连续」变成了免费的性质——不需要任何检查，因为写入路径本身不可能造出空洞。坏的一面是同一个会话只能有一个写入者：两个并发写入者会算出同一个下标。DSH 用两处防守把这条约束钉死。一是 append 会拒绝在发布另一个事件的过程中重入（index.ts:865）；二是从磁盘载入时，每条事件的 seq 必须严格等于它的下标（index.ts:652 附近的构造函数校验，注释里写明「篡改过的种子事件会表现为后端拒绝或内存日志与磁盘静默分叉」）。

写入前先拍快照

append 的第三行做了一件容易被忽略的事：它没有直接把调用方给的 data 放进日志，而是先过一遍 JSON 快照（index.ts:808）。快照失败就直接抛错，事件不进日志（index.ts:810）。

这一步同时解决三个问题。第一，日志里存的是快照，调用方事后改动自己那个对象不会改写已经记下的事实。第二，非 JSON 类型（BigInt、函数、undefined、NaN、循环引用）在写入点就被拒绝，而不是等到某次刷盘时才炸——文档里给的理由是「事件日志是持久的事实来源，所以坏事件必须在 append 处失败，而不是晚些时候在后端刷盘时失败」。第三，也是为回放服务的：日志里的每个字段都保证能无损地读回来，回放器因此不需要处理「这个字段可能是函数」这种情况。

我们的 labs/harness/session_log.py 用一行 dumps/loads 达到同样的效果：

def _json_snapshot(value: Any) -> Any:
    """把值拷成无损 JSON 快照；拷不动就当场报错，而不是等落盘时才失败。

    走一遍 dumps/loads 同时完成三件事：深拷贝、拒绝非 JSON 类型、拒绝 NaN/Infinity
    （DSH 的 append 也在写入处直接抛错，理由相同：日志是事实来源，坏事件要在写入点暴露）。
    """
    try:
        return json.loads(json.dumps(value, ensure_ascii=False, allow_nan=False))
    except (TypeError, ValueError) as exc:
        raise ValueError(f"event payload is not losslessly JSON-serializable: {exc}") from exc

Python 这边的 allow_nan=False 是关键：默认的 json.dumps 会把 float('nan') 写成裸的 NaN，那不是合法 JSON，载入方（甚至是 Python 之外的工具）读不了。

日志之外不许有第二份状态

只要承认日志是事实来源，就要接受随之而来的纪律：任何「当前状态」都必须能从日志折出来，不能另存一份。DSH 连「当前的请求头」都是这么处理的——它有一个专门的纯函数负责从日志里折出当前生效的请求头，注释写明这是「纯离线重建路径」：

export function foldRequestHeader(events: readonly SessionEvent[], from?: EpochHeader): EpochHeader | undefined {
  let state = from
  for (const event of events) {
    if (event.type === 'request/header') state = canonicalHeader(event.data.header)
  }
  return state
}

出处：request-header.ts:63。折的方式是「最后一条 request/header 胜出」，其余事件全部跳过。注意它接受一个 from 参数（接着上次折过的状态继续折），这是纯函数版本的增量优化；我们的实现干脆每次从头折一遍，代价是 O(n)，换来「绝不可能分叉」。

事件类型：日志里的词表

一份日志要能被别的程序理解，事件类型就不能是随手起的字符串。DSH 的做法是把词表写进类型系统：每种事件在 SessionEventMap 里声明自己的载荷形状（types.ts:281），然后由脚本生成一份「这个构建认识的全部事件名」的集合（known-event-types.ts:22）。生成的文件里写明了这份集合的用途：读取路径遇到集合之外的（且没有 ignorable 标记的）事件类型时拒绝解释这份日志，因为「静默跳过一个必需事件会重建出一个错误的会话」。

缺省即必需：读取方遇到一个自己不认识、又没带 ignorable 标记的事件类型时，必须拒绝重建这份会话，而不是静默跳过它——因为一个不认识的必需事件可能改变整份日志的解释方式。写方只对「丢了也不影响重建」的信息记录打这个标记。默认必需，意味着忘记打标记的后果是「过度拒绝」（麻烦），而不是「静默恢复出一个被掏空的会话」（灾难）。

这是一个值得照抄的默认值选择：在不确定的时候，选那个「出错时更吵闹」的一侧。

这些事件由谁写

日志的写入者是 agent loop，不是日志库。DSH 的 Session 只提供 append，具体什么时候写什么由循环决定：

  • turn 开始与结束：agent.ts:307、agent.ts:387。注意 turn/end 写在 finally 里，所以无论正常结束、被取消还是抛异常，这条事件都会落地——日志的「平衡性」（每个 turn/start 都有对应的 turn/end）就是靠这一点维持的。
  • step 开始与结束：agent.ts:331、agent.ts:358（同样在 finally 里）。
  • 模型回复：agent.ts:539。失败的尝试另记一条（agent.ts:486）。
  • 工具调用与结果：tool-calls.ts:264、tool-calls.ts:282。结果事件里还带 sourceEventSeqs: [callSeq]（tool-calls.ts:289），显式指回它的调用——这样「两个并行调用，哪个结果对应哪个调用」不需要靠顺序猜。
  • 系统提示词：agent.ts:423。每次请求前重新组装的提示词都作为一条 system/message 进日志，所以「提示词变了」也是可查的。

我们的 SessionLog.append 只做一件额外的事：把 seq 的分配和追加放进同一把锁，这样并发调用也不会撞号。

    def append(self, kind: str, payload: dict[str, Any] | None = None, *, turn: int = 0, step: int = 0) -> int:
        """追加一条事件并返回它的 seq。

        先做 JSON 快照再入日志：调用方之后改动传入的 dict，不会改变已经写进去的事实。
        seq 的分配和 append 在同一个锁里，所以并发调用拿到的 seq 不会撞车也不会跳号
        （DSH 用的是「seq = 日志下标」这条更简单的路子，代价是同一会话只能有一个写入者）。
        """
        if not isinstance(kind, str) or not kind:
            raise ValueError("event kind must be a non-empty string")
        snapshot = _json_snapshot(payload if payload is not None else {})
        with self._lock:
            event = Event(seq=len(self._events), kind=kind, payload=snapshot, ts=time.time(), turn=turn, step=step)
            self._events.append(event)
        return event.seq

seq 依然等于 len(self._events)，只是取长度和追加这两步不再可能被别的线程插进来。这是教学版能付得起的代价：真实实现要么像 DSH 一样把「单写者」当成硬约束，要么像我们的 JSONL 后端一样用一个句柄 API 把它固化下来。

请求头：为什么要把配置的指纹写进日志

消息历史只记录「模型看见了什么」，不记录「模型是在什么条件下被问的」。而同一个问题在不同条件下答案不同：换了模型、换了 provider、上下文窗口变了、工具列表变了、采样参数变了——任何一项变化都足以让两次运行不可比。所以 DSH 把这些条件也记进日志，事件叫 request/header，载荷是 EpochHeader（types.ts:240），里面有三样东西：调用配置（provider、model、推理强度、采样标量）、适配器实际materialize 出来的默认值、以及组装好的工具 schema 列表。

写入策略在 agent loop 里（agent.ts:643），三种原因分得很细：

      this.session.append('request/header', { header, reason: 'series' })
    }

出处：agent.ts:637-651；四种原因的语义（initial / resume / change / series）定义在 types.ts:273。

两个设计点值得单独拎出来。

第一，不变就不写。headerEquals 逐字段比较（工具 schema 按位置逐个比 JSON），相同就一条都不写。否则每一轮都写一条 header，日志立刻被自己的元数据淹没。同一张表里还有一份更细的记录：当工具列表发生增删时，循环会额外写一条 developer/message 把增删告诉模型（agent.ts:658）。这解决了一个真实的痛点：工具集变了但模型不知道，它会继续调用已经不存在的工具。

第二，「工具集变了」必须能被事后检测出来。这是把指纹写进日志的核心收益。DSH 的做法是存完整的工具 schema 列表，所以差异可以精确到某个 schema 的某个字段；教学版存名字列表加一个指纹就够了，因为差异报告只需要回答「哪些工具增删了」。

    def tool_set_changes(self) -> list[str]:
        """相邻两条 request/header 之间的工具集差异，形如 ``['+read', '-bash']``。

        日志里存了工具指纹，所以「这次运行的工具集和上次不一样」是可以事后检测出来的；
        没有指纹的话，只能看到消息历史莫名其妙变了。
        """
        names = [header.get("toolNames", []) for header in self.request_headers()]
        if len(names) < 2:
            return []
        previous, current = set(names[-2]), set(names[-1])
        added = [f"+{name}" for name in names[-1] if name not in previous]
        removed = [f"-{name}" for name in names[-2] if name not in current]
        return added + removed

指纹本身的算法有个细节：工具名按顺序参与哈希。

def tools_fingerprint(tools: Sequence[str]) -> str:
    """工具名列表的指纹。按顺序参与哈希：与 DSH 的 headerEquals 一致，
    工具的增删和改序都算变化——工具列表是提示前缀的一部分，改序一样会打断缓存。"""
    joined = "\n".join(str(name) for name in tools)
    return hashlib.sha256(joined.encode("utf-8")).hexdigest()[:16]

如果指纹对工具名排序后再哈希，那么「工具顺序变了」就不会被记为变化，而工具列表是提示前缀的一部分——改序一样会让 KV 缓存失效、一样会改变模型的判断。DSH 的 headerEquals 也是按位置比较的，两边一致。

请求头落进日志之后，还有一个顺带的好处：它是一条已知的「系列边界」。DSH 的 request/header 事件带 startsSeries 标记，压缩把历史替换掉之后需要靠它区分「新的一段对话」和「同一段对话的续写」。没有这个标记，裁剪之后就无法判断这段历史和之前的是不是一件事。

格式版本：读不认识的日志要说出来

日志一旦落盘，格式就冻结了。旧版本的代码要能读新版本的文件吗？通常不能。那就必须把「读不懂」变成一个明确的、能指导操作的错误，而不是猜着读或者崩在读一半。

DSH 把这件事做成了一套可以单独发布、单独测试的机制。当前格式版本是 4，写在类型里（types.ts:89）。每个历史版本各有一个「编解码器 + 相邻迁移」包，命名方式就是 session-format-v0-to-v1 到 session-format-v3-to-v4（v3→v4 的说明是「Tool-role V3-to-V4 migration with native V4 framing and delivery validation」，session-format-v3-to-v4/src/index.ts:1）。我们看到的版本一共 5 个（v0 到 v4），迁移边 4 条。

这套机制里有两条硬规则，是它的可靠性来源。

规则一：迁移只能相邻，链条必须完整。声明一条迁移时就会检查它是不是 vN → v(N+1)（chain.ts:31），编译链条时从 0 到当前版本逐条找，缺一条就直接报错（chain.ts:68）。这样「迁移能不能做」在启动时就确定了，不会在读到一份老日志时才失败。

规则二：比当前新的版本一律拒绝。读到 storedVersion > currentVersion 时，返回的不是「尽力而为」，而是一句给操作者看的话：stored Session uses newer format vN; this build writes vM（catalog.ts:57）。README 里专门写了这个措辞要求：用户看到的应该是「升级 harness」，永远不会是「会话日志损坏」。

还有一处细节值得学：历史版本的恢复用的是一个独立的、版本钉死的目录（historical.ts:11，它把 currentVersion 固定成 3，专门用来收集迁移的前置信息，而不去递归打开当前版本的会话）。理由是：如果历史恢复路径调用当前的恢复逻辑，那它自己就依赖于「当前逻辑是什么」——重构一次当前格式就可能把老文件的读取能力弄坏。把老版本的读取代码冻在一个不再改的目录里，这个耦合就断了。

我们的 labs 版本把同样的原则压成了三条检查：头记录必须有；version 必须恰好等于这个构建认识的版本；事件的 seq 必须严格等于它的下标。任何一条不满足都带行号抛 LogCorrupt。

class LogCorrupt(ValueError):
    """日志在提交前缀里损坏。带上第几行，因为「第几行坏了」是唯一能拿去修的信息。"""

    def __init__(self, line: int, reason: str) -> None:
        super().__init__(f"session log line {line}: {reason}")
        self.line = line
        self.reason = reason

把行号放进异常对象（而不只是塞进消息字符串）看起来是小事，实际差别很大：调用方可以程序化地处理「第 N 行坏了」，比如把坏行摘出来、把前后两段拼起来。DSH 的读取器报的是字节偏移（format.ts:484 里 line ${this.eventLine}），原理相同——定位信息必须结构化地传出来。

崩溃恢复：怎么从半截日志回到一致状态

日志解决了「数据还在不在」，但没解决「数据是否一致」。崩溃几乎总是发生在最坏的位置：一次工具调用已经记进日志、结果还没写；或者模型回了一半。恢复的目标是让日志重新变成一份合法的请求前缀——也就是每个 turn/start 有对应的 turn/end，每次工具调用有对应的结果。

DSH 把这件事做成一个纯函数：给定一份可能停在开口 turn 中间的日志，返回需要补写的事件列表。它先扫一遍日志，跟踪「当前有没有打开的 turn / step」以及「哪些工具调用还没答复」：

扫描完之后，如果没有开口的 turn 就返回空列表（日志本来就平衡，什么都不用做）。否则生成三条东西：给每个没答复的调用补一条错误结果、补一个 step/end（如果 step 也悬着）、补一个 turn/end。补出来的事件是确定性的：seq 从最后一条真实事件往后连续编号，时间戳直接复用最后一条真实事件的时间——不发明「未来」的时间，这样同一份日志跑两次恢复得到的补写事件逐字节相同，回放测试才能对得上。

补出来的错误结果分两种，措辞不一样，因为模型需要知道的事实不一样（repair.ts:34 起）:

  • 调用已经开始、结果没落盘：告诉模型「结果未知。按工具语义决定是否重试：只读或幂等的操作可以重试；可能有副作用的，先核实外部状态或者问用户。不要盲目重试。」
  • 调用还没被记为 started：告诉模型「中断发生在记录开始之前，如果还需要就重试。」

这不是随便写的提示词。它把「日志缺了什么」这个事实精确地翻译成了模型能据以行动的判断依据——这正好是「日志是事实来源」的价值兑现：因为日志知道那条调用到底开始没开始，所以恢复时才能给出有信息量的错误。

顺带一句，同一份机制还被 fork（从既有会话分叉）复用，只是原因改成 forked，措辞变成「这条调用在分叉点之后、父会话里可能已经完成」。

写入侧的对应机制：半行与截断

读取侧的恢复要跟写入侧的失败模式对上。JSONL 后端的写入是分批的：实时事件先进缓冲区（storage.ts:274），200 毫秒的窗口到期后一起刷盘（storage.ts:36）。批量写意味着进程被杀时最容易留下的是一行写到一半——也就是我们说的「残行」。

后端的处理策略写在扫描器的注释里，非常直白：结束扫描时，忽略那个没有结尾换行的最后一条记录，把它当作撕裂的尾巴（format.ts:462）。扫描器按字节找换行符，换行之前的算完整记录，换行之后的碎片留到下一块数据里（format.ts:438），所以最后剩下的碎片天然就是「没有换行的那一条」。恢复的结果里带着一个安全截断偏移量，写入句柄的第一次追加会先把撕裂的字节截掉再写新内容（storage.ts:328）。

关键在于：「坏行」和「半行」是两种不同的东西，处理方式必须不同。

提交前缀里的坏行没有结尾换行的最后一行
成因磁盘损坏、程序 bug、人工编辑进程在写这一行的中途被杀
含义日志本身不可信，后面的事件可能也被影响这一行从未被承诺过，前缀完好
正确反应拒绝加载，报出位置丢弃这一行，报告断点，继续加载前缀
DSHrecovery: 'strict'（format.ts:370）；正式读取报 corruptiontorn tail，截断后重写

DSH 把这个区分做成了配置项 SessionFormatRecovery，取值只有 'strict' 和 'recoverable'（types.ts:91）。注意，可恢复模式放过的只是尾巴，不是任何一行：一旦已经记下一个 issue，后面如果再出现完整记录，官方实现的处理是把它当作损坏处理——因为「坏行之后又有好行」说明坏的不是尾巴，而是中间。

我们的 labs 版本用一条更朴素的规则达到同样的区分：文件以 split("\n") 切开之后，如果最后一段是空字符串，那是正常的结尾换行；否则最后一段就是从未提交的残行。

    @classmethod
    def load(cls, path: str | Path, *, strict: bool = False) -> "SessionLog":
        """从 JSONL 载入并校验。

        - 头记录：版本必须是本文件认识的版本，读到更新版本直接拒绝（不要猜）；
        - 事件行：必要字段齐全、seq 从 0 连续；
        - 提交前缀里的坏行 → ``LogCorrupt``，异常里带行号；
        - 最后一行没有结尾换行 → 进程被杀的残行，丢弃并记进 ``warnings``；
          ``strict=True`` 时改为报错，适合「宁可失败也不要丢数据」的场合。
        """
        source = Path(path)
        text = source.read_text(encoding="utf-8")
        warnings: list[str] = []
        lines = text.split("\n")
        if lines and lines[-1] == "":
            lines.pop()  # 正常的结尾换行
        elif lines:
            torn = lines.pop()  # 没有结尾换行：这一行从未被提交
            number = len(lines) + 1
            message = f"line {number}: dropped incomplete final line ({len(torn)} bytes, no trailing newline)"
            if strict:
                raise LogCorrupt(number, "incomplete final line (torn tail) and strict loading was requested")
            warnings.append(message)

        header: dict[str, Any] | None = None
        events: list[Event] = []
        for number, raw in enumerate(lines, start=1):
            if not raw.strip():
                warnings.append(f"line {number}: skipped blank line")
                continue
            try:
                record = json.loads(raw)
            except json.JSONDecodeError as exc:
                raise LogCorrupt(number, f"not valid JSON ({exc.msg})") from exc
            if not isinstance(record, dict):
                raise LogCorrupt(number, "record is not a JSON object")
            if record.get("type") == HEADER_TYPE:
                if header is not None:
                    raise LogCorrupt(number, "duplicate session header")
                version = record.get("version")
                if version != SESSION_FORMAT_VERSION:
                    raise LogCorrupt(
                        number,
                        f"unsupported session format version {version!r}; this build reads v{SESSION_FORMAT_VERSION}",
                    )
                header = record
                continue
            if header is None:
                raise LogCorrupt(number, "event appears before the session header")
            event = Event.from_record(record, number)
            if event.seq != len(events):
                raise LogCorrupt(number, f"event seq {event.seq} is not contiguous (expected {len(events)})")
            events.append(event)

        if header is None:
            raise LogCorrupt(1, "no session header; this file is not a session log")
        log = cls(str(header.get("id", "session")), cwd=header.get("cwd"), events=events, warnings=warnings)
        log.created_at = float(header.get("createdAt", log.created_at))
        return log

载入成功之后，log.warnings 里就带着「在哪里丢了一行、那行有多大」。这比静默丢弃强得多：恢复是信息，不是掩盖。

什么时候允许丢

崩溃恢复的另一半是「什么可以安全丢弃」。DSH 的选择是：丢尾，绝不改中间。已经提交的事件永不重写。后端 README 里的表述是「在一次崩溃之后，磁盘上的日志保留着它被打断的最后一轮；提交前缀里的每一条记录都存活下来，恢复的读者通过它的写句柄补写合成的收尾事件」。

还有一个更晚才发生的裁剪机制值得提一句：投影缓存（projection-cache/index.ts:10）。它把某些投影的状态（比如统计、标题）定期存成检查点，冷启动时就不用把整份日志折一遍。它的定位写得很克制：是折叠的捷径，绝不是权威——一行记录可能过期（它的 seq 字段说明有多过期），但永远不会是错的。所以它的写路径是 fail-soft 的：丢一次写，代价只是下次冷读时多折一段尾巴。

这个措辞值得抄下来当设计原则：缓存可以过期，但不能说谎。实现方式是让缓存记录自己携带「我基于哪个 seq 算出来的」，读的时候跟日志的真实长度一比就知道要不要补折。

回放：把日志重新变成消息列表

到这里，回放几乎是免费的：日志已经包含了重建历史所需的一切，只需要一个把事件翻译成消息的函数。DSH 的实现叫 deriveMessages（index.ts:984），它的关键性质写在注释里：返回的是每次调用都全新的数组，但数组里的消息对象是共享且深冻结的——调用方既不能在不知情的情况下改动它，也不能通过它反过去改日志。它内部只走「产生消息的事件」这条序列，并且有增量缓存（纯追加只处理新节点，遇到替换就整体重建）。

更重要的是它在调用点的语义。DSH 的 agent loop 在发起请求前，唯一的历史来源就是这次推导：

    const boundaryMessages = session.deriveMessages()

出处：agent.ts:688，紧接着它就被放进请求对象（messages: boundaryMessages）。也就是说，循环不维护自己的消息数组——它每次都从日志推导。这就是「日志是事实来源」在代码里的落地形态：不是两份数据保持同步，而是只有一份数据，另一份是算出来的。

我们的 Replayer 只做推导这一件事，而且刻意不带任何跨调用状态：

class Replayer:
    """把日志重放成模型可见的消息列表。

    只由日志推导，**不另存一份状态**：同一个 seq 调用两次必须得到完全一样的结果。
    这正是确定性测试的基础——失败场景记一份日志，之后不调模型就能复现同一串消息。
    """

    def __init__(self, log: SessionLog) -> None:
        self._log = log
        # 上一次 messages_upto 为保持历史合法而丢掉的悬空 tool_use 数量（诊断用）。
        self.last_dropped_calls = 0

    def messages_upto(self, seq: int | None = None) -> list[dict[str, Any]]:
        """重放 seq（含）为止的事件为消息列表；``None`` 表示整份日志。

        规则：标记事件不产生消息；相邻的 tool/result 合并成一条 user 消息（厂商要求一批
        结果紧跟在一次调用之后）；截断落在 step 中间时，没有结果的 tool_use 会被丢掉——
        否则重放出来的历史不是合法的请求前缀，下一次请求会被厂商直接拒绝。
        """
        messages: list[dict[str, Any]] = []
        pending: dict[str, int] = {}  # tool_call_id -> 它的 tool_use 块所在消息的下标
        results_index: int | None = None  # 当前这条「工具结果」user 消息的下标

        for event in self._log.events:
            if seq is not None and event.seq > seq:
                break
            kind = event.kind
            if kind == "assistant/message":
                message = self._assistant_message(event)
                messages.append(message)
                results_index = None
                for block in message["content"]:
                    if block["type"] == "tool_use":
                        pending[block["id"]] = len(messages) - 1
            elif kind == "tool/result":
                call_id = str(event.payload.get("call_id", ""))
                block = {
                    "type": "tool_result",
                    "tool_use_id": call_id,
                    "content": str(event.payload.get("content", "")),
                    "is_error": bool(event.payload.get("is_error", False)),
                }
                if results_index is not None and results_index == len(messages) - 1:
                    messages[results_index]["content"].append(block)
                else:
                    messages.append({"role": "user", "content": [block]})
                    results_index = len(messages) - 1
                pending.pop(call_id, None)
            elif kind in ("system/message", "user/message"):
                messages.append(
                    {
                        "role": "system" if kind == "system/message" else "user",
                        "content": str(event.payload.get("content", "")),
                    }
                )
                results_index = None
            # 其余事件（turn/start、step/start、request/header、developer/message…）不改历史。

        dropped = 0
        for call_id, index in pending.items():
            kept = [
                block
                for block in messages[index]["content"]
                if not (block["type"] == "tool_use" and block["id"] == call_id)
            ]
            messages[index]["content"] = kept
            dropped += 1
        if dropped:
            # 空了内容或只剩空的 assistant 消息不要留在历史里（DSH 也把空 assistant 回复挡在转录之外）。
            messages = [m for m in messages if not (m["role"] == "assistant" and not m["content"])]
        self.last_dropped_calls = dropped
        return messages

    def last_boundary(self, seq: int | None = None) -> int:
        """≤seq 的最后一个安全截断点：一次 turn/end，或一次工具已全部配对的 step/end。

        分片续跑从这个 seq 接着重放，就不会看到半截 step。找不到时返回 -1。
        """
        boundary = -1
        pending: set[str] = set()
        for event in self._log.events:
            if seq is not None and event.seq > seq:
                break
            if event.kind == "assistant/message":
                for call in event.payload.get("tool_calls", []):
                    pending.add(str(call.get("id", "")))
            elif event.kind == "tool/result":
                pending.discard(str(event.payload.get("call_id", "")))
            elif event.kind == "step/end" and not pending:
                boundary = event.seq
            elif event.kind == "turn/end":
                pending.clear()
                boundary = event.seq
        return boundary

    @staticmethod
    def _assistant_message(event: Event) -> dict[str, Any]:
        """一条 assistant/message 事件 → 一条历史消息。"""
        content: list[dict[str, Any]] = []
        text = event.payload.get("text")
        if text:
            content.append({"type": "text", "text": str(text)})
        for call in event.payload.get("tool_calls", []):
            content.append(
                {
                    "type": "tool_use",
                    "id": str(call.get("id", "")),
                    "name": str(call.get("name", "")),
                    "input": _json_snapshot(call.get("args", {})),
                }
            )
        return {"role": "assistant", "content": content}

推导规则本身有四条，都是被厂商协议逼出来的：

  1. 标记事件（turn/start、step/end、request/header）不产生消息。它们只改状态。
  2. 相邻的 tool/result 合并成一条 user 消息。厂商要求 tool_result 块紧跟在它对应的 assistant 消息之后；分散成多条消息会被拒绝，也会白白浪费上下文。
  3. 截断落在 step 中间时，没有对应结果的 tool_use 块必须从推导结果里去掉。也就是原样保留「模型要了一次工具、工具没答」这种历史，会产出一个不合法的请求前缀。
  4. 推导结果必须是确定性的：同一个 seq 重放两次，逐字节相同。

第三条最容易做错，因为它看起来像是在丢信息。但日志本身没丢——被丢掉只是「这一次投影」，从日志里依然看得见那次调用发生过。这正是日志式的历史和数组式的历史的本质区别：数组只能有一份，删了就没了；日志可以有多种投影，每种投影可以按自己的用途做取舍。

按序号截断回放

截断点的选择有个讲究。随便取一个 seq 风险很大，因为截在 step 中间会触发上面的第 3 条规则（丢掉悬空调用）。所以回放器还提供一个「安全截断点」查询：返回不大于目标 seq 的最后一个 turn/end，或者一个所有工具调用都已答复的 step/end。

这在 DSH 里有对应物：会话可以从任意边界分叉出一份新的子会话（SessionForkErrorCode 里的 INVALID_BOUNDARY 就是「边界不是连续存在的 seq」），而分叉点落在开口 turn 里时，子会话会用 forked 原因补写收尾事件——和崩溃恢复走同一套代码。

回放为什么是确定性测试的基础

把日志当事实来源，最直接的回报是测试形态的改变。DSH 有一个专门的回放插件包（llm-replay/index.ts:462），作用是从一份真实会话日志里推出「这次运行一共调了几次模型、每次的原始流是什么」，然后让这个脚本顶替真实的模型适配器。

它的函数签名说明了一切：输入是事件数组，输出是一串「脚本条目」。推不出来的时候它会明说，而不是悄悄糊过去：如果某次调用没有以 finish 块结束（说明流是抛异常结束的），它会抛错并提示「这个场景需要一个 replay.override.json 旁挂文件」（llm-replay/index.ts:468）。

这套东西的价值在于把三类测试从「难以编写」变成「顺手就能写」：

  • 回归测试不需要花 API 费用，也不依赖模型行为稳定。日志记的是模型当时真实返回的字节。
  • 线上失败可以被固化成测试用例：把出问题那次的日志拿回来，回放一次，就得到了一次完全一样的运行。
  • 非模型部分的 bug 可以被隔离出来。因为模型输出被钉死了，测试失败必然是 harness 的问题。

我们 labs 里的测试是同一个思路的简化版：因为回放器只依赖日志，构造一段日志就等于构造了一个场景，不需要任何模型。

    def test_replay_rebuilds_the_model_visible_history(self) -> None:
        log = make_log()
        messages = Replayer(log).messages_upto()
        self.assertEqual([m["role"] for m in messages], ["system", "user", "assistant", "user", "assistant"])
        self.assertEqual(messages[0]["content"], "you are a coding agent")
        assistant = messages[2]["content"]
        self.assertEqual(assistant[0], {"type": "text", "text": "reading"})
        self.assertEqual(assistant[1]["type"], "tool_use")
        self.assertEqual(assistant[1]["input"], {"path": "a.py"})
        results = messages[3]["content"]
        self.assertEqual(results[0]["tool_use_id"], "c1")
        self.assertFalse(results[0]["is_error"])

还有一条性质值得单独测试，因为它正是「日志是唯一事实来源」这句话的操作化定义：在同一个截断点上，无论之后往日志里追加了多少事件，重放结果都不变。

    def test_append_during_replay_does_not_disturb_earlier_results(self) -> None:
        """回放的确定性与并发写入无关：截断点固定的重放结果不会因为又有新事件而变。"""
        log = make_log()
        replayer = Replayer(log)
        fixed = replayer.messages_upto(7)
        log.append("tool/result", {"call_id": "c9", "content": "late", "is_error": False})
        self.assertEqual(replayer.messages_upto(7), fixed)

裁剪、压缩与检查点

日志会无限增长。一个跑了几小时的会话，日志里可能有几百次工具调用、每次几万字符的输出。这些数据都在日志里，但不能都进上下文。所以需要一个明确的区分：日志是持久层，上下文是窗口层；两者不是同一份东西，裁剪只作用于后者。

DSH 的压缩是插件，但它改的也是日志——把一段历史替换成一条摘要事件。所以必须有一个机制标记「这段历史被替换掉了」，否则从日志推导出来的消息会把老消息和新摘要都算进去。DSH 的解法是给每个产生消息的事件配一个 surface 操作标记（types.ts:462），取值只有两种：普通追加，或者「替换掉某个 seq 区间」（{ op: 'replace'; startSeq: SessionSeq; endSeq: SessionSeq }）。推导函数就是按这些标记走的，注释里把话说得很清楚：「每个产生消息的追加都记录它的 surfaceOp，所以一条没有标记的原始事件（一个 chunk、一个 turn 边界）会被正确地排除在外，而压缩的 replace 会删掉被遮蔽的节点」（index.ts:970）。

检查点是另一件事：在模型请求和工具执行之前把日志刷到磁盘。DSH 有一个专门的插件管这件事，文档说得很明确——刷盘失败就不调用模型、不执行工具（checkpoint-policy/index.ts:58），挂在三个位置：模型流开始前（index.ts:64）、顶层工具执行前、以及每个 step 开始前（index.ts:80）。

这些数字和位置都指向同一个取舍：检查点的目的不是「尽快落盘」，而是「在产生副作用之前确保记录已经在磁盘上」。所以在工具执行前刷一次——如果刷盘失败，宁可不执行工具，也不要执行了一个已经发生、日志里却没有记录的动作。

裁剪策略本身在别的章节展开（压缩的具体策略见本模块后面的压缩章节，这里只讲它和日志的关系），这里只提它和日志的关系：裁剪产生的事件本身也要进日志。DSH 的压缩会写 compaction/start、compaction/end、compaction/summary 这几类事件，所以「模型当时看到的上下文是被压过的」这件事，事后也是可查的。这一点在我们的教学版里没有实现，见下面的坑与失败案例。

坑与失败案例

坑一：内存态与日志态分叉

触发条件：循环里维护一个 self.messages，同时又把每次事件写进日志；某处代码改了数组但忘了写日志，或者反过来。

后果：运行中的行为和重启后的行为不一致。这类 bug 特别难查，因为它只在「重启」这个维度上表现出来，而开发者平时不重启。更坏的情况是两者都「看起来对」，只有在做回放对比时才暴露。

DSH 怎么防的：根本不让第二份状态存在。循环不持有消息数组，每次请求前从日志推导（agent.ts:688）。连「当前请求头」这种小状态都走折叠函数（request-header.ts:63）。

教学版的防法：Replayer 是只读的，而且不带跨调用状态——它没法「忘记同步」，因为它没有可以不同步的东西。

坑二：序号不连续导致回放漏消息

触发条件：日志被外部工具过滤过、被合并过，或者两份日志被拼成一份；也可能是载入时期的解析 bug 静默跳过了一行。

后果：回放出来的历史少了一条消息，但没有任何报错。这比崩溃危险得多：模型会看到一段缺了一条 tool_result 的历史，可能因此重复执行一个已经有副作用的操作。而且它完全不会在测试里出现——因为测试用的日志是完整的。

DSH 怎么防的：seq = 日志长度让连续成为写入路径的自然结果；载入时显式校验从 0 连续（index.ts:652），并把「不连续」当成必须拒绝的错误，而不是警告。

教学版：同一处理方式，并且把行号和实际读到的 seq 一起报出来（LogCorrupt）。这里可以注意一个细节：跳号是在读到下一条时才暴露的，所以如果坏的是最后一行，就没有「下一条」来发现它——必须靠显式检查「这条事件的 seq 是否等于已读条数」。

坑三：日志里存完整工具输出，文件迅速膨胀

触发条件：工具结果原样进日志。一次 cat 一个大文件就有几 MB；一个跑一小时的会话可以轻松到几百 MB。

后果：写盘变慢（每次刷盘都要写这些字节）、加载变慢（每次恢复要读完整份）、备份和上传变得不现实。更隐蔽的后果是：因为这些内容也在上下文里，压缩机制会去处理它们——但压缩作用于上下文，管不了日志文件的大小。

DSH 怎么处理的：转存（spill）。工具结果超过阈值时（maxInlineTokens: 12500，见 base bundle 的装配）内容被写到外部文件，日志里只留一个引用。压缩侧还有另一个机制：工具结果超过 8192 字符时裁剪成开头 4096 + 结尾 1024 字符，中间的用省略标记替代——裁剪本身也是日志事件（compaction/prune）。

教学版没做这个，这是一个明确的简化。要补的话，最小的切入点是在 append 里对 tool/result 的 content 做长度检查，超阈值就写外部文件、日志里存路径。要注意的是：转存之后回放仍然要能重建出模型当时看到的那个字符串（引用必须能解析），否则回放就不再等价了。

坑四：半行 JSON 让整份日志载入失败

触发条件：进程在写某一行的时候被杀（或者机器断电）。这一行只写了一半，没有结尾换行，JSON 也不完整。

后果：如果载入器把「最后一行解析失败」和「中间某行解析失败」当成同一件事，那它会拒绝整份日志——用户丢掉的是整段会话，而实际上只损失了最后一行的内容。这是最典型的「错误处理写得太严格，反而造成更大损失」。

DSH 怎么防的：两个失败模式分开处理。完整的坏行按 corruption 拒绝，没有结尾换行的最后一条按可恢复的撕裂尾巴截断（format.ts:462）；写入句柄的第一次追加会先把撕裂字节截掉。判断依据是字节级的：哪一段后面有换行符，哪一段就是被提交过的。

教学版：load() 用「split 之后最后一段是不是空」来区分，丢弃残行并记进 warnings；strict=True 时改为报错。测试里专门覆盖了「残行前面的提交前缀必须全部载入成功」这一条。

坑五：把「未知事件类型」当成可以忽略

触发条件：日志里有一个本构建不认识的事件类型（可能是更新的 harness 写的，也可能是某个插件写的），读取方选择跳过。

后果：静默跳过一个必需事件会重建出一份错误的会话——DSH 的注释原话是「这样的日志很可能是更新的 harness 写的，而静默跳过一个必需事件会重建出一个错误的会话」。比拒绝加载更糟的地方在于：拒绝加载是可见的，错误重建是不可见的。

DSH 怎么防的：默认必需。ignorable?: true 只能由写方显式加上（types.ts:511），注释里写明这个默认值的方向：忘记打标记的后果是「过度拒绝」（麻烦），而不是「静默恢复出一个被掏空的会话」（灾难）。

这条对我们写的任何「宽容的读取器」都是一个提醒：宽容应该体现在格式变体上（多一个字段就忽略），而不是体现在语义缺口上（少一个事件就当没有）。

小结

这一章把历史从「一个数组」换成了「一份日志」，换来的性质有四条：

  1. 可恢复：任何时刻进程被杀，磁盘上的提交前缀都是完整的；恢复只需要补写收尾事件，不需要重跑。
  2. 可审计：「模型第 N 次请求看到了什么、当时的配置是什么」都可以从日志算出来，包括工具集变化这种容易被漏掉的信息。
  3. 可回放：历史是被推导的，不是被保存的，所以同一份日志永远给出同一串消息。
  4. 可演进：格式带版本、迁移只允许相邻、读不认识的版本要说清楚——这三条让日志能活过多次重构。

四个机制的边界也很清楚。日志解决「记什么」，检查点解决「什么时候必须已经在磁盘上」，压缩解决「上下文装不下」，回放解决「怎么把日志变回模型看得见的东西」。四者互相独立，但都建立在同一个前提上：日志是唯一的事实来源，其余都是它的投影。

下一章转向上下文压力的量化：怎么在请求发出之前就知道这份历史装不下，而不是等厂商返回错误再补救（下一章，见 Token 计量与上下文压力）。本章的日志正好是它的输入——压力是从日志推导出来的消息上量出来的，不是从某个单独维护的计数器上读出来的。
