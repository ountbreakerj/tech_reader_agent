第 18 章

重试与退避

主线故事 · 第 18 章（虚构）

那个 429 之后，林舟花了十分钟给橘子加上了重试：失败就等一秒，再试，最多试十次。当天晚上一切正常。

第二天上午十点，模型厂商有一次持续二十分钟的限流。小橘科技的三个客户同时在用橘子，每个客户开着两三个会话，一共九个 agent。九个 agent 在同一秒收到 429，在同一秒等完那一秒，又在同一秒发出重试，又在同一秒收到 429。日志里的时间戳整整齐齐，像一排在同一个节拍上撞墙的人。

更糟的是另一个会话。它收到的错误不是 429，是 400：prompt is too long。上下文超长了。橘子把它也当成了临时故障，老老实实重试了十次，每一次都把同样长的上下文原封不动地发出去，每一次都被拒，十次一共花了二十多秒，然后放弃。用户看着屏幕上的转圈，什么都不知道。

第三个问题是林舟自己发现的：重试成功之后，模型的回复开头总带着一句奇怪的话——“我注意到之前的请求出了错……”。他翻日志，发现上一次失败时收到的半截回复和错误信息，被原样留在了历史里，下一次请求时模型都看见了。

“你的重试有三个问题，”老唐数着手指，“不分什么错都重试；所有人同时重试；重试的时候把失败的垃圾也带上了。”

这一章要把这三行重试代码，变成一个真正能用的重试层：先分清哪些错误值得再试，再决定隔多久——指数增长、随机打散、优先听服务端的——然后定好上限，最后保证失败那次的残留不会进入下一次请求，并且在等待之前先记下“我在重试”。

到这一章为止，循环里任何一次模型调用失败，都按第 01 章的设计“结构化地停下来”：返回 llm_error，历史保持完整。这对教学够了，对生产不够：网络抖一下、厂商限流几秒，整个任务就中断，用户得手动点“继续”。

重试要解决的就是这类临时故障：再来一次很可能就好了的那种。难点不在于“再来一次”，而在于分清什么时候再来、隔多久、来几次，以及什么时候该承认“这不是临时的”。

先看全貌：重试与退避是什么、管哪些事

一句话：模型调用（或其他外部调用）失败后，harness 判断这次失败是不是临时的；是的话，等一段时间再试，等待时间随次数指数增长并加上随机抖动，直到成功、次数用完或者总等待时间超出预算。

这一层要管的事：

  • 分类：哪些失败可以重试（限流、服务端错误、超时、连接断开），哪些不能（鉴权失败、参数错误、上下文超长）。
  • 等待时间：指数退避、随机抖动、优先采用服务端的 Retry-After。
  • 上限：次数上限、单次等待上限、总等待上限，按“这一步”计算而不是整个会话累计。
  • 历史清洁：失败尝试的半截输出和错误信息不进下一次请求的上下文。
  • 留痕：先记录“要重试、等多久”，再开始等待；进程中途被杀，恢复后知道刚才在重试。
  • 最终失败时说什么：重试耗尽之后，给模型或用户一句有用的话，而不是十条原始错误。

四个决定，先给结论：

决定看起来省事的做法本章的结论
哪些错误重试所有异常都重试只重试临时故障；分类按状态码和错误类型做，不按错误文本里有没有某个词
隔多久固定等一秒指数退避 + 随机抖动；服务端给了 Retry-After 就听它的，超过上限就放弃而不是偷偷缩短
试几次一个固定次数，或者无限次数上限 + 总等待上限；计数按“这一步”清零
失败尝试的残留留在历史里，下一次照发失败尝试不提交任何消息；下一次请求的上下文和第一次完全相同

三个仓库在这一层分别是什么水平

DSH（TypeScript）：这一层做得最完整，而且拆成了两半。策略写在每个模型提供方的配置里：默认最多重试 5 次，初始等待 500 毫秒，单次上限 10 秒，抖动比例 0.1，可重试的错误码是空响应、限流、服务端错误、超时、传输错误五种。执行是一个独立的重试插件，挂在“模型请求失败”这个扩展点上；它每次重试都先写一条日志事件、再开始等待，重试计数从日志里读，进程重启也不会丢。它还有一个“永远重试”的模式，用于不能中断的场景。本章的主要参照。

OpenHarness（Python）：重试做在 API 客户端这一层，可重试的状态码是 429、500、502、503、529，网络错误也算可重试；等待用指数退避加抖动，优先读 Retry-After 头。另外它会解析“输出 token 上限太大”的报错，把上限调低后重试，并且这次重试不计入轮数。它的循环里还有一处用错误文本里是否含 “connect” 或 “timeout” 来区分网络错误，本章会把它当作分类方式的反例来讲。

learn-claude-code（教程）：前期没有重试；到集成章节才加了一个“连续 529（API 过载）最多两次”的上限。

labs（本章要写的）：labs/harness/retry.py，错误分类、退避计算、等待规划、带日志挂点的重试执行，23 条测试，时钟和随机数都可注入，测试不真的睡眠。

本章怎么读：

  1. 第 1 节讲错误分类，是整个重试层的前提：分错了，后面做得再好也是在给不可恢复的错误浪费时间。
  2. 第 2 节讲等待时间怎么算，配合测试里的“羊群”例子理解抖动的作用。
  3. 第 3 节讲上限和 Retry-After；第 4 节讲重试和历史、日志的关系，这一节连着第 04 章。
  4. 第 5 节讲重试放在哪一层；第 7 节的坑基本对应上面故事里的三个问题。

先分类：只有临时故障值得重试

重试的前提是“再来一次结果可能不同”。按这个标准，失败可以分成三类：

类别例子再试一次会怎样该怎么处理
临时故障429 限流、529 过载、5xx、请求超时、连接被重置、空响应过一会儿很可能成功退避后重试
请求本身有问题400 参数错误、401/403 鉴权失败、密钥缺失一万次结果都一样立刻失败，把原因说清楚
需要先改请求上下文超长、输出上限设得太大原样重发一定还失败；改完请求再发可能成功交给专门的恢复逻辑（压缩、调低上限），而不是重试

第三类最容易被混进第一类。故事里那个上下文超长的会话就是这样：它被当成临时故障重试了十次，每次都是同样的请求。正确的处理是第 07 章的压缩——先把请求改小，再发。DSH 和 OpenHarness 都把这件事单独处理：DSH 的压缩插件挂在同一个“请求失败”扩展点上，只有压缩确实改写了历史才返回“重试”；OpenHarness 对“提示过长”做一次反应式压缩再试，对“输出上限太大”解析出厂商允许的上限再试。它们都不是通用的重试，而是“改了请求再发”。

分类函数应该按状态码和错误类型来判断：

def classify_status(status: int | None, body: str = "") -> str:
    """把 HTTP 状态码和错误正文归到一个 kind。

    按状态码分类，不按错误文本里有没有 "timeout" 这个词：文本匹配会把
    「请求参数 timeout 不合法」这种 400 错误误判成可重试的超时。
    """
    lowered = body.lower()
    if status == 429 or status == 529 or "overloaded" in lowered:
        return RATE_LIMIT
    if status in (401, 403):
        return AUTH
    if status == 413 or "prompt is too long" in lowered or "context length" in lowered:
        return TOO_LONG
    if status == 408 or status == 504:
        return TIMEOUT
    if status is not None and 500 <= status < 600:
        return SERVER
    if status is not None and 400 <= status < 500:
        return INVALID
    return UNKNOWN

这里有一个看起来很小、其实很重要的选择：不按错误文本里有没有某个词来判断。OpenHarness 的循环里有一处是这样写的：错误信息里出现 “connect” 或 “timeout”，就当成网络错误。这类判断会把“请求参数 timeout 必须为正数”这样的 400 错误误判成可重试的超时，然后浪费一整轮退避序列。labs 的测试 test_word_timeout_in_400_is_not_a_timeout 专门钉住这一点。

DSH 在这一点上做得更彻底：错误对象只携带事实（状态码、错误类型、服务端给的等待时间），不携带“是否可重试”的结论；可不可以重试由策略里的错误码列表决定。它还特意把“凭据无效”和“流正常结束但内容不完整”排除在默认可重试集合之外——前者重试没用，后者重试可能导致重复的副作用。

labs 的可重试集合与 DSH 的默认一致：

DEFAULT_RETRYABLE = frozenset({RATE_LIMIT, SERVER, TIMEOUT, TRANSPORT, EMPTY})

等多久：指数退避加随机抖动

等待时间要回答两个问题：给服务端多少恢复时间，以及怎样避免所有客户端在同一时刻重试。

第一个问题用指数退避解决：第一次等 0.5 秒，第二次 1 秒，然后 2、4、8 秒……每次翻倍，直到一个上限。这样短暂的抖动很快就能恢复，持续的故障也不会被频繁的请求压得更重。

第二个问题用随机抖动解决。故事里九个 agent 用的都是“等一秒”，所以它们的重试永远对齐在同一秒，形成一波一波的请求洪峰。指数退避本身也不能解决这个问题——九个 agent 第一次都等 0.5 秒、第二次都等 1 秒，仍然对齐。只有给每次等待加上随机偏移，才能把这些请求在时间上打散。

def backoff_delay(policy: RetryPolicy, retry: int, rand: Callable[[], float] = random.random) -> float:
    """第 retry 次重试（从 0 开始）之前要等多久。

    指数增长、先夹上限、再加对称抖动、最后再夹一次上限：
    抖动加在夹上限之后，否则到了上限附近所有客户端又会对齐到同一个值。
    """
    base = min(policy.max_delay, policy.initial_delay * (2 ** retry))
    factor = 1 + policy.jitter * (2 * rand() - 1)
    return min(policy.max_delay, base * factor)

注意顺序：先算指数值、夹到上限，再乘抖动因子，最后再夹一次上限。如果只在乘抖动之前夹上限，到了上限附近所有客户端的等待时间又会落在同一个值上，抖动在最需要它的时候失效了。DSH 的退避函数也是“两次夹上限”的写法，它的测试里能看到具体数值：第一次重试抖动到最小时是 500 × 0.9 = 450 毫秒，第二次抖动到最大时是 1000 × 1.1 = 1100 毫秒。

抖动的效果可以直接用测试量出来：100 个客户端在第三次重试时的等待时间，没有抖动时最晚和最早相差 0 秒，抖动比例 0.5 时相差超过 2 秒：

    def test_jitter_spreads_a_herd(self) -> None:
        import random as _random
        gen = _random.Random(7)
        policy = RetryPolicy(initial_delay=1, max_delay=10, jitter=0.5)
        no_jitter = RetryPolicy(initial_delay=1, max_delay=10, jitter=0)
        spread = herd_spread(backoff_delay(policy, 2, rand=gen.random) for _ in range(100))
        flat = herd_spread(backoff_delay(no_jitter, 2) for _ in range(100))
        self.assertEqual(flat, 0)
        self.assertGreater(spread, 2)

抖动比例取多大：DSH 默认 0.1，即等待时间在 ±10% 之间浮动。比例越大，打散得越开，但单个请求的等待时间也越不可预测。对于同一个服务、同时可能有大量客户端重试的场景（比如一个团队的所有 agent 共用一个 API 账号），可以取得更大。本章 labs 的默认值 0.1 和 DSH 一致，测试里的 0.5 只是为了让效果更明显。

试几次：三种上限与 Retry-After

只有次数上限是不够的。指数退避下，第 10 次重试之前要等 0.5 × 2⁹ ≈ 256 秒（如果没有单次上限的话）；10 次加起来超过 8 分钟。用户不会等那么久，循环外面的整轮预算（第 19 章）也不会允许。所以要有三种上限：

上限防的是什么labs 默认（教学示意）DSH 默认
次数无限重试5 次5 次（即最多 6 次请求）
单次等待指数增长失控10 秒10 秒
总等待次数没到上限，时间已经太久60 秒（由次数和单次上限间接限定）

计数的范围也要定清楚。DSH 的重试计数在每一步开始（step/start）和每一轮结束（turn/end）时清零。也就是说，一次模型调用最多重试 5 次，而不是整个会话一共只能重试 5 次——后者会让一个长会话在中途某次限流之后，再也没有重试的机会。

服务端返回的 Retry-After 头是另一个等待时间的来源。它的意思是“请过这么久再来”，比本地算出来的退避时间更有依据，应该优先采用。但它也可能很长——几分钟甚至几小时。这时有三种做法：

做法问题
照等循环卡住几小时，用户以为程序死了
缩短到上限再试等于无视服务端的限流要求，大概率继续被拒，还可能被更严厉地限流
放弃，交给上层当前这一步失败，但状态清楚，上层可以决定切换模型、提示用户或者停下来

labs 和 DSH 都选第三种。DSH 的规则写得很清楚：Retry-After 在单次上限以内就原样采用；超过上限时，普通模式放弃并交给下一个处理者，“永远重试”模式改用本地退避。

def plan_wait(policy: RetryPolicy, failure: Failure, retry: int, waited: float,
              rand: Callable[[], float] = random.random) -> tuple[float | None, str, str]:
    """决定下一次等多久。返回 (等待秒数, 来源, 放弃原因)；等待为 None 表示放弃。"""
    if failure.kind not in policy.retryable:
        return None, "", f"{failure.kind} 不可重试"
    if retry >= policy.max_retries:
        return None, "", f"已重试 {retry} 次，达到上限 {policy.max_retries}"
    if policy.honor_retry_after and failure.retry_after is not None:
        if failure.retry_after > policy.max_delay:
            # 服务端要求的等待超过了我们愿意等的上限：不要偷偷缩短它（那等于无视限流），
            # 也不要无条件照等（可能是几小时）。放弃，让上层决定。
            return None, "", f"服务端要求等待 {failure.retry_after:.0f}s，超过单次上限 {policy.max_delay:.0f}s"
        delay, source = failure.retry_after, "retry-after"
    else:
        delay, source = backoff_delay(policy, retry, rand), "backoff"
    if policy.max_total is not None and waited + delay > policy.max_total:
        return None, "", f"累计等待将达到 {waited + delay:.1f}s，超过总上限 {policy.max_total:.0f}s"
    return delay, source, ""

plan_wait 是一个纯函数：给定策略、失败、已重试次数和已等待时间，返回“等多久”或“为什么放弃”。把它从执行逻辑里拆出来，所有上限规则都可以不睡觉地测试。

重试和历史、日志的关系

故事里第三个问题——重试成功后模型说“我注意到之前的请求出了错”——来自一个常见的实现错误：失败尝试的输出被写进了历史。

流式响应失败时，往往已经收到了一部分内容：几句话、半个工具调用。如果这些内容被当作一条 assistant 消息提交，下一次请求就会带着它；如果错误信息被当作一条 user 消息或工具结果提交，模型会看到它并开始“解释”。两种情况都会让重试后的回复和第一次不一样，而且常常更糟。

规则是：失败的尝试不提交任何消息。重试时发出的请求，应该和第一次请求逐字节相同（这也让前缀缓存继续有效，见第 06 章）。DSH 有两条测试专门守这条规则：失败尝试收到的半截内容只留在那一步的日志块里，不提交成 assistant 消息，也不触发工具副作用；重试后的模型上下文里既没有错误诊断，也没有半截输出。

另一方面，重试本身要留下记录，只是不在对话历史里，而在会话日志里。DSH 的顺序是：

  1. 决定要重试，写一条 llm/retry 事件（第几次、等多久、原因）；
  2. 开始等待，等待可以被取消；
  3. 等待结束，写一条 llm/retry-started 事件；
  4. 发出请求。

先写日志再等待，有两个好处。一是进程在等待期间被杀，恢复时能从日志里知道“刚才在第 3 次重试”，重试计数不会丢（DSH 的重试计数就是从日志投影里读出来的）。二是排查问题时能看到完整的时间线：哪一步失败了几次、每次等了多久、最后为什么成功或放弃。重试的用量也要单独记账：第 05 章讲过，DSH 的用量账本会把一次重试记成一次新的计费调用。

labs 用一个回调来表达“等待之前”这个挂点：

def retry_call(
    fn: Callable[[], T],
    policy: RetryPolicy | None = None,
    *,
    sleep: Callable[[float], None] = time.sleep,
    rand: Callable[[], float] = random.random,
    should_stop: Callable[[], bool] = lambda: False,
    on_attempt: Callable[[Attempt], None] | None = None,
) -> RetryOutcome:
    """调用 fn，按策略重试。fn 失败时必须抛 Failure；其他异常视为 UNKNOWN、不重试。

    on_attempt 在等待**之前**调用：这是「先写日志再等待」的挂点。
    """
    policy = policy or RetryPolicy()
    attempts: list[Attempt] = []
    waited = 0.0
    retry = 0
    while True:
        if should_stop():
            return RetryOutcome(False, failure=Failure(CANCELLED), attempts=attempts,
                                gave_up_because="调用方取消")
        number = len(attempts) + 1
        try:
            value = fn()
        except Failure as failure:
            delay, source, why = plan_wait(policy, failure, retry, waited, rand)
            attempt = Attempt(number, failure.kind, delay or 0.0, source)
            attempts.append(attempt)
            if delay is None:
                return RetryOutcome(False, failure=failure, attempts=attempts, gave_up_because=why)
            if on_attempt is not None:
                on_attempt(attempt)
            sleep(delay)
            waited += delay
            retry += 1
            continue
        except Exception as exc:  # noqa: BLE001 — 没分类的异常一律不重试
            failure = Failure(UNKNOWN, f"{type(exc).__name__}: {exc}")
            attempts.append(Attempt(number, UNKNOWN))
            return RetryOutcome(False, failure=failure, attempts=attempts,
                                gave_up_because="未分类的异常不重试")
        attempts.append(Attempt(number, None))
        return RetryOutcome(True, value=value, attempts=attempts)

on_attempt 在 sleep 之前被调用，测试 test_on_attempt_called_before_sleep 断言事件顺序是“先记录、后等待”。真实实现里，这个回调应该写会话日志（第 04 章的 SessionLog）。

重试放在哪一层

重试可以放在三个位置，各有取舍：

位置例子优点缺点
HTTP 客户端OpenHarness 的 API 客户端对上层透明，实现简单看不到会话状态：没法写会话日志，没法和压缩、切换模型这类恢复手段协作
循环的扩展点DSH 的“模型请求失败”扩展点 + 重试插件能写日志、能和其他恢复逻辑排队（压缩先试，不行再重试），策略可以按提供方配置需要一个扩展点机制
调用方自己每个调用模型的地方写一个 for 循环最直观重复、不一致，迟早有一处漏掉上限或分类

DSH 的设计有一个值得注意的细节：它的扩展点允许多个处理者排队。“上下文超长”这类失败先交给压缩插件，压缩插件确实改写了历史才返回“重试”；“永远重试”模式的重试插件也会先让下游的专门恢复逻辑跑一遍，自己作为最后的兜底。重试不是唯一的恢复手段，而是恢复链上的一环。

labs 的 retry_call 是一个通用函数，可以包住第 00 章 harness.llm 里的任何一次模型调用。要把它接进第 01 章的循环，最小的改动是在 run_agent 调用 llm.complete 的地方换成 retry_call(lambda: llm.complete(...))，并让适配器把 HTTP 错误转成带分类的 Failure。

重试耗尽之后说什么

重试最终失败时，循环要停下来（第 01 章的 llm_error），并且给出一句话。这句话有两个读者：用户，以及下一次续跑时的模型。它应该包含：失败的类型、尝试了几次、一共等了多久、为什么停止。不应该包含：每一次失败的原始错误文本——那是日志的事。

def describe_for_model(outcome: RetryOutcome) -> str:
    """重试最终失败时给模型（或用户）看的一句话。不要把每次失败的原始错误都塞进去。"""
    if outcome.ok:
        return ""
    tried = len(outcome.attempts)
    kind = outcome.failure.kind if outcome.failure else UNKNOWN
    return (f"Error: 模型请求失败（{kind}），共尝试 {tried} 次，等待 {outcome.total_wait:.1f}s；"
            f"停止原因：{outcome.gave_up_because}")

“为什么停止”这一项尤其有用。“达到次数上限”和“服务端要求等待 3600 秒”是完全不同的情况：前者可能过一会儿就好了，后者说明配额用完了，需要换模型或者等到明天。用户看到这句话，才能决定下一步。

坑与失败案例

坑一：所有错误都重试

  • 触发条件：except Exception: retry()。
  • 后果：鉴权失败、参数错误、上下文超长被重试到次数用完，用户白等几十秒，最后看到的错误和第一次完全一样。上下文超长的情况下，每次重试还按全价计费。
  • 怎么防：按状态码和错误类型分类，只重试临时故障；“需要先改请求”的失败交给专门的恢复逻辑。

坑二：固定间隔，所有客户端同时重试

  • 触发条件：time.sleep(1)，或者没有抖动的指数退避。
  • 后果：服务端从故障中恢复的那一刻，迎来所有客户端同时发出的重试，又被压垮。故障时间被延长，所有人的重试都失败。
  • 怎么防：指数退避加随机抖动；抖动加在夹上限之后。

坑三：失败尝试的残留进了下一次请求

  • 触发条件：流式响应中途失败，已收到的半截内容或错误信息被提交进历史。
  • 后果：重试后的请求和第一次不同，模型开始解释“之前的错误”，或者在半截工具调用的基础上继续，产生重复的副作用。前缀缓存也会失效。
  • 怎么防：失败尝试不提交任何消息；重试时的请求和第一次逐字节相同。半截内容只留在会话日志里供排查。

坑四：Retry-After 被忽略或被偷偷缩短

  • 触发条件：服务端返回了 Retry-After，客户端仍按本地退避（通常更短）重试；或者把它截断到单次上限。
  • 后果：在服务端明确要求等待的时间内持续发请求，继续被拒，严重时触发更长时间的限流甚至封禁。
  • 怎么防：Retry-After 在上限以内就照等；超过上限就放弃并说明原因，让上层决定。

坑五：重试计数整个会话累计

  • 触发条件：重试计数器是会话级的，从不清零。
  • 后果：长会话在前面遇到几次限流之后，后面的任何一次临时故障都直接失败，而用户不知道为什么“它今天特别脆弱”。
  • 怎么防：重试预算按“一步”计算，每一步开始时清零。DSH 在 step/start 和 turn/end 时清零。

坑六：重试有副作用的调用

  • 触发条件：把通用的重试包装套在工具调用上，比如一个“创建 issue”或“发送消息”的工具。第一次请求其实成功了，只是响应在返回途中丢了。
  • 后果：issue 被创建两次，消息被发送两次。
  • 怎么防：重试默认只用于模型调用和只读操作；有副作用的调用要么带幂等键，要么不自动重试，把“结果未知”如实告诉模型（第 04 章 DSH 的恢复逻辑就是这样处理的：已开始但结果未落盘的调用，补一条“结果未知，有副作用的操作先核实”的错误结果）。

一句话取舍：把重试放在 HTTP 客户端里最省事，而且对大多数单用户场景够用；一旦需要“重试可恢复、可审计、能和压缩等恢复手段协作”，就需要 DSH 那样把它放到循环的扩展点上，用日志作为重试状态的唯一来源。

小结

  • 先分类：只重试临时故障。“需要先改请求”的失败交给压缩或调整参数，而不是重试。分类按状态码和错误类型，不按文本。
  • 等待时间用指数退避加随机抖动，抖动加在夹上限之后；Retry-After 优先，超过上限就放弃而不是缩短。
  • 三种上限：次数、单次、总等待；计数按步清零。
  • 失败尝试不提交任何消息，重试的请求和第一次相同；重试本身先写日志再等待。
  • 重试耗尽时，说清楚失败类型、尝试次数、等待时间和停止原因。
  • 有副作用的调用不要套通用重试。

重试解决了“失败了再来”，但还有一类问题它管不到：请求根本没有失败，只是一直没有回来。继续读：超时。

新的重试上线后，下一次限流来的时候，九个 agent 的日志不再整齐划一：第一次重试散落在 0.45 到 0.55 秒之间，第二次在 0.9 到 1.1 秒之间。厂商的限流在三分钟后解除，九个会话里有八个在限流解除后十秒内恢复，用户几乎没有察觉。第九个会话碰上的是“上下文超长”，它没有被重试，而是交给了压缩，压完一次就继续跑了。

林舟正高兴，客户那边打来电话：“你们的助手卡住了，转圈转了二十分钟。”

他打开那个会话的日志，最后一条记录是一个 run_tests 工具调用，开始时间是二十分钟前，没有结束时间，没有错误，没有重试。它没有失败，所以重试层什么都没做。它只是一直没有回来。

“重试管的是‘失败了怎么办’，”老唐说，“这个连失败都没失败。”
