第 24 章

可观测性与成本

主线故事 · 第 24 章（虚构）

林舟的三个问题，一个都没能从会话日志里直接读出来。

“这三十多次为什么这么慢”——日志里只有一行“工具结果，耗时”，模型调用和工具调用混在一起，看不出这一轮到底花在哪。
“钱具体花在哪”——账本上只有一个总数，主线和子代理混在一起，重试和压缩也混在一起。
“下一周表现变差怎么知道”——没有同一口径的历史数据，只有一堆 JSONL 文件。

老唐在白板上画了三个框：一个框里写“慢在哪”，一个写“贵在哪”，一个写“整体怎么样”。

“日志是给回放用的，它记的是事实，”他说，“这三个问题要的是另外一套东西：能算的、能比的时间段统计。”

他们做出来的东西不复杂。第一件，让每一段工作都有开始和结束，并且知道自己的父级——一轮是一个大段，模型调用和每个工具调用是它下面的小段，于是“这一轮的 90 秒里，78 秒花在那个跑测试的工具上”变成一句可以直接说出来的话。

第二件，把 token 用量按四个桶分开算钱：没命中的输入、输出、缓存读、缓存写——这四个价格差一个数量级，混在一起算，账永远是错的。然后按轮、按模型、按类型（主线、重试、子代理、压缩）分别汇总。第一次看到“这次任务的费用里有 40% 是子代理”，林舟把委派的工具集收窄了一轮。

第三件，也是他一开始没重视的：默认不要上报内容。他们原本把每一次工具的参数和输出都写进了 span，直到阿青问了一句“你们会把这些传到哪里去”。改成只记工具名、耗时、输出长度之后，排查问题确实麻烦了一点，但不再有任何一段用户代码离开这台机器。

这一章讲这三件事怎么做，以及一条容易忘的原则：观测代码自己出错时，不能让 agent 出错。

第 04 章的会话日志解决的是“能不能回放”：它记录发生过的每一个事实，按顺序、可重放、可恢复。那是正确性的基础设施。这一章处理的是另外三类问题：慢在哪（时间花在哪一段工作里）、贵在哪（token 花在哪一类请求上）、整体怎么样（成功率、轮数、重试次数这些跨会话的指标）。

这三类问题的共同点是：它们都需要对日志做聚合，而不是读某一条。日志是事实来源，而观测是把事实变成可以回答问题的结构。

先看全貌：可观测性与成本是什么、管哪些事

一句话：可观测性把每一次运行拆成有开始、有结束、有父子关系的片段（span），从中算出时间分布；成本把 token 用量按桶和单价换算成钱，按轮、按模型、按类型汇总。

问题靠什么回答典型的看不够就出事的场景
慢在哪span 树：一轮里模型调用、每个工具、等待审批各占多少以为在等模型，其实在等一个卡住的下游 API
贵在哪用量账本：按桶、按轮、按类型以为主线贵，其实一半的钱花在子代理和重试上
整体怎么样跨会话指标：成功率、平均轮数、重试率、熔断次数表现变差了两周才发现，而且说不清从哪天开始

这一层要管的事：

  • span 的结构：谁是谁的父级、哪些是叶子、为什么父级的耗时不能直接拿来排序。
  • 用量分桶：普通输入、输出、缓存读、缓存写，各有各的单价。
  • 成本归属：主线、重试、子代理、压缩分别记，否则最贵的部分永远看不见。
  • 导出：一行一条 JSON，接得上任何日志系统；失败不影响 agent。
  • 隐私：默认只记元信息（工具名、耗时、长度），不记参数和输出全文。
  • 跨会话指标：能按天、按版本比较。

四个决定，先给结论：

决定看起来省事的做法本章的结论
计时在每个操作前后打日志算差值用带父子关系的 span，嵌套自动成为子级；看“最慢”时只看叶子，父级包含子级没有信息量
成本总 token 乘以一个平均单价四个桶分别计价；未知模型直接报错，不按 0 算
重试 / 子代理 / 压缩混进主线的账里各自单独一类：这些是典型的隐形开销
记录内容把参数和输出都记下来，方便排查默认只记长度和工具名；要记内容必须显式打开，并且让用户知道

三个仓库在这一层分别是什么水平

DSH（TypeScript）：采集和上报严格分开：一个包负责从每一条会话事件里采集，另一个包提供上报后端接口，还有一个包实现 OpenTelemetry 上报。它有两条独立的通道——普通事件和会话日志——而且只引入了 OTel 的 logs SDK，没有引入 trace 和 metrics。默认行为是只在用户主动反馈之后才上传会话日志，有一个环境变量可以整体关掉上报。另外还有一个基于整份日志的统计投影包，输出会话数、轮数、墙钟时间这类数字。

它还有一个值得学的细节：流式事件（agent/assistant-stream）是发出去了但不写进会话日志的；headless 入口把它们打到 stderr，或者用 --json 逐行输出。也就是说，“给程序看的结构化事件”和“给人看的进度输出”分开，都不污染日志。

OpenHarness（Python）：有一个 usage 聚合器，模块自己的说明写得很清楚——它只是简单地累加 input/output token，不做成本核算，也不处理缓存字段。

learn-claude-code（教程）：打印每轮的 token 用量，仅此而已。

labs（本章要写的）：labs/harness/observability.py，span 树与导出、按桶计价与账本、跨会话指标，13 条测试。

span：把一轮拆开

一个问题：“这一轮用了 90 秒，时间花在哪？”日志能回答，但要你自己去算——把这一轮的所有事件按时间排开，找出空档。span 把这件事变成结构：每段工作有开始、结束、名字、属性，以及父 span。

class Tracer:
    """收集 span。嵌套靠一个栈：with tracer.span(...) 里面再开的 span 自动成为子 span。"""

    def __init__(self, clock: Clock = time.monotonic, *, keep_content: bool = False,
                 sink: Callable[[dict[str, Any]], None] | None = None) -> None:
        self.clock = clock
        self.keep_content = keep_content
        self.sink = sink
        self.spans: list[Span] = []
        self._stack: list[Span] = []
        self.sink_errors = 0
        self.trace_id = uuid.uuid4().hex[:16]

    @contextmanager
    def span(self, name: str, **attrs: Any) -> Iterator[Span]:
        parent = self._stack[-1].span_id if self._stack else None
        current = Span(name, uuid.uuid4().hex[:8], parent, self.clock(), attrs=redact(attrs, keep_content=self.keep_content))
        self._stack.append(current)
        try:
            yield current
        except BaseException as exc:
            current.status = "error"
            current.attrs["error"] = type(exc).__name__
            raise
        finally:
            current.end = self.clock()
            self._stack.pop()
            self.spans.append(current)
            self._emit(current)

    def _emit(self, span: Span) -> None:
        """导出一条 span。导出失败只计数，不影响 agent：观测不能改变行为。"""
        if self.sink is None:
            return
        try:
            self.sink(to_record(span, self.trace_id))
        except Exception:  # noqa: BLE001
            self.sink_errors += 1

    def children(self, span_id: str) -> list[Span]:
        return [s for s in self.spans if s.parent_id == span_id]

    def slowest(self, n: int = 3, *, leaf_only: bool = True) -> list[Span]:
        """最慢的几段工作。默认只看叶子 span：父 span 的耗时包含子 span，排在前面没有信息量。"""
        parents = {s.parent_id for s in self.spans}
        pool = [s for s in self.spans if not leaf_only or s.span_id not in parents]
        return sorted(pool, key=lambda s: s.duration, reverse=True)[:n]

用法就是普通的上下文管理器，嵌套的那一层自动成为子 span：

    def test_nested_spans_form_a_tree(self) -> None:
        clock = FakeClock()
        tracer = Tracer(clock)
        with tracer.span("turn") as turn:
            with tracer.span("model.call", model="big-model"):
                clock.advance(2)
            with tracer.span("tool.run_tests"):
                clock.advance(5)
        self.assertEqual(turn.duration, 7)
        self.assertEqual([s.name for s in tracer.children(turn.span_id)], ["model.call", "tool.run_tests"])

三个细节：

  • 异常会被记录并继续抛出。span 的 status 变成 error，属性里带上异常类型。它不吞异常——观测不能改变行为，这是本章第一节就要定下的规则。
  • 找“最慢”时只看叶子 span。父 span 的耗时包含子 span，永远排在前面；一条 turn 的 90 秒，背后是某个 tool.run_tests 的 78 秒。labs 的 slowest() 默认过滤掉有子 span 的那些：
    def slowest(self, n: int = 3, *, leaf_only: bool = True) -> list[Span]:
        """最慢的几段工作。默认只看叶子 span：父 span 的耗时包含子 span，排在前面没有信息量。"""
        parents = {s.parent_id for s in self.spans}
        pool = [s for s in self.spans if not leaf_only or s.span_id not in parents]
        return sorted(pool, key=lambda s: s.duration, reverse=True)[:n]
  • 计时用单调时钟（第 19 章坑六），和超时用的是同一个原则。

span 的名字要有约定，否则一年后你会在同一个面板上看到 model_call、model.call、llm 三种写法。labs 用的是 <类别>.<对象>：turn、model.call、tool.read_file、tool.run_tests、compaction、subagent。名字里带上具体对象（工具名），是为了让聚合有意义：把 tool.run_tests 的耗时加起来，就是这个项目里“跑测试”总共花了多久。

导出：失败不能影响 agent

span 要能导出去才有用——接日志系统、接追踪后端、或者最简单地写进一个 JSONL 文件。这里有一条容易被忽略的规则：导出失败只计数，不影响 agent。磁盘满了、上报端点不通、序列化出错，都不应该让一次正在进行的任务失败。

def _emit(self, span: Span) -> None:
    """导出一条 span。导出失败只计数，不影响 agent：观测不能改变行为。"""
    if self.sink is None:
        return
    try:
        self.sink(to_record(span, self.trace_id))
    except Exception:  # noqa: BLE001
        self.sink_errors += 1

测试里用一个总是抛异常的 sink，断言 span 照常收集、错误被计数：

    def test_sink_failure_does_not_break_agent(self) -> None:
        def broken_sink(record):
            raise OSError("disk full")

        tracer = Tracer(FakeClock(), sink=broken_sink)
        with tracer.span("turn"):
            pass
        self.assertEqual(tracer.sink_errors, 1)
        self.assertEqual(len(tracer.spans), 1)

导出的记录形状尽量贴近 OpenTelemetry 的约定（trace_id、span_id、parent_id、name、duration），这样以后换成真正的 OTel 导出器时，下游的查询不用重写。DSH 的做法更彻底：采集和上报分成不同的包，上报后端是一个可替换的接口，默认的后端只在用户反馈后上传，还有一个环境变量可以一次关掉全部上报。它的普通事件和会话日志走两条独立的通道——因为它们的用途不同，采样策略和保留时间也应该不同。

还有一件事值得在 span 之外单独做：给人看的进度输出。DSH 的流式帧事件不写日志，headless 入口把它们打到 stderr 或者用 --json 逐行输出。分开的好处是：日志保持结构化、可回放；“现在正在读第 7 个文件”这类进度只出现在终端里，不污染日志，也不进上下文。

成本：按桶算，按类型归属

第 05 章讲过用量有四个桶：普通输入、输出、缓存读、缓存写。第 06 章讲过缓存读的价格通常是普通输入的十分之一左右。这两件事合在一起，意味着一件事：用一个平均单价乘以总 token，算出来的钱可以差好几倍。

def cost_of(usage: Usage, model: str, prices: dict[str, dict[str, float]] = DEMO_PRICES) -> float:
    """按四个桶各自的单价算钱。未知模型直接报错：静默按 0 算会让账本看起来很便宜。"""
    if model not in prices:
        raise KeyError(f"没有模型 {model!r} 的价格；请在价格表里补上，不要按 0 计")
    p = prices[model]
    return (usage.input * p["input"] + usage.output * p["output"] +
            usage.cache_read * p["cache_read"] + usage.cache_write * p["cache_write"]) / 1_000_000

有一个细节是刻意的：未知模型直接报错。如果按 0 计费，一个模型名字写错的配置会让账单看起来非常便宜，而你不会发现。价格表本身应该来自配置，因为价格会变；labs 里的数字是教学示意。

比单价更容易做错的是归属。一次任务的花费通常分布在四类请求上：

类型什么时候产生典型占比（教学示意）怎么降
主线每一轮的模型调用最大头，但通常不是唯一的大头压缩（07）、卸载（08）、减少轮数
重试第 18 章的退避重试，每次重试都是一次完整计费调用故障期间可以到 30% 以上错误分类、熔断（20）
子代理第 23 章的每次委派批量任务里可能超过一半收窄工具集、收紧轮数、别为小任务开子代理
压缩第 07 章的摘要请求稳定在 5%–15%更好的压缩阈值、更省的摘要模型
@dataclass
class CostLedger:
    """按轮记账。重试、子代理、压缩各自单独一类：它们是最常见的「隐形开销」。"""

    prices: dict[str, dict[str, float]] = field(default_factory=lambda: dict(DEMO_PRICES))
    entries: list[LedgerEntry] = field(default_factory=list)
    budget: float | None = None

    def record(self, turn: int, model: str, usage: Usage, kind: str = "main") -> LedgerEntry:
        entry = LedgerEntry(turn, model, usage, cost_of(usage, model, self.prices), kind)
        self.entries.append(entry)
        return entry

    def total(self) -> float:
        return sum(e.cost for e in self.entries)

    def by(self, key: str) -> dict[Any, float]:
        out: dict[Any, float] = {}
        for e in self.entries:
            k = getattr(e, key)
            out[k] = out.get(k, 0.0) + e.cost
        return out

    def cache_hit_rate(self) -> float:
        """缓存命中占全部输入的比例。分母是 input + cache_read + cache_write。"""
        u = sum((e.usage for e in self.entries), Usage())
        denominator = u.input + u.cache_read + u.cache_write
        return u.cache_read / denominator if denominator else 0.0

    def over_budget(self) -> bool:
        return self.budget is not None and self.total() > self.budget

    def summary(self) -> str:
        parts = [f"共 ${self.total():.4f}"]
        kinds = self.by("kind")
        for kind in ("retry", "subagent", "compaction"):
            if kinds.get(kind):
                parts.append(f"{kind} ${kinds[kind]:.4f}")
        parts.append(f"缓存命中率 {self.cache_hit_rate():.0%}")
        if self.budget is not None:
            parts.append(f"预算 ${self.budget:.2f}" + ("（已超出）" if self.over_budget() else ""))
        return "，".join(parts)

账本按「轮」记，每一轮结束时打印一次增量。轮级的可见性比会话总数有用得多：当一个任务的总价是 4 美元时，你更想知道的是“第 17 轮花了 1.2 美元”，而不是“总共 4 美元”。第 17 轮发生了什么，日志里通常能直接看到——很可能是一次压缩之后历史变得很长，或者开了五个子代理。

cache_hit_rate() 是另一个值得长期盯的数字。缓存命中率的突然下降，通常意味着提示的前缀变了：工具列表顺序变了、系统提示里插进了时间戳、Skill 索引的顺序不稳定（第 22 章）。这个数字的下降会直接体现在账单上，而且很难从别的地方看出来。

跨会话指标

前面两类回答的是“这一次怎么样”。还有一类问题是“最近怎么样”：成功率有没有下降、平均轮数有没有变多、重试是不是变频繁了。这类问题需要同一口径的计数器，并且能按时间比较。

@dataclass
class Metrics:
    """计数器。跨会话聚合，用来看「整体怎么样」，而不是排查某一次。"""

    counters: dict[str, int] = field(default_factory=dict)

    def inc(self, name: str, by: int = 1) -> None:
        self.counters[name] = self.counters.get(name, 0) + by

    def rate(self, part: str, whole: str) -> float:
        total = self.counters.get(whole, 0)
        return self.counters.get(part, 0) / total if total else 0.0

值得长期跟踪的指标，按重要性排序：

指标它变差意味着什么
任务成功率（按停止原因分组）最直接的信号；按 max_turns、error_budget、llm_error 分开看，能直接指向原因
每任务平均轮数上升通常意味着工具或提示变差了，模型在打转
每任务平均花费和上一项一起看：轮数没变但花的钱变多，多半是缓存命中率掉了
缓存命中率前缀稳定性的体检指标（第 06 章）
重试率、熔断次数外部依赖的健康度（第 18、20 章）
工具错误率（按工具）哪个工具最常失败；一个工具错误率突然上升，通常是被改坏了
人工审批的同意率同意率接近 100% 说明审批疲劳（第 16 章）

“按停止原因分组”是其中最有价值的一条。一个笼统的“成功率 82%”几乎不提供信息；把它拆成“12% 撞上轮数上限、4% 撞上错误预算、2% 模型调用失败”，每一个都有明确的下手方向。

DSH 有一个基于整份日志的统计投影包，输出会话数、轮数、墙钟时间这类数字——它的实现方式和这里说的一样：不是另存一份指标，而是从日志投影出来。日志是唯一的事实来源，指标是可以随时重算的视图。这个选择的好处是：指标口径变了，可以对历史日志重新算一遍，而不需要等到改完才生效。

默认不记内容

观测最容易踩的坑不是技术问题，是隐私问题。开发阶段最方便的配置是“把参数和输出都记下来”，于是用户仓库里的代码、凭据、聊天内容全部进了 span，然后被上报到一个你未必控制得住的地方。

def redact(attrs: dict[str, Any], *, keep_content: bool = False) -> dict[str, Any]:
    """去掉可能包含用户内容的字段，只保留长度。keep_content=True 时原样保留（需要用户同意）。"""
    if keep_content:
        return dict(attrs)
    out: dict[str, Any] = {}
    for key, value in attrs.items():
        if any(s in key.lower() for s in SENSITIVE_KEYS):
            out[f"{key}_chars"] = len(str(value))
        else:
            out[key] = value
    return out

规则很简单：默认把可能含内容的字段换成长度。tool_input 变成 tool_input_chars: 128，tool（工具名）这种元信息原样保留。要记全文，必须显式打开，而且这件事应该让用户知道——DSH 的默认后端只在用户主动反馈后才上传会话日志，这是同一个思路的另一种实现。

“只记长度”会不会让排查变难？会。但换来的是：你可以放心地把 span 发到自己的日志服务上、可以放心地截图给别人看、可以让新人入职第一天就打开追踪。真要排查某一次具体的内容，会话日志里本来就有（第 04 章），而它是本地的、可控的。

还有一类字段需要小心：文件路径。它不算内容，但是元信息里隐私性最高的：“用户正在修哪个文件” “项目叫什么名字”都能从路径看出来。合理的折中是记录相对工作区的路径，或者只记顶层目录名。

观测接进组装版

第 25 章的 MiniHarness 里，span 是这样挂上去的：

位置span 名属性

注意 model.call 的 span 包住的是整个重试序列，而不是单次请求。这样“最慢的模型调用”回答的是“等模型这件事总共花了多久”，正好是用户感受到的时间。如果只包住单次请求，一次退避重试会表现为几个零散的慢 span，加不起来。

成本记账的位置在模型调用成功之后：拿到 usage，按四桶归一化（第 05 章的 normalize_usage），按类型记进账本。重试的用法要单独记一笔——DSH 的用量投影里，一次重试算作第二次计费调用；如果只记成功的那一次，账面会比实际低。

坑与失败案例

坑一：用平均单价算钱

  • 触发条件：总 token 乘以一个单价，不分桶。
  • 后果：命中缓存的场景下严重高估，长上下文场景下可能低估；两种误差都会让成本优化的方向判错。
  • 怎么防：四个桶分别计价；价格表来自配置；未知模型报错而不是按 0 算。

坑二：重试、子代理、压缩不单独记账

  • 触发条件：所有模型调用记在同一个池子里。
  • 后果：这三个最容易出问题的部分永远看不见。故事里“一半的钱花在子代理上”这件事，混账是看不出来的。
  • 怎么防：按类型记（主线 / 重试 / 子代理 / 压缩），每次汇总时分别列出。

坑三：观测代码把 agent 拖垮

  • 触发条件：每产生一条 span 就同步写文件、或者同步调用一个上报接口；上报接口超时没有上限。
  • 后果：一次任务变慢几十秒甚至卡住；磁盘写满让整个任务失败。
  • 怎么防：导出失败只计数；上报要异步、要有超时、要有队列上限，满了就丢 span 而不是阻塞真实工作。

坑四：span 里记了内容全文

  • 触发条件：默认把工具参数和输出写进 span，并且导到外部系统。
  • 后果：用户的代码和凭据离开了用户的机器；一次误操作就能把私密内容发给第三方；合规上说不清。
  • 怎么防：默认只记长度和元信息；要记内容显式打开并告知用户；路径这类元信息也要考虑。

坑五：只看总耗时，不看分布

  • 触发条件：监控上只有“平均任务耗时”这一个数字。
  • 后果：平均值被大量快任务拉低，掩盖了那 5% 卡住两分钟的任务；而用户抱怨的恰恰是后者。
  • 怎么防：看分位数，也看最慢的叶子 span；把“哪一类工作最慢”暴露出来。

坑六：指标口径变来变去

  • 触发条件：每一版实现都顺手改一下统计口径（这次算不算重试？子代理算不算一个任务？）。
  • 后果：趋势图看不出趋势，只看出改版；明明变好了，图上显示变差了。
  • 怎么防：指标从日志投影出来，口径定义写进代码注释；改口径时对历史日志重算，而不是让断层留在图上。

DSH 的两条通道（普通事件与会话日志）值得单独说一句：会话日志是完整、有序、可回放的事实；普通事件是给监控用的、可以采样、可以丢。混成一条通道的话，你要么丢掉可回放性，要么让监控数据里塞满不该上传的内容。分开之后，两者的保留策略和隐私策略都可以各自定。

小结

  • 日志回答“发生了什么”，span 回答“慢在哪”，账本回答“贵在哪”，计数器回答“最近怎么样”。
  • span 要有父子关系；找最慢时只看叶子；计时用单调时钟；名字要有约定，带上具体对象名。
  • 导出失败只计数，绝不影响 agent；上报要异步、有超时、有队列上限。
  • 成本按四个桶分别计价；未知模型报错；按主线 / 重试 / 子代理 / 压缩分别归属。缓存命中率是前缀稳定性的体检指标。
  • 指标从日志投影出来，口径写进代码；成功率按停止原因分组才有用。
  • 默认不记内容，只记长度和元信息；要记全文必须显式打开。

装上 span 之后，那三十多次“用了七八轮”的委派有了答案：其中二十二次的子代理时间几乎全花在等一个内部文档搜索的 MCP 调用上，每次二十多秒。问题不在子代理，在那个服务；他们把它挪到了本地缓存之后，那些委派从七八轮掉到了两三轮的等待。

账本上的发现更直接：主线占 41%，子代理占 38%，重试占 14%，压缩占 7%。重试那 14% 全部来自同一天的下午——那正是厂商故障、熔断器还没装上的那次。

阿青看到 span 里不记内容，问了一句他们能不能也拿到这个数据。老唐说可以，只记工具名和耗时，阿青那边拿去做他们自己的看板。

一切看起来都齐了。然后阿青问了一个谁都没想过的问题：“我周五下班前让它改一个模块，它改到一半，改了三个文件，测试还没跑。我关掉终端走了。周一早上我打开它，它知道自己在干什么吗？”

林舟打开那个会话的日志，答案是不会。历史在日志里，但新开一个会话时，橘子只收到一条空白的“你好”。

“你造了一堆部件，”老唐说，“现在把它们装成一台机器，然后回答阿青的问题。”
