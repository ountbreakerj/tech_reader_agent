第 3 章

执行管线与并发

主线故事 · 第 3 章（虚构）

林舟给橘子写了个调度员。第一版非常朴实：模型要几个工具，就按顺序一个一个跑。演示那天，橘子要读六个文件，屏幕上一条一条往外蹦，客户盯着看了四十几秒，问：“它在干嘛？”

林舟说：“在读文件。”客户说：“六个文件不能一起读吗。”

第二版改成了“并发一把梭”：一条回复里的调用全部同时发出去，谁先回来谁先入历史。效率上去了，当天下午就出了两件事。

第一件。橘子要改两个文件，回复里一次给了两个 edit_file，改的恰好是同一份 config.py。两个调用同时读到旧内容，各自改一处，各自写回去。后写的那个把前一个的修改整个盖掉了，而且两个调用都报告成功。

第二件。一批六个调用里有三个 read_file 和一个 run_tests。跑测试的花了 6 秒，三个读取加起来 0.2 秒，于是结果按完成时间排进了历史：先是读取，再是测试报告。模型看到的顺序和它自己请求的顺序不一样，把那份测试报告当成了“改之前的旧状态”，又白跑一轮。

老唐看完日志：“你那不是并发，是同时撒手。”

这一章要弄清楚三件事：一条回复里的多个调用，谁可以并排跑、谁必须挡在前面；结果按什么顺序交回去；其中一个失败、超时或者被取消时，同一批里的其他调用怎么办。正文里也会读到 OpenHarness 的写法——它选了“一把并发”这条路，注释和后果都值得看一遍。

模型的一条回复里可以带多个 tool_use 块。第 2 章讲了单个工具怎么注册、怎么被调用、失败怎么变成错误结果；这一章处理的是它们同时出现时的问题：谁可以一起跑，谁必须单独跑，结果按什么顺序交回给模型。

问题本身不复杂，但很容易做错。天真的实现是「多个就 gather 一把并发」，代码只有几行，代价是：两个都写同一个文件的调用会互相覆盖；一条慢命令会占满全部并发额度；先完成的调用先入历史，于是 tool_result 的顺序和模型请求的顺序对不上。这些都不是理论风险——OpenHarness 就选了这条路，本章会把它的注释和后果一起读一遍。

先看全貌：执行管线与并发是什么、管哪些事

一句话：模型一次说了好几个工具调用之后，由 harness 决定这些调用怎么排序、哪些能同时跑、结果按什么顺序写回历史。这一层也叫工具执行管线。

它管的是五个问题，本章按这个顺序讲：

  • 并行还是顺序：哪些调用可以一起跑，依据是工具自己上报的只读标记。
  • 并发上限：一条回复里有二十个调用，不能一次全开出去。
  • 提交流程：结果按模型请求的顺序写回，还是按完成时间写回。
  • 失败隔离：一个工具抛异常，同一批里的兄弟要不要一起作废。
  • 超时与取消：某一条卡住了怎么办；用户按下中断，还没开始的调用怎么收场。

四个决定，先给结论：

决定看起来省事的做法本章的结论
并发依据不确定就一起并发，快只有明确标成只读的才能并行；标记缺失、分类抛异常、参数不合法，一律当独占处理
结果顺序谁先完成谁先写必须按模型给出的调用顺序提交，哪怕后面的先跑完
一个失败整批作废、抛异常失败只属于那一条调用，变成错误结果；兄弟调用照常提交
取消没跑的调用直接丢掉没派发的调用要补一条错误结果，否则历史里会留下没有结果的调用

这一章主要对照谁

OpenHarness（Python）：本章的主要反面对照。它把头一批调用直接 gather 出去，注释里写了为什么，也写了代价。读它的价值在于看清“一把并发”会带来哪些后果，以及它的作者是怎么权衡的。

DSH（TypeScript）：生产级做法。有界滚动池、并发上限、按模型顺序提交、取消时补结果。这一层它做得最完整，第 01 章已经讲过它的池子，本章只补提交顺序和取消两处细节。

learn-claude-code：只有顺序 for 循环，没有并发，也没有取消。它的位置是“最小可用”，不作为本章的对照重点。

labs（本章要写的）：labs/harness/tool_runtime.py 里的分批、有界并发、按序提交、超时与取消，全部可以用 FakeLLM 和假工具跑出来。

一次回复里多个 tool_use：先分批，再执行

DSH 把这一步的调度逻辑单独放在一个文件里，模块注释开头就是那句判据（tool-calls.ts:2）：

原文：Exclusive calls form barriers; 独占调用形成屏障；并行调用进有界滚动池，启动前重新分类。

用一句话概括整个算法：按模型给出的顺序扫一遍调用，连续的「可并行」调用合成一批，每个「独占」调用单独成一批；批与批之间顺序执行，批内并发。 于是三批的结构自然地把屏障表达了出来——独占调用开始之前，前面批的结果必须全部提交完，它天然就是一道墙。

真正决定「可并行还是独占」的是一个由工具自己声明的分类器。DSH 的类型契约在 ToolExecutionMode：

index.ts:359

它的两条注释写明了语义：parallel 可以与兄弟调用重叠，exclusive 单独运行并形成排序屏障。分类本身在同一个文件的 executionMode() 里，只有 9 行，但这 9 行是整个并发策略的判据源：

executionMode(exec: ToolExecutionInput): ToolExecutionMode {
  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
  try {
    const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
    return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
  } catch {
    return { kind: 'exclusive' }
  }
}
index.ts:1309-1318

逐条读它的判据，全是"不满足就独占"：工具解析不出来（未知工具）→ 独占；没有声明 isConcurrencySafe → 独占；分类器返回的不是严格 true（返回 'yes'、返回真值对象都不算）→ 独占；分类器抛异常 → 独占；参数校验不过 → 独占。也就是说，并发是需要显式申请的特权，不是默认值。测试把这个契约钉得很细，execution-mode.spec.ts 里五条用例分别覆盖了显式 true、缺声明、未知工具、按参数返回 false、参数非法五种情形（第 28、40、51、56、69 行）。

还有两点值得注意：

  • 分类器是一元的（设计笔记 2026-07-10-parallel-tool-call-execution.md:19）：返回 true 是工具在承诺「我能和任何同样返回 true 的兄弟重叠」，调度器不会去比较两个调用、也不会证明它们的资源访问不冲突。所以「两个写同一个路径才冲突、写不同路径就安全」这类关系型规则表达不出来——这种调用的安全性取决于兄弟，就必须保持独占（同文件第 21 行）。
  • 分类是按调用参数做的，不是工具的静态属性。rw 这个工具在 mode: 'read' 时返回 parallel、在 mode: 'write' 时返回 exclusive（execution-mode.spec.ts:62 的分类器，第 65-66 行的断言）。

分批的循环在 executeToolCalls() 里。它的主体只有十几行，值得逐行看：

tool-calls.ts:85-100

两个关键点：

  1. const group = mode === 'parallel' ? planned.slice(next) : [first]（第 90 行）——分类结果是 parallel 时，把剩下的全部调用都交给这一批，而不是只取一段。真正的上限不靠切分实现，靠批内的滚动池（后文讲）。分类结果是独占时，只有这一个调用成批。
  2. 第 86 行的注释 Commit before classifying again so registry changes affect unstarted calls. 解释了为什么分类是惰性的：每一批提交完才去分类下一批。这不只是省一次调用——工具注册表可能被插件在运行中改动（第 2 章讲过注册是 effect、卸载即撤销），所以在「前面的批」执行期间新注册的独占工具，会影响尚未开始的调用。设计笔记把这条列为明确的后果（笔记:105）：工具注册是一次调度边界，注册表变更只影响还没启动的调用，已经进入池子的调用保留它进入时的调度决定。

把这两条合起来，就是本章要动手实现的东西。Python 版把 batch 切分单独抽成一个纯函数 plan_batches()，因为它最该被单独测试、也最容易被单独讲清楚：

def plan_batches(
    calls: Sequence[ToolCall],
    specs: dict[str, ToolSpec],
    max_parallel: int = DEFAULT_MAX_PARALLEL,
) -> list[list[str]]:
    """把一批调用切成按顺序执行的批次。纯函数，不做任何 I/O。

    规则（与 DSH tool-calls.ts 的 runGroup 分组一致）：
    - 连续的可并行调用合成一批，批内同时最多 max_parallel 个在跑；
    - 每个独占调用单独成一批，构成屏障：它开始前，前面的批必须全部提交完；
    - 未声明的工具按 fail-closed 归为独占（它仍会拿到一条 unknown tool 错误结果）。
    """
    batches: list[list[str]] = []
    current: list[str] = []
    for call in calls:
        spec = specs.get(call.name)
        parallel = spec.is_parallel if spec is not None else False
        if parallel:
            current.append(call.call_id)
            continue
        if current:
            batches.append(current)
            current = []
        batches.append([call.call_id])
    if current:
        batches.append(current)
    return batches

注意 specs.get() 返回 None 时（未知工具）parallel 是 False——这就是 fail-closed，和 DSH 的 if (!tool?.isConcurrencySafe) return { kind: 'exclusive' } 一个意思。测试里 test_undeclared_tool_fails_closed_to_exclusive 钉住了这条。

这个纯函数最有价值的性质是可以离线断言。模型给 [读, 写, 读]，答案就是三批 [[读], [写], [读]]；[写, 读, 读, 写, 读] 是 [[写], [读, 读], [写], [读]]——首尾的写在批的两端各自独立，不会和相邻的读混批。DSH 的测试 tool-calls.spec.ts:126 取了中间那个例子，断言恰好三组。

批内：有界滚动池与并发上限

分批只决定了「哪些能一起跑」，还没决定「同时最多跑几个」。DSH 的做法是有界滚动池：按模型顺序启动调用直到上限，每当一个调用结算就立刻补位。上限来自一条真实配置，不是示意值：

constants.ts:6

它被接进 agent-loop 插件的唯一一条循环相关配置里（index.ts:346，min(1)、默认 10）。设计笔记说明了它的边界语义（笔记:43）：独占批就是上限为 1 的池子，上限设成 1 就完全退化为串行。这条给了运维一个零风险的开关。

滚动池的循环条件本身就是注解（tool-calls.ts:200）：

tool-calls.ts:200

三个条件分别是：没有中止、还有没启动的、在跑的数量没到上限。补位之前还要再做一次分类（tool-calls.ts:205）：如果下一个调用已经变成非 parallel，就停止补位——它属于下一个独占批，得等当前池子排空。这正是设计笔记里的「惰性分类」（笔记:29）：每道屏障之后重新解析下一个调用，每次补充池子之前重新分类之后的所有调用。

Python 版把上限交给 ThreadPoolExecutor(max_workers=limit)——池子本身就是有界滚动池，提交多于上限的调用会排队等 worker 空出来，语义与 DSH 的 inFlight.size < maxParallelToolCalls 等价：

def execute_batch(
    call_ids: Sequence[str],
    calls: dict[str, ToolCall],
    specs: dict[str, ToolSpec],
    *,
    max_parallel: int = DEFAULT_MAX_PARALLEL,
    timeout: float | None = None,
    cancelled: Callable[[], bool] | None = None,
) -> list[CallResult]:
    """执行一批调用，按传入顺序返回结果（完成顺序不影响返回顺序）。

    并发上限就是线程池的 worker 数：同一时刻真在跑的工具体不超过 max_parallel，
    无论这一批有多少个调用（多出来的提交排队等额度）。每个工具自己的 timeout
    优先于本批的 timeout；超时、异常、未知工具都只是这一条调用变成 is_error，
    同批其他调用照常跑完、各自归因。
    """
    limit = max(1, min(int(max_parallel), len(call_ids)))
    is_cancelled = cancelled or (lambda: False)
    results: dict[str, CallResult] = {}

    def run(call: ToolCall) -> None:
        if is_cancelled():
            # 取消之后不再启动新的工具体；已经启动的会跑完，结果照样按序提交
            results[call.call_id] = cancelled_result(call)
            return
        spec = specs.get(call.name)
        # 计时从拿到 worker 额度、真正开始调工具体算起：排队不该算进工具自己的预算
        started = time.monotonic()
        try:
            if spec is None:
                raise LookupError(UNKNOWN_TOOL_RESULT.format(name=call.name))
            budget = timeout if spec.timeout is None else spec.timeout
            outcome = spec.fn(dict(call.args))
            if budget is not None and time.monotonic() - started > budget:
                raise ToolCallTimeout(f"tool {call.name!r} exceeded its {budget}s budget")
            results[call.call_id] = CallResult(
                call.call_id, call.name, str(outcome), False, started, time.monotonic(),
            )
        except Exception as exc:
            failed = error_result(call, exc)
            failed.started_at, failed.finished_at = started, time.monotonic()
            failed.timed_out = isinstance(exc, ToolCallTimeout)
            results[call.call_id] = failed

    with ThreadPoolExecutor(max_workers=limit) as pool:
        for call in (calls[cid] for cid in call_ids):
            pool.submit(run, call)
    # 结果按输入顺序取，不是按完成顺序
    return [results[cid] for cid in call_ids]

测试用高水位而不是「总耗时」来断言上限被遵守，因为耗时断言在负载机器上会抖：每个工具体进出时对计数器加减，test_peak_concurrency_never_exceeds_the_cap 提交 6 个各睡 30ms 的调用、上限 3，断言观察到的峰值恰好是 3，并且总耗时不少于两波（≥55ms）。上限设成 1 时峰值必须是 1——这条对应 DSH 的 maxParallelToolCalls: 1 is fully serial（tool-calls.spec.ts:311）。

结果按原序提交：提交顺序 ≠ 完成顺序

这是整章最容易做错、后果也最隐蔽的一条。

模型 API 对消息结构有硬要求：每个 tool_use 都必须有对应的 tool_result，而 DSH 的 DeepSeek 适配器在序列化时还额外校验「调用之后必须紧跟结果」，否则直接抛 INVALID_REQUEST（serialize.ts:141，第 1 章讲过消息格式）。并发执行会让结果完成顺序和请求顺序不一致，如果按完成顺序往历史里追加，顺序就乱了。

DSH 的解法是一个提交游标。它藏在一行注释里，但读起来是整段设计的核心：

tool-calls.ts:146

配套的是 commitReady()（第 147-161 行）：只要「按模型顺序的下一个槽位」还没有结果就什么都不做；一旦有了，就提交它、推进游标、再看下一个。于是先完成的快调用会被扣在槽位里，等前面慢的兄弟提交完才轮到它。同一个循环里，additionalContexts（工具或 post-execute 中间件产生的附加上下文）也在这一刻按模型顺序取出来交给下一步（第 157 行）——顺序一致的范围不止工具结果本身。

设计笔记第 47 行把这条讲得最清楚：已经启动的调用各占一个模型顺序槽位，只有游标所在的下一个槽位准备好了，才追加 tool/result 并收集 additionalContexts；实时界面可以显示多个正在进行的调用，但结果和工具后的上下文始终是模型顺序的。代价在后果一节（第 101 行）：有序提交会让快的调用被慢的兄弟挡住。DSH 接受了这个代价，因为回放和模型历史的顺序比 UI 的即时性重要。

DSH 的测试 tool-calls.spec.ts:230 专门构造了「后一个先结算」的场景：放行 c2，断言此刻 tool/result 事件数为 0（结果被扣住了），再放行 c1，最后两个结果的顺序是 [c1, c2]。

Python 版用最朴素的方式达成同一件事：并发跑完之后，按输入顺序从结果字典里取出来。关键在最后两行——return [results[cid] for cid in call_ids]，而不是 list(results.values())。字典的插入顺序在这里恰好是完成顺序，用它就会复现那个 bug；测试 test_reversed_completion_order_still_submits_in_input_order 让 c1/c2/c3 分别睡 60/30/5 毫秒，断言返回顺序仍是 c1、c2、c3，同时断言 results[2].finished_at < results[0].finished_at——即完成顺序确实反了，如果实现按完成顺序返回，这条断言会挂。

子进程型工具与纯计算工具的区别

到这里为止，把「工具」当成一个黑盒函数是够用的。但真实 harness 里工具分两类，它们对并发和取消的容忍度完全不同：一类是纯计算或纯读（读文件、grep、web fetch、列目录），另一类是要起子进程的（bash、跑测试、调外部命令）。后者有三个纯函数没有的性质：

  1. 它占用外部资源。并发 10 个 pytest 不是慢 10 倍，是可能一起 OOM 或一起超时。
  2. 它需要被真的杀掉。取消一个纯函数只是不再等它；取消一个子进程必须发信号，而且可能留下孤儿进程。
  3. 它的超时是外部强加的，不是自己算出来的。

这三条在源码里都留下了痕迹。先看 DSH 的声明策略——设计笔记第 63 行把哪些工具选择了并行摊开列了出来，读这一行基本就等于读 DSH 对"什么算安全"的完整判断：

原文：The shipped declarations are conservative. web search、web fetch、filesystem read、session-query 的 trace/read 工具、以及 subagent 委托选择并行；filesystem 的 write/edit、bash 工具、session-query 的 search 工具、workflow、用户交互、todo 变更、PTC 模式、Cordis 变更工具全部保持独占。bash 因为找不到可靠地按参数判断的分类器，保持独占。

一句「bash 保持独占」是整段里最重的设计判断：它不是忘了开，是明确承认判不出来而不开。同一个文件第 21 行给了理由的一般形式（笔记:21）：分类器无法表达「这些写只在路径不同时才安全」这类关系型规则，所以安全性取决于兄弟的调用必须保持独占。bash 的命令本身就是不透明的字符串，连一元判断都做不了。

顺带一个颇有意思的例外，第 65 行：filesystem read 依赖一个很窄的记录器例外——它的同步观察更新可能乱序落定，但 write/edit 在真正改文件前会重新检查观察到的版本号，所以过期的状态只会产生一个 FS_STALE_VERSION 错误，不会静默覆盖。这说明并发安全的（部分）保障可以下沉到工具自己的版本检查里，而不必全靠调度器串行化。

再看超时。DSH 没有把超时写进调度器，而是做成一个挂在 tools/execute 上的插件 timeout-policy：工具用 timeoutMs 声明预算，插件把预算变成对 exec.signal 的期限，到期后把结果替换成 TOOL_TIMEOUT 错误。它的模块注释说清了这种协作式超时的边界：

原文：A tool declares `timeoutMs` and promises to honor `exec.signal`……a tool that ignores or slowly handles cancellation can keep the caller waiting because the package cannot hard-stop downstream work.（包 README 的 Summary 一节）——工具必须真的理会取消信号，插件没法硬停下游工作。

OpenHarness 在这一点上选择了硬停。它的 bash 工具把超时上限直接写进参数模型（bash_tool.py:24），超时用 asyncio.wait_for 加 _terminate_process(..., force=True) 强制收尾（bash_tool.py:61-64）。两种取向各有代价：DSH 的方式不会和工具 promise 赛跑（不会「先返回超时、工具还在后台写文件」），但依赖工具配合；OpenHarness 的方式确定性强，但强杀可能留下半写状态。

至于「多个调用并发时哪个参数错了」这类归因问题，两边的做法都是让每条调用各自产生结果。DSH 里未知工具抛 ToolNotFoundError、工具本体异常转成错误结果（tools/src/index.ts:1585、1593），而且 pre-execute 的拒绝也是一个 isError 结果而不是中止整批——tool-calls.spec.ts:411 那条测试同时放了一个拒绝和一个抛异常的 pre-execute 钩子，断言两个都拿到结果、且 pre/post 观察顺序都是模型顺序。

取消、超时、以及一个失败时同批怎么办

三种异常路径要分开处理，混在一起会出系统性 bug。

一个工具失败：不牵连兄弟

这条两库的结论一致，但理由不同。DSH 在 pre/post-execute 层面就让失败变成结果：被拒绝的调用拿到 Error: <原因> 的 isError 结果回给模型（index.ts:1532），同批其他调用不受影响。OpenHarness 是在 asyncio.gather 上加了 return_exceptions=True，而它的注释把原因写得比源码更直白（query.py:853）：

原文：# Use return_exceptions=True so a single failing tool does not abandon its siblings as cancelled coroutines and leave the conversation with un-replied tool_use blocks (Anthropic's API rejects the next request on the session if any tool_use is missing a matching tool_result).

注意这个理由的链条：问题不在"某个工具失败了"，而在"失败会让兄弟协程被取消掉，于是留下没有结果的 tool_use，下一次请求被 API 直接拒绝"。 这是把并发和消息合法性绑在一起的典型例子——一个纯调度层面的选择，最后的表现形式是"整个会话在下一次请求时报错"。

超时：只是这一条调用失败

Python 版把超时处理成"这一条结果变成 is_error、且带 timed_out 标记"。两个细节是刻意的：

  • 计时从拿到 worker 额度之后开始，不是从提交开始。否则上限为 3、有 10 个调用时，排在后面的调用会因为"排队时间"被误判成超时。
  • timed_out 只认本模块自己抛的 ToolCallTimeout，不认 TimeoutError。工具体自己抛的 socket 超时是它的实现细节，应该原样归因为一次普通失败，不能被算成调度器超时。测试 test_a_tools_own_timeout_error_is_not_misattributed 钉住了这条区分。
  • 工具自己的预算优先于整批预算（budget = timeout if spec.timeout is None else spec.timeout），避免一个声明了长预算的工具被配置里的默认值误杀。

作为对照，OpenHarness 的单工具路径和并发路径的超时行为不一样：单个工具时异常被 try/except 就地接住（query.py:825-833），多个工具时靠 gather 的 return_exceptions，两条路径都正确、但代码是两份。

取消：没派发的调用要补结果

用户按下中断时，DSH 的处理有一处非常克制的地方：它先排空已启动的调用，再把它们的结果按顺序提交，最后才给未派发的调用补上合成结果。 补结果的原因写在文件头注释里（tool-calls.ts:8）：

原文：Abort records synthetic error results for skipped calls so replay stays valid.（中断时为跳过的调用记下合成错误结果，让回放仍然合法。）

补的内容是一条固定文案的 isError 结果（tool-calls.ts:253，Error: tool call aborted before dispatch），错误码是 ABORTED_BEFORE_DISPATCH。补结果的循环是第 241 行（tool-calls.ts:241），第 97 行是整批都被跳过的路径。DSH 的测试覆盖了两个取消窗口：信号在一批开始前就已经中止（tool-calls.spec.ts:459），以及中止发生在有序的 pre-execute 期间（第 490 行）——两种情况下都断言 tool/call 事件有两条、tool/result 也有两条，各自带 ABORTED_BEFORE_DISPATCH。

Python 版把这条不变式实现成 run_pipeline() 的尾部补齐：

def run_pipeline(
    calls: Sequence[ToolCall],
    specs: dict[str, ToolSpec],
    *,
    max_parallel: int = DEFAULT_MAX_PARALLEL,
    timeout: float | None = None,
    on_cancel: Callable[[], bool] | None = None,
) -> list[CallResult]:
    """按批次跑完一整步，返回与 calls 等长、且同序的结果列表。

    批次在开跑前一次规划好；发生取消后，当前批的结果照常提交，之后不再启动
    新批次，剩余未派发的调用各补一条「派发前已中止」的错误结果——这样模型的
    历史里不会留下没有 tool_result 的 tool_use。
    """
    planned = plan_batches(calls, specs, max_parallel)
    by_id = {call.call_id: call for call in calls}
    results: list[CallResult] = []

    for batch in planned:
        if on_cancel is not None and on_cancel():
            results.extend(cancelled_result(by_id[cid]) for cid in batch)
            continue
        results.extend(execute_batch(
            batch, by_id, specs,
            max_parallel=max_parallel, timeout=timeout, cancelled=on_cancel,
        ))
    return results

返回值的长度恒等于输入长度，是这个函数唯一需要保证的事。测试 test_cancel_before_dispatch_backfills_every_remaining_call 一开始就返回取消，断言 4 条结果全为 cancelled；test_cancel_mid_pipeline_commits_started_and_backfills_the_tail 让第一个（独占）调用执行期间置上取消标记，断言第一条不是 cancelled 而是正常内容、后两条是 cancelled——已派发的调用不会被丢弃。

还有一个更细的取消语义值得点出来。DSH 的 dispatchToolBody() 注释说：Cancellation never abandons the body: a started promise reaches quiescence before its outcome becomes `ABORTED`（index.ts:1567-1568）。也就是说，"取消"对已经开始的工具体不是一个中断，而是"结果被改写成中止"。而且这里区分了两个错误码：工具体已经跑过 → ABORTED，工具体没跑 → ABORTED_BEFORE_DISPATCH（index.ts:1560 就是这个二选一的判断）。这个区分对模型有意义：前者结果未知、可能需要核实，后者可以放心重试。

Python 版只用了后一种（CallResult.cancelled 表示"派发前已中止"），没有实现工具体跑到一半被改写成中止的分支——这是本章的简化，真实实现里这一支需要工具真的理会取消信号（见上一节 timeout-policy 的说明）。

按批次跑一整步

把三段拼起来需要一个驱动函数。DSH 里它是 executeToolCalls()（tool-calls.ts:60），签名里除了调用列表和信号，还有一个 acceptContext 回调——已经提交的结果里带的附加上下文要交回给循环，排进下一步的收件箱。

DSH 里这个队列叫 next-step：工具执行期间产生的上下文（包括工具自己调 ctx.inject() 塞的）排在下一步的输入里，而且排在工具结果之后。第 1 章讲过 inbox 的两个队列；这里的顺序约束是它的直接后果：tool-calls.ts:157 那一行的 acceptContext(context) 只会在结果已经追加之后被调用，所以模型看到的顺序永远是「工具结果 → 工具产生的上下文」，不会反过来。

坑与失败案例

坑 1：按完成顺序追加结果，tool_result 与 tool_use 对不上。 触发条件是并发段里有快有慢：先完成的写进历史，顺序就和模型请求的顺序不一致。后果分两极——模型可能把结果配错调用（它按位置理解结果），以及某些适配器直接拒绝请求：DSH 的 DeepSeek 序列化在本地就校验「调用之后必须紧跟结果」，不满足时抛 INVALID_REQUEST（serialize.ts:141）。DSH 的防法是提交游标（tool-calls.ts:146）；Python 版的防法是从输入顺序取结果，测试让完成顺序真的反过来验证它。

坑 2：并发写同一个文件。 两个 edit 作用在同一个文件上，各自读到旧内容、各自写回，后写的覆盖先写的。DSH 的防法是不让它发生：filesystem 的 write/edit 不声明 isConcurrencySafe，因此按 fail-closed 成为独占屏障，一个批里只会有一个。相对的，filesystem read 敢开并发，是因为它有版本号复查兜底（笔记:65）——写操作改文件前会重查观察到的版本，过期就报 FS_STALE_VERSION。这里有个更普遍的教训：即使两个调用都是独占、批内串行，批与批之间也没有文件锁，真正防止竞态的仍是工具自己的版本检查。

坑 3：并发上限不分类型，长命令占满全部额度。 如果上限是全局的、且 bash 也进了并行池，一个 5 分钟的构建会占住 10 个额度里的 1 个——还算好；但如果有 3 个长命令同时发出，剩下 7 个 fast read 得排队，或者反过来 10 个长命令把机器打满。DSH 的两道闸对此都有回应：上限只限制一个 agent 步骤内发起的调用（笔记:103 明确写了这条边界——provider 自己的配额控制不归它管），以及 bash 干脆不进并发池。tool-calls.ts:200 的滚动池则是另一层保护：额度一空出来立刻补位，不会出现"等整批完成再开下一批"的空转。

坑 4：取消后留下没有结果的 tool_use。 用户中断时，模型回复里已经发出的调用有一些永远不会被执行。如果只把整个 turn 标记成 aborted 就返回，历史里就留了没有 tool_result 的 tool_use——下一次请求被 API 拒绝。这一条 OpenHarness 的注释讲得最透（query.py:849-852：发 API 会拒绝带悬空 tool_use 的会话），DSH 的应对是给每个跳过的调用补一对 call/result（tool-calls.ts:8、97、241、253）。OpenHarness 自己则走另一条路：下一次提交前把悬空的调用整条消息删掉（messages.py:119、169）——补结果 vs 删调用，两种都能让请求合法，但前者保留了"这件事尝试过"的信息，模型下一轮知道该重试还是先核实，后者则把痕迹抹掉。

坑 5：把分类器当成纯函数用，但在里面做了 I/O。 DSH 的设计笔记明确要求分类器是同步纯函数，"只检查当前调用的参数，不做 I/O 或任何变更"（笔记:17）。一旦分类器里读文件或查网络，分类的结果就依赖于"它什么时候被调用"——而调度器是惰性分类、会调很多次的（每次补位前、每道屏障后）。同一份参数在不同时刻可能得到不同的分类，屏障就不确定了。DSH 甚至特意在方案对比里拒绝"有状态分类"（笔记:79），理由是它会在分类和派发之间制造空隙。

坑 6：把并发上限当成果延迟的免费午餐。 并行段确实会让兄弟调用重叠，但有序提交这条约束意味着整批的可见延迟等于最慢的那个调用。DSH 自己把这条列为明确的代价（第 101 行），Python 版的行为也一样：test_fast_later_call_does_not_jump_ahead_of_a_slow_earlier_one 里 c2 瞬间返回，但它在结果列表里仍然排在睡 60ms 的 c1 后面。想要 UI 上先看到 c2 的结果，就不能只靠一个有序结果列表，得让调用方订阅完成事件——这是 onProgress 一类的接口，本章的 labs 没有实现。

与前后章的衔接

本章的三个接口点是后面几章的地基：

  • 结果提交之后发生什么，由 第 1 章的循环判定接管——一批工具跑完，模型被再叫一次，看它还要不要继续。
  • 谁来决定一个调用该不该被允许执行（而不是并发与否），是 第 2 章的工具注册与守卫链；本章的 is_parallel 只回答"能不能和兄弟重叠"，不回答"该不该跑"。
  • CallResult 里那三个时间戳（started_at/finished_at）和 timed_out/cancelled 两个标记，是本章留给可观测性那一章的原始素材：DSH 把这些信息写进会话事件的每一条 tool/call 与 tool/result，本章的实现只把它们留在内存里。

本章的 labs 是 labs/harness/tool_runtime.py，测试在 labs/tests/test_tool_runtime.py：py -m unittest discover -s labs/tests -t labs -p "test_tool_runtime.py"，28 条用例、总计约 0.5 秒。相比 第 1 章的 loop.py，这一章只替换了 execute_tools() 那一个函数——循环的其余部分（停止条件、截断、错误预算）完全不变，这也是把调度单独抽出来的好处。
