第 9 章

短期与工作记忆

主线故事 · 第 9 章（虚构）

“存在自己嘴里”这件事，林舟回想起来其实一直存在，只是那次压缩把它放大了。橘子以前会在回复里自言自语：“好的，我已完成第 1 步，接下来做第 2 步。”看起来挺有条理，但这句话一旦被压掉，或者模型自作主张跳了一步，就没有任何东西能纠正它。

老唐的提议是把这份进度从“模型说的话”变成“模型写的文件”：

“给它一个 todo 工具。它每完成一项就更新一次。这份清单不归它管，归 harness 管——harness 负责存、负责校验，压缩的时候也保住它。”

当天下午就撞了一堵墙：橘子一次把三项都标成了“进行中”，还有一项在清单里出现了两次。第二天又出了新问题——它在清单里写了整整四十条，其中三十条是“读某个文件”。清单本身成了第二份上下文。

“所以这份东西也不能全信它，”老唐说，“得定规矩：同时只能有一项在进行中，重复的当场拒掉，条数太多就提醒它合并。”

这一章要弄清楚：工作记忆为什么做成工具、写进去的数据由谁负责校验、写入方式选整表覆盖还是增量补丁、压缩之后这份清单怎么保住。后半章还会讲到“先出计划、批准后再动手”这种更前置的用法。

模型在一个会话里需要记住两类东西。第一类是“刚才发生了什么”：用户说了什么、调了哪些工具、结果是什么。这就是消息历史，hx-01、hx-04、hx-07 已经讲过它的结构、日志和压缩。第二类是“我现在要干什么、做到哪一步了”：任务拆成了哪几步，哪一步正在做，哪几步做完了。这一章只讲第二类，也就是工作记忆。

工作记忆出问题的典型症状是：压缩之后模型不知道自己做到哪一步，把已经改好的文件又改一遍，或者干脆宣布完成，漏掉清单上后半截。下面看真实 harness 怎样把这份状态从“模型嘴里说说”变成“模型显式写入、harness 校验和保管”的数据。

先看全貌：短期与工作记忆是什么、管哪些事

一句话：模型在一个会话里要记住两类东西。第一类是“刚才发生了什么”，那就是消息历史；第二类是“我现在要干什么、做到哪一步了”，这就是工作记忆。本章只讲第二类。

工作记忆出问题的典型症状：压缩之后模型不知道自己做到哪一步，把已经改好的文件又改一遍，或者干脆宣布完成、漏掉清单后半截。

这一层要管的事：

  • 存在哪：为什么做成工具，而不是让模型在回复里说。
  • 怎么写：整表覆盖还是增量补丁，各有代价。
  • 校验：谁保证“同时只有一项在进行中”这类约束成立。
  • 回显：写完怎么让模型看到当前全貌。
  • 生命周期：压缩、崩溃恢复、陈旧提醒怎么处理这份状态。

四个决定，先给结论：

决定看起来省事的做法本章的结论
进度记在哪模型在回复里自己说写成结构化数据，由工具写入、harness 保管；嘴上的话会被压缩丢掉
写入方式每次提交整份清单整份覆盖好实现好校验，代价是模型容易漏抄；增量补丁省 token，但要有幂等和冲突规则
状态约束交给模型自觉同时只能有一项在进行中这类规则由 harness 校验，违反就拒绝并说明理由
压缩时和普通历史一起摘要工作记忆是“当前状态”，不能被摘要掉；要么保原样，要么在压完之后重建

DSH（TypeScript）：有独立的待办包和目标包，状态写进会话日志，回放时重建。想看清“工作记忆怎么和持久化配合”就读它。

OpenHarness（Python）：有会话记忆服务，另外它的计划模式是把“先出计划”做成一种权限模式，是本章后半段的主要参照。

labs（本章要写的）：labs/harness/working_memory.py，整表覆盖加校验，外加一个最小的计划闸门。

短期记忆的两层

记忆类教程里常见的几种“短期记忆”，放到真实 harness 里看，大多不是独立模块：

  • 对话缓冲（conversation buffer）：把所有消息原样存进一个列表，每次全发。amt 的实现就是一个 conversation_buffer_memory.ipynb:107。这就是每个 harness 的消息历史本身。
  • 滑动窗口：只留最近 N 条，amt 用 sliding_window_memory.ipynb:133。真实 harness 几乎不这样直接截断，因为按条数砍会拆开 tool_use 和它的结果（hx-07 第 3 节）。
  • token 缓冲：超出 token 预算就从最旧的开始弹出，见 token_buffer_memory.ipynb:262。它对应的是 harness 里的“按 token 阈值触发压缩”，只是真实实现会先剪工具结果、再摘要，而不是直接丢。
  • 工作记忆与上下文窗口管理：amt 12 号 notebook 把条目分成“钉住”和“可驱逐”两区，驱逐只在未钉住的条目里挑，见 working_memory_context_window.ipynb:317。“钉住区”的思路在真实 harness 里对应系统提示和运行时上下文（hx-06）：压缩不碰它们，每次请求重新拼。

amt 的 notebook 输出全部为空、从未运行过，这里只把它当示意代码读算法，不引用任何“运行结果”。

结论是：前三种在真实 harness 里都等于“消息历史 + 压缩”。真正需要单独做的，是模型主动维护的那份结构化状态：待办列表（todo）、计划（plan）、当前目标（goal）。它们和消息历史的区别在于写入者是模型自己，而且内容需要在压缩后继续成立。

为什么做成工具，而不是让模型在回复里写

模型完全可以在回复里写一段“接下来我要：1. … 2. … 3. …”。问题在于这段文字只是消息历史的一部分：harness 读不懂它，校验不了它，压缩时也不知道它比别的文字更重要。把它做成工具调用，换来三样东西：

  • 结构：参数有 schema，状态只能是枚举值，harness 能逐项校验，不合法就把错误还给模型。
  • 归属：写入发生在工具执行里，harness 知道“谁在第几轮写了什么”，可以落进会话日志，回放时重建。
  • 可观测：UI 能把它画成进度面板，harness 能据此判断“好久没更新了”。

两家做法都配了一句引导。lcc 写在系统提示里，code.py:58。DSH 写在工具描述里，而且明确说单步小任务不要用，index.ts:46。后者更值得学：一个不加限制的待办工具会被模型拿来给每个一句话的问题列清单，白白多一轮工具调用。

写入方式：整表覆盖还是增量 patch

三家都叫 todo_write，语义却不一样。

DSH 和 lcc 是整表覆盖：每次调用都传完整列表，替换上一版。DSH 在参数描述里把这一点写死，index.ts:142。整表覆盖的好处是状态永远自洽：模型这一刻认为的表就是 harness 存下的表，不存在“patch 打到一半”或者“两次 patch 顺序颠倒”的中间态。代价是每次都要重写全表，表长了就浪费输出 token，所以 lcc 把表长卡在 20 项。

OpenHarness 的 todo_write 是增量的，而且对象是磁盘上的 Markdown 文件：参数是单个 item、一个 checked 布尔和默认 TODO.md 的路径，todo_write_tool.py:15-17。新项追加，已有项勾掉，按整行文本匹配，todo_write_tool.py:35-43。它没有 in_progress，也不能删项。这更接近“项目里的 TODO 文件”，不是会话内的工作记忆。

校验：状态字段与“只能一个 in_progress”

DSH 的校验函数做三件事：内容去首尾空白后不能为空，内容不能重复，in_progress 的个数受部署配置约束。

function toTodoList(raw: { content: string; status: string }[], allowParallel: boolean): TodoItem[] {
  const todos: TodoItem[] = []
  const seen = new Set<string>()
  let active = 0
  for (const item of raw) {
    const content = item.content.trim()
    if (content.length === 0) {
      throw new Error('invalid todo: `content` must be a non-empty string')
    }
    if (seen.has(content)) {
      throw new Error(`invalid todos: duplicate content ${JSON.stringify(content)}`)
    }
    seen.add(content)
    if (item.status === 'in_progress') active++
    todos.push({ content, status: item.status as TodoItem['status'] })
  }
  if (!allowParallel && active > 1) {
    throw new Error(`invalid todos: at most one task may be in_progress (got ${active})`)
  }
  return todos
}

出处：index.ts:80-100。状态枚举不在这里查，而是由 schema 层先拦下（index.ts:151），未知字段也被 additionalProperties: false 拒绝。注释给了理由：日志里存的快照必须等于模型以为自己写的东西，形状不对就在边界上大声失败，不能悄悄压平。

“只能一个 in_progress”在 DSH 里不是固定规则，而是一个必填配置 index.ts:37。它连工具描述一起变：并行时要求“正在做的都标 in_progress”，单线时要求“恰好一个”（index.ts:63-67）。base 装配里取的是 true，cordis.patch.yml:432-435，因为 DSH 有子代理和后台命令，确实会有几件事同时在跑。lcc 则写死成一个，code.py:156-157。

labs 的版本把两家合在一起：整表、带 id、状态合法、最多 20 项，并行与否由参数决定。和 DSH 不同的一点是用 id 而不是 content 判重，因为后面的 diff 要按 id 对齐。

def validate_todos(raw: Any, *, allow_parallel: bool = False) -> list[TodoItem]:
    """把模型给的整张表校验成规范形式；任何一处不合法就整体拒绝，不做部分写入。"""
    if not isinstance(raw, list):
        raise TodoError("todos 必须是数组")
    if len(raw) > MAX_TODOS:
        raise TodoError(f"最多 {MAX_TODOS} 项，收到 {len(raw)} 项")
    items: list[TodoItem] = []
    seen: set[str] = set()
    for index, entry in enumerate(raw):
        if not isinstance(entry, dict):
            raise TodoError(f"todos[{index}] 必须是对象")
        item_id = str(entry.get("id", "")).strip()
        content = str(entry.get("content", "")).strip()
        status = entry.get("status")
        if not item_id or not content:
            raise TodoError(f"todos[{index}] 缺少 id 或 content")
        if item_id in seen:
            raise TodoError(f"todos[{index}] 的 id {item_id!r} 重复")
        if status not in STATUSES:
            raise TodoError(f"todos[{index}] 的状态 {status!r} 不合法，只能是 {', '.join(STATUSES)}")
        seen.add(item_id)
        items.append(TodoItem(item_id, content, status))
    active = sum(item.status == "in_progress" for item in items)
    if not allow_parallel and active > 1:
        raise TodoError(f"同时只能有一项 in_progress，收到 {active} 项")
    return items

写入后怎样回显给模型

两家的回显方式差别很大。lcc 在工具结果里返回整张表的渲染文本，code.py:159-160，每项一个 [ ] / [>] / [x] 标记，末尾带完成计数（code.py:162-177）。校验失败时返回 Error: … 字符串，code.py:183-189。

DSH 的工具值里带着整张表和计数，但真正渲染给模型的只有一行计数：

出处：index.ts:187-190。render 的返回值就是工具结果里模型看到的内容（tools/src/index.ts:1845）。理由并不难猜：表是模型自己刚写的，参数还在同一轮的 assistant 消息里，再原样回一遍就是重复花 token。表的完整内容走的是会话日志和 UI，不走工具结果。

labs 取了中间路线：返回一行 diff 摘要加整张表的渲染。diff 告诉模型“你这次实际改了什么”，在模型以为自己改了某项、实际却写错 id 的时候特别有用。渲染只取决于表的内容，不带时间戳、不重排，同样的表永远是同样的字节；工具结果在之后的请求里是历史前缀的一部分，字节稳定才不会破坏前缀缓存。

def render_todos(items: list[TodoItem]) -> str:
    """给模型看的紧凑文本。只取决于表的内容，不带时间戳、不重排：同一张表永远是同一串字节。"""
    if not items:
        return "(no todos)"
    lines = [f"{MARKERS[item.status]} {item.id}. {item.content}" for item in items]
    done = sum(item.status == "completed" for item in items)
    lines.append(f"({done}/{len(items)} completed)")
    return "\n".join(lines)
def diff_todos(old: list[TodoItem], new: list[TodoItem]) -> TodoDiff:
    """按 id 对齐两版表。用 id 而不是 content 对齐，模型改写措辞时不会被误判成「删一项加一项」。"""
    before = {item.id: item for item in old}
    after = {item.id: item for item in new}
    added = tuple(i for i in after if i not in before)
    removed = tuple(i for i in before if i not in after)
    changed = tuple(
        (i, before[i].status, after[i].status)
        for i in after
        if i in before and before[i].status != after[i].status
    )
    return TodoDiff(added, removed, changed)
    def write(self, raw: Any, *, round_no: int) -> str:
        """todo_write 工具的实现：校验 -> 整表替换 -> 返回工具结果文本。

        校验失败抛 TodoError，表和 last_write_round 都不动：失败的写入不算「更新过」。
        """
        new_items = validate_todos(raw, allow_parallel=self.allow_parallel)
        change = diff_todos(self.items, new_items)
        self.items = new_items
        self.last_write_round = round_no
        return f"Updated todos ({change.describe()})\n{render_todos(new_items)}"

生命周期：持久化、压缩与陈旧提醒

持久化：写进会话日志，回放时重建

DSH 的 execute 校验通过后，把整张表作为一条 todo/write 事件追加进会话日志，index.ts:199。“当前表”不是一个单独存的变量，而是对日志做折叠得到的投影：遇到 todo/write 就换成新表，遇到下一轮的 turn/start 就清空，index.ts:128-129。所以恢复会话、分叉会话都能拿回同一张表，不需要额外的存档格式。注意它在新一轮开始时清空：DSH 把待办当成“这一轮的进度面板”，不是跨轮的长期清单。

lcc 的表是模块级全局变量 code.py:180，只在内存里，进程退出就没了。OpenHarness 的表是工作目录里的 TODO.md，跨会话一直在，但它属于项目文件，不属于会话状态。

labs 的 TodoList.replay 照 DSH 的思路做：从事件列表里取最后一次 todo/write，与历史有没有被压缩无关。

压缩会不会把待办摘丢

这是工作记忆最容易出事的地方。表本身存在消息历史之外，可模型看到这张表的唯一途径，是历史里那次 todo_write 调用的参数和结果。压缩一旦把这段历史摘要掉，harness 手里的表还在，模型却不记得了。

OpenHarness 的压缩会额外生成几份“附件”带过压缩边界，其中有计划模式附件 compact/__init__.py:635-651，没有待办附件。不过它的待办在磁盘上，模型随时可以重新读 TODO.md。DSH 我在 packages/context、packages/compaction 下搜 todo，没找到把表重新放进模型上下文的代码；压缩后模型还记不记得进度，取决于摘要有没有写进去。其他包我没有逐个排查。

labs 的做法是让 harness 在压缩后把未完成的表重新放进运行时上下文（hx-06 讲的每次请求重新拼的那一段）。表全部完成就返回空串，不再占位置。

def todo_context(todo: TodoList) -> str:
    """压缩之后由 harness 重新放进运行时上下文的一段。表做完了就不再占位置。"""
    if not todo.has_open_items():
        return ""
    return "<current_todos>\n" + render_todos(todo.items) + "\n</current_todos>"

陈旧提醒

三家里只有 lcc 有提醒。它在主循环里数“连续多少轮没调 todo_write”，满 3 轮就往这一批工具结果后面追加一段 <reminder>Update your todos.</reminder>，然后计数归零，code.py:340-344。提醒放在工具结果所在的那条 user 消息里，不改系统提示，所以不破坏前缀缓存。

这个计数器有两个盲区：它从会话开头就开始数，模型从来没写过待办也会被催；它不看表里还有没有未完成项，全做完了照样催。DSH 的 packages/todo、packages/plan 里搜不到 remind；OpenHarness 的 engine 和压缩模块里也没有与待办相关的提醒。

labs 把提醒写成纯函数，补上这两个条件，并且从“上次写入”和“上次提醒”里较晚的那个算起，避免每轮都提醒。阈值 3 取自 lcc，属于教学示意。

def should_remind(
    last_write_round: int | None,
    current_round: int,
    has_open_items: bool,
    *,
    last_reminded_round: int | None = None,
    after: int = REMIND_AFTER_ROUNDS,
) -> bool:
    """本轮要不要附加「更新待办」提醒。

    - 从没写过待办：不提醒。单步任务本来就不需要待办，逼它写只会制造噪声。
    - 没有未完成项：不提醒。表已经做完，再催就是在催一份不存在的进度。
    - 否则从「上次写入」和「上次提醒」里较晚的那个算起，满 after 轮才提醒，避免每轮都提醒。
    """
    if last_write_round is None or not has_open_items:
        return False
    since = max(last_write_round, last_reminded_round if last_reminded_round is not None else last_write_round)
    return current_round - since >= after

计划模式：先出计划，批准后才动手

计划（plan）是工作记忆的另一种形态：不是边做边勾的清单，而是动手之前先交给用户审的一份方案。计划模式把这件事做成一个会话状态：进入后模型只调查、不修改；交出计划、用户批准后才回到正常模式。它和权限天然相关，但两家的接法完全相反。

OpenHarness：计划模式就是一种权限模式

OpenHarness 把 PLAN 直接定义成权限模式之一，modes.py:12。权限检查器先放行所有只读工具，再在计划模式下拒绝其余工具：

        # Read-only tools always allowed
        if is_read_only:
            return PermissionDecision(allowed=True, reason="read-only tools are allowed")

        # Plan mode: block mutating tools
        if self._settings.mode == PermissionMode.PLAN:
            return PermissionDecision(
                allowed=False,
                reason="Plan mode blocks mutating tools until the user exits plan mode",
            )

出处：checker.py:132-141。注意前面还有一条 FULL_AUTO 直接放行（checker.py:129-130），权限模式是单选的，计划模式和全自动不能同时成立。

进出计划模式的两个工具都只做一件事：改设置文件里的模式再存盘，enter_plan_mode_tool.py:25-27、exit_plan_mode_tool.py:25-27。退出工具没有参数，不带计划，也不问用户。它没有覆写 is_read_only，按基类默认算写工具（base.py:46-49），所以计划模式下它会被上面那条规则拦下，实际能退出的只有用户的 /plan off 命令。

还有一点要留意：检查器在构造时就把设置对象存下了（checker.py:60-61）。/plan 命令改完设置会立刻重建检查器（registry.py:1509-1512），模型调用 enter_plan_mode 只改了磁盘。在我核对过的普通消息路径里（runtime.py:732-746），只有 UI 状态从磁盘刷新（runtime.py:575），检查器没有重建，要等下一次带 refresh_runtime 的命令（runtime.py:660-661）。也就是说，模型自己进入计划模式后，界面显示已在计划模式，写工具却可能还没被拦。这一点我没有实际运行验证。

压缩时，OpenHarness 根据工具元数据里记下的模式（query.py:451-454）生成一份“计划模式仍然有效”的附件带过边界（compact/__init__.py:636-645）。附件里预留了 plan_summary，但在 src/openharness 里没有任何代码写这个字段，这一行实际上永远不会出现。

DSH：计划模式只是一段提示，限制交给权限系统

DSH 的模块注释开门见山：计划模式是记在日志里的协作状态，激活时往每次请求里加一段部署方提供的指导；沙箱模式和审批策略各自独立执行限制，不读也不写计划状态，plan-mode/src/index.ts:6。指导段只在计划模式激活时返回非空文本，index.ts:216-224。

退出工具 exit_plan_mode 则管得很严：

  • 不在计划模式时调用直接报错，index.ts:301-303。
  • 参数必须是以 # 标题开头的 Markdown 计划，index.ts:304-306。
  • 通过用户提问通道把计划交给用户，选项只有“Approve”和“Keep planning”，index.ts:313-322。
  • 没选 Approve 就抛错，用户的反馈原样进工具结果，模型改了再交，index.ts:349-354。
  • 批准后不立刻切换，而是记一个待生效意图，到下一步开始前才写进日志，index.ts:355-359。同一批里剩下的工具调用仍按计划模式的指导执行。

退出工具在非计划模式下也一直注册着，进出计划模式只改提示段、不改工具目录，index.ts:15-17。工具目录在请求前缀里，频繁增删工具会让前缀缓存失效（hx-06）。

lcc 的 s05 没有计划模式。

labs：一个最小的计划闸门

labs 取 OpenHarness 的“只读放行、其余拦截”，加上 DSH 的“退出要带计划、要用户批准”，并且像 DSH 一样让出口在计划模式里始终可调，否则模型永远交不出计划。它和 hx-13、hx-16 的权限检查是串联关系：闸门放行之后，还要再过一遍正常的权限规则。

@dataclass
class PlanGate:
    """计划模式闸门：只读阶段先出计划，用户批准后才放开写工具。"""

    read_only_tools: frozenset[str]
    active: bool = False

    def check(self, tool_name: str) -> GateDecision:
        if not self.active:
            return GateDecision(True, "not in plan mode")
        if tool_name in self.read_only_tools:
            return GateDecision(True, f"{tool_name} is read-only")
        if tool_name == EXIT_PLAN_TOOL:
            # 出口本身不是只读工具，但必须放行，否则模型永远提交不了计划
            return GateDecision(True, "the exit tool must stay callable in plan mode")
        return GateDecision(False, f"plan mode blocks {tool_name}; present the plan with {EXIT_PLAN_TOOL} first")

    def enter(self) -> None:
        self.active = True

    def exit(self, plan: str, *, approved_by_user: bool) -> GateDecision:
        """退出需要两样东西：一份像样的计划，和用户的批准。模型自己说「我觉得可以了」不算。"""
        if not self.active:
            return GateDecision(False, "not in plan mode")
        if not plan.strip().startswith("#"):
            return GateDecision(False, "the plan must be markdown starting with a # heading")
        if not approved_by_user:
            return GateDecision(False, "the user chose to keep planning; revise and present again")
        self.active = False
        return GateDecision(True, "plan approved; write tools are allowed from the next step")

坑与失败案例

  1. 压缩后模型忘了进度。触发：长会话触发压缩，摘要没把最近一次 todo_write 的内容写进去。后果：harness 手里的表还在，模型却从头规划，或者重复做已完成的步骤。OpenHarness 只给计划模式做了压缩附件（compact/__init__.py:635-651），待办靠磁盘上的 TODO.md 兜底；DSH 里我没找到压缩后重新注入待办的代码。labs 的 todo_context 是一种补法。
  2. 提醒变成噪声。触发：单步任务里模型从没写过待办，或者表早已全部完成。后果：lcc 照样每 3 轮塞一次 Update your todos.（code.py:340-344），模型为了消除提醒去写一张没用的表，白白消耗轮次和 token。lcc 没防；labs 的 should_remind 在这两种情况下都返回 False。
  3. 按文本匹配的增量更新会重复。触发：OpenHarness 的 todo_write 勾选时，模型把条目文字稍微改了一点（比如多了个句号）。后果：unchecked_line in existing 匹配失败，走到追加分支，表里同时出现一条没勾的旧项和一条已勾的新项（todo_write_tool.py:35-43）。没有 id，也没有校验，源码没防。整表覆盖的做法（DSH、lcc、labs）天然没有这个问题。
  4. 模型自己进入计划模式，闸门却没关上。触发：模型调用 OpenHarness 的 enter_plan_mode。后果：设置文件和界面都显示计划模式，但检查器是构造时存下的设置（checker.py:60-61），要等下一次带 refresh_runtime 的命令才重建（runtime.py:660-661），这期间写工具仍按旧模式判定。这是我读代码得出的结论，没有实际运行验证。labs 的 PlanGate 把状态和判定放在同一个对象里，不存在两份状态不同步。
  5. 计划模式出口被自己拦住。触发：OpenHarness 计划模式下模型调用 exit_plan_mode。后果：它不是只读工具（base.py:46-49），被计划模式规则直接拒绝、不弹确认（checker.py:137-141），模型只能请用户敲 /plan off。唯一的例外是用户把它写进 allowed_tools（checker.py:105），而这个列表默认为空。注意这条坑只在检查器本身处于计划模式时出现，比如用户用 /plan on 进入；如果是模型自己调 enter_plan_mode 进去的，按上一条，检查器还停在默认模式，退出工具只会走普通的写工具确认。这样能防止模型擅自退出，代价是模型没有提交计划、请求批准的通道。DSH 把出口做成必须带计划、必须经用户批准的工具（index.ts:313-322），两头都照顾到了。
