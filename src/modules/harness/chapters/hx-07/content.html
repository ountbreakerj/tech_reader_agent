第 7 章

上下文压缩

主线故事 · 第 7 章（虚构）

四万行 grep 结果把窗口塞满之后，老唐给的方案很直接：“太长了就压一压，把老的内容总结成几句话。”

林舟的第一版实现只有十几行：数一下历史里有几万字符，超了就从中间切一半，前面和后面各留一段。上线当天中午就炸了——厂商直接返回 400。他把请求抓下来一看，切割点正好落在一对“模型要求读文件”和“工具返回文件内容”的中间，于是历史里留下了一个没有结果的调用。这正是第 01 章那三次翻车里的第一次，换了个地方又犯了一遍。

第二版改成了“从末尾往前保留最近 N 轮，其余交给模型总结”。这次请求能发出去了，但下午橘子犯了个更隐蔽的错：它把用户早上那句“别动公开接口，我下周要给别人用”总结丢了。压完之后它高高兴兴地改了一个公开函数的签名，测试全过，用户第二天才发现。

“第一版是切错地方，第二版是丢错东西。”老唐在纸上画了一条线，“压可以，但你得知道每一次压会丢什么，丢的东西谁能兜住。”

这一章要弄清楚：压缩有哪几个等级、什么时候该用贵的、切割点为什么不能落在调用和它的结果之间、摘要里必须保留什么，以及压失败时怎么收场。

一个 agent 会话的上下文只涨不落。系统提示、工具 schema、用户消息、模型的每次回复、每个工具的执行结果，全都往里加。工具结果的增长速度还特别快：一次 cat 一个大文件就是几千行，一次 grep 递归扫仓库可能就是几万个字符。真跑起来，一个几十轮的会话把窗口塞满，往往只花十几分钟。

塞满之后只有两条路：请求被厂商拒绝（CONTEXT_WINDOW_EXCEEDED 这类错误），或者你自己动手把历史折小。这一章讲第二条路——而且重点不在「怎么折」，在于折的时候会丢掉什么，以及怎么保证丢完之后那份历史还能发出去。

压缩是本章唯一一个「会主动删除模型已经看到过的信息」的部件。别的部件出错，最多是慢一点、贵一点；这个部件出错，模型会开始忘事、重复劳动、甚至按照它自己编出来的摘要去改一个不存在的接口。所以这一章有相当一部分篇幅花在两件事上：切分点（不能拆开工具调用和它的结果），以及熔断（失败之后不要每轮都重试）。

先看全貌：上下文压缩是什么、管哪些事

一句话：历史只涨不落，总有塞满的一天。压缩就是在不破坏历史合法性的前提下，把旧内容折小——而且重点不在“怎么折”，在于折的时候会丢什么。

这一层要管的事：

  • 分级：便宜但丢得多的手段先用，不够再动用贵的手段。
  • 触发：什么时候压。信号来自第 05 章的预算。
  • 切割点：从哪里切开历史，绝不能拆开一次调用和它的结果。
  • 摘要内容：用户的约束、当前目标、已经做过的决定，这些不能丢。
  • 失败兜底：压缩本身是一次模型请求，它也可能失败或超长。
  • 记录：压过之后，历史里要留下痕迹，让回放和排查还能对得上。

四个决定，先给结论：

决定看起来省事的做法本章的结论
怎么压截掉中间一段，或者从头裁多级级联：先做低损失的处理（清理、卸载），不够再摘要；摘要付出的是一次额外请求
切割点按字符数就近切只能切在完整的一轮之间；拆开调用与结果的配对，下次请求直接 400
摘要保留什么让模型“总结一下前面”显式要求保留目标、约束和已完成的决定；这些丢了模型会做出错误判断
压完怎么记录就地改掉历史，不留痕在日志里表达“这里发生过一次压缩”，回放和排查才说得清

三个仓库在这一层分别是什么水平

DSH（TypeScript）：做得最系统。packages/compaction 里是多级级联，有明确的触发原因，而且压缩是在日志层表达的——压过之后历史仍然能从日志重建。本章主要参考。

OpenHarness（Python）：services/compact/__init__.py 是一套能用的实现，还有一个手动触发的入口；触发时机上偏保守。适合对照“手动压”和“自动压”的差别。

learn-claude-code（Python，教程）：s08 讲上下文压缩，三十来行的最小版本。读它是为了先看清“摘要压”这条主线的骨架。

labs（本章要写的）：labs/harness/compaction.py，分级处理、切割点检查、摘要保留项、熔断，都能单独跑测试。

压缩丢掉的是什么

先把损失说清楚，因为它决定了级联的顺序。hx-04 建立的立场是「日志是事实来源，消息列表只是投影」——压缩动的是投影，不是日志。DSH 里这一点是显式的：真正从历史里消失的那些节点，官方的说法叫 shadowed（被遮蔽），它们的事件仍然原样躺在日志里，只是不再进入「下一次请求要发什么」这份推导结果。

所以压缩的损失可以精确地分类：

  • 可恢复的损失：事件还在日志里，只是不参与本轮请求。DSH 的日志里因此能查到「第 200 条工具结果原本是什么」，即使界面和模型都看不到它了。这也是为什么压缩在 DSH 里是一次日志事件（compaction/start / compaction/summary / compaction/end），而不是对历史数组的原地修改。
  • 不可恢复的损失：摘要。原始文本被一段更短的话替换，那句话里没有的信息就永久没了——除非你把它写进了摘要。（后面 第 4 节会讲摘要提示词要盯住哪几项。）
  • 看起来可恢复、实际很贵的损失：把工具结果的正文换成占位符。原始输出可能在磁盘上（hx-08 的 spill），但让模型拿回来要走一次工具调用，上下文里又要放回来——通常等于把这轮省下的空间还回去。

结论是：越便宜的压缩，丢掉的东西越少；越贵的压缩，丢掉的越多。级联的顺序不是性能优化，是损失控制。

判断标准：一次压缩值不值得做，看它「省下的 token」和「模型下一次做决定时缺不缺这块信息」。工具结果的正文往往几千 token 里只有几行有用——这是最值得先砍的。用户那句「不要改公开接口」可能只有十几个 token，砍掉它省不下什么，却可能让整个任务跑偏。

多级级联：先便宜低损失，再贵高损失

DSH 的装配把三个粒度不同的压缩件放在同一棵插件树上，它们的触发条件和代价完全不同。

第 0 级是 spill（hx-08 的主题）：工具结果超过 maxInlineTokens 就落盘，上下文里只留预览和路径。这一步发生在工具结果进入历史的时刻，不是事后补救，所以它不叫压缩。第 1 级是 tool-result-pruner：把已经落在历史里的超长工具结果掐头去尾，中间换成一个标记。第 2 级是 compaction-basic：调一次模型，把一段历史折成一条摘要。

装配顺序写在 base 补丁里，注释把意图说得直接：

    # runs, preserving the model-visible result within the configured budget.
    - id: tool-result-pruner
      name: '@deepseek-ai/dsh-compaction-tool-result-pruner'
      config:
        thresholdChars: 8192
        headChars: 4096
        tailChars: 1024

出处：cordis.patch.yml:418-425。配置值本身也是取舍：超过 8192 字符才动，保留开头 4096、结尾 1024。开头保留得多——错误信息、命令回显、文件头通常在开头；结尾保留得少，因为「最后几行」在长输出里往往是进度提示或没有任何信息量的收尾。

裁剪必须保证结果一定变小，否则这一步就变成了纯粹的噪声。pruner 在配置解析阶段就把这件事算死：

我们自己这一级的实现读起来就是这个思路的 Python 版：只换正文，别的一律不动。

def prune_tool_results(
    messages: Messages,
    *,
    keep_recent: int = 4,
    min_chars: int = PRUNE_MIN_CHARS,
) -> tuple[Messages, int]:
    """第 1 级：把较旧的工具结果正文换成占位符。返回 ``(新历史, 省下的字符数)``。

    只动 ``tool_result.content``。``tool_use_id``、``is_error``、消息顺序、
    消息条数全部不变——所以这一步之后的历史一定还是合法的，
    压缩本身不可能成为一次 400 的原因。（工具结果的 ``is_error`` 为真时默认跳过：
    错误信息往往是模型下一步做决定的依据，见「坑与失败案例」。）

    ``keep_recent`` 数的是**工具结果条数**，不是消息条数。
    OpenHarness 的 ``microcompact_messages`` 是同一个口径
    （``all_ids[-keep_recent:]`` 对应这里的最后 N 条结果），并且照样会
    ``keep_recent = max(1, ...)`` 强制至少留一条。我们也保证至少留一条。
    """
    positions: list[tuple[int, int, dict[str, Any]]] = []
    for message_index, message in enumerate(messages):
        content = message.get("content")
        if not isinstance(content, list):
            continue
        for block_index, block in enumerate(content):
            if isinstance(block, dict) and block.get("type") == "tool_result":
                positions.append((message_index, block_index, block))

    keep = max(1, keep_recent)
    if len(positions) <= keep:
        return messages, 0

    pruned = _deep_copy(messages)
    saved = 0
    for message_index, block_index, block in positions[:-keep]:
        text = block.get("content")
        if not isinstance(text, str) or len(text) < min_chars:
            continue
        if PRUNE_SKIP_ERRORS and block.get("is_error"):
            continue
        target = pruned[message_index]["content"][block_index]
        before = len(pruned[message_index]["content"][block_index]["content"])
        target["content"] = PRUNE_PLACEHOLDER.format(n=before)
        saved += before - len(target["content"])
    if saved <= 0:
        return messages, 0
    return pruned, saved

注意 positions[:-keep] 只裁旧的那些，而且统计口径是工具结果条数而不是消息条数。OpenHarness 的微压缩是同一个口径，并且同样强制至少留一条：keep_recent = max(1, keep_recent) # never clear ALL results（compact/__init__.py:821）。那条注释值得记住：永远不要清掉全部结果。最近一次工具输出几乎总是模型下一步的依据。

第 2 级只在第 1 级不够时才动

DSH 的 compactIfNeeded 把两级的先后写成了显式顺序：先让 pruner 落一轮（它不调模型），重新量一次，只有仍然超阈值才去选摘要范围。

出处：index.ts:321-327。prune 是通过 this.ctx.get('toolResultPruner') 拿到的可选服务（index.ts:292），注释写明「Pruning is optional so compaction-basic remains independently composable」——压缩的每一级都是一个可独立卸载的插件，缺了哪一级就少一层，不是坏掉。这个设计对写 harness 的人有直接借鉴：级联的每一级都做成独立的、可取可不取的部件，联调时能单独关掉一层看效果。

我们的控制器是同一个结构：

    def level_for(self, used: int) -> str:
        """按当前用量决定这次该做哪一级（还没考虑是否能成功）。"""
        ratio = used / self.budget
        if ratio >= self.summarize_ratio:
            return "summarize"
        if ratio >= self.prune_ratio:
            return "prune"
        return "none"

这里的 0.8 和 0.95 是教学示意值——DSH 的同名默认是 0.8（config.ts:20），但它只有一个压力阈值，第二个「必须压」的档位是我们为了看清级联加的。真实部署里这两个数应当来自按模型配置的窗口，而不是常量（hx-05）。

    def compact_once(self, messages: Messages) -> CompactionResult:
        """跑一次级联。失败时原样返回历史，并记账到熔断器。

        关键约定：**返回的历史永远可以直接发给 API**——第一条是 user、
        tool_use 与 tool_result 配对完整。压缩不许把一份合法历史变成非法历史，
        否则错误会从「上下文太长」变成「请求格式错误」，更难查也更难恢复。
        """
        before = _chars(messages)
        if self.breaker.open:
            return CompactionResult(
                messages=messages,
                level="none",
                chars_before=before,
                chars_after=before,
                notes=[f"熔断已打开（连续失败 {self.breaker.failures} 次），本轮跳过压缩"],
            )
        level = self.level_for(self.count(messages))
        if level == "none":
            return CompactionResult(messages, "none", before, before, ["用量在阈值以下"])

        notes: list[str] = []
        failed = False
        try:
            pruned, saved = prune_tool_results(messages, keep_recent=self.keep_results)
        except CompactionError as exc:
            self.breaker.record_failure(exc)
            return CompactionResult(messages, "none", before, before, [f"第 1 级失败：{exc}"])
        if saved > 0:
            notes.append(f"第 1 级裁剪旧工具结果，省 {saved} 字符")
            messages = pruned
            achieved = "prune"
        else:
            notes.append("第 1 级无可裁剪内容")
            achieved = "none"

        # 做第 1 级之后重新量一次：便宜的那一级可能已经够了，
        # 那就不要再花一次模型调用去做贵的那个。DSH 里的顺序也是这个：
        # 先让 toolResultPruner 落一轮（它不调模型），只有重新量完仍然超阈值，
        # 才去选摘要范围（compaction-basic/src/index.ts 的 compactIfNeeded）。
        if level == "summarize" and self.level_for(self.count(messages)) == "summarize":
            if self.summarize is None:
                notes.append("需要第 2 级但没有传入 summarize，止步于第 1 级")
            else:
                try:
                    folded = summarize_prefix(
                        messages, self.summarize, keep_recent=self.keep_recent
                    )
                except CompactionError as exc:
                    self.breaker.record_failure(exc)
                    notes.append(f"第 2 级失败：{exc}")
                    failed = True
                else:
                    if len(folded) < len(messages):
                        notes.append(f"第 2 级摘要，历史 {len(messages)} → {len(folded)} 条")
                        messages = folded
                        achieved = "summarize"
                    else:
                        notes.append("第 2 级没有缩短历史，按失败处理")
                        self.breaker.record_failure("summary did not shrink history")
                        failed = True

        after = _chars(messages)
        if after < before:
            if not failed:
                self.breaker.record_success()
        elif not failed:
            # 做完了却一点没省下来：算「压缩无效」，同样进熔断计数，
            # 否则下一轮会一模一样地再来一次。
            # （已经记过一次的失败不重复计数：阈值说的是「连续失败几次」，
            # 不是「失败有几条理由」。）
            self.breaker.record_failure("compaction did not reduce the history")
        return CompactionResult(messages, achieved, before, after, notes)

两个阈值给的是「大概要做什么」，实际做到哪一级由 achieved 记录。这两个值经常不一样，而且不一样才是正常的：阈值说「该做第 2 级」，但第 1 级裁剪之后重新量一次发现已经够了，于是不做摘要——省下一次模型调用，也少丢一块信息。反过来，第 2 级失败了，achieved 停在 prune，历史仍然比原来小，turn 可以继续。

DSH 的两个触发原因

自动压缩有两个入口，语义不同。一个挂在 step 边界上按压力触发：

      if (!signal.aborted) {
        try {
          const result = await this.compactIfNeeded(agent, 'pressure', signal)
          if (result !== null) logResult(result, 'step pressure')
        } catch (error: unknown) {

出处：index.ts:158-166。压力触发的阈值默认在窗口的 80%（config.ts:20），并且还要额外扣掉一个 headroom（默认 65536 token，config.ts:75）。实际阈值取「比例」和「窗口减去输出预留再减去余量」两个约束里更紧的那个（config.ts:191-194）——这个算法和 hx-05 里 budget.py 的 pressure_budget 是同一件事。

另一个挂在请求失败上，只在厂商明确回报「上下文超长」时动作：

      if (failure.code !== CONTEXT_WINDOW_EXCEEDED_CODE || signal.aborted) return next()
      this.overflowAgents.set(agent.session, agent)
      const target = routedTarget(agent.session)
      if (target === undefined) return next()
      const policy = resolveTargetPolicy(this.config, target)
      const retries = this.overflowRetries.get(agent) ?? 0
      if (retries >= policy.maxOverflowRetries) return next()

出处：index.ts:194-200。三件事挤在这五行里，每件都值得抄。

  • 只处理那一种错误码。CONTEXT_WINDOW_EXCEEDED_CODE 自己是常量（error.ts:25），不拿错误文本做字符串匹配。上下文超长是一个可判定的状态，不是一个需要猜的句子。
  • 超长恢复次数有上限。maxOverflowRetries 默认 1（config.ts:106）：同一个 Agent 连续两次因为超长被打回来，就放手让错误往上走。没有这个上限，压缩无效的历史会变成一个死循环。
  • 按「有效路由」取策略。阈值和保留量挂在具体 provider/model 上，因为不同模型的窗口不同。

压缩有进展时它才返回 retry：

切分点：为什么不能拆开 tool_use 和它的结果

这是本章唯一一个「做错了会立刻 400」的点，所以它值得单独一节。

工具调用在历史里的形状是一个请求加一个回答：助手发出一条带 tool_use 的消息，紧接着有一条带 tool_result 的消息（hx-03 讲的是把这套配对真正执行起来的管线）。把历史切成「旧的要压缩」和「最近的原样保留」两段时，如果切点正好落在这一对中间，就会得到两种都不合法的东西：旧的那段以一个没人回答的工具调用结尾，新的那段以一个没有对应调用的结果开头。多数 API 会直接拒绝这份历史。

所以「哪些位置可以切」是一个必须精确计算的问题，不能靠数消息条数。DSH 把它实现成一份缓存的前缀平衡表。

/** Return how one surface event changes the in-progress tool-call count. */
function eventDelta(event: SessionEvent): number {
  switch (event.type) {
    case 'assistant/message':
      return event.data.message.content.filter(block => block.type === 'tool-call').length
    case 'tool/result':
      return -1
    default:
      return 0
  }
}

出处：tool-pairing.ts:28-38。一条助手消息可能同时发起多个工具调用，所以增量是「数出来的」，不是 1。这个细节容易漏：一轮里模型并发调三个工具，按 +1 算就会在第 2、3 个结果处把计数压成负数。

折的过程就是把这个增量累加，把「计数为 0」的每个位置记下来：

  const processed = cache.cutBalanced.length - 1
  const tail = seqs.slice(processed)
  // Validate the unseen tail before mutating the live cache, so a corrupt
  // append cannot leave a partially advanced state behind.
  const pendingCuts: boolean[] = []
  let inProgressToolCalls = cache.inProgressToolCalls
  for (const seq of tail) {
    // oxlint-disable-next-line typescript/no-deprecated -- Existing Session history read; migration deferred.
    const event = session.eventAt(seq)
    if (event === undefined || event.seq !== seq) {
      throw new Error(`tool-pairing balance: surface seq ${seq} has no matching session event (corrupt surface)`)
    }
    inProgressToolCalls += eventDelta(event)
    if (inProgressToolCalls < 0) {
      throw new Error(`tool-pairing balance: tool/result at surface seq ${seq} has no matching tool-call (corrupt surface)`)
    }
    pendingCuts.push(inProgressToolCalls === 0)
  }

出处：tool-pairing.ts:46-63。三个工程点：

  • 增量缓存。每追加几条事件就只折新增的那几条（seqs.slice(processed)），不从头发起。历史越长，这一点越重要——每次压缩都重扫整份 history 是 O(n²) 的。
  • 先在临时数组里攒，全部合法才写回缓存。注释的理由是「a corrupt append cannot leave a partially advanced state behind」：坏数据进来时缓存要么完全没动，要么整体重建，不会停在一个半新半旧的状态。
  • 计数变负就抛错。这是「历史本身坏了」的信号（一个结果找不到它对应的调用），不是「这次不能压缩」。

这份平衡表有两种用法，对应两个函数的差别：toolPairingBalancedBefore 判断某个位置之前可不可以切（tool-pairing.ts:112），toolPairingBalancedAfter 判断之后（tool-pairing.ts:124）。一次替换同时需要这两个检查：范围的两端都必须是平衡边界，否则砍出来的旧段在开头或结尾挂着半个工具调用。

选范围时它从保留区的起点往回退，退到第一个平衡位置为止：

  while (keepFromIdx > firstIdx) {
    // oxlint-disable-next-line typescript/no-non-null-assertion
    if (toolPairingBalancedBefore(session, surfaceNodes[keepFromIdx]!)) break
    keepFromIdx -= 1
  }
  if (keepFromIdx <= firstIdx) return null

出处：region.ts:143-148。往回退的方向意味着「保留区变大一点、被压缩的部分小一点」——宁可这次少压一点，也不拆开配对。退到没有可用的平衡点就返回 null（不压缩），而不是硬压。

我们的实现把同一件事写成一次前缀扫描加一次回退：

def balance_flags(messages: Sequence[dict[str, Any]]) -> list[bool]:
    """返回每一处切分点是否「配对平衡」。

    结果比消息数多一个：``flags[i]`` 是第 i 条消息**之前**的切分点，
    ``flags[len(messages)]`` 是整段历史末尾的切分点。

    做法是一次前缀扫描：助手消息里的每个 ``tool_use`` 记 +1，每条 ``tool_result``
    记 -1，计数为 0 的位置才算平衡。这和 DSH 的做法一致
    （``packages/compaction/compaction/src/tool-pairing.ts``：它维护的
    ``inProgressToolCalls`` 就是同一个量，只是它按 surface 增量缓存）。

    注意 flags 里出现 False 完全正常：一轮工具调用进行到一半时，
    前缀里就有一个没人回答的 tool_use。只有**整段末尾**那个 flag 必须是 True。
    所以下面两个问题要分开回答：

    * 「哪些位置可以切」——看 :func:`safe_cut_index`；
    * 「这份历史配对完整吗」——只看最后一个 flag，见 :func:`pairing_complete`。

    遇到「结果比调用多」（计数变负）直接抛错：这样的历史本身就不合法，
    压缩只会把坏数据带到更远的地方。
    """
    flags = [True]
    pending = 0
    for message in messages:
        pending += _pending_delta(message)
        if pending < 0:
            raise CompactionError(
                "历史里出现了没有对应 tool_use 的 tool_result：这份历史本身不合法，"
                "先修数据再压缩"
            )
        flags.append(pending == 0)
    return flags
def _pending_delta(message: dict[str, Any]) -> int:
    """一条消息让「未配对的工具调用」计数变化多少。"""
    content = message.get("content")
    if not isinstance(content, list):
        return 0
    delta = 0
    for block in content:
        if not isinstance(block, dict):
            continue
        kind = block.get("type")
        if kind == "tool_use":
            delta += 1
        elif kind == "tool_result":
            delta -= 1
    return delta
def safe_cut_index(messages: Sequence[dict[str, Any]], desired: int) -> int:
    """把切分点从 ``desired`` 往回挪到最近的平衡位置。

    返回的是「新历史从这里开始」的下标：0 表示不切，``len(messages)`` 表示全切。
    只往后挪不往前挪是刻意的——往后挪会切掉更少的旧内容，但这比拆开配对安全。
    一条 ``desired`` 之前全是未配对调用的历史（例如整段历史都在一对调用之间）
    就退回 0，宁可这次不压。

    DSH 在选范围时做的是同一件事，但方向相反：它从保留区的起点往前退
    （``packages/compaction/compaction-basic/src/region.ts`` 里的
    ``while (keepFromIdx > firstIdx)`` 循环，每退一步查一次
    ``toolPairingBalancedBefore``）。两边都在挪同一个点，差别只是
    「保住最近 K 条」还是「多切一点旧内容」。
    """
    flags = balance_flags(messages)
    index = min(max(desired, 0), len(messages))
    while index > 0 and not flags[index]:
        index -= 1
    return index

两个实现有处值得注意的差别。DSH 的 flags 是缓存的增量折，我们的每次都从头扫（代价 O(n)，换来「绝不可能分叉」——和 hx-04 里 foldRequestHeader 的取舍一样）。另外我们的 safe_cut_index 只往回挪，而 _pending_delta 对助手消息是数块数、对结果消息减一——和 eventDelta 一一对应。

这里还有一个容易踩的细节：flags 里出现 False 是正常的，一轮工具调用跑到一半时前缀里就有个没人回答的调用。所以「能不能切」看的是某个 flags[i]，而「这份历史合法吗」只看最后一个 flag。我们把后者单独拆成一个函数，就是为了不让这两件事混在一个 all() 里：

def pairing_complete(messages: Sequence[dict[str, Any]]) -> bool:
    """整段历史的 tool_use 与 tool_result 是否全部配平。

    这就是「能不能直接发给 API」在配对维度上的答案。切分点的 flags 里可以有
    False（正跑到一半的轮次），但末尾的 flag 必须是 True——否则就是
    「助手调了工具，结果没回来」，多数 API 会直接拒这份历史。
    """
    try:
        return balance_flags(messages)[-1]
    except CompactionError:
        return False
def history_is_valid(messages: Messages) -> bool:
    """校验一份历史能不能直接发给 API。

    两条规则，都是客户端可以自己检查、不必等 400 的：

    * 第一条消息必须是 user（多数 API 要求，Anthropic 的 Messages 协议尤其如此）；
    * 整段历史的 tool_use / tool_result 必须配平（见 :func:`pairing_complete`），
      配对完整即可——中间某一轮跑到一半不算问题。

    这个函数是本章的「断言」：任何压缩步骤之后都该能过。写测试时先拿它过滤，
    比拿真 API 试错便宜得多。
    """
    if not messages:
        return False
    if messages[0].get("role") != "user":
        return False
    return pairing_complete(messages) and _starts_with_real_user_content(messages)

def _split_preserving_tool_pairs(
    messages: list[ConversationMessage],
    *,
    preserve_recent: int,
) -> tuple[list[ConversationMessage], list[ConversationMessage]]:
    """Split older/newer segments without cutting through a tool_use/result pair.

    The preserved segment is also sanitized so trailing orphan tool_use blocks
    never survive the compaction boundary.
    """

    if len(messages) <= preserve_recent:
        return [], sanitize_conversation_messages(list(messages))

    split_index = max(0, len(messages) - preserve_recent)
    while split_index > 0 and _boundary_crosses_tool_pair(messages[split_index - 1], messages[split_index]):
        split_index -= 1

    older = list(messages[:split_index])
    newer = sanitize_conversation_messages(list(messages[split_index:]))
    return older, newer

摘要要保留什么

第 2 级的成品是一段话。这段话里没写的，模型就真的不知道了。所以提示词不是文案问题，是接口问题——它决定了「压缩后模型还能不能继续干活」。

DSH 的摘要指令是一份固定结构，八个小节，逐条列出来（summarizer.ts:32-67）：任务与意图、关键技术概念、文件与代码、错误与修复、未完成的活、当前在做的事、下一步、关键上下文。旁边还跟着几条硬规则，其中两条特别值得抄：保留精确的文件路径、命令、错误字符串、标识符和数值；以及不要在摘要里提到「这次总结」或「上下文被压缩过」（原话是「Do NOT mention this summarization request or that the context was compacted.」）。后面这条不是为了好看：如果摘要里写了「我们刚才压缩了上下文」，模型会在下一步先跟你聊压缩这回事，白花一轮。

更值得学的是摘要请求本身怎么发出去的。它没有另起一个「你是摘要器」的 system prompt，而是把原会话的系统提示、工具 schema、以及被压缩的那段消息原样拼在前面，只在最后追一条压缩指令，并对齐 KV cache：

  const messages: RequestMessage[] = [
    ...input.messages,
    deepFreeze({
      role: 'user',
      content: [{ type: 'text', text: COMPACTION_INSTRUCTION }],
    }),
  ]

出处：summarizer.ts:145-151，input 的构造在 region.ts:544-563（系统头 + 被遮蔽段逐条投影成消息）。注释给出的理由是「Keeping the conversation's own system prompt, tools, and message prefix in front of it makes the auxiliary call a genuine prefix of the last routed request, so the provider's KV cache is reused instead of invalidated」——摘要请求成了上一次请求的真前缀，缓存能接着用（hx-06 讲这套前缀稳定性）。代价是摘要请求本身可能非常大；收益是它便宜得多，而且模型是在真的那段对话上做总结，不需要重新解释背景。

我们这边的摘要指令保留了同一批要点：

SUMMARY_INSTRUCTION = """把上面的对话折成一份可以继续干活的检查点。用要点罗列，不要散文。
必须覆盖下面每一项，没有内容就写「无」，不要省略任何一节：

- 任务目标：用户最初提出、后来又补充过的目标，逐字保留关键约束
- 已做的决定：选了什么、为什么这么选、被否决的方案
- 改动过的文件：精确路径，以及每个文件为什么重要
- 错误与修复：出过的错、怎么解决的、用户因此提过什么意见
- 未完成的事：用户明确要求但还没做完的
- 下一步：对齐最近一次请求的单个动作

注意最后一句「不要提及这次总结动作，也不要复述这份说明本身」——这是从上面那条规则直接搬过来的。

摘要落地时必须包装成一条 user 消息，这有两个理由：多数 API 要求历史以 user 开头（摘要替换的正是开头那段），以及模型对 user 消息里的内容更倾向于当成「既定事实」而不是「自己说过的话」。DSH 给这条消息加了固定前言，措辞的用意是让模型把它当背景、不复述：

const CHECKPOINT_PREAMBLE =
  'This is an automatically generated checkpoint condensing an earlier span of the conversation to free up context. Treat the captured context as established background and build on it without restating it. Continue the task directly from the messages that follow, without acknowledging this checkpoint.'

出处：summarizer.ts:70-71；它还用一个标记对把摘要正文包起来（<compacted-summary>，summarizer.ts:22），并且明确规定「如果对话里已经有一个先前的检查点，不要照抄，把仍然成立的事实保留、过时的丢掉、新的合并进来」。反复压缩因此不会变成摘要的摘要的摘要那样层层衰减。

我们的对应实现更朴素，但把「反复压缩」这件事也考虑进去了：

def summary_message(summary: str, *, cut: int, total: int) -> dict[str, Any]:
    """把摘要包成一条 user 消息，替换掉被折掉的那段历史。

    必须是 user 消息：多数 API 要求历史以 user 开头，而摘要替换的正是开头那一段。
    措辞明确要求模型把摘要当作背景、不要复述它——否则模型经常会在下一步
    先来一句「我了解到我们正在……」白白花掉一轮。
    """
    return {
        "role": "user",
        "content": (
            f"【自动检查点】以下是较早的 {cut} 条消息（共 {total} 条）的压缩摘要。"
            "把它当成既有背景，直接接着干活，不要复述它。\n\n"
            f"{summary}"
        ),
    }
def summarize_prefix(
    messages: Messages,
    summarize: Summarizer,
    *,
    keep_recent: int = 6,
) -> Messages:
    """第 2 级：把较早的若干条折成一条摘要，最近 ``keep_recent`` 条原样保留。

    切分点由 :func:`safe_cut_index` 决定；``summarize`` 是调用方传进来的函数
    （测试里用普通函数或 FakeLLM，生产里可能就是一次 ``LLM.complete``）。

    摘要失败会把原始异常包成 :class:`CompactionError` 抛出——注意是**抛出**，
    不是「退化成不压缩」。调用方（:class:`Compactor`）知道该怎么记账并继续，
    而这里静默吞掉失败会让上层以为压缩成功、于是每轮都重试。
    """
    cut = safe_cut_index(messages, len(messages) - max(0, keep_recent))
    if cut <= 0:
        return messages
    older, newer = messages[:cut], messages[cut:]
    try:
        summary = summarize(_deep_copy(older))
    except Exception as exc:  # noqa: BLE001 —— 任何失败都要让调用方看到
        raise CompactionError(f"摘要失败：{exc}") from exc
    if not isinstance(summary, str) or not summary.strip():
        raise CompactionError("摘要为空：压缩没有腾出任何信息空间，视为失败")
    return [summary_message(summary, cut=cut, total=len(messages)), *newer]

两处约定值得单独说。第一，摘要为空按失败处理（摘要为空：压缩没有腾出任何信息空间，视为失败）：一个空摘要换掉了整段历史，是一种比不压缩严重得多的损坏。第二，摘要不能把历史变长——所以 compact_once 里判断的是 len(folded) < len(messages)，DSH 也有同样一条守卫，比较的是摘要的估算 token 和被遮蔽内容的 token（region.ts:418-422，报错文本是「summary is not smaller than the shadowed content」）。压完不缩小的压缩是纯亏损：花了钱、丢了信息、位置还占着。

压缩与日志：DSH 为什么在日志层表达压缩

DSH 的压缩结果不是「一份新的消息数组」，而是一条带 replace 的日志事件：

  session.append('user/message', checkpointMessage, {
    surfaceOp: { op: 'replace', startSeq: start, endSeq: end },
    sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
  })

出处：region.ts:506-509。这一行同时做了四件事，每一件都是为回放服务的：

  • 替换而不是删除。surfaceOp: { op: 'replace', startSeq, endSeq } 说的是「从这个 seq 到这个 seq 的位置，以后由我这条消息代表」。被替换的事件一条都没被删，它们只是不再出现在推导结果里。
  • 来源可追。sourceEventSeqs 指回「压缩开始标记、摘要、以及所有被遮蔽的节点」——事后可以精确回答「这条摘要是从哪些事件折出来的」。
  • 摘要本身也是日志事件。session.append('compaction/summary', {...})（region.ts:491-505）记录了摘要文本、provider/model、maxTokens、usage，以及被遮蔽的范围和 token 数。压缩花了多少钱、压掉了多少内容，都能从日志里算出来。
  • 用一对标记框住整个事务。compaction/start（region.ts:210）和 compaction/end（region.ts:237）。start 一旦落地就是锁：别的压缩看到它还没配对的 end，就会以 busy 拒绝（region.ts:308-320，报错文本里写着「the session compaction lock is already active」）。失败时 end 带上错误照样写一条（region.ts:245），注释说这是刻意的：「every later failure makes exactly one compaction/end attempt; a failed close deliberately leaves the unmatched start detectable」——失败的压缩在日志里是看得见的，不是静悄悄的。

推导侧只有一句话要记：deriveMessages 沿着表面走，遇到 replace 就把被遮蔽的节点从推导里去掉（index.ts:967-974的注释原话是「a compaction replace deletes the shadowed nodes from the derivation」）。所以「日志不丢」和「模型看不到」这两件事在 DSH 里是同一个机制的两面，而不是两套状态。

第 1 级的裁剪用的是同一套 replace，只是范围退化成一个节点：

出处：index.ts:160-171。注意注释里的「shadow-price protocol」：compaction/prune 这条事件紧挨着替换事件写下，它的作用是告诉纯消费者「刚才那个被替换掉的节点值多少 token」，这样计费方不需要自己保存每个节点的历史价格。把「这次替换省了多少」也写进日志，是一个很实用的习惯——不写的话，压缩的效果事后就查不出来了。

顺带说一句 /compact 这个人工入口。它做的事和自动压缩不完全一样：在下限以下也压一次，只是要求 Agent 处于空闲（command-compact/src/index.ts:67 → compaction-basic/src/index.ts:383-435），失败原因分成六类逐条报给用户（busy / cancelled / changed / summary / commit / persistence）。「用户手动触发的压缩要给出可读的失败原因」这件事，值得在自己的 harness 里保留——自动压缩失败可以静默重试，手动压缩失败必须说清楚为什么。

压缩失败的熔断

压缩失败之后最坏的做法是「下一轮再试一次」。摘要要花一次模型调用，而失败往往是确定性的：历史本身太大、模型不支持这么长的输入、配额用完了。每轮重试一遍等于每轮白花一次钱、白等一段时间，最后还可能把一整轮 turn 拖死。

所以每个实现都有一个计数器加一条短路。OpenHarness 的短路写得很直白：

def should_autocompact(
    messages: list[ConversationMessage],
    model: str,

    *,
    context_window_tokens: int | None = None,
    auto_compact_threshold_tokens: int | None = None,

    if state.consecutive_failures >= MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES:

出处：compact/__init__.py:1095-1105，阈值是 3（第 57 行）。计数在成功时清零、失败时加一（第 1642-1645 行），而且失败被 except Exception 接住后返回原历史（第 1660 行）——压缩失败绝不让整个 turn 崩掉。

我们的版本把计数器和状态封装在一起：

@dataclass
class CircuitBreaker:
    """连续失败计数。到阈值就停止尝试压缩，直到有人显式复位。

    这条规则解决的是「压缩一直失败、于是每轮都重试一遍」：一次摘要要花一次
    模型调用，失败还往往是确定性的（历史太大、模型不支持长输入、配额用尽），
    每轮重试等于每轮白花一次钱。

    OpenHarness 的做法是一个计数器加一条短路：
    ``packages/.../compact/__init__.py`` 里 ``should_autocompact`` 的第一行就是
    ``if state.consecutive_failures >= MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES: return False``。
    我们在成功时也清零——它那边的清零挂在 turn 结束上，两者都在「环境变了」时
    重新给一次机会。
    """

    max_failures: int = MAX_CONSECUTIVE_FAILURES
    failures: int = 0
    last_error: str = ""

    @property
    def open(self) -> bool:
        """是否已经熔断（停止尝试压缩）。"""
        return self.failures >= self.max_failures

    def record_success(self) -> None:
        self.failures = 0
        self.last_error = ""

    def record_failure(self, error: BaseException | str) -> None:
        self.failures += 1
        self.last_error = str(error)

什么时候算一次失败，值得单独列一下。我们把三类都算进去：

  • 摘要函数抛错（包成 CompactionError 后记一次）；
  • 摘要跑完但历史没有变短（DSH 的「summary is not smaller」守卫对应的情形）；
  • 整个级联跑完却一点没省下来（after >= before）。这一类最容易被漏：函数没抛错、返回值也「正常」，但下一轮还会一模一样地再触发一次。

反过来说，有几件事不该计入失败：第 2 级没被触发（第 1 级已经够了）、没有传摘要函数、用量在阈值以下。这些都是正常路径，记进熔断器会让熔断在毫无问题的时候打开。测试里这几种情形是分开断言。

    def test_consecutive_failures_open_the_breaker(self) -> None:
        messages = conversation(rounds=4)
        compactor = self._failing_compactor(messages)
        levels = [compactor.compact_once(messages).level for _ in range(MAX_CONSECUTIVE_FAILURES)]
        # 第 2 级失败，但第 1 级已经生效，所以每次都退到 prune。
        self.assertEqual(levels, ["prune"] * MAX_CONSECUTIVE_FAILURES)
        self.assertTrue(compactor.breaker.open)
        blocked = compactor.compact_once(messages)
        self.assertEqual(blocked.level, "none")
        self.assertIn("熔断", " ".join(blocked.notes))
        self.assertIs(blocked.messages, messages)
    def test_breaker_resets_after_a_success(self) -> None:
        breaker = CircuitBreaker()
        breaker.record_failure("x")
        breaker.record_failure("y")
        self.assertFalse(breaker.open)
        breaker.record_success()
        self.assertEqual(breaker.failures, 0)
        self.assertFalse(breaker.open)

DSH 这边有更细的一层：超长恢复的计数是按 Agent存的（WeakMap<Agent, number>，index.ts:134），并且在两种「环境变了」的信号上清零：Agent 回到 idle（index.ts:178-180），以及这条会话又产生了一条助手消息——注释说这是为了「即使工具调用让同一个 turn 继续到下一次请求，成功的一次响应也开启一段新的超长恢复序列」（index.ts:182-188）。这个区分很细但很重要：熔断要记的是「连续失败」，只要中间成功过一次，就该重新给一次机会。

坑与失败案例

坑一：切分点拆开了 tool_use 和它的结果，请求直接 400

触发条件：按「保留最近 N 条消息」切历史，N 刚好落在一对工具调用中间。

后果：旧段以孤儿 tool_use 结尾、新段以孤儿 tool_result 开头，厂商返回 400。最难受的地方是错误信息通常只说「格式不合法」，不告诉你哪一对拆了；而压缩逻辑看上去「成功执行了」，于是排查方向容易跑偏到工具 schema 或提示词上。

源码怎么防：DSH 在选范围时就把两端都限制在平衡边界上，而且范围一旦不合法在压缩开始之前就抛错（region.ts:349-355，报错文本直接点明「would split a step's tool-call/result pair」）。OpenHarness 在选完切点之后还会再把保留段 sanitize 一次。我们的 safe_cut_index 只往回挪不往前挪，就是这个坑的防线。测试里对每个可能的 desired 都断言结果平衡。

坑二：摘要丢掉了用户最初的约束

触发条件：把「总结这段对话」当成通用任务交给模型，不指定必须覆盖哪些内容。模型倾向于总结最近的活动——它刚读完的那一大堆工具输出听起来最「重要」。

后果：三条优化建议、五个文件路径原样保留，而用户第三轮说的「不要改公开接口，线上有别的服务在调」没了。接下来模型高高兴兴重构了公开接口——而且它自己不知道记错了什么，因为它手上只有那份摘要。

源码怎么防：DSH 的压缩指令把「Primary Request and Intent」放在第一节，要求「quote verbatim where the exact wording matters」；OpenHarness 的 BASE_COMPACT_PROMPT 更直接，第九条要求「All User Messages: Non-tool-result user messages (preserve exact wording for context)」（compact/__init__.py:991）。两家都要求「逐字保留」，因为约束往往只在措辞里。

另一个相关坑在裁剪这一级：它默认跳过带 is_error 的结果。labs 的 PRUNE_SKIP_ERRORS 就是这个开关。理由很实际——报错信息通常是模型下一步唯一的依据，而它往往不长（不占多少 token），裁它收益小、损失大。DSH 的 pruner 没有这个区分（它只按长度挑），所以这是个可以争论的选择；我们的实现选了保守的那一边。

坑三：每轮都触发压缩，成本飙升

触发条件：压缩之后仍然超阈值（例如单条工具结果本身就塞满窗口，压不动）。下一轮的压力检测再触发一次，又调一次模型。

后果：账单上多出一串摘要调用，每一轮都白等一次模型；如果是确定性的失败（比如摘要请求本身也超长），这个循环永远不会自己停。

源码怎么防：四道，缺一不可。

  1. 压缩次数上限：compactionRetries 默认 1，超过还在阈值之上就抛错（index.ts:343-346，报错文本「compaction still above threshold after N compaction attempts」）。
  2. 超长恢复上限：maxOverflowRetries 默认 1（config.ts:105，下一行是 maxOverflowRetries），同一个 Agent 反复因超长被打回来就放手。
  3. 压缩锁：compaction/start 没配对 compaction/end 之前，第二次压缩以 busy 拒绝。
  4. 失败熔断：OpenHarness 的 consecutive_failures 到 3，或我们 CircuitBreaker 的同名机制。

我们还有一个降级路径值得说：第 2 级失败但第 1 级已经落地时，历史仍然是小的，achieved 停在 prune，turn 继续跑——但因为这一轮记了一次失败，连续三次之后连第 1 级也不再试。这是有意的：如果裁剪有效，压力很快会落回阈值以下，熔断根本不会打开；熔断打开了，说明这个会话已经进入了「压缩解决不了」的状态，继续压只是浪费。

坑四：把「压缩成功」当成「一定有进展」

触发条件：摘要返回了内容、函数没抛错，但估算下来没有比原来小——比如历史本来就只有两条消息，摘要加了前言反而更长。

后果：压缩被记为成功，压力检测下一轮照旧触发，形成一场「什么都没发生」的死循环，而且日志上看不出异常。

源码怎么防：DSH 用「写进日志的 replaceGeneration 有没有变」和「摘要 token 有没有小于被遮蔽的 token」两条硬判据（index.ts:229-232、pruner index.ts:118）；我们的判据是 after < before 和 len(folded) < len(messages)，不满足就记一次失败。

坑五：压缩请求本身超长

触发条件：把要压缩的那一整段原样发给模型去总结，而这段本身就快到窗口上限了。

后果：摘要请求也报超长，压缩永远失败——而失败的原因恰恰是「历史太长」，形成一个死结。

源码怎么防：OpenHarness 走的是「分段输入 + 截断重试」：请求前先把输入折叠到上限内（compact/__init__.py:302 一带的 try_context_collapse），摘要请求真的被拒了就丢掉最老的一段再试，最多三次（第 1291-1295 行，MAX_PTL_RETRIES = 3）。DSH 走的是另一条路：先让免模型的 pruner 把结果正文压掉（index.ts:294-301，超长触发时先 pruner、重测、再选范围），常常在摘要之前就把体积降下来了。我们的 lab 没有实现这一层，这是本章没覆盖的部分之一。

小结

压缩这件事可以压缩成四条规则：

  1. 按代价排序。免模型的先做、只有不够才调模型；每做一级重新量一次，够了就停。阈值决定「本来打算做哪一级」，achieved 记录「实际做到哪一级」，两者不一样是正常的。
  2. 切分点必须配对平衡，两端都要查。宁可这次不压，也不要拆开 tool_use 与 tool_result；切完之后再校验一次历史能不能直接发出去（第一条是 user、配对完整）。
  3. 摘要里最该保住的是约束和路径。任务目标逐字、文件路径精确、未完成的事单列、不要提「压缩」这件事。摘要必须比被替换的内容小，否则算失败。
  4. 压缩是日志事件，不是对内存数组的删除。被遮蔽的节点留在日志里，推导时跳过；压缩花了多少钱、压掉了什么，都能事后查出来。失败要留痕（DSH 连失败的 compaction/end 都写），失败要有熔断，不能每轮重试。

第 1 级（裁剪旧工具结果）属于 hx-08 讲的「工具输出卸载」的近亲，区别只在于它是事后补救、而且不动结构。下一章（hx-08）会讲更彻底的一步：大输出在落地时就直接改成「预览 + 路径」，让上下文里根本不出现完整内容——那样连压缩都省了。压缩的输入是 token 用量，那套估算和分级在 hx-05；摘要请求要复用上次请求的前缀，背后的缓存条件在 hx-06。
