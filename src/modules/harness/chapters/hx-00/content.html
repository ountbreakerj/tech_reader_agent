全景图：Harness 由哪些部件组成

这一章不写新机制，只做三件事：讲清楚 harness 的边界在哪里，把后面 25 章对应的部件摆成一张图，再告诉你五个参考仓库分别该怎么用。读完你应该能回答：一段代码算不算 harness；某个线上问题该去哪一章找；想看某个机制的生产级写法该打开哪个文件。

Harness 是什么、不是什么

模型只做一件事：读一段上下文，产出一段 token。这段 token 里可能有自然语言，也可能有结构化的“我想调用某个工具、参数如下”。其余所有事都是 harness 做的：决定模型看到什么，把模型的调用请求变成真实动作（或者拒绝），把结果送回去，决定什么时候停，并在过程中记账、留痕、兜底。

这个定义可以在最小实现里直接看到。learn-claude-code 第一章的整个 harness 只有一个函数 code.py:96：调用模型、把回复追加进历史、检查有没有工具调用，没有就返回 code.py:110，有就执行并把结果追加回去。三个可运行的仓库骨架完全一样：OpenHarness 是 query.py:700 的 while 加上 query.py:808 的“没有工具调用就结束”；DeepSeek Harness 是 agent.ts:549 的同一判断。三者的差别全在骨架周围。

它不是什么

  • 不是 prompt 模板。learn-harness-engineering 第二讲开篇就说 index.md:8。提示词是 harness 的一个输出，harness 还要负责执行、状态和边界。
  • 不是模型的一部分。DeepSeek Harness 的架构文档写明模型适配器、工具注册表、会话日志乃至 agent loop 本身都是可替换的插件 architecture.md:9。换模型不必换 harness；反过来，同一个模型套不同的 harness，表现可以差很多。
  • 不是某个框架。151 行的 s01_agent_loop/code.py 是 harness，一万多个文件的 DSH 也是 harness。区别在覆盖了多少部件、每个部件做得多深。
  • 不是工作流编排。工作流里下一步由代码决定；agent harness 里下一步由模型决定，harness 负责划边界、兜底和记账。

判断标准：一段代码如果影响“模型看到什么”或“模型的请求如何落地”，它就属于 harness。按这个标准，指令文件的加载、工具输出的截断、重试策略、审批弹窗都属于 harness，模型权重和推理服务不属于。

同一机制，四种做法：停止判定

仓库怎么判定代价适用场景

本模块怎么读、labs 怎么跑

每章的结构固定：先讲机制在源码里的哪一行、为什么这样写，再给出 labs 里对应的 Python 实现（正文代码块与 labs/ 文件逐字一致，由工具核对），然后列坑，最后用一张表对比各仓库的做法。

为什么默认是 FakeLLM

labs 的所有测试和示例默认用 FakeLLM，不连任何真实模型。理由有三条：

  • 可复现。同一个脚本每次跑出同样的轨迹。真实模型在同样输入下可能换一种工具调用顺序，测试就成了抽奖。
  • 零成本。harness 的大部分 bug 和模型能力无关，没必要花 token 去复现。
  • 能精确构造失败场景。“第三轮输出被截断在工具参数中间”“模型调用了不存在的工具”“拒答”这些分支，用真实模型几乎碰不到，用脚本一行就能写出来。脚本项既可以是固定的 AssistantTurn，也可以是函数，根据当时的历史决定回复。
class FakeLLM:
    """按脚本顺序回放回复的假模型：测试可复现、零成本，能精确构造失败场景。"""

    def __init__(self, script: list[ScriptItem]) -> None:
        self._script = list(script)
        self.calls: list[Messages] = []

    def complete(self, system: str, messages: Messages, tools: list[dict[str, Any]]) -> AssistantTurn:
        # 存深拷贝：循环随后还会往 messages 里追加，断言要看的是模型“当时”看到的历史
        snapshot = copy.deepcopy(messages)
        self.calls.append(snapshot)
        step = len(self.calls)
        if step > len(self._script):
            raise ScriptExhausted(f"脚本只有 {len(self._script)} 步，第 {step} 次调用没有可回放的回复")
        item = self._script[step - 1]
        return item(snapshot) if callable(item) else item

两个细节。第一，calls 存的是深拷贝：循环会继续往同一个 messages 列表里追加，如果只存引用，事后断言看到的是最终历史，而不是模型当时看到的历史。第二，脚本用完时抛 ScriptExhausted 而不是返回空回复：循环多调了一次模型本身就是 bug，应该让测试失败。lcc 的假 API 也是这么做的，多要一轮就 test_agent_loop_boundaries.py:45。

DSH 走得更远：它的回放插件从真实会话日志里推导出逐次调用的回放脚本 index.ts:462，前提正是“模型可见即入日志”。hx-04 会在 labs 里实现同样的“把真实失败轨迹存成 FakeLLM 脚本”。

消息历史以 Anthropic 格式为准

labs 的历史统一用 Anthropic 风格的 dict 列表，块只有 text、tool_use、tool_result 三种。选它不是因为厂商，而是因为它把“调用”和“结果”都做成带 id 的块，配对关系一目了然；OpenAI 格式只在适配器发请求的那一刻临时转换，不进入历史。

def assistant_from_turn(turn: AssistantTurn) -> dict[str, Any]:
    """把模型回复写回历史；有原始块就用原始块，保证下次请求与厂商当初返回的一致。"""
    if turn.blocks:
        return {"role": "assistant", "content": copy.deepcopy(turn.blocks)}
    content: list[dict[str, Any]] = []
    if turn.text:
        content.append({"type": "text", "text": turn.text})
    for call in turn.tool_calls:
        content.append(
            {"type": "tool_use", "id": call.id, "name": call.name, "input": copy.deepcopy(call.args)}
        )
    return {"role": "assistant", "content": content}

turn.blocks 是 AnthropicLLM 收到的原始 content 块。之所以优先用它，是因为响应里可能有 thinking 这类 labs 不解析的块，它们需要原样回传；从 text 和 tool_calls 重新拼会把它们弄丢。hx-01 的循环在截断、拒答时会从这份原始块里剔除 tool_use，所以这里不做任何过滤。

跑测试

从 tech-reader-modular 根目录执行 py -m unittest discover -s labs/tests -t labs。-t labs 让 labs/ 成为顶层目录，测试里因此写 from harness.llm import ...。tests/test_llm.py 覆盖 FakeLLM 的顺序、脚本耗尽和调用记录，两个真实适配器的请求体构造与响应解析，OpenAI 格式的双向转换，以及缺 key 报错。真实适配器的网络发送被抽成可替换的 _post(url, headers, body) 方法，测试里替换掉，全程不发网络请求。

坑

坑 1：把 harness 写成 prompt 模板

触发条件：在系统提示里写“不要删除文件”“失败三次就停下”“输出不要超过多少字”，然后以为这些约束生效了。

后果：这些是请求，不是约束。模型大多数时候会遵守，但“大多数”不够：长上下文里提示被稀释，或者工具输出里混进一句相反的指令，规则就可能失效。出事时你也查不到是哪一层没拦住，因为根本没有那一层。

源码怎么防：把“必须”写成代码，提示词只负责“最好”。lcc 从 s03 开始把“不许删”做成执行前的三道闸（见 上文）；OpenHarness 的敏感路径保护排在所有规则之前，注释写明任何模式都不能覆盖，就是为了防模型或注入内容去读凭据文件 checker.py:84；“最多跑多少轮”是 query.py:700 的循环条件，而不是提示里的一句话。

没防住的例子：lcc 第一章的 run_bash 只有子串黑名单 code.py:81。rm -rf ~ 不包含名单里的任何子串，会被直接执行。这是教程有意留的简化，hx-14 会讲怎么把命令拆开再判定。

坑 2：没有确定性测试，只能靠真模型调

触发条件：每改一次 harness，就用真实模型跑一遍任务，“看起来没问题”就提交。

后果：同样的输入每次轨迹不同，回归无法自动化；而 harness 最容易出错的分支（输出截断在工具参数中间、拒答、并行工具里一个抛异常、429）用真实模型几乎碰不到，等碰到时已经在生产上了。每次验证还要花钱。

源码怎么防：三个可运行仓库都给模型留了替身接口。OpenHarness 的模型客户端协议注释写明它同时服务于测试和生产 client.py:81；lcc 的测试用假 API 驱动每一章的循环；DSH 能从真实会话日志推导回放脚本。labs 的 FakeLLM 是同一个思路的最小版本。实用的做法是：真实模型跑出的每一条失败轨迹都存下来，改写成 FakeLLM 脚本，变成永久的回归用例。

坑 3：厂商差异泄漏进循环

触发条件：循环里直接写 if resp.stop_reason == "tool_use"。后来接了一个 OpenAI 兼容服务，它返回的是 finish_reason: "tool_calls"；或者某个服务带着工具调用却报 "stop"；或者厂商新增了 pause_turn、refusal 这样的取值。

后果：工具调用被当成正常结束丢掉，任务半途而废却显示“完成”；或者反过来，被截断的半截 tool_use 被拿去执行。随后循环里开始出现 if provider == ... 分支，适配层形同虚设。

各仓库怎么处理：OpenHarness 的 OpenAI 客户端把 finish_reason 原样塞进 stop_reason 字段 openai_client.py:433，于是同一个字段里混着两套词汇；它的循环靠完全不读这个字段来回避问题（query.py:808），代价是分不清正常结束和截断。DSH 在适配器边界一次性翻译 translate.ts:90，循环只认内部取值。labs 的做法如下：

def parse_openai_response(data: dict[str, Any]) -> AssistantTurn:
    choice = data["choices"][0]
    message = choice.get("message") or {}
    calls = [_openai_tool_call(c) for c in message.get("tool_calls") or []]
    finish = choice.get("finish_reason") or ""
    stop_reason = _FINISH_TO_STOP.get(finish, finish)
    if calls and stop_reason == "end_turn":
        # 有的兼容服务带着工具调用却报 stop；在适配器里纠正，循环只看统一后的值
        stop_reason = "tool_use"
    usage = data.get("usage") or {}
    return AssistantTurn(
        text=message.get("content") or "",
        tool_calls=calls,
        stop_reason=stop_reason,
        usage={
            "input_tokens": usage.get("prompt_tokens", 0),
            "output_tokens": usage.get("completion_tokens", 0),
            "raw": usage,
        },
    )

_FINISH_TO_STOP 把 stop、tool_calls、length 分别映射到 end_turn、tool_use、max_tokens；表里没有的取值（例如 content_filter）原样透出，让循环和日志都看得见。AnthropicLLM 则不做任何映射，stop_reason 原样保留，因为 Anthropic 的词汇就是 labs 的统一词汇。效果是：hx-01 的循环里不会出现任何厂商名。

坑 4：适配器静默“修好”坏数据

触发条件：兼容服务返回的工具参数不是合法 JSON，可能是输出被截断了，也可能是模型写错了。

后果：OpenHarness 在解析失败时把参数改成空字典 openai_client.py:234。工具于是以空参数运行，报出“缺少必填参数”，而真实原因是“你给的 JSON 坏了”。模型看到的错误和真实原因对不上，往往会用同样的方式再试一次。

labs 怎么防：保留原文，把判定留给执行管线。hx-03 会把带 __raw_arguments__ 的调用直接变成 is_error 结果，告诉模型参数不是合法 JSON 并附上原文。

def _openai_tool_call(raw_call: dict[str, Any]) -> ToolCall:
    raw = raw_call["function"].get("arguments") or "{}"
    try:
        args = json.loads(raw)
    except json.JSONDecodeError:
        args = None
    if not isinstance(args, dict):
        # 不静默改成 {}：保留原文，让执行管线把“参数不是合法 JSON”报回给模型
        args = {"__raw_arguments__": raw}
    return ToolCall(id=raw_call["id"], name=raw_call["function"]["name"], args=args)

同样的原则也适用于错误。OpenHarness 的循环用字符串匹配给异常分类，消息里含 connect、timeout、network 的算网络错误 query.py:778，其余一律算 API 错误。labs 让 LLMHTTPError 带上状态码和完整响应体往上抛，重试策略（hx-18）按状态码决定，不猜字符串。

取舍：自己写，还是用现成的

本模块一路自己写，但这不是唯一选项。下表对比四条路线；“Claude Agent SDK”指把 Claude Code 打包成库的那个 SDK，它自带文件读写、编辑、Bash、搜索等工具，以及循环、上下文管理、hooks、子代理、权限和会话，但和其他三条路线一样只提供 harness，部署要自己负责。
