第 5 章

Token 预算与计数

上下文窗口是 harness 面对的唯一硬上限。轮数、工具调用次数、重试次数都可以商量，窗口不行：请求一旦超过它，厂商直接返回 400，这一轮的推理、这一轮已经跑掉的工具全部作废。而按 token 计费的账单同样不给商量余地。所以一个能长时间跑的 harness 必须自己算账，而且要在发请求之前就算出来。

本章先用 labs 里的 budget.py 把三件事拆开——估算、窗口切分、用量账本——再逐库对照它们各自怎么算这笔账。压缩策略本身是 hx-07 的主题，本章只负责回答“什么时候该压缩”这个信号；prompt cache 的读写 token 怎么进成本，衔接 hx-06。

术语：prompt 指一次请求里所有输入（系统提示、工具定义、历史、本轮输入）合起来的 token 数，completion 指模型本次生成的 token 数，两者相加才是这一次请求对窗口的占用。厂商的 usage 字段名五花八门，本章统一用 input / output / cache_read / cache_write 四个桶。

为什么 harness 必须自己算账

模型适配器当然知道窗口是多大，但它只在下游：等你把请求交给它，它要么发出去，要么发出去之后收到 400。harness 需要的判断发生在更上游——“这一批工具结果还能不能塞进历史”“还剩多少空间给下一次模型调用”“现在是不是该触发压缩”。这些决定必须自己算，因为只有 harness 知道下一个要填进上下文的东西是什么。

DSH 把“窗口是多少”明确划给适配器，把“现在用了多少”留给 meter，中间靠一条命令式接口串起来。窗口值与路由绑定：

原文：mount this plugin when a consumer needs token or context pressure for compaction decisions, occupancy displays, or telemetry … model capacity belongs to the adapter that owns the exact provider/model route and is available through ctx.llm.resolveModelInfo().context（token-meter/README.md:28）。

同一份文档把这条分工的另一半说得很直白：meter 只测压力，不做任何循环决策，也不向模型增加任何可见内容。决策权留在压缩插件手里。

OpenHarness 走的是另一条路：它把窗口大小写成一张按模型名猜测的表，没有 provider 元数据可查。默认 200K，靠字符串匹配模型名兜底：

def get_context_window(model: str, *, context_window_tokens: int | None = None) -> int:
    """Return the context window size for a model (conservative defaults)."""
    if context_window_tokens is not None and context_window_tokens > 0:
        return int(context_window_tokens)
    m = model.lower()
    if "opus" in m:
        return 200_000
    if "sonnet" in m:
        return 200_000
    if "haiku" in m:
        return 200_000
    # Kimi / other providers — be conservative
    return _DEFAULT_CONTEXT_WINDOW

compact/__init__.py:1065-1077。所有分支都返回同一个数——这张表的实际作用是“允许环境变量覆盖，否则一律 200K”。对未知模型这会偏乐观；OpenHarness 的对策不是查得更准，而是把阈值压得更低（见 第 4 节）。

估算与实测：先估，再回填

没有分词器时的估算

真实分词器要么是个几百 KB 的模型文件，要么是一次网络往返（厂商的 count_tokens 接口）。两者都不适合在每个决策点上调用。所以所有 harness 都先估：

@dataclass
class HeuristicCounter:
    """按字符类别估算的计数器：没有分词器时的兜底。

    单调不减：count("") == 0，且 a 是 b 的前缀时 count(a) <= count(b)。
    估算必然有误差，误差用 provider 的 usage 修正，不靠调系数。
    """

    ascii_chars_per_token: float = ASCII_CHARS_PER_TOKEN
    cjk_chars_per_token: float = CJK_CHARS_PER_TOKEN
    other_chars_per_token: float = OTHER_CHARS_PER_TOKEN

    def count(self, text: str) -> int:
        if not text:
            return 0
        ascii_n = cjk_n = other_n = 0
        for ch in text:
            if ord(ch) < 128:
                ascii_n += 1
            elif _is_cjk(ch):
                cjk_n += 1
            else:
                other_n += 1
        tokens = (
            ascii_n / self.ascii_chars_per_token
            + cjk_n / self.cjk_chars_per_token
            + other_n / self.other_chars_per_token
        )
        return int(tokens) if tokens == int(tokens) else int(tokens) + 1

三个系数（ASCII 4 字符 / token、CJK 1 字 / token、其余 2 字符 / token）都是教学示意，不是任何厂商的分词器。count 保证单调不减：count("") == 0，且前缀的估计值不超过整体的估计值——预算决策依赖这一条，否则“再加一段内容”可能反而让估计值变小，分级信号会抖。

按字符类别分开算不是洁癖。DSH 的固定启发式是一刀切的四字符一 token，它自己承认这个选择在中文上会严重低估：

原文：The fixed four-characters-per-token heuristic underprices CJK text and JSON schemas; the provider anchor carries exactly that error when usage is reused.（token-meter/README.md:154）。

低估的后果不是“省了钱”，而是压缩触发得太晚：你以为还剩 30% 空间，实际已经贴到窗口边。DSH 的取舍是接受这个误差，但让误差可测量——把 provider 的真实值当锚点，只把锚点之后的变化量按启发式算（2.2）。

OpenHarness 的估算器更简单，也是四字符一 token，但方向相反——它向上取整再乘一个填充系数：

def estimate_tokens(text: str) -> int:
    """Estimate tokens from plain text using a rough character heuristic."""
    if not text:
        return 0
    return max(1, (len(text) + 3) // 4

除数就是 4，加 3 是向上取整；非空文本至少报 1。token_estimation.py:10。往上再乘的填充系数是 4/3：

原文：TOKEN_ESTIMATION_PADDING = 4 / 3（compact/__init__.py:75），注释写明是 conservative，用在汇总时：return int(total * TOKEN_ESTIMATION_PADDING)（compact/__init__.py:131）。

两者合起来：OpenHarness 宁愿高估 33%，换来“阈值保守”。代价是压缩触发得早，多花一次摘要调用的钱。

用 usage 回填：DSH 的锚点与增量

估算的误差可以消除一半——每次响应返回时，厂商会告诉你这次请求的真实 prompt 有多大。聪明的做法不是用真实值替换历史，而是只把锚点之后的变化量按启发式算。

DSH 的做法正是这样。measure() 返回的 totalTokens 由两部分相加：一个基线（baseline）和一个相对基线变化的带符号增量（surfaceDeltaTokens）：

    return deepFreeze(structuredClone({
      logRevision: state.consumedEvents,
      baseline,
      surfaceDeltaTokens,
      totalTokens: Math.max(0, baseline.tokens + surfaceDeltaTokens),
      surfaceTokens: surface.surfaceTokens,
      nodes: surface.nodes,
    }))

token-meter/src/index.ts:183-190。注意 Math.max(0, ...)：增量可以是负数（比如压缩把一段历史换成了摘要），但合计不能为负。

基线何时用真实值、何时用估算值，条件写得很紧：

      // Signed heuristic deltas remain conservative only from an anchor
      // that is at least as large as the matching full heuristic price.
      baseline = usage !== undefined && usageTokens(usage) >= estimatedAnchorTokens
        ? { kind: 'usage', tokens: usageTokens(usage), usage }
        : { kind: 'estimated', tokens: estimatedAnchorTokens }

token-meter/src/index.ts:166-170。三个条件缺一不可：有 usage、请求信封（envelope）与上次成功调用逐字相同、且真实值不低于同一份内容按启发式算出来的值。第三条是防止“真实值比估计值小”破坏保守性——若真实 prompt 比估计的小，而增量仍按启发式算，两者相减出来的压力会偏乐观。

真实值怎么进桶也有讲究。DSH 内部把缓存读写当互不重叠的桶，加总时直接相加：

/** Sum disjoint provider usage buckets without double-counting reasoning output. */
function usageTokens(usage: TokenUsage): number {
  return usage.inputTokens
    + (usage.cacheReadTokens ?? 0)
    + (usage.cacheWriteTokens ?? 0)
    + usage.outputTokens
}

token-meter/src/index.ts:70-76。这条“互不重叠”的不变量写在类型定义里：

原文：Counts are DISJOINT: inputTokens is uncached input only; cached input is reported separately as cacheReadTokens/cacheWriteTokens (billed input = sum of the three). Adapters whose providers fold cache hits into a total prompt count (DeepSeek's prompt_tokens) subtract them out.（llm/src/types.ts:170-173）。

最后一句是重点：减去 cache 这件事由适配器做，不是由 meter 做。适配器是唯一知道厂商原始字段语义的地方。翻译层里就是一张字段映射表：

  const keys = { input_tokens: 'inputTokens', output_tokens: 'outputTokens', cache_read_input_tokens: 'cacheReadTokens', cache_creation_input_tokens: 'cacheWriteTokens' } as const

llm-deepseek/src/translate.ts:36。上游 Anthropic 兼容端点的四个字段名，直接映到内部四个桶名。labs 的 normalize_usage 做的是同一件事，但要多处理一种形状（第 5 节）。

回填的边界：锚点什么时候失效

“只算增量”要求增量算得对。DSH 的增量是按当前路由重新定价的差值，而重新定价只在两边的路由相同时才可比。所以锚点携带了当时的请求信封：

interface MeasurementAnchor {
  readonly header: EpochHeader | undefined
  /** Priced surface immediately before the anchored assistant message commits. */
  readonly nodes: readonly MeterSurfaceNode[]
  /** Fixed-heuristic price of the call's provider output. */
  readonly assistantTokens: number
  /** Provider usage of the call, when it reported one under a known header. */
  readonly usage: TokenUsage | undefined
}

token-meter/src/index.ts:52-60。文档把失效条件列成一条明确的限制：

原文：Provider usage is only reusable for an identical canonical envelope — tools, provider, model, or call-config changes deliberately fall back to full heuristic estimation.（token-meter/README.md:142）。

换模型、换工具集、改 max_tokens，锚点立刻作废，退回全量估算。这是对的：真实的 prompt 大小是不同请求之间最不该被复用的东西。

预算怎么切分

窗口不是“历史能放多少”。同样一个 200K 的窗口，要先扣掉输出预留，再扣掉安全余量，剩下的才是历史能触顶的位置。labs 把切分显式写成属性，让每一层都能单独检查：

    def plan(
        self,
        counter: Counter,
        system_prompt: str = "",
        tool_schemas: list[dict[str, Any]] | None = None,
        messages: list[dict[str, Any]] | None = None,
    ) -> BudgetPlan:
        """把窗口切成几块，并给出这次请求的分级。"""
        system_tokens = counter.count(system_prompt) if system_prompt else 0
        tools_tokens = count_tools(counter, tool_schemas or [])
        history_tokens = count_messages(counter, messages or [])
        used = system_tokens + tools_tokens + history_tokens
        budget = self.pressure_budget
        return BudgetPlan(
            context_window=self.context_window,
            output_reserve=self.output_reserve,
            safety_margin=self.safety_margin,
            system_prompt=system_tokens,
            tool_schemas=tools_tokens,
            history=history_tokens,
            message_budget=self.message_budget,
            pressure_budget=budget,
            used=used,
            available_input=budget - used,
            level=self.level_for(used),
            ratio=used / budget,
        )

四层的关系：message_budget = context_window - output_reserve，pressure_budget = message_budget - safety_margin，used = 系统提示 + 工具 schema + 历史，available_input = pressure_budget - used。available_input 允许为负——负值表示“还差多少”，不是无意义值，调用方拿它直接算压缩目标。

DSH 的压缩配置把同样的切分做成了带默认值的策略，并且每一层都有自己的名字。默认余量是 65536：

原文：const headroomTokens = config.headroomTokens ?? 65_536（compaction-basic/src/config.ts:75）。

输出预留则取自“这次请求实际会用的 max_tokens”，而不是某个配置常量：

function reservedCompletionTokens(agent: Agent, defaultMaxTokens: number | undefined): number {
  const configured = agent.session.requestHeader()?.config.maxTokens
  return configured ?? defaultMaxTokens ?? 0
}

compaction-basic/src/index.ts:65-68。请求信封自带的上限优先，否则用适配器给该模型的默认值，都没有就不预留——注释解释了为什么必须这样查：厂商把输出和输入算在同一个窗口里。

三级预算的减法在这里写成三段，每一段都带一条自己的报错信息：

  const messageBudgetTokens = contextWindow - reservedCompletionTokens
  if (messageBudgetTokens <= 0) {
    throw new TargetPressureConfigError(
      targetKey,
      `compaction-basic: ${targetKey} reserves ${reservedCompletionTokens} completion tokens `
      + `of its ${contextWindow}-token context window, leaving no message budget; configure `
      + "the adapter model's contextWindow above the effective request maxTokens",
    )
  }
  const pressureBudgetTokens = messageBudgetTokens - policy.headroomTokens

compaction-basic/src/config.ts:172-181。报错信息里直接写“把适配器的 contextWindow 配到 maxTokens 以上”——配置错误在启动时炸掉，而不是等到某个请求 400 才发现。

阈值最后取两个数的较小值：按比例算出的窗口分数，与“输出预留和安全余量之后剩下的全部”：

  const thresholdTokens = Math.floor(Math.min(
    contextWindow * policy.thresholdRatio,
    pressureBudgetTokens,
  ))

compaction-basic/src/config.ts:191-194，比例默认 0.8（compaction-basic/src/types.ts:11）。Math.min 保证小窗口下不会因为比例太大而越界——比例是软的，预算是硬的。

工具 schema 是容易被漏掉的一块。它每个请求都全额发送，且与历史无关，所以 DSH 把它单独算：

export function estimateToolsTokens(header: EpochHeader | undefined): number {
  if (header?.tools === undefined || header.tools.length === 0) return 0
  return Math.ceil(JSON.stringify(header.tools).length / CHARS_PER_TOKEN) + BLOCK_OVERHEAD
}

token-meter/src/estimate.ts:99-102。JSON.stringify 意味着它算的是序列化之后的体积，包括括号、引号和键名——这正是模型实际看到的东西。

不变量：Budget.plan 算出的 used 必须等于三个组成项之和，且 available_input 等于预算减 used。测试 labs/tests/test_budget.py 里的 test_available_input_subtracts_every_consumer 逐项检查。运行：py -m unittest discover -s labs/tests -t labs -p "test_budget.py"。

分级信号：什么时候该压缩

预算算出来只是一个数，决策需要的是一个级别。labs 分四档，对应四种动作：正常继续、先发一次提示、压缩或拒绝、直接拒绝。

    def level_for(self, used: int) -> Level:
        """分级：正常 / 接近上限 / 必须压缩 / 已经放不下。

        四个档位对应四种决策：继续、先发一次提示、压缩或拒绝、直接拒绝。
        """
        if used > self.pressure_budget:
            return "overflow"
        if used >= self.pressure_budget * self.hard_ratio:
            return "must_compact"
        if used >= self.pressure_budget * self.near_limit_ratio:
            return "near_limit"
        return "ok"

阈值是参数（near_limit_ratio 默认 0.8、hard_ratio 默认 0.95，都是教学示意），__post_init__ 校验 0 < near_limit_ratio < hard_ratio <= 1——档位顺序写反了在构造时就报错，而不是等到某次请求给出自相矛盾的信号。跟 hx-01 的停止条件一样，这里也把“判定”和“动作”分开：level_for 只读不写，返回一个字符串。

DSH 的对应物是压缩触发点。measure() 的结果拿去和一个阈值比，比不过就返回 null（不压缩）：

const spec = resolveCompactSpec(
  policy,
  info.context.contextWindow,
  reservedCompletionTokens(agent, info.defaultMaxTokens),
)
if (measurement.totalTokens < spec.thresholdTokens) return null

compaction-basic/src/index.ts:314-319。窗口从 resolveModelInfo 拿，拿不到就直接抛错，不猜：

原文：compaction-basic: no context capacity for ${targetKey}; configure contextWindow on that adapter model（compaction-basic/src/index.ts:307-312）。

对比 OpenHarness 的做法：窗口靠猜（compact/__init__.py:1065），阈值靠减：

    reserved = min(MAX_OUTPUT_TOKENS_FOR_SUMMARY, 20_000)
    effective = context_window - reserved
    return effective - AUTOCOMPACT_BUFFER_TOKENS

compact/__init__.py:1090-1092。预留输出取 min(20000, ...)，再减掉一段固定缓冲 AUTOCOMPACT_BUFFER_TOKENS = 13_000（compact/__init__.py:55）。没有比例阈值，就是一个绝对值的减法。触发判定是一行比较：

    token_count = estimate_message_tokens(messages)
    threshold = get_autocompact_threshold(
        model,
        context_window_tokens=context_window_tokens,
        auto_compact_threshold_tokens=auto_compact_threshold_tokens,
    )
    return token_count >= threshold

compact/__init__.py:1106-1112。注意 >=：阈值本身算“该压了”，和 labs 的闭区间一致。

OpenHarness 还有第三种信号，值得一提：它不只看自己估的数，还接住厂商的报错。识别“prompt 过长”靠一长串子串匹配（query.py:66-87），命中就做一次反应式压缩，而且只做一次：

原文：if not reactive_compact_attempted and _is_prompt_too_long_error(exc):（query.py:768），配合 MAX_PTL_RETRIES = 3 这类上限。

这是估算失败时的兜底，不是主要路径——但它暴露了估算型 harness 的通用结构：主动信号（自己算）和被动信号（厂商报错）本来就需要各有一套，因为前者可能算错，后者只有在已经浪费一次请求之后才会出现。

用量账本与成本

预算管的是“能不能发出去”，账本管的是“发出去花了多少”。两者用同一批 usage 数据，但职责不同：预算吃估算值（要快），账本只吃 provider 的真实值（要对得上账）。

第一步是归一化。同一个概念在不同厂商有不同的字段名，还有一种形状差异需要处理：

def normalize_usage(raw: dict[str, Any]) -> dict[str, int]:
    """把厂商 usage 归一化成四个桶：input / output / cache_read / cache_write。

    Anthropic 的三个输入桶互不重叠（input_tokens 只是未命中缓存的部分），
    所以原样搬运即可。OpenAI 的 prompt_tokens 已经把命中缓存的量算在里面，
    要减掉，否则成本会被重复计入。
    """
    if not raw:
        return {"input": 0, "output": 0, "cache_read": 0, "cache_write": 0}

    # 形状判定按「有没有 Anthropic 风格的 input_tokens」，不按有没有缓存字段：
    # 一次未命中任何缓存的响应里，两个 cache 字段都不会出现。
    if "input_tokens" in raw or "output_tokens" in raw:
        return {
            "input": int(raw.get("input_tokens", 0) or 0),
            "output": int(raw.get("output_tokens", 0) or 0),
            "cache_read": int(raw.get("cache_read_input_tokens", 0) or 0),
            "cache_write": int(raw.get("cache_creation_input_tokens", 0) or 0),
        }

    prompt = int(raw.get("prompt_tokens", 0) or 0)
    details = raw.get("prompt_tokens_details") or {}
    cache_read = int(details.get("cached_tokens", 0) or 0)
    return {
        "input": max(0, prompt - cache_read),
        "output": int(raw.get("completion_tokens", 0) or 0),
        "cache_read": cache_read,
        "cache_write": 0,
    }

那个形状判定条件是个实战细节：最初的写法判断“有没有 cache 字段”，结果一次未命中任何缓存的 Anthropic 响应（两个 cache 字段都不存在）被当成了 OpenAI 形状，input_tokens 被读成 0，账本全是零。测试 test_anthropic_shape 覆盖不到它，因为那个用例特意带了缓存字段——所以 test_accumulates_across_turns 用的是最朴素的 {input_tokens, output_tokens}。这个 bug 是写这一章时真踩到的。

账本按轮次汇总，并保留每次计费调用的明细：

    def record_usage(self, raw_usage: dict[str, Any], calls: int = 1) -> dict[str, int]:
        """记一次响应。`calls` 用于一次响应里含多次计费调用的情况（例如重试）。"""
        buckets = normalize_usage(raw_usage)
        if calls > 1:
            buckets = {key: value * calls for key, value in buckets.items()}
        self.total = _add(self.total, buckets)
        self.per_turn[self.turn] = _add(self.per_turn.get(self.turn, {
            "input": 0, "output": 0, "cache_read": 0, "cache_write": 0,
        }), buckets)
        self.attempts.append({"turn": self.turn, "calls": calls, **buckets})
        return buckets

为什么要有 calls 参数：一次重试是两次计费。DSH 把这件事放进了投影单元的名称里：llm/retry-started 会关闭上一份用量样本的替换槽，让重试的那次另算一笔：

原文：A final assistant-message sample replaces streaming usage from the same attempt; llm/retry-started ends that replacement scope, so a retry in the same step contributes another billed attempt.（token-meter/README.md:49）。

投影的具体实现是“同一 (turn, step) 内后者替换前者，超出这个范围就累加”：

    if (event.type === 'llm/retry-started') {
      return state.last?.turn === event.data.turn && state.last.step === event.data.step
        ? { ...state, last: null }
        : state
    }

usage-projection.ts:123-127。清空替换槽之后，重试的样本落进来时 previous 是空的，于是走加法而不是减法。

成本必须按四个桶分开算，因为缓存读和缓存写的单价和未命中输入不是一个量级。labs 把单价做成必传参数：

    def cost(self, buckets: dict[str, int]) -> float:
        return (
            buckets.get("input", 0) * self.input
            + buckets.get("output", 0) * self.output
            + buckets.get("cache_read", 0) * self.cache_read
            + buckets.get("cache_write", 0) * self.cache_write
        ) / 1_000_000

价格绝不写死。写死的那一刻，账单就变成了过期的账单——而且没人会记得回来改。OpenHarness 干脆完全不算钱，CostTracker 只累加两个整数：

    def add(self, usage: UsageSnapshot) -> None:
        """Add a usage snapshot to the running total."""
        self._usage = UsageSnapshot(
            input_tokens=self._usage.input_tokens + usage.input_tokens,
            output_tokens=self._usage.output_tokens + usage.output_tokens,
        )

engine/cost_tracker.py:14-19。它甚至连缓存桶都没有——UsageSnapshot 只有 input_tokens 和 output_tokens 两个字段（api/usage.py:11-12）。这在只用 Anthropic 直接端点、不开 prompt cache 的部署里没问题，但一旦命中缓存，两边的账都对不上。

OpenHarness 的 usage 每次响应重置一次再取最后一个事件的值，也就是只保留最近一次：

原文：usage = UsageSnapshot()（query.py:725），流结束时 usage = event.usage（query.py:752）。

累加是别人的事：调用方把每次的 snapshot 交给 CostTracker.add。分工清楚，但中间的每一步都要有人接住——漏接一次，账本就少一笔。DSH 用会话日志解决这个问题：用量是事件，投影单元从日志重放出来，不需要任何人“记得上报”。

坑与失败案例

坑 1：把 cache 命中量重复计入

触发条件：厂商的 usage 里 prompt_tokens 已经把命中缓存的部分算在内，而账本又单独加了一次 cached_tokens。

后果：prompt 越大、缓存命中越多，虚报越严重。开了 prompt cache 的部署里，账单会成倍偏大，而成本估算偏高通常没人会去查——它看起来“只是保守”。

源码怎么防的：DSH 把“互不重叠”写进类型注释，并把减法指定给适配器：

原文：Adapters whose providers fold cache hits into a total prompt count (DeepSeek's prompt_tokens) subtract them out.（llm/src/types.ts:172-173）。

labs 的 normalize_usage 在归一化时减："input": max(0, prompt - cache_read)。减完再 max(0, ...) 兜底，防止脏数据把 input 变成负数。注意 OpenHarness 没有防——它根本没有缓存桶，命中缓存的部分被当成 input 全额计入。

坑 2：估算偏低，压缩来得太晚

触发条件：中文语料 + 大工具 schema（JSON）走 4 字符 / token 的估算。int 里的方括号、引号、type 字段名，在分词器眼里都占 token。

后果：真实占用比估出来的高出一大截，压缩信号迟迟不触发，直到某次请求直接 400。整轮推理作废，重试时还得先压缩——等于把成本付了两遍。

源码怎么防的：DSH 的选择是不防估算误差、但承认它并限制它的传播范围——真实值当锚点，只有锚点之后的变化量按启发式算，所以误差不会随轮数累积：

原文：Present the composition rows as an approximate composition, never as a total.（token-meter/README.md:154）。

OpenHarness 的方向相反：用 4/3 填充把估算系统性抬高。这也是防——用早触发换不爆窗口。两种取舍都可以接受，危险的是第三种：既不校准、也不留余量，还相信自己数出来的数。

坑 3：形状判定太窄，账本静默归零

触发条件：按“有没有缓存字段”区分厂商 usage 形状。一次没命中任何缓存的响应里，cache_read_input_tokens 和 cache_creation_input_tokens 都不出现。

后果：Anthropic 形状的响应走进 OpenAI 分支，prompt_tokens 取不到，input 记成 0。账本安静地全零，不报错。这类 bug 特别难发现，因为“估算/预算”部分全都正常，只有对账时才看得出。

源码怎么防的：labs 改成按供应商独有的必需字段判定（input_tokens / output_tokens），并且测试用最朴素的响应形状：

    def test_accumulates_across_turns(self):
        self.ledger.record_usage({"input_tokens": 1_000, "output_tokens": 100})
        self.ledger.new_turn()
        self.ledger.record_usage({"input_tokens": 2_000, "output_tokens": 200})
        self.assertEqual(self.ledger.total["input"], 3_000)
        self.assertEqual(self.ledger.total["output"], 300)
        self.assertEqual(self.ledger.tokens_at_turn(1)["input"], 1_000)
        self.assertEqual(self.ledger.tokens_at_turn(2)["input"], 2_000)

教训可以推广：形状判定的依据必须是“这种形状一定有的字段”，不是“某种形状可能有的字段”。DSH 的做法更彻底——它不认识形状，形状差异在适配器里被抹平，meter 只看到内部类型。

坑 4：重试的用量没另算一笔

触发条件：一个 step 里发生重试，账本把两次 attempt 当成同一次调用，只记了后一次。

后果：账本比账单小。重试率高的部署里，偏差能达到一倍——而且方向很“安慰”：你以为成本可控。

源码怎么防的：DSH 用 llm/retry-started 显式关闭替换槽，让重试另立一笔（usage-projection.ts:123-127）；labs 用 record_usage(..., calls=2) 在调用点把倍数说清楚。判断标准很简单：厂商按调用计费，账本就必须按调用记账，不管这几次调用是不是属于同一个逻辑步骤。

坑 5：只归档“最后一份”用量样本

触发条件：循环每轮把 usage 变量重置，只把最后一个事件的值交出去。

后果：任何一处忘了上报就永久丢失，账本无法重放核对。OpenHarness 里的 usage = UsageSnapshot()（query.py:725）就是这个形状——它本身没问题，但正确性依赖调用链上每一环都接住。

源码怎么防的：DSH 的选择是把用量变成事件，投影从会话日志重放，谁读谁算，不依赖“有人记得上报”。代价是日志里必须记全（这也是 DSH 那条“Model-visible means logged”的另一面）。

把它接进循环

本章的模块在 labs 里是独立的：它不认识 run_agent，也不知道工具怎么执行。接法是三处：

  1. 发请求前：plan() 一次，拿到 level。ok 直接发；near_limit 发出去并提示；must_compact / overflow 先压缩再发——压缩策略见 hx-07。available_input 为负时，它就是要压掉的目标量。
  2. 响应回来时：ledger.record_usage(turn.usage)。labs/harness/messages.py 的 AssistantTurn.usage 已经放好了归一化前的原始字典，适配器不动它。
  3. 下一轮开始前：ledger.new_turn()。轮号与 run_agent 的 turns 计数口径一致（见 hx-01 的术语框）。

有两条纪律值得单独写下来。第一，预算用估算值，账本用真实值，不要把两者混在一个字段里——一旦混了，你既不知道预算为什么触发，也不知道账为什么对不上。第二，估算的系数和阈值都必须是参数，写死等于把配置债务藏进代码，等模型一换代就全部失效。

下一章 hx-06 会用到这里的两个桶：cache_read 和 cache_write。缓存能不能省钱，取决于命中率——而命中率只有靠这两个桶分别统计才看得出来。
