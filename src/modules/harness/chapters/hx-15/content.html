第 15 章

沙箱

主线故事 · 第 15 章（虚构）

那份假密钥的事过去两天，老唐在白板上画了个院子：一圈墙，墙里是项目目录，墙外是林舟的整个家目录——SSH 密钥、浏览器配置、另外三个客户的仓库，还有一个叫 .aws 的文件夹。

“橘子现在住在哪儿？”老唐问。

“项目目录里。”林舟说。

“它的进程住在哪儿？”

林舟愣了一下。橘子是用他的账号启动的，它跑的每一条命令都继承了他的全部权限和全部环境变量。grep -rn "API_KEY" . 里那个点，指的是当前目录；可如果模型写的是 grep -rn "API_KEY" ~，规则会因为路径越界拦下它，但一条 python -c "..." 里面打开什么文件，规则根本看不见。更早的时候，他还发现橘子跑过一次 env——为了“确认 Python 路径”——输出里有他的 GitHub token、两个云厂商的密钥，全部原样进了上下文，进了会话日志，也进了那天发给模型厂商的请求。

“前面两章都在回答‘该不该让它跑’，”老唐说，“这一章回答的是：就算放它跑了，它最多能碰到什么。”

老唐说完，又补了一句让林舟记到现在的话：“还有，别骗自己。你在 Python 里写的这个院子，墙是纸糊的。你得清楚哪几面墙是真的，哪几面只是画上去的。”

这一章要搭这个院子：命令在指定目录里跑，路径越界在执行前拦住，凭据类的环境变量不传给子进程，跑太久就杀掉，输出太多就落盘。然后专门花一节讲清楚，标准库能搭出的这个院子挡不住什么，以及要挡住它们需要换成什么。

权限规则（第 13 章）和命令解析（第 14 章）回答的都是“这次调用该不该发生”。它们都有漏判的可能：规则没写全，解析器遇到没见过的语法，用户在疲劳时点了“同意”。沙箱处理的是漏判之后的事——即使一条不该放行的命令真的跑起来了，它能造成的损失有多大。

这是一个思路的切换：从“识别坏动作”切换到“限制所有动作的影响范围”。前者永远在追赶，后者一旦设好就不依赖对每一条命令的理解。

先看全貌：沙箱是什么、管哪些事

一句话：沙箱是工具执行时的受限环境。它规定命令在哪个目录里跑、能看到哪些环境变量、能跑多久、能输出多少，以及能读写哪些路径。

它和前两章的关系是串联的：

  1. 权限规则决定这次调用能不能发出去；
  2. 命令解析帮权限规则看懂 run_bash 那一条字符串；
  3. 沙箱决定发出去之后，它最多能碰到什么。

沙箱要管的五件事：

  • 工作目录：命令在哪里跑，相对路径相对谁解析。
  • 路径边界：参数里的路径先规范化再判断是否越界，越界在执行前拒绝。
  • 环境变量：子进程只拿到白名单里的变量；令牌、密钥、口令一律不传。
  • 资源上限：超时、输出长度上限，超出时的处理方式（杀进程、落盘）。
  • 执行方式：直接执行程序，还是交给 shell 再解析一遍。

四个决定，先给结论：

决定看起来省事的做法本章的结论
环境变量子进程继承父进程的全部环境白名单传递；凭据类变量名一律剥离，连策略里主动注入的也不例外
执行方式用 shell 执行整条字符串，最方便默认直接执行 argv，不经过 shell；需要管道时由 harness 自己拼，或者在已经过解析的前提下显式开启
超时不设，或者设一个很大的值每个调用都有超时；超时要杀掉进程，结果里写清“被杀了”，而不是返回半截输出装作正常
隔离的强度在 Python 里检查路径就算沙箱了进程内的检查只能挡住 harness 看得见的路径；要挡住子进程自己打开的文件，必须用操作系统级隔离（容器、只读挂载、系统调用过滤）

三个仓库在这一层分别是什么水平

DSH（TypeScript）：把执行环境抽象成独立的一层，工具通过这一层执行，而不是自己去拉子进程。这让“换一种隔离方式”（本地进程、容器、远程执行）不需要改工具代码，是本章架构上最值得借鉴的一点。

OpenHarness（Python）：bash 工具直接在本地起子进程，带超时与输出截断；隔离主要依赖权限模式与确认，而不是执行环境本身。适合对照“没有独立执行层时，安全靠什么”。

learn-claude-code（教程）：subprocess.run(..., shell=True) 加一个超时，继承全部环境变量。它是本章的起点：每一节要补的，恰好就是这一行里缺的。

labs（本章要写的）：labs/harness/sandbox.py，工作目录、路径边界、环境白名单、超时与输出落盘，23 条测试，其中 2 条专门记录它挡不住的东西。

本章怎么读：

  1. 第 1 节讲为什么默认不经过 shell，这是执行层最基础的一个决定。
  2. 第 2 到第 4 节分别是路径、环境变量、资源上限，三者都可以直接抄进项目。
  3. 第 5 节讲执行结果怎么告诉模型；第 6 节是本章最重要的一节——标准库能做到的隔离，边界在哪里。
  4. 第 7 节讲怎么把沙箱和前两章接起来；第 8 节的坑可以当执行层的自查清单。

安全部分不再逐条标注 文件:行号，各仓库的实现用包名与函数名指代。

默认不经过 shell

执行一条命令有两种方式：

方式Python 写法谁来解析命令风险
经过 shellsubprocess.run("ls -la " + path, shell=True)系统 shell（sh / cmd）字符串里的 ;、$(...)、&& 都会被执行；参数拼接即注入
直接执行subprocess.run(["ls", "-la", path])没人解析，argv 原样传给程序参数里的特殊字符只是普通字符

经过 shell 的问题不只是“危险”，而是它让第 14 章的解析和实际执行变成了两件事：解析器看到的是字符串，执行时 shell 会按自己的规则再解析一遍。只要两者对某个语法的理解不一致（转义规则、编码、Windows 与 POSIX 的差别），判定就和执行脱节了。

所以 labs 的默认是直接执行 argv，shell=False：

@dataclass
class SandboxPolicy:
    """沙箱的策略。所有字段都是「更严的方向」上的默认值。"""

    root: str
    timeout: float = 10.0
    max_output: int = 200_000          # 字符数上限，超出部分落盘（正文 hx-08）
    allow_network: bool = False        # 只影响我们注入的环境变量，不构成真实隔离
    allow_write: bool = False          # 只挡 argv 里看得见的写路径；子进程自己开文件挡不住
    extra_env: dict[str, str] = field(default_factory=dict)
    shell: bool = False                # 默认不用 shell 执行，避免二次解析

    def __post_init__(self) -> None:
        self.root = str(Path(self.root).resolve())

这个默认值会让一部分命令跑不起来——管道、重定向、通配符展开都是 shell 的功能。有两种处理方式：

  • 由 harness 自己实现需要的那一小部分。比如“读文件并搜索”拆成两个工具调用，而不是一条 cat a | grep b。这是最稳的做法，代价是工具数量变多。
  • 在已经通过第 14 章解析的前提下显式开启 shell。解析结论是 readonly 的命令，交给 shell 执行的风险可控；结论是 opaque 的，绝不交给 shell。

learn-claude-code 用的是 shell=True，因为它的 bash 工具接收的就是一条字符串。教学上没问题，但这一行是从教程到产品时第一个要改的地方。

工作目录与路径边界

沙箱有一个根目录，命令在这里跑，相对路径相对它解析。路径边界的判定复用第 13 章的 resolve_within，越界统一转成沙箱自己的异常：

    def resolve(self, candidate: str, *, write: bool = False) -> Path:
        """把候选路径解析到沙箱内。写操作在只读沙箱里直接拒绝。

        越界统一转成 SandboxViolation：调用方只需要认识沙箱这一种异常，
        permissions 里的 PathEscape 是它的实现细节。
        """
        if write and not self.policy.allow_write:
            raise SandboxViolation(f"沙箱是只读的，不能写 {candidate!r}")
        try:
            return resolve_within(self.root, candidate)
        except PathEscape as exc:
            raise SandboxViolation(str(exc)) from exc

为什么要把 PathEscape 转成 SandboxViolation？因为调用沙箱的代码只应该认识沙箱这一种异常。权限层的异常类型是沙箱的实现细节；如果它漏出去，调用方就得同时捕获两种异常，迟早有一处会漏捕，然后一个越界路径就变成了一次未处理的崩溃。

执行前检查 argv 里的路径：

    def check_argv_paths(self, argv: Sequence[str], *, write: bool = False) -> None:
        """检查 argv 里看起来像路径的参数。

        教学版只挑「含分隔符或点是文件」的裸参数；真实实现会给每个工具声明
        哪些参数是路径，而不是靠猜。这里保守：拿不准就放过，由权限层兜底。
        """
        for arg in argv[1:]:
            if arg.startswith("-"):
                continue
            if any(sep in arg for sep in ("/", "\\", "..")) or Path(arg).suffix:
                self.resolve(arg, write=write)

这段代码是靠猜的：含路径分隔符、含 .. 或带扩展名的参数被当成路径。它会漏（cat secret 里的 secret 没有任何路径特征），也会误判（grep v1.2 a.txt 里的 v1.2 有扩展名）。真实项目的做法是让工具声明哪些参数是路径，而不是从 argv 里猜——这和第 02 章“schema 是唯一真相”是同一个思路。run_bash 这类无法声明参数的工具，正是沙箱最难管的地方，也是第 6 节要讲的局限的来源。

写操作的判定按程序名精确匹配，而不是看程序名里是否含有 rm：

WRITE_PROGRAMS = frozenset({
    "rm", "rmdir", "mv", "cp", "touch", "mkdir", "tee", "ln", "chmod", "chown",
    "truncate", "dd", "install", "rsync", "unzip", "tar", "patch",
})

子串匹配的问题第 14 章已经讲过：format、transform 里都有 rm。这类错误在执行层出现时尤其难查，因为它表现为“只读沙箱里某个无害的命令莫名其妙被拒”，而日志里只有一句“沙箱是只读的”。

环境变量：白名单传递，凭据一律剥离

子进程默认继承父进程的全部环境变量。对 agent 来说这几乎总是错的：harness 进程的环境里通常有模型厂商的 API key，开发者机器上还有 GitHub token、云厂商凭据、数据库口令。只要模型跑一次 env 或 printenv，这些值就进了上下文，接着进日志、进下一次请求、进摘要、进记忆。

labs 用两层过滤：

    def build_env(self, base: Mapping[str, str] | None = None) -> dict[str, str]:
        """构造子进程环境：白名单 + 剥离敏感变量 + 注入额外变量。"""
        source = dict(base if base is not None else os.environ)
        env: dict[str, str] = {}
        for key in SAFE_ENV_KEYS:
            if key in source:
                env[key] = source[key]
        for key, value in self.policy.extra_env.items():
            if any(hint in key.upper() for hint in SECRET_HINTS):
                # 策略里想注入凭据也不行：这条路径只用于无害的开关。
                continue
            env[key] = value
        if not self.policy.allow_network:
            # 不构成真实隔离（进程仍能开 socket），只是把常见的代理变量清掉，
            # 让「不能用网」这件事在行为上可见。正文会说明这一点。
            for key in list(env):
                if "proxy" in key.lower():
                    env.pop(key, None)
        return env
  1. 白名单：只有 PATH、HOME、TEMP、语言设置这类运行程序必需的变量会被传下去。白名单之外的一律不传，不需要判断它是不是凭据。
  2. 凭据名剥离：策略里额外注入的变量，如果名字里有 TOKEN、SECRET、PASSWORD、API_KEY 这类词，同样不传。这一层防的是“为了让某个工具能用，在配置里把密钥塞进 extra_env”这种善意的错误。
SECRET_HINTS = (
    "TOKEN", "SECRET", "PASSWORD", "PASSWD", "APIKEY", "API_KEY", "CREDENTIAL",
    "AUTH", "COOKIE", "SESSION_KEY", "PRIVATE_KEY", "ACCESS_KEY", "SSH_",
)

那工具确实需要凭据怎么办？比如一个调用内部 API 的工具。答案是凭据不经过子进程环境：由 harness 进程自己持有凭据、自己发请求，工具拿到的只是结果。凭据一旦进入子进程，你就无法控制子进程把它打印到哪里。

测试 test_secret_not_visible_to_child 在父进程里设置一个 LEAK_TEST_TOKEN，然后在子进程里读它，断言读到的是 absent。这条测试值得放进每个 harness 的测试集：它很短，但覆盖的是最常见、后果最严重的泄露路径。

关于网络：allow_network=False 在 labs 里只是把代理相关的环境变量去掉，不构成隔离——子进程仍然可以直接打开网络连接。标准库没有办法禁止一个子进程联网。真正的网络隔离需要操作系统或容器层面的手段（网络命名空间、防火墙规则、没有网卡的容器）。这个字段保留在策略里，是为了让“这次运行不应该联网”这件事在配置和日志里可见，而不是因为它能挡住什么。

资源上限：超时、输出、落盘

资源上限防的不是攻击，而是失控：一条 tail -f、一个等待输入的交互程序、一次意外的无限循环。没有超时，循环会一直卡在这一步；没有输出上限，一次 cat 就能塞满上下文。

    def run(
        self,
        argv: Sequence[str],
        *,
        cwd: str | None = None,
        timeout: float | None = None,
        stdin: str | None = None,
    ) -> ExecResult:
        """在沙箱里跑一条命令。不抛异常，所有失败都变成结果。"""
        started = time.monotonic()
        args = list(argv)
        if not args:
            return ExecResult(False, args, None, "", "空命令", 0.0, violation="空命令")

        workdir = self.resolve(cwd) if cwd else self.root
        try:
            write_hint = Path(args[0]).name.lower().removesuffix(".exe") in WRITE_PROGRAMS
            self.check_argv_paths(args, write=write_hint)
        except SandboxViolation as exc:
            return ExecResult(False, args, None, "", "", time.monotonic() - started, violation=str(exc))

        budget = timeout if timeout is not None else self.policy.timeout
        env = self.build_env()
        try:
            proc = subprocess.run(
                args,
                cwd=str(workdir),
                env=env,
                capture_output=True,
                text=True,
                encoding="utf-8",
                errors="replace",
                timeout=budget,
                shell=self.policy.shell,
                stdin=subprocess.DEVNULL if stdin is None else subprocess.PIPE,
                input=stdin,
                creationflags=_no_window_flags(),
            )
        except subprocess.TimeoutExpired as exc:
            stdout = _as_text(exc.stdout)
            stderr = _as_text(exc.stderr)
            return ExecResult(
                False, args, None, stdout, stderr, time.monotonic() - started,
                timed_out=True, truncated=False,
            )
        except FileNotFoundError:
            return ExecResult(
                False, args, None, "", f"命令不存在：{args[0]}", time.monotonic() - started,
            )
        except OSError as exc:
            return ExecResult(False, args, None, "", f"{type(exc).__name__}: {exc}", time.monotonic() - started)

        duration = time.monotonic() - started
        stdout, truncated_out, spill_out = self._cap(proc.stdout, "stdout")
        stderr, truncated_err, spill_err = self._cap(proc.stderr, "stderr")
        return ExecResult(
            ok=proc.returncode == 0,
            argv=args,
            returncode=proc.returncode,
            stdout=stdout,
            stderr=stderr,
            duration=duration,
            truncated=truncated_out or truncated_err,
            spill_path=spill_out or spill_err,
        )

这段代码里有几个决定：

  • stdin 默认接到空设备。不这样做的话，一个等待输入的程序（python 不带参数、git commit 不带 -m、任何“确认请输入 y”的脚本）会一直等到超时。接到空设备之后它会立刻读到 EOF，通常马上就退出了。
  • 所有失败都变成结果，不抛异常：超时、命令不存在、权限错误、路径越界，都返回 ExecResult。这和第 01 章“工具异常不能打断循环”是同一条规则在执行层的落实。
  • 超时被杀时保留已有输出。TimeoutExpired 里带着进程被杀前已经产生的输出，这部分对模型判断“卡在哪一步”很有用。
  • 超长输出落盘，复用第 08 章的思路：上下文里只留前 N 个字符和文件路径，全文在磁盘上可以按需取回。
    def _cap(self, text: str, stream: str) -> tuple[str, bool, str | None]:
        """超长输出：截前 N 个字符，全文落盘，返回路径。"""
        if len(text) <= self.policy.max_output:
            return text, False, None
        self.spill_dir.mkdir(parents=True, exist_ok=True)
        path = self.spill_dir / f"{stream}-{int(time.time() * 1000)}.txt"
        path.write_text(text, encoding="utf-8")
        head = text[: self.policy.max_output]
        return head, True, str(path.relative_to(self.root))

超时的默认值 10 秒是教学示意，不是推荐值。实际项目里超时应该按工具分开设置：跑测试可能需要几分钟，列目录不应该超过几秒。把超时设成“够所有命令用”的一个大数，等于没设。

执行结果怎么告诉模型

沙箱拒绝或者命令失败时，模型收到的文字决定了它下一步做什么。labs 把五种结局区分开：

    def as_tool_result(self) -> str:
        """给模型看的文本。失败要带上原因，否则模型只会重试同一条命令。"""
        if self.violation:
            return f"Error: 沙箱拒绝执行：{self.violation}"
        head = " ".join(self.argv)
        if self.timed_out:
            return f"Error: 命令在 {self.duration:.1f}s 后超时被杀：{head}（已终止整个进程）"
        body = self.stdout if self.ok else (self.stdout + self.stderr)
        note = f"（输出超过 {len(body)} 字符，已落盘 {self.spill_path}）" if self.truncated else ""
        return f"$ {head}\n{body}{note}"
结局模型收到什么模型应该做什么
沙箱拒绝（越界、只读）“沙箱拒绝执行：路径 ../x 越出工作区”改用工作区内的路径；不要重试同一条
超时被杀“命令在 10.0s 后超时被杀（已终止整个进程）”换一个不会阻塞的写法（加参数、限制范围），而不是原样重试
命令不存在“命令不存在：xxx”换命令，或者告诉用户需要安装什么
非零退出命令的标准输出与标准错误根据错误信息修正
成功但输出超长前 N 个字符 + “已落盘到某路径”需要更多内容时按页读取落盘文件

最需要区分的是“超时”和“失败”。如果超时被报告成一次普通的非零退出，模型会以为命令本身有错，于是修改参数重试同一条命令，再超时一次。明确说出“被杀了”，模型才会意识到问题在于这条命令会阻塞。

这个沙箱挡不住什么

这一节是本章最重要的部分。labs 的沙箱是在 Python 进程里做检查，它能管的只有 harness 看得见的东西：argv 里的参数、传给子进程的环境、子进程的运行时间和输出。子进程一旦启动，它做什么 harness 就看不见了。

具体来说，下面这些它都挡不住：

挡不住的事例子原因要挡住需要什么
子进程自己打开的文件python -c "open('/home/dev/.ssh/id_rsa').read()"文件路径在代码字符串里，不在 argv 的路径参数里文件系统隔离：容器、只读挂载、chroot、只给工作目录挂载权限

labs 用两条测试把这个局限钉住，断言的是“局限确实存在”：

    def test_readonly_flag_does_not_stop_child_writes(self) -> None:
        sandbox = Sandbox(readonly_policy(str(self.root)))
        result = sandbox.run([PY, "-c", "open('made-by-child.txt', 'w').write('x')"])
        self.assertTrue(result.ok)
        self.assertTrue((self.root / "made-by-child.txt").exists())

为什么要写一条“断言有漏洞”的测试？因为局限最大的危险是被遗忘。半年后有人看到 readonly_policy() 这个名字，会自然地以为它是只读的，然后把它用在一个真正需要只读保证的场景里。这条测试让局限出现在测试报告里；等哪天换成了真正的隔离，这条测试会失败，提醒你把它改写成“现在挡住了”。

那这个沙箱还有什么用？它挡住的是模型的常规行为里最常见的那部分：用相对路径越界、在参数里写 ../、读凭据环境变量、跑一个永不退出的命令、输出一大堆东西。这些占了实际事故的大多数，而它们都发生在 harness 看得见的地方。它挡不住的是有意构造的绕过，那需要操作系统来挡。把两件事分清楚，你就知道什么时候进程内检查够用，什么时候必须上容器：只要 agent 会处理不可信输入（网页、第三方仓库、用户上传的文件），就应该上真正的隔离，因为那时“有意构造的绕过”就不再是假设了（第 17 章）。

把沙箱接进执行流水线

三道关的顺序是：权限规则 → 命令解析（只对 run_bash）→ 沙箱执行。前两道在执行前，第三道在执行时：

层回答的问题拿到的信息漏判时谁兜底
权限规则（13）这次调用能不能发出去工具名、参数沙箱
命令解析（14）这条命令会做什么命令字符串权限规则的默认值 + 沙箱
审批（16）人同不同意调用的预览沙箱
沙箱（15）跑起来之后最多能碰到什么执行时的环境操作系统级隔离（如果有）

这张表最后一列说明了沙箱的位置：它是所有判断类机制的兜底。判断类机制（规则、解析、审批）都会因为“看错”而漏，沙箱不依赖“看对”。

架构上值得借鉴的是 DSH 的做法：执行环境是一个独立的层，所有需要执行外部程序的工具都通过这一层。这样有两个好处。一是不会有绕过沙箱的工具——如果每个工具自己调 subprocess，总会有一个工具忘了加限制。二是隔离方式可以替换——本地开发用进程内检查，处理不可信输入时切到容器，工具代码不需要改。

labs 的 Sandbox 也是按这个思路写的：工具不直接调 subprocess，而是调 sandbox.run()。换成容器实现时，保持 run() 的签名和 ExecResult 的结构不变即可。

坑与失败案例

坑一：子进程继承了全部环境变量

  • 触发条件：subprocess.run(...) 不传 env 参数。
  • 后果：模型跑一次 env，所有凭据进上下文，然后进日志、进发给厂商的请求、进压缩摘要、可能进长期记忆。这是一次泄露变成多次泄露的典型路径，而且事后很难清理干净。
  • 怎么防：环境变量白名单传递；凭据由 harness 进程持有，不进子进程。加一条“父进程设置假 token、子进程读不到”的测试。

坑二：用 shell 执行拼接出来的字符串

  • 触发条件：subprocess.run(f"grep {pattern} {path}", shell=True)。
  • 后果：模型给的 pattern 里只要有 ; rm -rf ~，就会被执行。而且这个注入发生在 harness 自己的代码里，不在 run_bash 工具上，权限规则和命令解析都看不到。
  • 怎么防：用 argv 列表执行，shell=False。模型参数永远作为单独的 argv 元素传递，不参与字符串拼接。

坑三：超时之后返回半截输出，装作正常

  • 触发条件：超时被捕获后，把已有的部分输出当作结果返回，不标注超时。
  • 后果：模型以为命令正常结束了，把半截的测试输出当成完整结果——“测试只跑了 12 个，全部通过”，实际上第 13 个卡住了。
  • 怎么防：超时作为独立的结局，结果文字第一句就写“超时被杀”。labs 的 ExecResult.timed_out 与 as_tool_result() 就是这么做的。

坑四：交互式程序把循环卡死

  • 触发条件：子进程的 stdin 没有处理，命令在等待输入（git commit 打开编辑器、脚本问“确定吗？”）。
  • 后果：每次都等到超时，而且超时之后模型通常会重试同一条命令。
  • 怎么防：stdin 默认接到空设备，让等待输入的程序立刻读到 EOF；同时设置 GIT_EDITOR=true、CI=1 这类让工具进入非交互模式的环境变量（放进环境白名单的额外注入里）。

坑五：把进程内检查当成隔离

  • 触发条件：系统只有 Python 层面的路径检查，就开始处理第三方仓库或者网页内容。
  • 后果：一段被注入的指令让模型跑 python -c "..."，代码字符串里的路径完全不经过检查，沙箱的“只读”和“工作区”都失效。
  • 怎么防：清楚记录进程内沙箱的局限（labs 的 LimitTests）；处理不可信输入时换成操作系统级隔离。名字也很重要：如果一个策略挡不住子进程写文件，就不要叫它 readonly 而不加说明。

坑六：超时只杀了直接子进程

  • 触发条件：命令启动了自己的子进程（测试框架、构建工具、开发服务器）。
  • 后果：超时后 harness 以为命令结束了，孙进程继续占着端口、吃着 CPU，下一次运行时报“端口已被占用”。在长时间运行的 agent 里，这类残留进程会越积越多。
  • 怎么防：在 POSIX 上用新的进程组启动子进程，超时时杀整个进程组；在 Windows 上用 Job Object。labs 的教学版没有做这一步，正文这里列出来，作为从教学版走向真实实现时必须补上的一项。

一句话取舍：在可信的本地仓库里，进程内检查加环境白名单加超时，已经能挡住绝大多数事故；一旦 agent 要处理不可信输入，就必须换成操作系统级隔离。最值得提前做的不是隔离本身，而是 DSH 那种“执行层独立”的结构——它让你在需要更强隔离的那一天，只换一层，而不是改所有工具。

小结

  • 沙箱是判断类机制（规则、解析、审批）的兜底：它不依赖“看对”，只限制影响范围。
  • 默认直接执行 argv，不经过 shell；模型参数永远不参与字符串拼接。
  • 环境变量白名单传递，凭据由 harness 持有，不进子进程。
  • 每个调用都有超时；超时单独报告，stdin 接空设备，超长输出落盘。
  • 进程内的沙箱挡不住子进程自己打开的文件、联网、残留进程、资源耗尽。把局限写成测试，处理不可信输入时换成操作系统级隔离。
  • 所有执行外部程序的工具走同一个执行入口，隔离方式才可以替换。

到这里，模型的每个动作都有了三道关：能不能做、做的是什么、做了最多能怎样。还剩一个问题：规则说“问人”的时候，到底怎么问。继续读：审批与升档。
