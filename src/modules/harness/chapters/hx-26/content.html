第 26 章

Agent 范式

主线故事 · 第 26 章（虚构）

白板背面写下的第一个问题来自阿青团队自己的活：“我们想把过去两年的故障复盘整理成一份一页纸的经验清单。”

橘子用最直接的办法做：读一份复盘、写一段、接着读下一份。读到第十一份，它的上下文里已经堆了十份复盘的全文和十段半成品，而它写出来的清单开始重复——第五份和第八份讲的是同一类问题，但它没有发现，因为那两份相隔太远，中间隔了六个文件。

老唐换了三种做法试同一件事。

第一种，让它先列出计划再执行：“先按主题把四十八份复盘分成六组，每组写一小段，最后合并。”它列了计划，橘子照着执行，中途发现分组不合理，重新分了一次。清单的质量明显好了，但多花了规划的时间。

第二种，把四十八份拆成六组，每组开一个独立的子代理，各自总结，最后主线合并。整体快了很多，每组内部的细节互不干扰。代价是有一组的结论和另一组对不上，因为两组对“配置错误”和“部署错误”的划分不同——子代理彼此看不到对方。

第三种，先让橘子写一版，然后交给一个“评审”角色，拿着他们的故障复盘模板逐条核对，把不合格的退回去重写。这一版最慢，但只有这一版让阿青直接拿去用了。

“零件是同一套，”老唐说，“摆法不一样，结果差得很多。”

这一章不再讲新的部件，而是讲怎么摆：同一套循环、工具、权限、委派，按什么样的控制流去解一个任务。这是全书最后一章。

前二十五章造的是 harness。这一章换一个角度：用这些部件，按什么样的控制流去解一个任务。同一个 harness，摆法不同，成本和效果可能差好几倍。

这些摆法在文献里被叫做 agent 范式。它们不是互斥的选项，也不是越复杂越好；它们各自适合某一类任务。真正需要练的能力，是看到一个任务之后判断该用哪一种——或者判断这个任务根本不该交给 agent。

先看全貌：有几个范式、分别适合什么

一句话：范式是 harness 之上的控制流——谁决定下一步、什么时候结束、状态放在哪。同一个 agent 循环，可以摆成六种以上的形状。

范式控制流适合的任务主要代价
ReAct思考 → 行动 → 观察，循环到给出答案边探索边决定的任务：查文档、调试、找 bug容易在同一个思路上打转；轮数不好预估
Plan-and-Execute先列完整计划，再逐步执行，可重新规划步骤明确、需要人先审计划的任务多一次规划调用；计划可能第一步就被现实推翻
分治（Divide and Conquer）拆成独立子任务，分别求解，再合并子任务彼此独立的批量工作：总结长文档、迁移很多文件合并是新的失败点；子任务之间看不到彼此
DAG 规划有依赖关系的子任务按拓扑顺序执行，同层可并行有明确前置关系的工程任务：先建表、再写接口、最后端到端测试规划结果必须校验（缺依赖、成环）
Reflexion做 → 评审 → 反思 → 带着反思重做有可验证标准、第一次常常不达标的任务必须有外部评审信号；多花轮数
多 agent 编排协调者分派给不同角色的 worker，再汇总需要不同视角或不同工具集的任务：审查 + 测试 + 文档沟通与汇总成本高；角色之间可能不一致

四个决定，先给结论：

决定看起来省事的做法本章的结论
怎么选范式用最熟的那一种看两件事：子任务之间是否独立、有没有可验证的完成标准
要不要先规划总是先列一个计划步骤少于三步、或者下一步取决于刚看到的结果时，直接 ReAct；计划值得列的时候是“做完之后能让人审”
谁来验收让模型自己说“完成了”能验证的就跑验证（测试、规则、模板）；不能验证的，才让人看
什么时候停下等模型说完了每个范式都要有自己明确的上限：轮数、子任务数、尝试次数、递归深度

三个仓库在这一层分别是什么水平

DSH（TypeScript）：本体是一个 ReAct 循环（思考与工具调用交替），把“长任务不跑偏”交给外部机制——一个专门的长任务包用工作区当作长期记忆和事实来源，靠循环推进工作。它没有内置“先规划再执行”这一步，而是通过指令文件和 Skill 把计划写在仓库里。

OpenHarness（Python）：本体也是循环；有几种权限模式，其中“计划模式”限制了执行类的工具，用于先让人看方案。

learn-claude-code（教程）：课程后期有一课专门讲目标循环，属于长任务的规划与推进；其余章节都是循环加不同部件。

三个仓库的共同点是：它们都只提供一种执行形状（循环），把别的范式当成“指令 + 工具组合”来实现。这是很务实的做法，也是本章后面要展开的观点——范式的差别主要在提示、工具集和外部验收机制上，而不一定需要新的运行时。

labs（本章要写的）：labs/harness/paradigms.py，六个范式各写成一个小函数，都基于同一套 run_agent 和 LLM 协议，18 条测试用 FakeLLM 回放。

本章怎么读：

  1. 第 1 节讲 ReAct，以及它其实是第 01 章循环的一种用法，不是新东西。
  2. 第 2、3 节讲 Plan-and-Execute 与分治，这两节给出“什么时候值得先规划 / 什么时候值得拆开”。
  3. 第 4 节讲 DAG，第 5 节讲 Reflexion（外部验证信号是关键），第 6 节讲多 agent 编排。
  4. 第 7 节给出选择流程，第 8 节讲组合，第 9 节讲什么时候不该用 agent。

本章讲的是控制流与取舍，不引用具体源码行；各仓库的做法按已核对的笔记描述。

ReAct：思考、行动、观察

ReAct 是 2022 年提出的一种提示与循环方式：让模型交替地产出“思考”和“行动”，行动的结果作为观察回灌，直到它能给出答案。名字来自 reasoning（推理）加 acting（行动）。

它和本书第 01 章讲的 agent loop 是同一件事，唯一的区别是要求模型把思考写出来：

REACT_SYSTEM = (
    "每一步先用一两句话写出你的思考（以「思考：」开头），再决定调用哪个工具；"
    "看到工具结果后继续思考。确定答案后，不再调用工具，直接给出最终回答。"
)

为什么值得多写这几句思考？因为循环里每一步看到的只有历史：如果历史里只有工具调用和工具结果，模型下一步只能从“刚才发生了什么”重新推断“我在做什么”。把思考写下来，前面的意图就留在了上下文里，后续每一步都能看到。

    def test_thoughts_and_actions_interleave(self) -> None:
        llm = FakeLLM([
            tool("search", "思考：先查一下默认超时是多少。", q="timeout"),
            tool("calc", "思考：文档说 30 秒，换算成毫秒。", expr="30*1000"),
            text("默认超时是 30000 毫秒。"),
        ])
        trace = react(llm, "默认超时是多少毫秒？", TOOLS, SCHEMAS)
        self.assertEqual(trace.actions, ["search", "calc"])
        self.assertEqual(len(trace.thoughts), 3)
        self.assertTrue(trace.thoughts[0].startswith("思考"))
        self.assertEqual(trace.answer, "默认超时是 30000 毫秒。")
        self.assertEqual(trace.stop, "completed")

ReAct 的代价要说清楚：

  • 多花 token。每轮多写一段思考，思考也会一直留在历史里。
  • 思考会变成承诺。模型写下“我先检查配置，再检查代码”，后面即使发现方向不对，也倾向于把这句话执行完。这类现象在有明确计划的任务里更明显。
  • 轮数不好预估。它在探索类任务里效率最高（不需要预先知道路怎么走），在步骤明确的任务里反而比直接列计划更慢。

适合 ReAct 的信号：你不知道答案在第几个文件里；下一步做什么取决于刚才看到的输出；需要边查边判断。

Plan-and-Execute：先列计划，再执行

和 ReAct 相反的一种摆法：先让模型把完整计划列出来，再一步步执行，每步执行完可以让规划者根据结果调整剩余计划。

def plan_and_execute(planner: LLM, executor_factory: Callable[[], LLM], task: str,
                     tools: dict[str, Tool], schemas: list[dict], *,
                     max_steps: int = 10, replan: bool = True) -> PlanRun:
    """先规划、再逐步执行。每执行完一步，可以让规划者根据结果修改剩余计划。

    和 ReAct 的区别：计划是显式的数据，可以在执行前给人看、可以校验、可以在第 n 步时修改；
    代价是多了规划调用，而且计划可能在第一步就被现实推翻。
    """
    run = PlanRun()
    plan = [str(s) for s in parse_json_list(ask(planner, PLANNER_SYSTEM, task))]
    run.plans.append(list(plan))
    while plan:
        if len(run.steps) >= max_steps:
            run.stop = "max_steps"
            return run
        step = plan.pop(0)
        done = "\n".join(f"- {s}：{r}" for s, r in run.steps)
        prompt = f"总任务：{task}\n已完成：\n{done or '（无）'}\n现在执行这一步：{step}"
        result = run_agent(executor_factory(), EXECUTOR_SYSTEM, prompt, tools, schemas, LoopConfig(max_turns=6))
        run.steps.append((step, result.final_text.strip() or f"（未完成：{result.stop}）"))
        if replan:
            done = "\n".join(f"- {s}：{r}" for s, r in run.steps)
            plan = [str(s) for s in parse_json_list(ask(
                planner, REPLANNER_SYSTEM, f"总任务：{task}\n已完成：\n{done}\n原剩余计划：{json.dumps(plan, ensure_ascii=False)}"))]
            run.plans.append(list(plan))
    run.stop = "completed"
    return run

它比 ReAct 多出来的东西是计划本身是一份数据——可以在执行前展示给人看、可以校验（步骤数、是否有循环依赖）、可以在执行到一半时修改：

    def test_plan_then_execute_with_replan(self) -> None:
        planner = FakeLLM([
            text('["列出文件", "统计行数", "写报告"]'),
            text('["统计行数", "写报告"]'),
            text('["写报告"]'),          # 规划者可以根据结果修改剩余计划
            text("[]"),
        ])
        executor_outputs = iter(["共 3 个文件", "共 120 行", "报告已写好"])
        run = plan_and_execute(planner, lambda: FakeLLM([text(next(executor_outputs))]), "做个统计", TOOLS, SCHEMAS)
        self.assertEqual(run.stop, "completed")
        self.assertEqual([s for s, _ in run.steps], ["列出文件", "统计行数", "写报告"])
        self.assertEqual(len(run.plans), 4)

什么时候值得先规划：

信号为什么
步骤多（超过五步）且相互关系明确计划能帮你（和模型）看到全局，避免走一步看一步导致的返工
想让人先审一遍方案再动手计划是数据，可以直接展示、直接编辑；这是 OpenHarness 的“计划模式”在做的
步骤之间需要保持一致的约定计划里可以写明约定（命名、风格、接口），执行时每一步都能看到

什么时候不值得：步骤少于三步；或者下一步严格取决于刚看到的结果（这时候列出来的计划第一步就会被推翻，白花一次调用和一笔 token）。

有一个细节容易忽略：重新规划的频率。每一步都重新规划最灵活，但每一步都要多一次模型调用；只在失败时重新规划最省，但可能沿着一个错误的计划走很多步。折中做法是：每一步执行完都检查一次“原计划是否还成立”，只有在偏离时才重新规划——labs 的实现里，规划者被明确告知“如果任务已经完成，输出空数组”，这也给了它提前收工的机会。

分治：拆开、各自解、合并

分治解决的是故事里那种问题：四十八份复盘，每份都要读全文，但主线不需要记住每一份的细节——它只需要每组的一段结论。

def divide_and_conquer(llm: LLM, task: str, *, max_depth: int = 2, max_children: int = 4,
                       depth: int = 0) -> DacNode:
    """递归地拆分、求解、合并。

    分治适合「子任务彼此独立」的情况：总结一份很长的文档（按章节）、审查一个大 PR（按文件）、
    调研一个问题（按方向）。每个子任务在自己的上下文里完成，主上下文只看到子结果。
    两个必要的上限：递归深度和分支数，否则拆分本身就会失控。
    """
    node = DacNode(task, depth)
    parts: list[str] = []
    if depth < max_depth:
        parts = [str(p) for p in parse_json_list(ask(llm, SPLIT_SYSTEM, task))][:max_children]
    if not parts:
        node.result = ask(llm, SOLVE_SYSTEM, task)
        return node
    node.children = [divide_and_conquer(llm, p, max_depth=max_depth, max_children=max_children, depth=depth + 1)
                     for p in parts]
    pieces = "\n".join(f"[{c.task}]\n{c.result}" for c in node.children)
    node.result = ask(llm, MERGE_SYSTEM, f"总任务：{task}\n子任务结果：\n{pieces}")
    return node

它的适用条件很明确：子任务彼此独立。四十八份复盘可以按主题分组，组与组之间不需要互相参照；反过来，“把昨天的改动整理成一份发布说明”就不适合拆——每一条改动都可能影响别人怎么理解另一条。

三个必须设的上限：

  • 递归深度。拆出来的子任务还能再拆，不设深度会一直拆下去，每一层都是一次模型调用。
  • 分支数。一次拆出二十个分支，合并那一步就要读二十份结果，合并本身又变成了一个新的长任务。
  • 拆不动的就直接做。labs 的实现里，模型可以返回空数组表示“这个任务足够小，直接完成”——判断“不需要拆”和判断“怎么拆”同样重要。

合并是分治最容易被低估的一步，也是它最典型的失败点：故事里两组子代理对“配置错误”和“部署错误”的划分不同，合并出来的清单里同一类问题出现了两次。三个缓解办法：拆分时就把分类标准写清楚（而不是让每个子代理自己决定）；合并时明确要求“发现重复或矛盾要指出来”；或者干脆把合并也当成一个需要判断的子任务，用一次专门的模型调用来做。

DAG 规划：有依赖的分层执行

分治假设子任务彼此独立。现实中很多任务有依赖关系：“先设计表结构，再写接口，再写页面，最后端到端测试”——接口依赖表结构，端到端测试依赖接口和页面。

def topo_layers(tasks: list[DagTask]) -> list[list[str]]:
    """按依赖关系分层：同一层的任务互不依赖，可以并行；下一层依赖上一层。

    规划结果来自模型，必须校验：依赖不存在的任务、重复 id、有环，都在执行前报错。
    """
    ids = [t.id for t in tasks]
    if len(set(ids)) != len(ids):
        raise ValueError("任务 id 重复")
    known = set(ids)
    for t in tasks:
        missing = [d for d in t.deps if d not in known]
        if missing:
            raise ValueError(f"任务 {t.id} 依赖了不存在的任务 {missing}")
    remaining = {t.id: set(t.deps) for t in tasks}
    layers: list[list[str]] = []
    while remaining:
        ready = sorted(i for i, deps in remaining.items() if not deps)
        if not ready:
            raise CycleError(f"依赖有环：{sorted(remaining)}")
        layers.append(ready)
        for i in ready:
            del remaining[i]
        for deps in remaining.values():
            deps.difference_update(ready)
    return layers

拓扑分层之后，同一层里的任务互不依赖，可以并行；每一层执行完再进下一层：

    def test_each_task_sees_only_its_deps(self) -> None:
        seen = {}

        def solve(task, inputs):
            seen[task.id] = sorted(inputs)
            return f"{task.id}-done"

        results, _ = run_dag(self.TASKS, solve)
        self.assertEqual(seen["e2e"], ["api", "ui"])
        self.assertEqual(seen["api"], ["schema"])
        self.assertEqual(results["e2e"], "e2e-done")

两件事值得强调：

  • 规划结果必须校验。依赖了不存在的任务、id 重复、依赖成环，这三种错误在模型给出的计划里都可能出现（尤其成环：模型会写出“A 依赖 B，B 依赖 A”这种看起来合理的东西）。校验要在执行前做，报错要具体。
  • 每个任务只拿到它依赖的结果，而不是全部已完成的结果。这既省上下文，也避免无关信息干扰判断。labs 测试里 e2e 只看到 api 和 ui 的结果，看不到 schema 的——因为 schema 的内容已经体现在接口里了。

DAG 的代价是“层”的粒度不容易定好：一层里塞十个任务，并行度上去了，但任何一个人的失败都会让整层重来；一层一个任务，就退化成串行。实践中常见的是“层内不超过 3–5 个，且尽量让同层的任务类型相同”（都是读、都是改、都是验证）。

Reflexion：做完之后自我反思

Reflexion 的思路：第一次尝试失败后，让模型根据失败信息写一段反思，再带着这段反思重做。它的核心不是“反思”这个动作，而是失败信息从哪里来：

def reflexion(llm: LLM, task: str, evaluate: Callable[[str], tuple[bool, str]], *,
              max_attempts: int = 3) -> list[Attempt]:
    """尝试 → 评审 → 反思 → 带着反思再尝试。

    关键在评审器 evaluate：它必须是**外部的、可验证的**信号（测试是否通过、规则是否满足），
    而不是让同一个模型自己说「我觉得对了」。没有外部信号的反思，常常只是把错误换个说法重复一遍。
    反思只保留最近几条，避免它们自己把上下文撑满。
    """
    attempts: list[Attempt] = []
    reflections: list[str] = []
    for _ in range(max_attempts):
        memo = "\n".join(f"- {r}" for r in reflections[-3:])
        prompt = task if not memo else f"{task}\n\n之前失败的反思：\n{memo}"
        output = ask(llm, ATTEMPT_SYSTEM, prompt)
        passed, feedback = evaluate(output)
        attempt = Attempt(output, passed, feedback)
        attempts.append(attempt)
        if passed:
            break
        attempt.reflection = ask(llm, REFLECT_SYSTEM, f"任务：{task}\n你的输出：{output}\n评审结果：{feedback}")
        reflections.append(attempt.reflection)
    return attempts

评审器必须提供外部的、可验证的信号：

评审信号例子可信度
测试结果跑一遍测试，哪个用例失败最高：客观、可复现
规则检查lint、模板校验、schema 校验高
另一个模型的判断（带明确标准）“逐条核对这份清单是否覆盖模板里的五项”中：标准要写得具体，否则变成另一个模型的印象
让同一个模型自评“我觉得对了”—低：它常常把错误换个说法再说一遍

故事里的第三版就是最好的例子：评审角色拿着他们的故障复盘模板逐条核对，这是“带明确标准的外部判断”，所以那一版能直接用。

三个实现细节：

  • 反思要短。labs 提示里写的是“两三句话，不要写代码”——反思会进入下一次尝试的提示，一篇长反思会把任务本身挤到后面。
  • 只保留最近几条反思。labs 只带最后三条。每一条反思都是“这一轮之前失败过”，积累太多会让模型变得过度谨慎。
  • 尝试次数有上限，而且失败要如实报告。三次之后还是不过，就把三次的输出和三次的失败原因一起交给人，不要挑一个看起来最像的当成结果。

多 agent 编排：协调者与角色

最后一种摆法：一个协调者把任务分派给不同角色的 worker，各自完成后由协调者汇总。

def orchestrate(coordinator: LLM, workers: dict[str, Worker], task: str, ...) -> OrchestrationRun:
    """协调者分派、worker 各自完成、协调者汇总。

    每个 worker 有自己的系统提示和工具集（权限按角色收窄，hx-23）。
    协调者给出的角色名必须在名单里，不在的拒绝并记录——不要让模型临时发明一个角色。
    """

它和第 23 章的子代理有什么区别？子代理是“同一件事、拆给多个平行的执行者”；编排是“不同的事、交给不同能力的人”。前者的差异在于任务，后者的差异在于角色：审查者便宜但严格，测试者只会写测试，文档者只读代码不写代码。

它的三种典型收益：

  • 工具集按角色收窄。审查者只有读权限，它对代码库的任何判断都不会改坏东西；这正是第 23 章“权限只能收窄”的应用。
  • 视角隔离。让写代码的和审代码的角色分开，比同一个上下文既当运动员又当裁判更容易发现问题。
  • 成本优化。简单角色（改格式、生成文档）用便宜的小模型，判断密集的角色用大模型。

它的代价也很实在：汇总成本。协调者要把各角色的结果读进来汇总，这一步的输入可能比任何单个角色都长。而且角色之间可能给出矛盾的结论——协调者的提示里明确要求“指出它们之间的分歧”，而不是把矛盾抹平，这一点对用户信任很重要。

labs 的实现里有一个刻意的限制：协调者给出的角色名必须在预设名单里，不在的拒绝并记录。让模型临时发明一个角色（“再加一个 hacker 角色来绕过权限”），本质上是让被管理的对象决定管理结构。

怎么选：一个判断流程

面对一个任务，可以按这个顺序问自己四个问题：

  1. 这件事有可验证的完成标准吗？有（测试、校验、模板）→ 优先用 Reflexion，因为你能自动判断做得好不好。没有 → 后面要么依赖人验收，要么把标准写出来。
  2. 它需要分几步、步与步之间有依赖吗？步骤多但彼此独立 → 分治。步骤多且有依赖 → DAG。步骤少或者下一步取决于刚看到的结果 → ReAct。
  3. 需要不同的视角或不同的工具集吗？需要 → 多 agent 编排。不需要 → 单 agent 加上第 23 章的子代理就够了。
  4. 整个过程要让人参与吗？要 → Plan-and-Execute（计划可审）加第 16 章的审批。不要 → 前面几项已经覆盖。
任务的样子建议
“这个测试为什么失败”ReAct：答案在第几个文件里事先不知道
“给这个功能写一份实现方案，给我看看”Plan-and-Execute：产物就是计划，需要人审
“把这 200 个文件的日志调用换掉”分治 + 子代理：每个文件独立，主线只要结论
“做数据迁移：先建表、再灌数据、再切读流量”DAG：有硬依赖，顺序错不得
“写一个符合我们规范的模块，规范有 40 页”Reflexion：规范检查是可验证的外部信号
“审一下这个 PR，顺便补测试，再更新文档”多 agent 编排：三种角色、三种工具集
“把邮件收件箱整理一下”先别交给 agent，看第 9 节

范式可以叠加

这六种不是单选题。实际系统里常见的是几层叠在一起：

  • 编排 + 分治：“审查者”这个角色本身可以把二十个文件拆给二十个子任务。
  • 计划 + DAG：先规划出任务清单，再把清单里的依赖关系解析成 DAG 执行。
  • ReAct + Reflexion：循环里每一轮结束都跑一次验证，不过就带着失败信息进入下一轮——这其实是很常见的形态，只是没人叫它 Reflexion。
  • 任何范式 + 长任务连续性（第 25 章）：跨天的任务无论用哪种摆法，都需要交接文件；DAG 尤其需要，因为“哪些节点做完了”必须落在文件里。

叠加时要小心一件事：上限要按总数算，不能按每层算。一个“编排 + 分治”的系统里，如果三层各自允许 10 次尝试、5 个子任务，那么最坏情况是 10 × 5 × 5 = 250 次模型调用。第 23 章讲过这个问题，在范式叠加时会更严重。

labs 的六个函数都留了上限参数，并且在文档里写明每个上限是防什么的。看这些参数怎么设，比看控制流本身更能学到一个真实系统的分寸感。

什么时候不该用 agent

这一节用否定的方式给整本书收尾。

范式做得再漂亮，也不改变一个事实：agent 的优势在于处理事先描述不清楚的任务。如果一个任务能被完整、无歧义地写成步骤，那么脚本、SQL、构建流水线或者一段普通的代码做这件事，会更快、更便宜、更可靠。用 agent 做这类任务，你是在花模型的价钱买确定性的东西。

几个明确的“该用脚本而不是 agent”的信号：

信号为什么要用脚本
步骤完全固定，每次一样写一次脚本就能重复用；用 agent 每次都要重新理解一遍
需要确定性发布、部署、数据迁移这类操作的顺序和边界不该由概率模型决定
失败代价高且无法重来删数据、发消息、转账——这类操作应该由人或者严格校验的代码来做
输入输出是结构化的格式转换、字段映射写正则或 SQL 更准
任务是“跑一下看结果”直接跑，不用经过模型理解一遍

反过来，agent 真正占优的地方：需求描述得含糊、边界要靠探索（“找出这个项目里为什么会有这个奇怪的现象”）；每次输入都不一样、没法写成规则（“把这个 issue 处理掉”）；以及中间结果需要判断才能决定下一步（“这个测试失败是环境问题还是代码问题”）。

一个实用的组合是：用 agent 找到该做什么，用脚本去做。让 agent 分析出“这 200 个文件里，有 37 个需要改”，然后由一段确定的脚本去改这 37 个文件。这样既用上了模型的判断力，又把执行放在了可复核、可重跑的地方。

小结

  • 范式是 harness 之上的控制流。六种常见摆法：ReAct、Plan-and-Execute、分治、DAG、Reflexion、多 agent 编排。
  • 选择看三件事：子任务是否独立（分治 / DAG）、有没有可验证的完成标准（Reflexion）、需不需要不同视角（编排）。步骤少或下一步取决于刚才的结果，就用 ReAct。
  • Plan-and-Execute 的价值是计划变成可审、可改的数据；代价是多一次调用，而且第一步就可能被推翻。
  • 分治的两个失败点：合并（重复与矛盾）和上限（深度、分支数）。
  • Reflexion 的关键是外部验证信号；让同一个模型自评，通常只是把错误换个说法。
  • 编排的收益来自角色与工具集的差异，代价是汇总成本和角色间的不一致。
  • 范式可以叠加，但上限要按总数算。
  • 能被完整写成步骤的任务，用脚本而不是 agent；最好的组合常常是“agent 判断该做什么，脚本去做”。

全书到这里结束。从第 00 章的一个循环开始，到最后这一章的控制流，中间多了上下文管理、记忆、安全、韧性、扩展、可观测性和连续性——但最核心的那件事一直没变：模型负责提出下一步，harness 负责判断这一步能不能做、做了会怎样、做完之后记住什么。

主线故事 · 尾声（虚构）

那份一页纸的经验清单，阿青最后采用的是第三版的产物——先用分治把四十八份复盘分成六组，每组一个子代理写一段；最后一轮交给评审角色，拿着他们的模板逐条核对，不合格的退回重写。橘子在过程中被打回了两次，改完的版本阿青直接发给了部门。

老唐把四页白板背面那行字擦掉，重新写了一句：“先想清楚这活适合怎么摆，再动手。”

小满——那个从第二章开始就在旁边看着的实习生——问了一个问题：“那我们以后是不是每写一个功能，都要先把这六种摆法试一遍？”

“不用，”老唐说，“你在心里过一遍就够了：这件事要几步、这几步之间有没有依赖、做完之后你能不能自己验证。答完这三个问题，摆法基本就定了。”

“那要是三个问题都答不上来呢？”

“那就先别写代码，”老唐说，“先把这三件事想明白。”

橘子还在跑。它的日志里现在有主线、子代理、重试、压缩、审批、拦截、熔断、降级、交接和 span —— 这些东西加在一起，就是这二十六章讲的那一层：模型外面那个让它真的能干活的程序。
