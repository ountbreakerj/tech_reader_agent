第 8 章

工具输出卸载

上一章讲完工具怎么执行、结果怎么写进历史，还剩一个没解决的问题：有些结果根本装不进上下文。一条 grep -r、一次 npm install、一个被拉下来的网页正文，随便就几万到几十万字符。这一章处理的就是从「工具产出内容」到「内容进入历史」之间的那一步。

先看清这一步的位置。工具结果的生死链条是这样：工具执行 → 结果经过 tools/post-execute 之类的后置策略 → 写进会话日志 → 推导成模型可见的消息。卸载发生在第二步和第三步之间，它改的是「写进日志的那份内容」，而不是「日志里已有的内容」。这个位置决定了它和压缩（第 07 章）是两件事：卸载在结果产生的那一刻就动手，压缩在历史已经太长之后才动手。后面第 6 节会把这条分界线画清楚。

本章先讲清楚为什么不能直接塞（第 1 节），再区分截断和卸载（第 2 节），然后是 labs 的完整实现（第 3 节）、三个生产实现的逐库对照（第 4 节）、预览该长什么样（第 5 节）、与压缩的分工（第 6 节），最后是坑（第 7 节）。前置章节：工具执行流水线见 第 02 章，会话日志见 第 04 章，token 计量见 第 05 章。

1. 大输出为什么不能直接塞进上下文

四条理由，严重程度递增。

一是窗口。这是最容易被高估的一条，因为大家会下意识觉得「窗口有 200K，塞几万字符没问题」。问题是窗口是整轮对话共享的：系统提示、工具 schema、前 40 轮的历史、这一轮你自己写的计划，全都在同一个预算里。一条 8 万字符的 grep 结果按四个字符一个 token 估算就是 2 万 token（教学示意：具体比例取决于语言和分词器），在 200K 窗口里占 10%，而这条结果的寿命往往只有一步——模型看完发现要找的字符串在第 3812 行，然后就再也不看它了。

二是成本。历史里的每一条消息在之后每一次请求里都会被重新发一遍。一步塞进去 2 万 token，后面还有 30 步，就是 60 万 token 的输入。卸载做的正是这件事：把「每步都要重发的 2 万 token」换成「只发一次的三百 token 预览」。

三是缓存。前缀缓存（prompt caching）命中要求请求前缀逐字节一致。把一条巨大的工具结果放进历史，本身不会破坏前缀——它在历史尾部。但如果它把上下文推到窗口边缘、触发了自动压缩，压缩会重写历史中段，从改写点往后的缓存全部失效。卸载的价值在这里是间接的：它让「还没到需要压缩的程度」这件事多维持很多步。DSH 对缓存这件事有明确表态，连子代理的派生方式都要为缓存让路（fork 方式继承父代理的历史，注释里写着 the inherited history remains eligible for KV Cache reuse）。

四是注意力稀释。这条最难量化，但在实际使用里最容易观察到。历史里躺着一份 8 万字符的日志，模型在回答一个和它无关的问题时会反复扫到它，偶尔还会被里面的内容带偏——比如日志里恰好有一行 Error: permission denied，模型就开始解释这个无关的错误。上下文里的一切都是提示，包括你不想让它看见的那部分。

结论：大输出不是「大一点就慢一点」的线性问题，它同时抬高成本、挤占窗口、增加缓存失效概率、并且污染注意力。所以策略不是「尽量少塞」，而是根本不让它进来，同时保证模型需要时能拿回去。

2. 截断和卸载的区别

表面上看两者都是「结果太长了，少放点进去」。区别在于信息有没有去处，以及模型知不知道自己在看不完整的东西。

learn-claude-code 的 s08 保留了最原始的写法：

        output = (result.stdout + result.stderr).strip()
        return output[:50000] if output else "(no output)"

code.py:92

这就是纯截断：切掉的部分没有任何去处，返回的字符串里也没有任何标记说明自己被切过。模型看到的是一个以第 50000 个字符结尾的普通字符串，它会理所当然地认为这就是 bash 命令的完整输出。于是出现最典型的失败：模型说「构建失败了，日志最后一行是 Compiling foo v0.3.1」——而真正的错误在下一行，正好被切掉了。模型没有任何线索去怀疑自己的判断。

把两者的差别列成表更清楚：

截断（out[:N]）卸载（spill）
被去掉的内容永久丢失（只在内存里的那份字符串上，进程退出即消失）原样落盘，逐字节可恢复

还有一个反直觉的点：卸载比截断更省 token。截断版的 out[:50000] 是 50000 字符全部进入历史；卸载版只放 2000 + 2000 字符的预览加说明块。也就是说截断不是「卸载的廉价版」，它是「更贵且更差的那个版本」。

3. labs：一个最小可用的卸载器

先看三个常量，它们划定了策略的边界：

DEFAULT_LIMIT_CHARS = 12_000
# 预览的头部/尾部分配。OH 只留头部 3000；DSH 把预算对半分给 head 和 tail，
# 因为报错信息常在输出的最后几行。
DEFAULT_HEAD_CHARS = 2_000
DEFAULT_TAIL_CHARS = 2_000
# 分页读取的默认每页行数，模拟模型后续怎么按需取回。
DEFAULT_PAGE_LINES = 200

十二万字符这个阈值是教学示意，不是任何仓库里的常量。真实实现给出的数字：DSH 用 token 计（maxInlineTokens: 12500），OpenHarness 用字符计（16000 字符），learn-claude-code 用字符计且阈值是 30000（code.py:257）。三个数字差了两倍多，说明这个阈值没有「正确答案」，它取决于你的工具集和平均输出大小。

labs 选择字符而不是 token，理由很实际：算 token 要依赖分词器，而分词器版本会变；字符数是确定的。代价是同一个阈值对中文和英文的语义不同（中文一个字符约等于一个 token，英文大约三到四个字符一个 token）。生产实现必须解决这个问题，DSH 的做法是接一个 ctx.tokenMeter 服务做统一计量（第 05 章）。

3.1 什么不能卸载

这是全章最容易被跳过的一节，也是最容易踩坑的一节。前面讲的所有好处都建立在「卸载是无害的」这个前提上，而三种情况下它有害：

def should_spill(*, is_error: bool, content: str) -> bool:
    """判断一份工具结果能不能卸载。

    三种不卸载的情况，理由各不相同：

    - **错误结果**：错误信息是模型纠正自己的唯一依据，长度通常很小，卸载只会让它
      多一次取回操作。DSH 的 spill-policy 不区分 isError（``retainable()`` 只看
      block 类型），但它的阈值是 12500 token，错误信息根本够不到。
    - **二进制**：预览里是乱码，尾部也是乱码，模型看不出内容是什么。
    - **完整的 JSON**：预览必然把它截断，而模型看到以 ``{`` 开头的内容会当成 JSON
      去解析，然后得到一个「语法错误」——比不卸载更糟。
    """
    if is_error:
        return False
    if looks_binary(content):
        return False
    if is_complete_json(content):
        return False
    return True

错误结果。错误文本是模型下一步行动的唯一依据，而且它天然很短（一个栈顶、一条 permission denied）。把它卸载掉只会让模型多花一步去取回。注意 DSH 的 spill-policy 在这一点上是不设防的：它的 retainable() 只看内容块的类型（index.ts:37-39），完全不看 isError。它能这么做是因为阈值（12500 token）远高于任何正常错误信息的长度，也就是说这条防线是靠阈值间接提供的，不是显式写的。你自己写的时候要显式区分——一旦你的工具会产生带完整堆栈的错误（Python 的 traceback 里带一段源码上下文，几千字符很常见），这条间接防线就没了。

二进制内容。预览里是乱码，尾部也是乱码，说明块说的是「路径在哪」，但模型打开也看不懂。looks_binary 的实现刻意写得很土——只查 NUL 字节：

def looks_binary(content: str) -> bool:
    """粗略判断是不是二进制内容。

    真正的 harness 在工具层就知道输出的类型（DSH 的工具必须声明 output schema）；
    到了卸载这一步只剩字符串，只能靠特征猜。猜错的方向要选对：把二进制当文本
    交给模型，代价是一堆乱码 token；把文本当二进制不卸载，代价只是上下文变大一点。
    """
    return _BINARY_PROBE in content

这里有一个设计信号值得注意：如果卸载层只剩一个字符串可用，说明前面某层把信息丢掉了。DSH 的工具必须声明输出 schema（index.ts:1075），所以「这是不是文本」在工具层就是已知的，卸载层不需要猜。

完整的 JSON。这条最隐蔽：工具返回一份 4 万字符的完整 JSON，预览截成头 2000 + 尾 2000，中间省略。模型看到以 { 开头、以 } 结尾的内容 —— 它认为这是一份完整的 JSON 文档，尝试解析，然后在中间撞上省略标记，得到一个「语法错误」的结论。比这更糟的是它会认为工具返回了坏数据。所以完整 JSON 要么整体放进去，要么明确告诉模型「这份 JSON 不完整」——但后者的正确做法是在工具层就改成流式或分页接口，而不是在卸载层打补丁。

3.2 预览怎么切

def build_preview(content: str, head_chars: int, tail_chars: int) -> tuple[str, int]:
    """切出头部 + 尾部，返回（预览文本，被省略的字符数）。

    两个细节：

    - 头尾之和可能超过原内容（内容比阈值大但比 head+tail 小），这时直接退化成
      整份内容，不能凭空多出省略标记。
    - 省略量必须按 ``原文长度 - 头 - 尾`` 算，不能用 ``len(TRUNCATION_MARK)``
      之类的近似值——这个数字会写进预览给模型看。
    """
    if len(content) <= head_chars + tail_chars:
        return content, 0
    head = content[:head_chars] if head_chars > 0 else ""
    tail = content[-tail_chars:] if tail_chars > 0 else ""
    omitted = len(content) - len(head) - len(tail)
    return f"{head}{TRUNCATION_MARK}{tail}", omitted

头尾都留、而不是只留头部，是被实际使用逼出来的结论。错误信息在输出的尾部：编译失败在最后几行，测试失败的汇总在最后几行，Traceback 的最后一行才是异常类型。只留头部的话，模型看到的是 2000 字符的进度日志，最有价值的那几行被切掉了。

DSH 把这一点做成了量化规则，值得照抄：头尾各拿预算的一半。

  let remaining = Math.ceil(budget / 2)

retention.ts:58（头部先取一半），retention.ts:75（尾部再取一半）。两个数一个向上取整一个向下取整，是刻意的——头尾之和不能超过预算。

它的切分函数还处理了一个 labs 没处理的边界：不能把 UTF-8 字符切成两半。textSlice 在切点落在代理对（surrogate pair）中间时往外挪一格（retention.ts:20）。emacs 里的乱码字符进到上下文，模型会把它当成需要解释的内容 —— 这是「输出被污染」而非「输出被截断」。

3.3 说明块：给模型的四句话

def format_notice(
    *,
    path: Path,
    original_chars: int,
    omitted_chars: int,
    head_chars: int,
    tail_chars: int,
) -> str:
    """给模型看的说明块。这是整章最重要的一段文本。

    它必须回答模型的三个问题：**我看到的不是全部吗**（已省略 N 字符）、**剩下
    的去哪了**（路径）、**我怎么拿回来**（用带 offset/limit 的读取工具）。缺了
    第一条模型会把预览当全文（lcc 的 ``out[:50000]`` 就是这个下场）；缺了第三条
    模型只会说「输出被截断了，我换个命令重试一遍」。
    """
    return (
        f"[工具输出已卸载]\n"
        f"原始大小：{original_chars} 字符（本次只显示头部 {head_chars} 与尾部 {tail_chars} 字符，"
        f"已省略 {omitted_chars} 字符）\n"
        f"完整输出：{path}\n"
        f"取回方式：{RECALL_TOOL}(path, page=N)，每页 {DEFAULT_PAGE_LINES} 行；"
        f"也可以对路径做 grep 检索。\n"
        f"注意：上面只是预览，不是完整内容——不要根据预览的结尾断定输出已结束。"
    )

四句话各有各的用途，缺一句就有一类失败：

  • 「原始大小 + 已省略」：让模型知道自己在看什么。少了它，模型把预览当全文，而它的推理会建立在这个错误前提上——这正是 lcc 那个 out[:50000] 的失败模式。
  • 「完整输出：路径」：这是唯一的抓手。DSH 把这个字段叫 locator 并刻意做成不透明类型（Branded<'SpillLocator'>，types.ts:13-18），说清楚是「本地后端可能是文件路径，远端或数据库后端可能是 URI 或 key，消费方渲染它但不要解析它」。这个区分很重要：一旦你的代码去 split('/') 解析这个 locator，换成远端存储时整条链路都要改。
  • 「取回方式」：少了它，模型最可能的反应是「输出被截断了，我重跑一遍命令」。重跑一轮的成本远高于读几页文件。DSH 的本地后端把这句话写死在返回值里（index.ts:159），理由写在接口定义里：backend supplies the locator and retrieval hint appropriate for its storage substrate（index.ts:11-12）——提示语由后端提供，因为只有后端知道该怎么取。
  • 最后那句「不要根据预览的结尾断定输出已结束」：labs 额外加的。因为头尾都保留时，预览的结尾看起来像是输出的结尾（它就是尾部那段），模型很容易据此下结论。这是唯一一条在其他实现里没看到、但实验下来确实需要的提示。

DSH 的说明块还多一个字段：被省略的图片数量。它的说明块格式化函数把三样东西拼在一起（notice.ts:21-24）：省略量、locator、取回提示。常量在文件顶部单独抽出来定义（LOCATION = ' Full formatted result stored at: '、GUIDANCE_SEPARATOR = '. '），因为同一个文件里还有一个 hasSpillNotice 函数要反向识别这段文本——回放旧日志时，harness 需要判断「这条历史里已经带着说明块了，不要重复处理」。用常量而不是字面量，是为了让正反两侧不可能漂移。

3.4 落盘：命名、去重、路径穿越

    def spill(
        self,
        *,
        tool_name: str,
        call_id: str,
        content: str,
        is_error: bool = False,
        limit_chars: int = DEFAULT_LIMIT_CHARS,
        head_chars: int = DEFAULT_HEAD_CHARS,
        tail_chars: int = DEFAULT_TAIL_CHARS,
    ) -> SpillResult:
        """需要就卸载，不需要就原样返回。

        ``call_id`` 目前只用于让调用方把预览和自己的日志对上；DSH 把
        ``{kind: 'tool', toolName, callId, label}`` 整份塞进 spill 存储，
        因为它的后端可能是数据库或远端，需要这份来源信息建索引。
        """
        del call_id  # 本地后端只靠内容哈希和工具名命名，来源信息记在会话日志里。
        if not should_spill(is_error=is_error, content=content):
            return SpillResult(content=content, spilled=False, original_chars=len(content))
        if len(content) <= limit_chars:
            return SpillResult(content=content, spilled=False, original_chars=len(content))

        digest = hashlib.sha256(content.encode("utf-8")).hexdigest()[:16]
        path = self.session_dir / f"{digest}-{safe_name(tool_name)}.txt"
        deduplicated = digest in self._written
        if not deduplicated:
            self.session_dir.mkdir(parents=True, exist_ok=True)
            # 先写临时文件再原子替换：并发写同一份内容时不会留下半份文件。
            tmp = path.with_suffix(".tmp")
            tmp.write_text(content, encoding="utf-8")
            tmp.replace(path)
            self._written[digest] = path

        preview, omitted = build_preview(content, head_chars, tail_chars)
        notice = format_notice(
            path=path,
            original_chars=len(content),
            omitted_chars=omitted,
            head_chars=head_chars,
            tail_chars=tail_chars,
        )
        return SpillResult(
            content=f"{notice}\n\n--- 预览开始 ---\n{preview}\n--- 预览结束 ---",
            spilled=True,
            path=path,
            original_chars=len(content),
            omitted_chars=omitted,
            deduplicated=deduplicated,
        )

三个决定值得展开。

文件名由内容哈希决定。同一份输出（比如同一个 git status 跑两遍）第二次落盘没有任何收益：磁盘上多一份一模一样的文件，而模型看到的说明块指向不同路径，回放日志时更难对上。用内容哈希做前缀，第二次直接复用。注意这里和 DSH 的选择相反：DSH 的文件名是 {随机 6 字节十六进制}-{转义后的 suggestedName}（store.ts:110），也就是说同一份内容卸载两次会写两个文件。它选随机名的理由是安全：名字不可预测，别的本地用户没法预先放一个符号链接来重定向写入（注释里明说不允许被 redirectable via a planted symlink）。所以这是一个真实的取舍——去重 vs 防符号链接攻击，labs 选了前者因为它是教学实现，DSH 选了后者因为它是多用户系统上的真实部署。

会话目录名用哈希而不是会话 id 本身。会话 id 可能来自配置、命令行参数、或另一个服务，直接当路径段用就是一个路径穿越入口。DSH 的做法是同一套（store.ts:79），目录名是 session-{sha256 前 12 位}。哈希的另一个好处是：会话 id 本身不会泄露到文件系统上。

工具名要清洗，但不能只靠清洗。labs 用白名单正则 safe_name()，把 ../../etc/passwd 变成 etc_passwd。DSH 走得更远，用的是一个单射编码：

    out += ch !== '~' && /^[A-Za-z0-9._-]$/.test(ch)
      ? ch
      : '~' + code.toString(16).toUpperCase().padStart(4, '0')

store.ts:63-65。注释把单射的理由写全了（store.ts:43-50）：每个码位要么原样保留，要么转义成 ~XXXX，而 ~ 自身也要转义，所以不同的输入永远不会映射到同一个文件名。清洗法的弱点是两个不同的工具名可能洗出同一个名字（a/b 和 a_b 都变成 a_b），如果没有哈希前缀就会互相覆盖。整段 . 和 .. 也单独处理成 ~002E，因为它们是路径段里唯一有特殊含义的值。

写入本身有两处细节。第一，文件权限是 0600、目录权限是 0700，且用 wx（独占创建）打开：

    await mkdir(dir, { recursive: true, mode: 0o700 })
    try {
      handle = await open(path, 'wx', 0o600)
      break
    } catch (error: unknown) {
      /* v8 ignore start -- requires another process to remove the directory
         between mkdir and open, or an external permission/IO race. */
      if (isErrno(error, 'ENOENT')) continue
      throw error
      /* v8 ignore stop */
    }

store.ts:111-124。wx 的含义是「文件已存在就失败」，这挡住了「别人预先在同名位置放一个软链接」的情况。第二，那个 ENOENT 重试循环处理的是一个真实的竞态：mkdir 和 open 之间目录被别人删掉（比如清理进程刚好扫到这里）。它被 v8 ignore 包着，注释老实承认「要靠另一个进程在 mkdir 和 open 之间删目录才能触发」——这是那种「不写也行，但写了就不会在凌晨三点炸」的代码。

3.5 取回：分页读取的边界

    def read_page(self, path: Path, page: int = 0, page_lines: int = DEFAULT_PAGE_LINES) -> str:
        """按页取回卸载文件，模拟模型后续的读取。

        两件事必须做：**把路径钉回会话目录**（否则模型可以传 ``../`` 去读别的
        会话甚至别的用户的文件），以及**在页尾明确写出「还有没有下一行」**——
        模型无法从一页内容的结尾看出来它是不是文件的结尾。
        """
        resolved = Path(path).resolve()
        base = self.session_dir.resolve()
        if not resolved.is_relative_to(base):
            raise SpillPathError(f"取回路径必须在 {base} 之内：{resolved}")
        if not resolved.is_file():
            raise FileNotFoundError(f"卸载文件不存在（可能已被清理）：{resolved}")
        if page < 0:
            raise ValueError("page 不能为负数")

        lines = resolved.read_text(encoding="utf-8").splitlines()
        start = page * page_lines
        chunk = lines[start:start + page_lines]
        if not chunk:
            return f"[空页] page={page} 超出范围：共 {len(lines)} 行。"
        last = start + len(chunk)
        more = f"还有 {len(lines) - last} 行，用 page={page + 1} 继续。" if last < len(lines) else "这是最后一页。"
        return f"[page={page} 第 {start + 1}-{last} 行 / 共 {len(lines)} 行] {more}\n" + "\n".join(chunk)

这里有两个必须自己做、不能指望模型的判断。

路径必须钉回会话目录。说明块里给了模型一个路径，模型下一轮会把它传回来。中间这一圈里，路径可以被模型改写（它能自己编一个路径，也可以被提示注入影响）。所以取回端必须resolve() 之后检查它是不是还在会话目录下——用 is_relative_to 做结构判断，而不是字符串前缀匹配（/work/session-news 的字符串前缀是 /work/session-ne，前缀判断会误放行）。labs 的这条检查偏严：连同一个 root 下别的会话的目录也读不了，因为那同样是别的会话的工具输出。生产实现里这条边界有的在存储层（DSH 的会话目录划分），有的在工具层（只允许读工作区内的路径）。

页尾必须说明还有没有下一行。模型从一页内容的结尾看不出这是文件的结尾还是分页的结尾——如果 read_page 只返回内容，模型看到最后一行是 } 就会认为「读完了」。所以响应头里带位置信息（第 1-200 行 / 共 3812 行）和明确的续读指令。空结果也不能静默返回空字符串：模型请求第 50 页而文件只有 10 页时，返回 "" 会让它以为文件是空的，然后据此得出「工具输出是空的」这个错误结论。所以越界要显式回答（labs 返回 [空页] 加总行数）。

DSH 在这个位置的做法是「不给模型新的取回工具，而是复用已有的 read 工具」。它的 read 接受 offset（1 起的起始行）和 limit（行数，默认 2000）：

  const offset = args.offset === undefined ? 1 : parsePositiveInteger(args.offset, 'offset')
  const limit = args.limit === undefined ? maxLimit : parsePositiveInteger(args.limit, 'limit')
  if (limit > maxLimit) throw new Error(`limit must be less than or equal to ${maxLimit}`)

read.ts:57-59。这个选择比 labs 的专用取回工具更好，理由是模型只需要学会一种读文件的方式：卸载文件是文件，会话产生的其他产物也是文件，读完再 read_image 看图片也是同一套。DSH 甚至把这个引导写进系统提示（read.ts:74），也就是说「大文件要分页读」这件事在提示词层面就被教过了。

4. 逐库对照

三个仓库的规模差了两个数量级，正好看到同一个机制在不同权重下的形态。

4.1 DSH：拆成三个包

DSH 把卸载拆成三个独立的包，接口定义在 dsh-spill：

export abstract class SpillStore extends Service {
  constructor(ctx: Context) {
    super(ctx, 'spillStore')
  }

index.ts:45-48，整个抽象接口只有一个方法：saveText。它的模块注释把「故意只做这么点」写成了明确的设计声明（index.ts:8-12）：它不拥有保留策略（那是 dsh-output-retention）、不拥有工具结果替换（那是 dsh-spill-policy）、不拥有取回或检索 API。

这个三分的好处是每一层可以单独换。存储层换成远端对象存储时，只要 saveText 还能返回一个 locator，策略层一个字都不用改——locator 被刻意做成不透明类型就是为了保证这一点。代价是多两个包、多两个包的测试和维护。

本地存储实现里的关键路径：会话目录由会话 id 的哈希派生（store.ts:78-81），写入走 saveTextFile（store.ts:108），返回路径和 UTF-8 字节数（store.ts:130）。字节数由后端算而不是让策略层算，因为只有后端知道自己写进磁盘的是什么编码。

存储根默认是进程私有的临时目录（store.ts:37，前缀 dsh-spill-）。因为它不在会话目录里，会话被删除时卸载文件不会跟着删，所以它必须自带清理：插件激活时启动一次清理扫描（index.ts:96-101），默认清掉 30 天前的文件（index.ts:68）。注释解释了为什么不设更短：Retention is deliberate — a resumed or forked session may still reference an older locator until it ages out（index.ts:44-46）。这是一个容易被忽略的耦合：只要卸载文件的路径存在于历史里，清理它就是在制造一个模型能看见但不存在的引用。

策略层挂在工具流水线的 post-execute 上，第一件事是先跑别人的决定：

  ctx.on('tools/post-execute', async (exec, result, next): Promise<PostToolDecision> => {
    const decision = await next()
    if (decision.kind !== 'accept' || Object.hasOwn(decision, 'value') || exec.name === 'read') return decision

index.ts:133-135。三个跳过条件各有理由：next() 的结果不是 accept 就别碰（别人已经决定了）；Object.hasOwn(decision, 'value') 说明有人替换了整个值（那是值级替换，不是内容级保留）；exec.name === 'read' 是排除 read 工具本身——这是一个很实际的保护。

为什么排除 read？因为 read 的输出已经是它自己按预算切好的（前面看到 READ_LIMIT = 2000 行），而且读的往往就是一个卸载文件。如果卸载对 read 也生效，模型读一个 3000 行的卸载文件会得到「一个指向卸载文件的卸载文件」，多一层跳转。「读工具的输出不该被再次卸载」这条规则，在你自己的实现里同样成立。

最后一个细节是注册时那个 { prepend: true }：

  }, { prepend: true })

index.ts:150。prepend 是 Cordis 事件系统的监听者排序选项（events.ts:255），注册时用 unshift 插到数组头而不是 push 到尾。为什么必须排在前面？因为 tools/post-execute 是 waterfall（index.ts:1787-1790），监听者按顺序串成 next 链，每个监听者拿到的 result 是前一个处理过的。如果卸载排在后面，它看到的是已经被别人裁过的内容——可能已经被截断成 8192 字符（DSH 的 tool-result-pruner 就是这么干的），那时卸载就无从判断「原本有多大」。要拿到最原始的完整结果，就必须排在链条最前。这是一个通用规则：任何「基于结果全长做决策」的后置策略，都必须 prepend。

4.2 OpenHarness：一个函数

OH 把整个卸载逻辑放在引擎循环里，紧挨着工具执行：

        tool_name=tool_name,
        tool_use_id=tool_use_id,
        output=result.output,
    )
    if artifact_path is not None:
        _remember_active_artifact(context.tool_metadata, str(artifact_path))
    tool_result = ToolResultBlock(

query.py:985-997。这是最省事的形态：没有服务、没有扩展点、没有独立的包————因为在 OH 的架构里这个位置只有一个消费者（引擎循环），抽象出来只是多一层间接。

注意 is_error 是在卸载之后才填进结果的（tool_result 的构造里 is_error=result.is_error 直接抄工具的返回，与卸载无关）。所以 OH 的错误结果也会被卸载——如果一个工具返回了几万字符的错误堆栈，它照样会变成「预览 + 路径」。这是 labs 显式排除的情况，值得留意：两种做法都说得通（错误信息太长时确实该落盘），但你要知道自己选了哪种。

路径命名在这里是另一套思路：{时间戳}-{清洗后的工具名}-{随机 12 位}.txt（query.py:534-537），时间戳按 %Y%m%d-%H%M%S 排前缀，好处是按目录列表排序就是时间序，排查问题时很直观。清洗函数只保留字母数字和 ._-，最后截到 80 字符（query.py:519-521），空结果退化成字面量 "tool"。

卸载文件路径还额外进了一个「活跃产物」追踪列表（query.py:990-991），供后续的微压缩（microcompact）判断「这个文件是不是还要用」。这正是 第 07 章要讲的层与层之间的接口：卸载把文件交出去，压缩需要知道它还在不在用。

OH 的另一个特点是三个阈值是运行时可调的：OPENHARNESS_TOOL_OUTPUT_INLINE_CHARS、OPENHARNESS_TOOL_OUTPUT_PREVIEW_CHARS、OPENHARNESS_MICROCOMPACT_TOOL_RESULT_CHARS，环境变量缺省时才用常量（tool_outputs.py:15-23），并且有最小值下限（minimum=256）。非法值只记警告然后回退默认值，不崩。这套写法值得抄：阈值是最需要按部署调整的参数，改一行环境变量比改代码重新部署快得多。

4.3 learn-claude-code：只截断，以及在错误的时间点卸载

lcc 的 s08 里有两套并存的做法，而且它们的分工值得单独讲。

第一套在工具内部，就是前面那个 out[:50000]（code.py:92）——纯截断，永久丢失。

第二套在压缩器里，是真正的落盘加预览：

code.py:340-345，落盘目录是工作区下的 .task_outputs/tool-results（code.py:65），文件名直接用清洗后的 tool_use_id。

这里有 lcc 最值得学的一个设计：它会先检查输出里是不是已经带着一个路径，带着就直接复用，不再落一次盘：

        if output.startswith("<persisted-output>\n"):

                (line.removeprefix("Full output: ")
                 for line in output.splitlines()
                 if line.startswith("Full output: ")),

        prefix = "[Earlier tool result saved at "

        return str(path)

code.py:320-338。三件事挤在一个函数里：识别自己的两种说明块格式（<persisted-output> 和 [Earlier tool result saved at …]）、把路径钉回自己的目录（is_relative_to 那两行——和 labs 的 read_page 完全同一个检查）、以及确认文件真的还在。这两条保护在同一个文件里出现两次（还有个名字几乎一样的方法在 is_archive_marker 里），说明作者是被真实问题咬过的：模型能看见的路径字符串是不可信输入，读之前必须验。

lcc 的第三套做法是在压缩阶段卸载，这才是它的主线。压缩器维护一份「最近 3 条工具结果不算旧」的规则（code.py:430），把更早的结果落盘并替换成一行引用：block["content"] = f"[Earlier tool result saved at {saved_path}]"（code.py:441）。

这是本章最想让你避开的一个形态：它是卸载，但它发生在历史已经产生之后。代价有两个。第一，不可逆——一旦 block["content"] 被覆盖，原始工具结果就只剩磁盘上和原始历史里各一份，而「原始历史」如果本身是被 snip_compact 归档过的（code.py:414-416），链条就更长了。第二，时机太晚——它是在上下文已经逼近上限时（CONTEXT_CHAR_LIMIT = 50000）做的补救。而卸载的全部价值在于「一开始就别让它进来」，此时它已经进来了、已经花掉了每一轮的 token、已经把缓存推到了临界点。补救能救回容量，救不回已经付出的成本。

顺带记一个 lcc 做对的地方：它替换后的文本只保留路径，连一行预览都不留。这样做让模型对「这里有过一个大结果」完全没有上下文，只能去读文件——从「省 token」的角度是最优的，从「模型能不能自己决定要不要读」的角度是最差的。

5. 预览设计：什么信息值得占 token

预览是模型唯一能直接看到的东西，所以它上面每一个字符都在和别的字符竞争预算。四条经验。

第一，头尾不对称是有意的。如果输出是日志，头部是启动信息（通常已知），尾部是结果或错误（未知）。labs 给头尾各 2000 字符是简化的选择，DSH 的头尾各拿一半同样是简化——真实实现可以让比例可配：headChars: 4096, tailChars: 1024，也就是四比一（这是 DSH 的 tool-result-pruner 的默认值，config.ts:10-14）。注意同一份 DSH 代码里两个组件给的默认值不一样（卸载层头尾各半，裁剪层四比一），说明这确实是个按场景调参的东西，没有普适解。

第二，省略量必须是精确数字，不能是「若干」。模型用这个数字判断「值不值得去读」。看到「已省略 18400 字符」，它知道里面可能有东西；看到「已省略部分内容」，它没有任何判断依据。DSH 在这件事上做得最细：它有一个专门的类型来描述省略量，none / exact / unknown 三态（output-retention/index.ts:40-43），而且模块注释里专门划清了一件事：truncated 的含义是「因为预算而省略了本来可用的内容」，不是「上游本身就是不完整的」（output-retention/index.ts:11-15）。权限失败、跳过的二进制文件、部分不可读的候选，都留在工具自己的领域字段里，不混进 truncated。这个区分的价值是：模型看到 truncated 时会去读文件，看到「权限失败」时会去改权限。把两种都塞进一个布尔值，模型就只能靠猜。

第三，说明块的开销要算进预算。DSH 在这件事上有一个不显眼但重要的处理：它在决定保留多少内容之前，先把说明块本身的价格预留出来：

      const reserved = price(GAP) + price({ type: 'text', text: `\n\n${worstNotice.text}` })
      if (price(worstNotice) > maxTokens) throw new Error(`spill notice for ${toolName} exceeds maxInlineTokens`)
      const retained = retainContent(content, Math.max(0, maxTokens - reserved), price)

index.ts:112-114。先算「最坏情况说明块」的价格（用 worstNotice，即假设全部内容都被省略的那份），把它从预算里扣掉，剩下的才给内容；如果说明块本身就超预算，直接抛错而不是产出一个超预算的结果。这里的教训很直白：边界条件是能构造出来的——一个路径特别长、省略量位数特别多的说明块，在小预算下足以吃掉全部空间。

第四，相邻文本要合并。DSH 最后有一段看起来多余但确实是必要的代码：

index.ts:119-126。每一段独立的文本块在协议层都有封装开销（Anthropic 的 content 数组里每个块都要序列化一遍 {"type":"text","text":…}），相邻的文本块合并成一个能省下这点开销。头、省略标记、尾部、说明块在原结构里是四个块，合并后是一整个 —— 省下的虽然不多，但这是免费省下的，因为它不改变任何语义。

6. 卸载和压缩的分工

这两个机制经常被混在一起讲，因为都能「减小上下文」。但它们作用在完全不同的时刻，解决完全不同的问题。

卸载（本章）压缩（第 07 章）
触发位置工具结果产生时，进日志之前历史已经太长，或请求已被拒（上下文超长）
作用对象一条结果一段历史（多条消息）
判断依据长度（绝对阈值）总 token 与窗口容量的相对关系
产出预览 + 目录路径摘要（模型生成）或裁剪标记（模型无关）
可逆性可逆，原文在磁盘上摘要不可逆；裁剪如果写了标记事件则可在日志里还原
成本一次本地写盘一次额外的模型调用（摘要式），或纯字符串操作（裁剪式）
对缓存无影响（结果还没进历史）从改写点起前缀缓存全部失效

DSH 的装配里两者并存，而且顺序写得很明确。先卸载：

      name: '@deepseek-ai/dsh-spill-local'

    - id: spill-policy
      name: '@deepseek-ai/dsh-spill-policy'
      config:
        maxInlineTokens: 12500

cordis.patch.yml:406-412，再裁剪：

    # runs, preserving the model-visible result within the configured budget.

      config:

        tailChars: 1024

cordis.patch.yml:418-425。注释直说了顺序理由：Compacts oversized tool results before the broader conversation compactor runs——先收拾工具结果，再动整段对话。

两个组件的触发时机不同：卸载挂在 tools/post-execute（每次工具执行都跑，tools/index.ts:1655），裁剪挂在压缩流程里（只在压缩被触发时跑）：

    if (trigger === 'context-overflow') {
      if (prune !== undefined) {
        prune.pruneSession(agent.session)
        measurement = meter.measure(agent.session)
      }
      const range = selectCompactableRange(agent.session, measurement, 0)

compaction-basic/index.ts:294-299。注意 prune 是从上下文里可选取出来的（ctx.get('toolResultPruner')），注释说明了理由：Pruning is optional so compaction-basic remains independently composable。也就是说裁剪是压缩的可选前置步骤，而不是压缩的一部分——没装裁剪插件压缩照样能跑，只是要多摘要一些内容。

还有一个细节把本章的主题钉住了：裁剪是往日志里追加事件的，不是改写已有事件。

      session.append('compaction/prune', {

index.ts:160。为什么？因为日志是事实来源（第 04 章），它只能追加。所以裁剪不是「把历史里的大结果删掉」，而是「追加一条事件说明这个节点以后的可见内容被裁过了」。这也是它能被回放的原因——重放一遍日志，裁剪的效果会原样重现。

这一点对卸载同样成立，而且它决定了卸载的唯一正确位置：既然日志只追加，那么结果一旦写进去就没法改。所以「结果写进日志」这一步必须发生在卸载之后。DSH 的顺序是：工具执行 → finalizeScheduledExecution 里调 postExecute（tools/index.ts:1655）→ 循环拿到已经处理过的结果 → appendToolResult 写日志（tool-calls.ts:282-289）。卸载在 postExecute 里，写日志在它之后，所以落进日志的就是预览版，原始全文从未进入过历史。

对照 lcc 的做法（在压缩阶段覆盖 block["content"]）就能看出这条顺序的价值：lcc 的历史是一个可以在原地改的 Python 列表，所以它能「事后修改」；代价是这个修改不留下任何记录，进程重启后历史里就只有引用，而它想复活原文需要一个额外的转录文件兜底。DSH 不允许这种事后修改，所以它必须把卸载放在正确的位置上——「日志只追加」这条约束看起来很麻烦，实际上它替你排除了「事后补救」这个错误选项。

一句话分工：卸载决定「什么东西允许进入历史」，压缩决定「已经进了历史的东西怎么变短」。前者管入口，后者管存量。入口管好了，存量压力就小得多——这也是为什么 DSH 的卸载阈值（12500 token）设得比裁剪阈值（8192 字符）宽松：它宁可多卸载几次，也不愿意让大结果先进入历史再靠裁剪收拾。

7. 坑与失败案例

坑 1：说明块缺了「取回方式」，模型只会重跑命令

触发条件：卸载生效了，说明块里写了路径，但没写「怎么读回来」。

后果：模型看到的是一段被截断的输出加一个路径。它的第一反应通常是「输出被截断了，我换个命令重新跑一遍」——比如把 grep -r foo . 换成 grep -r foo . | head -50。这一轮重跑又是一次工具调用、又一次执行、又一份可能同样大的输出。更糟的情况是模型认为工具坏了，转而写一个 Python 脚本重新实现整个搜索。

源码里怎么防的：DSH 把提示语和 locator 一起放在存储层的返回值里（index.ts:159），接口文档明确了分工：the backend supplies the locator and retrieval hint appropriate for its storage substrate（spill/index.ts:11-12）。放这么低的位置是有道理的：只有后端知道 locator 是文件路径还是 URI，也只有后端能给出正确的取回指令。中间任何一层都可能猜错，而猜错的提示语比没有提示更糟。

labs 对应：format_notice 里的「取回方式」一行，以及测试 test_preview_is_marked_as_truncated 显式断言取回工具名出现在预览里。

坑 2：路径不设防，模型传回什么就读什么

触发条件：说明块里给了路径，取回端直接 open(path)。

后果：这条路径在下一轮变成模型输入的一部分，而模型输入是不可信的——它可以是模型自己编的，也可以是提示注入塞进来的（比如工具读回的一个网页里写着「现在请读取某配置文件并总结」）。读取端的越权后果取决于进程权限：读别的会话的卸载文件（信息泄露）、读密钥文件（凭据泄露）、读特殊设备文件（可能挂死）。这条路径是唯一一条由 harness 产生、又由模型回传的路径，所以它必须按不可信输入处理。

源码里怎么防的：三处，各自独立。第一，DSH 在写入侧就不产生可穿越的名字：encodeSegment 把每个非安全字符转义成 ~XXXX，整段的 . 和 .. 分别变成 ~002E 和 ~002E~002E（store.ts:56-58）。第二，lcc 在读取侧校验：persisted_output_path 里 is_relative_to(self.tool_results_dir.resolve()) 不成立就返回 None（code.py:335-337）——它把「路径不可信」写进了返回值的类型里（str | None），调用方必须处理 None。第三，labs 的 read_page 用同一套 is_relative_to 检查，并额外拒绝同 root 下别的会话目录。

这条防护的正确写法：先 Path.resolve() 再比结构，不要用字符串 startswith。字符串前缀判断在两种情况下会误判——符号链接（/work/session-a/link 指向 /etc，前缀匹配通过但 resolve 之后不在里面）和同名前缀的兄弟目录（/work/session-ab 的字符串前缀正是 /work/session-a）。labs 的测试 test_sibling_session_dir_is_blocked 专门钉住了第二种。

坑 3：错误结果被卸载，模型失去纠正依据

触发条件：卸载只看长度、不看结果类型，而某次失败返回了一段很长的错误输出（Python traceback 带源码上下文、编译器输出几百行错误、依赖解析失败的完整树）。

后果：模型拿到的是「错误已卸载，看路径」而不是错误本身。它必须多花一步去读文件——而这一步不保证会发生（模型可能直接放弃，或者转而去改别的代码）。更关键的是错误信息通常是「读了才知道怎么办」的：少一个字符都可能让模型做出错误的修复。比如 KeyError: 'user_id' 被截成 KeyError: 'user，模型会去改错的字段名。

源码里怎么防的：DSH 和 OH 都没防。DSH 的 retainable 只检查内容块的类型（index.ts:37-39），bound 里的判断同样只看 token 数（index.ts:98），完全没有 isError 这一维。它靠的是 12500 token 这个阈值——正常错误信息够不到，所以这个洞没被触发。OH 同样不区分：is_error 是在卸载之后才填进 ToolResultBlock 的（query.py:992-997）。

labs 对应：should_spill 第一行就检查 is_error，测试 test_error_results_stay_inline 钉住它。这是 labs 相对三个生产实现唯一「更严格」的地方，理由是教学版没有生产级的阈值调优余量——写死一条规则比依赖「阈值够大」更可靠。

坑 4：卸载排在别人后面，看到的是已经被裁过的内容

触发条件：多个监听者挂在同一个 tools/post-execute waterfall 上，卸载没有排在前面。

后果：waterfall 的语义是每个监听者拿到的 result 是前一个处理过的（events.ts:228）。如果前面有个「把工具结果裁到 8192 字符」的监听者，卸载看到的就是 8192 字符——它不认为需要卸载，于是进历史的是一份被静默截断的内容。信息永久丢失，而且模型不知道。这是最隐蔽的一种失败，因为卸载自己的日志会显示「本次没有卸载」，看起来一切正常。

源码里怎么防的：spill-policy 注册时带 { prepend: true }（index.ts:150），Cordis 据此用 unshift 而不是 push 插监听者（events.ts:255）。prepend 本身是标准的监听者选项（events.ts:114）。另一个理由在 DSH 的注释里：post-execute 的监听者按注册顺序串成链，先注册的看到更原始的结果。

通用化这条经验：任何「基于结果全长或全貌做决策」的后置策略都必须 prepend。反过来说，任何「在别人的结果上做进一步加工」的策略（加语法高亮、加元数据）应该排在后面。这个顺序不是风格问题，它决定了策略能不能看到真实输入。labs 的 SpillStore.spill 是纯函数式的（把完整 content 当参数传进来），等于用函数签名表达了「必须看到原文」这件事——如果你的架构里有 waterfall，就要靠 prepend 表达同一件事。

坑 5：完整 JSON 被截成预览，模型当成坏数据

触发条件：工具返回一份完整的大 JSON（搜索结果、API 响应、导出数据），卸载按字符切头尾。

后果：模型看到的预览以 { 开头、以 } 结尾——这在语法上看起来就是一份完整的 JSON 文档。它尝试解析，在中间撞上省略标记，然后得出「工具返回了非法 JSON」的结论。这是一个彻底的误判：工具没问题，JSON 也没问题，是卸载把一份正确的文档改成了错误的。更糟的是模型可能因此去「修工具」，而真正该做的是分页读取数据。

源码里怎么防的：没有直接防，靠的是工具设计。DSH 的工具必须声明输出 schema（index.ts:1075），所以返回结构化数据的工具是已知的，理论上可以在卸载层识别出来绕开。但 DSH 的 spill-policy 走的是内容块路线（ContentBlock[]），结构化结果早已被渲染成文本（read-render.ts 之类的模块负责把对象渲染成行号文本），卸载层看到的仍然是一个文本块——它已经没有「这是 JSON」这个信息了。所以正确的做法在更上游：需要返回大结构化数据的工具应该自己分页（像 read 的 offset/limit 那样），而不是返回一坨然后指望卸载层处理。

labs 对应：is_complete_json 保守地检查首尾配对，配对成功就不卸载。测试 test_complete_json_stays_inline 和 test_json_looking_log_can_still_spill 是一对，分别钉住「真 JSON 不卸载」和「长得像 JSON 的日志照卸载」。

坑 6：卸载文件被清理了，历史里还留着路径

触发条件：卸载根不在会话目录下（比如放系统临时目录），且清理策略按时间删除。

后果：一条几十步之前的历史里写着「完整输出在某临时目录下的某个文件」，模型（或用户点开链接）去读，文件已经没了。这时模型只能看到「文件不存在」这个事实，它无法判断「是我记错了」还是「文件被删了」，于是可能去重跑那个工具。如果这是一次昂贵的网络请求，重跑就是白花。

源码里怎么防的：DSH 用两个手段。第一，清理周期默认 30 天（index.ts:68），注释解释了为什么不设短：Retention is deliberate — a resumed or forked session may still reference an older locator until it ages out（index.ts:44-46）。「被续跑的会话仍可能引用旧 locator」这句话给出了一个很容易漏掉的约束：卸载文件的寿命不能短于会话历史的寿命，而分叉出来的会话会继承父会话历史里的 locator。第二，清理只删文件不删历史，所以最坏情况是「路径存在但文件不存在」，模型得到的是一个明确的失败而不是一个沉默的错误。

lcc 的读取端在这一点上是更彻底的做法：persisted_output_path 会检查 path.is_file()（code.py:336），文件不在了就当从来没有过路径，让上层走正常的落盘流程重新写一份。

labs 对应：read_page 对不存在的文件抛 FileNotFoundError，错误文本里写明「可能已被清理」——因为那是最可能的解释，直接写出来能让模型少猜一步。

8. 小结

四句话。

  • 卸载的位置在「结果产生」和「写进日志」之间，不是历史已经太长之后的补救。日志只追加这条约束决定了它必须在入口处解决。
  • 它和截断的区别不在「少了多少」，而在「信息有没有去处」和「模型知不知道」。缺了说明块，卸载就退化成一种更贵的截断。
  • 说明块要回答四个问题：原始多大（已省略多少）、去哪了（路径）、怎么拿回来（取回指令）、以及「这不是全文」。DSH 的接口文档把 locator 和取回提示都归给存储后端，因为只有后端知道该怎么说。
  • 三个「不卸载」的边界要靠自己显式写：错误结果、二进制内容、完整结构化的 JSON。三个生产实现里有两个对错误结果不设防，靠阈值兜着——那是建立在阈值调优之上的隐式约定，你的阈值一变它就不成立了。
