第 6 章

Prompt cache 稳定性

前面几章讲了历史怎么存（会话日志）、上下文压力怎么量（token 预算）。这一章要处理一个平时看不见、只在账单上看得见的问题：你的 harness 每一轮都在重新拼一份一模一样的前缀，那么它到底有没有被复用？

prompt 缓存（provider 侧的 KV 前缀缓存）不是「省一点钱」的小优化，它是 agent harness 里唯一一个「改动一行代码就可能让成本翻几倍、而且没有任何功能症状」的地方。它的规则简单到只有一条：前缀匹配。前缀里任何一个字节变了，从那个字节之后的所有缓存全部失效。没有例外，没有部分补偿——provider 不是「尽量复用」，而是「第一个不同的 token 之前的部分能复用」。

这一章的目标是把这个「没有症状的成本失血」变成可诊断、可测试、可回归的东西。做法是：把一次请求渲染成确定的字节序列，然后用一个纯函数回答「这一次和上一次比，缓存从哪个字节开始失效」。

前缀缓存到底在缓存什么

先说清楚机制，因为后面所有的坑都是这条机制的推论。

你每次请求发给模型的东西，在线上是一串有序的 token。provider 把这段 token 序列送进 transformer 之后，中间的注意力键值对可以留着下次用——但只有在「下次请求的开头和这次一模一样」时才留得住。这就是「前缀缓存」。于是它的两条推论是：

  • 命中长度 = 最长相同前缀的长度，不是「相似度」、不是「差几行」。差一个字符，从那个字符起全部重新算。
  • 渲染顺序决定了什么东西最贵。Anthropic 官方文档给出的顺序是 tools → system → messages。这意味着工具声明排在整条请求的最前面：工具列表变了，连系统提示词一起全部失效；而历史里最后一条消息变了，只影响它自己之后的部分。

「官方文档给的顺序」这一点需要标一下出处：Anthropic 的 prompt caching 文档里写明缓存是前缀匹配、请求的渲染顺序是 tools → system → messages，并列举了几种常见的静默失效来源（系统提示里放当前时间、JSON 键顺序不稳定、工具列表顺序变化）。这些是 provider 文档里的事实，不是本仓库源码里的行，所以下面讲到它们时只标出处类型、不配 src-ref。能用源码证明的，是各家 harness 面对这条规则时做了什么。

为什么值得当成一等公民：一次多步的 turn，模型请求次数等于 step 数；一次长任务的会话，请求次数是几十上百次。这些请求里 90% 以上的输入是同一段历史——如果每轮都整段重算，你付的是「每次都从零读一遍全部上下文」的钱。省下来的那部分不是边际改善，而是量级差。

我们不需要相信任何数字就能验证这条规则：把请求渲染成字节，自己比一遍。这正是 labs/harness/prompt_cache.py 做的事。

把请求渲染成确定的字节

要诊断缓存，第一步是让「这次请求会发什么」变成可比较的对象。这里有个陷阱：Python 的 dict 保持插入顺序，json.dumps 默认继承它。而插入顺序经常取决于上游并发任务的完成顺序——于是两次逻辑上完全一样的请求，渲染出的字节不同，缓存静默失效。所以渲染的第一条纪律是：键排序 + 固定分隔符。

def canonical_json(value: Any) -> bytes:
    """确定性的 JSON 字节序列：键排序、无多余空白、非 ASCII 不转义。

    sort_keys 解决「同一个 dict 两次 dumps 出不同字节」这类静默失效：
    Python 的 dict 保持插入顺序，而插入顺序经常取决于上游并发任务的完成顺序。
    """
    text = json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
    return text.encode("utf-8")

第二条纪律是渲染顺序固定，而且每条消息各占一个可复用单位。这一点比「三段式」更细，但它是本章后面全部诊断的基础：只有把消息拆成单位，「追加一条消息」和「改写第 2 条消息」才区分得开。前者前缀完整命中，后者从第 2 条起全部失效——在真实账单上差了一个量级，粗粒度的段级比较看不出区别。

def render_request(
    tools: Sequence[Mapping[str, Any]],
    system: str,
    messages: Sequence[Message],
) -> RenderedRequest:
    """把一次请求渲染成一条前缀，并按单位算出累积哈希。

    顺序是 tools → system → messages。空系统提示词仍然占一个单位（长度 0），
    因为「有没有这一部分」本身也是前缀的一部分。
    """
    units: list[Unit] = [
        Unit(kind="tools", label="tools", payload=canonical_json(canonical_tools(tools))),
        Unit(kind="system", label="system", payload=system.encode("utf-8")),
    ]
    for index, message in enumerate(messages):
        units.append(
            Unit(kind="message", label=f"messages[{index}]", payload=message.canonical)
        )
    frozen = tuple(units)
    return RenderedRequest(units=frozen, hashes=unit_hashes(frozen))

注意 Unit.framed 在拼字节时把 label 也写进去了。这不是为了好看：它保证「同样的字节出现在不同位置」不会算出同一个哈希。否则一个恰好等于系统提示词文本的用户消息会被当成同一段前缀的一部分。

工具列表：注册顺序是加载产物，不是语义

工具声明排在渲染顺序的最前面，所以它的稳定性决定整条请求的天花板。而工具的注册顺序几乎总是「插件加载顺序」这种和语义无关的东西。DSH 在提示词组装里显式规范化了顺序：

function orderTools(tools: ToolSchema[], toolOrder: string[] | undefined, knownNames: ReadonlySet<string>): ToolSchema[] {
  const reserved = tools.find(tool => tool.name === TOOL_ORDER_REST)
  if (reserved !== undefined) {
    throw new Error(`tool provider returned reserved tool name "${TOOL_ORDER_REST}" (reserved for toolOrder's rest entry)`)
  }
  if (toolOrder === undefined) return tools.sort(compareToolNames)
  const unknown = toolOrder.filter(name => name !== TOOL_ORDER_REST && !knownNames.has(name))
  if (unknown.length > 0) {
    throw new Error(`toolOrder lists unregistered tool${unknown.length > 1 ? 's' : ''} ${unknown.map(name => `"${name}"`).join(', ')}; known tools: ${[...knownNames].sort().join(', ') || '(none)'}`)
  }
  const listed = new Set(toolOrder)
  const rest = tools.filter(tool => !listed.has(tool.name)).sort(compareToolNames)
  return toolOrder.flatMap(name =>
    name === TOOL_ORDER_REST ? rest : tools.filter(tool => tool.name === name))
}

出处：system-prompt/index.ts:222；默认分支就是排序这一行 index.ts:227。三个细节值得抄：

  • 默认排序：没有配置 toolOrder 时按名字排序，而不是按注册顺序。所以「顺序不稳定」这件事在默认路径上就被消掉了。
  • 比较函数是 code-unit 逐字符比（index.ts:238，注释写明 locale-independent, so the order is identical on every machine）。不用 localeCompare：那种比较在不同机器、不同 locale 下结果可能不同，同一份配置在两台机器上会渲染出不同的前缀。
  • 配置了顺序就必须配对了：toolOrder 里写了一个没注册的工具名，assemble() 直接抛错而不是静默忽略。这是个有意为之的取舍——配置错的时候大声失败，比悄悄渲染出一个和预期不同的前缀好。

我们这边对应的是 canonical_tools：

def canonical_tools(tools: Sequence[Mapping[str, Any]]) -> list[dict[str, Any]]:
    """工具集规范化：按名字排序。

    注册顺序是插件加载顺序的产物（DSH README 的原话是 registration order is a
    plugin-load artifact），它跟模型的判断无关，却会改变提示前缀。排序把它消掉。
    """
    return [dict(tool) for tool in sorted(tools, key=lambda tool: str(tool["name"]))]

诊断：第一个差异落在哪个字节

有了规范渲染，缓存问题就变成了一个纯函数问题：给定上一次和这一次，回答「最长相同前缀有多长」。这个函数是本章最该抄走的一段代码——它把「缓存命中率掉了」这种模糊抱怨，变成「第 2 条消息被改写了」这种可操作结论。

def diff_prefix(prev: RenderedRequest, curr: RenderedRequest) -> RequestDiff:
    """找出两次请求的第一个差异，并据此判断这次最多能复用多少缓存。

    这是整个模块的核心纯函数：给定两次渲染结果，回答「缓存从哪个单位、哪个字节开始失效」。
    三种形态的后果差别很大，是本章反复要讲的：
      1. 工具或系统提示词变了 —— 命中在它之前，之后全废；
      2. 历史里第 k 条消息被改写 —— 命中到 k-1，之后全废；
      3. 尾部追加 —— 前缀完整命中，只有新增部分要重新计算。
    """
    return _diff(prev, curr)

它区分三种形态，因为三者的成本完全不同。关键在于：它不是按「段」比，而是按字节比。段级比较会给出一堆假警报（「messages 变了」——但变的其实只是尾部多了一条），字节级比较才能算出真实的可复用长度。两者都要，因为它们回答的是不同问题：段级回答「谁干的」，字节级回答「亏了多少」。

最后把「缓存」本身也变成可离线的对象：一个只记前缀哈希的模拟器。真实缓存还有 TTL、最小可缓存长度、按模型区分等维度，但本质规则只有一条——前缀必须逐字节相同。把它写成一个二十行的类，缓存行为就进了单元测试。

    def lookup(self, request: RenderedRequest) -> int:
        """返回这次请求命中的**单位数**（0 表示连工具声明都没命中）。"""
        hit = 0
        for digest in request.hashes:
            if digest not in self._seen:
                break
            hit += 1
        return hit

它的 store 只记「前缀」而不是整串，这个选择让它自动具备了真实缓存的关键性质：下一次请求多一条消息时，它前面的单位哈希没变，所以照样命中。追加式历史天然对缓存友好，这不是巧合，而是「只记前缀」的必然结果。

分层设计：稳定的系统提示词 + 运行时上下文快照

现在讲本章最重要的工程结论。harness 的系统提示词里总有一天要塞进「当前时间」「工作目录」「git 分支」「待办列表」这类东西——它们对模型有用，而且真的该被看到。问题在于塞进哪里。

直觉答案（拼进系统提示词）是错的，而且错得很贵：系统提示词排在渲染顺序的第二个位置（tools 之后、messages 之前），它一变，整条历史全部失效。改成「作为一条消息追加在历史之后」，同样的信息、同样的模型可见内容，但前缀完整保住。两种做法的差别不是「更好一些」，而是「命中率 100%」和「从系统提示词之后全部重算」。

def build_request(
    *,
    system: str,
    tools: Sequence[Mapping[str, Any]],
    messages: Sequence[Message] = (),
    runtime_context: str | None = None,
    context_in_system: bool = False,
) -> RenderedRequest:
    """构造一次请求。

    ``context_in_system=False``（推荐）：易变的运行时事实（时间、cwd、git 状态、todo）
    作为一条独立消息追加在历史**之后**——它只是前缀的一条尾巴，前缀本身不受影响。
    这对应 DSH 的 runtime-context 快照：渲染成一条 user 消息，而不是拼进系统提示词。

    ``context_in_system=True``（反例）：把同样的内容拼进系统提示词。系统提示词排在第二个
    单位，它一变，整条请求从那里就开始偏离，后面全部失效——而模型在这种配置下看到的内容
    和「好」版本完全一样，所以失效没有任何可见症状。
    """
    history: list[Message] = list(messages)
    rendered_system = system
    if runtime_context is not None:
        if context_in_system:
            rendered_system = f"{system}\n\n{runtime_context}"
        else:
            history.append(Message(role="user", text=runtime_context, source="runtime-context"))
    return render_request(tools, rendered_system, history)

DSH 把这条路走到了极致：运行时上下文有自己的消息来源、自己的投影状态、自己的「已清除」标记，完全不进系统提示词。

  project(current: string, sections: readonly ContextSnapshotSection[]): UserMessage | undefined {
    if (this.retained === undefined && current.length === 0) return
    const snapshot = current.length === 0 ? CLEARED : current
    if (this.retained?.text === snapshot) return
    return createUserMessage({
      content: [{ type: 'text', text: snapshot }],
      // The cleared marker has no contributions left to attribute.
      source: sections.length === 0
        ? { kind: SOURCE }
        : { kind: SOURCE, form: 'snapshot', sections },
    })
  }

出处：runtime-context.ts:152，类定义在 runtime-context.ts:114。三行就够看出设计意图：

  • if (this.retained?.text === snapshot) return——渲染结果和上次一样就什么都不产生，不写日志、不发新消息。这是「无害的运行时上下文」的关键：内容没变就不该让请求字节变。
  • 清空时发的是 CLEARED 这句固定文本（runtime-context.ts:20），不是什么都不发。为什么？因为模型需要知道「刚才那份快照作废了」。用一句固定文本表达作废，比删掉那条消息（造成历史改写=缓存断裂）便宜得多。
  • 快照以 user/message 的形式追加（agent.ts:430），而不是 system/message。选哪一个角色决定了它落在渲染顺序的哪个位置。

同样的信息在文本层面是这么拼的：joinContextSections 给整段加了一个自述标题（system-prompt/index.ts:313），逐条说明「这一份快照取代更早的运行时上下文快照」。有了这句话，即使快照被覆盖、被清空，模型也知道该以最新的为准，不会把两份快照拼起来读。

调用点：每轮怎么决定「要不要重写」

真正决定成本的是调用点。DSH 的 step 里，每次尝试都会做两件事，而且顺序不能换：

      const currentContext = this.loopCtx.systemPrompt.refreshContext(assembly, assembleContextFor(this, signal))
      const sections = renderContextSections(currentContext)
      const context = this.runtimeContext.project(joinContextSections(sections), sections)
      signal.throwIfAborted()
      const startsRequestSeries = firstAttempt && decision.startsRequestSeries === true
      const commits = this.systemPrompt.project(renderedPrompt, {
        inHistory: preparedCall?.systemPromptUpdate === 'in-history',
        startsSeries: startsRequestSeries
          || this.requestSurfaceGeneration !== this.session.surface.contentGeneration
          || (preparedCall?.toolUpdate === undefined && this.toolsChanged(assembly.tools)),
      })

出处：agent.ts:411-421。这里有三条可以直接搬走的规则。

规则一：系统提示词是「渲染一次」，运行时上下文是「每次刷新」。renderedPrompt 在整个 step 的重试循环外算好（agent.ts:407），循环内的 while (true)（agent.ts:409）只刷新上下文（agent.ts:411）。重试（llm-retry 那次）不会重新组装提示词，所以重试的请求和上一次的首字节一致——这正是「等一个 429 再试一次」不该白付一遍全量输入的原因。

规则二：系统提示词的准入策略由「是否要归并」决定。SystemPromptProjection.project 的三条分支很直白：没有系统节点就追加头节点；不支持的路线、新序列、或渲染为空时，把新文本写回第一个系统节点（这会从那个节点起打断前缀）；否则「在延续的序列里、路由支持历史内更新」时，把变更追加到已缓存历史之后。DSH 自己把这条规则写在 README 里：

前缀复用要求同一 provider 与模型路由下，此前的消息与声明保持逐字节一致。原地替换某个系统节点的提示词变更，会使请求从该节点的第一个 token 起就不同——该节点是第 0 号节点时则整个请求都不同。当已准备调用声明 systemPromptUpdate: 'in-history' 时，同一序列延续期间的非空提示词变更会追加到已缓存历史之后，因此直到该历史末尾的前缀仍可复用。

出处：agent-loop/README.md:164。同一份 README 在 system-prompt 那边还有一句更狠的自述：provider cache sharing and measured hit rates are not guaranteed（system-prompt/README.md:154）。也就是说：harness 只能保证「该稳定的地方稳定」，命中与否最终由 provider 决定。这个诚实的边界值得学。

规则三：「新请求序列」是一个显式概念，不是一个副作用。SystemPromptDecisionInput.startsSeries 的注释把三种触发条件列全了：pre-step 监听者声明了新序列、上次请求以来 surface 变了、或者「路由不支持工具更新时工具集变了」（runtime-context.ts:44-46）。把「哪些情况允许打断缓存」集中成一个可以读、可以测的判定，比让十几个地方各自决定「要不要重写系统提示词」可靠得多。

顺序表：为什么路径和端点排在最后

DSH 把提示词段和运行时上下文的位置都集中登记在一张表里。运行时上下文只占四个位置，而且每个位置的产品代码都用 getContextOrder() 去取，不写字面量：

  WORKING_DIRECTORY: 100,
  SANDBOX_POLICY: 110,
  APPROVAL_POLICY: 115,
  SUBAGENT_DELEGATION: 120,
} as const

出处：system-prompt/index.ts:170。系统提示词段那张表更长，但有一条注释把设计意图说透了：// Local paths and endpoints follow reusable instructions.（index.ts:161）。本地路径、本地 URL 这种「每台机器、每个 checkout 都不一样」的内容，被排到 HARNESS_SOURCE: 10000、WEB_SURFACE: 10100，也就是几乎最末尾——让它们尽可能地远离前缀的开头。includeRuntimeContext 默认开（index.ts:428），但东西放在哪张表里、第几位，是被显式设计过的。

具体到「工作目录」这个最典型的易变量，DSH 的注册代码短得可以直接照抄：

    ctx.systemPrompt.context({
      name: 'working-directory:current',
      order: ctx.systemPrompt.getContextOrder('WORKING_DIRECTORY'),
      required: true,
      interpolate: false,
      text: context => context.agent === undefined ? '' : this.contextText(context.agent.session),
    })

出处：working-directory/src/index.ts:90-96。它的文本是 Current working directory: "…"（index.ts:173），而且取的是已提交的目录、不做文件系统 IO（get() 读的是投影状态）。三个取舍连着看：

  • required: true 意味着它不会被上下文抑制开关屏蔽掉——工作目录是必须让模型看到的。
  • interpolate: false 意味着不做变量插值。路径里出现 {{ 这种字符时不会被当成模板——省掉一整类「路径内容改变了渲染结果」的事故。
  • 它只在真的变了的时候产生新文本。目录没变 → 快照文本没变 → RuntimeContextProjection.project 返回 undefined → 一个字都不发。

审批策略是同一个思路的另一个例子，而且注释直接写明了理由：switching policy does not rewrite the stable system-prompt cache prefix（user-approval/src/index.ts:161）。用户切成「全自动」不该让整条历史重算一遍——把策略放进运行时上下文，切一次只花一条消息的钱。

     可复用 428/428 字节（共用 5 个单位）

整段命中率：bad 0.1554，good 0.5969（教学示意）

读法：坏版本的第二次请求只复用了工具声明那一个单位（153 字节），系统提示词之后的一切全部重算；好版本的第二次请求复用了上一次的全部内容（428/428），只有新追加的那条快照要算。整段命中率被第一次请求（必然 0 命中）拉低，所以别用累计命中率判断改动效果——要看增量请求的复用比例，那才是稳态。

还有一个反直觉的结论要点出来：「好」版本的绝对命中率不一定是 100%。追加式历史里，每一次新增内容本身都要重算（哪怕它是纯追加）。所以一个健康的 harness 的稳态是「每次都复用绝大多数 token」，而不是「每次都全命中」。把期望值定错，会导致你去优化根本不值得优化的地方。

工具集变了怎么办：写一条消息，别改系统提示词

工具列表变化是前缀缓存最难处理的一种变化，因为它同时有两种需求：模型必须知道工具变了（否则它会继续调用已经不存在的工具），而工具声明又排在渲染顺序的最前面（一改就全断）。

DSH 分两件事处理。第一件：渲染字节变了就是变了——toolsChanged 直接拿当前 schema 和上一条 header 里的 schema 比（agent.ts:291），不试图掩饰。第二件：另外写一条 developer/message 把增删告诉模型，而不去重写系统提示词里的工具说明段。

      const previousNames = new Set(baseline.tools?.map(tool => tool.name))
      const currentNames = new Set(tools.map(tool => tool.name))
      const additions = tools.filter(tool => !previousNames.has(tool.name))
        .map(tool => ({ type: 'tool-addition' as const, toolName: tool.name }))
      const removals = (baseline.tools ?? []).filter(tool => !currentNames.has(tool.name))
        .map(tool => ({ type: 'tool-removal' as const, toolName: tool.name }))
      if (additions.length > 0 || removals.length > 0) {
        session.append('developer/message', {
          ...position,
          message: createDeveloperMessage({ source: { kind: 'tool-registry' }, content: [...additions, ...removals] }),
          ...additions.length > 0 ? { headerSeq } : {},
        }, { surfaceOp: 'append' })
      }

出处：agent.ts:653-665。这段代码值得逐点拆：

  • 增删分开记，各自带工具名，因为模型对这两件事的处理不对称：新增的可以马上用，被移除的必须停止调用。
  • source: { kind: 'tool-registry' } 标明来源是工具注册表，不是用户说的话。这条消息在日志里有明确的来源标记，回放和界面都能归因。
  • 只有新增才引用 headerSeq（...additions.length > 0 ? { headerSeq } : {}）。因为新增工具需要模型知道「去哪份声明里找它」，而移除不需要指向任何新声明。
  • surfaceOp: 'append' 表明这是追加，不是替换。追加是不打断前缀的操作——这是整段代码能兼顾「模型知情」和「前缀复用」的根据。

我们的模拟器对这段策略给出的判定是：工具集合变化命中 0 个单位（工具在最前面，改了就全断），新增工具后写的那条 developer/message 则是一次纯追加（命中率 100%）。两件事分开记，正是为了让后者不背上前者的成本。

DSH 还为子代理的 fork 方式留了一条注：继承历史之所以能复用 KV 缓存，是因为子代理不重选模型——provider 和 model 与父代理保持一致（cordis.patch.yml:382）。同一个前缀在不同模型上是两份缓存，「顺手换个小模型省点钱」的代价可能比省下来的多。

观测：命中率必须在日志里

前面所有设计都有一个共同前提：缓存失效是静默的。模型照常回答，功能全对，界面全绿——只有账单和延迟在变。所以这一章的最后一块是观测：如果命中率不可见，前面所有的纪律都会在三个月内被一次「顺手加个时间戳」的提交悄悄破坏。

provider 侧的信号在 usage 里。DSH 的适配器把厂商字段直接映射成内部字段：

  const keys = { input_tokens: 'inputTokens', output_tokens: 'outputTokens', cache_read_input_tokens: 'cacheReadTokens', cache_creation_input_tokens: 'cacheWriteTokens' } as const

出处：llm-deepseek/translate.ts:36；内部字段 cacheReadTokens?: number 定义在 llm/types.ts:186。注意「缓存读」和「缓存写」是两个分开的字段，不是「缓存命中 bool」——这个区分很重要，下面讲坑的时候会用到。

更值得抄的是 DSH 怎么把这件事变成一条可执行的断言：一个需要真实 API key 的 e2e 测试，跑一轮包含工具调用的多步 turn 加一轮后续，然后要求第二次之后的每一次请求的 cacheReadTokens 都大于 0。

    // The first request has nothing to hit; every later one shares its
    // predecessor as a byte-identical prefix, so the provider must report
    // cached prompt tokens (prompt_cache_hit_tokens → cacheReadTokens).
    for (const usage of usages.slice(1)) {
      expect(usage!.cacheReadTokens ?? 0).toBeGreaterThan(0)
    }

出处：request-cache.e2e.ts:91-96。测试文件开头把这条测试的定位写得很清楚：mock 只能证明「追加式扩展」，只有真实 provider 才能证明「真的命中了」（request-cache.e2e.ts:14-22）。里面还有一个容易被忽略的细节：那段系统提示词被刻意写长，作者注明长到足以覆盖 provider 的缓存块粒度（64 token）（request-cache.e2e.ts:24-25）。真实缓存有最小可缓存长度，短前缀本来就不该命中——不知道这一点的人会对着一个必然为 0 的数字查半天。

还有一个反向的观测：谁在花钱、谁在省钱。上下文压缩（下一章）的摘要调用是个典型：它要重新读一遍历史来生成摘要，如果这段历史和正常请求的字节不一致，那这次读是全新的、无法复用的。DSH 的做法是让摘要调用的前缀逐字节对齐对话最后一次请求的系统提示词、工具和历史：

The replayed system prompt, tools, and shadowed-region messages match the conversation's last routed request byte-for-byte, so the provider's warm prefix cache is reused up to the trailing instruction; only that instruction, and the summary output, is uncached.

出处：compaction-basic/README.md:233，源码里的注释同义（summarizer.ts:76）。它同时说明了一件事的代价：Routing the summarizer to a different provider/model, or compacting a non-head range, forgoes this reuse.——「压缩用便宜的小模型」和「缓存复用」是互斥的，得算清楚再选。

我们的离线观测

没有真实 API 的时候，观测靠 labs 里的模拟缓存。它给的是「单位级命中数」，落到正文里就是那句最关键的话：先看增量请求的复用比例，再看累计命中率。

    def hit_ratio(self) -> float:
        """教学示意：整段过程中的命中字节占比（分母含首次请求的全量）。"""
        return round(self.hit_bytes / self.sent_bytes, 4) if self.sent_bytes else 0.0

这个定义的缺陷要主动写出来：分母含第一次请求（必然 0 命中），所以会话越长这个数字越好看，短会话则天然难看。判断一次改动是不是稳定化改进，应该比「相邻两次请求的复用字节数」，也就是下面这个更直接的量：

def common_unit_count(prev: RenderedRequest, curr: RenderedRequest) -> int:
    """两个前缀哈希列表从前往后有多少个单位相等。"""
    count = 0
    for left, right in zip(prev.hashes, curr.hashes):
        if left != right:
            break
        count += 1
    return count

它比累计命中率更适合当回归指标，因为它是增量的：把「上一轮渲染结果」和「这一轮渲染结果」一对比，得到一个整数，整数变了就是有人让前缀退化了。把它写进日志，就得到一条可以被测试守住的量。

把它的输出写进日志，就得到一条可以被回归测试守住的量。这也是本章建议你立刻动手做的一件事：在每次请求前算一次 diff_prefix，把 「first_change」 记进会话日志。它比 provider 的 usage 早一步告诉你缓存为什么掉了——usage 告诉你「这次命中 0」，日志告诉你「因为系统提示词里的时间戳从 10:00 变成 10:01」。

三种取舍都成立，因为它们优化的是不同的东西。DSH 要的是「所有路由都不退化」——所以它做能力协商、做显式序列边界、把不确定的部分写进 README。OH 要的是「一次问清楚就有稳定的前缀」——把环境信息在开始时拍一次快照，之后不变；代价是日期跨天、cd 之后要主动重建提示词（它有 set_system_prompt，query_engine.py:102）。lcc 是最简单的对照：assemble_system_prompt 每轮重新拼，里面有一行 Current time: …（精确到秒）——按本章的规则，这等于每一轮都自愿放弃整个系统提示词前缀。它作为教学代码完全合理，因为它的目标是让每个机制都看得见；但这也是一个绝好的反例：加了这一行，代码可读性没变，成本结构变了。

顺带说一个诚实的观察：三家都没有设置 provider 侧的缓存断点。cache_control 这类显式标记能把缓存边界钉在你想要的位置（而不是让 provider 自己猜），但它需要按 provider 写分支，而且标记位置本身就是一份要维护的策略。DSH 的选择是把「让前缀天然稳定」当成主路径，把「显式标记」留给适配器层的一个能力字段（它的适配器目录里确实有「这个端点是否接受工具定义上的 cache_control」这一项）。这是一个可辩护的取舍：稳定化是普适的，标记是 provider 特有的。

坑与失败案例

坑一：时间戳进系统提示词，而且是「精确到秒」

触发条件：系统提示词里拼进当前时间、日期，或者「距会话开始已经过了 N 分钟」这类值。后果：系统提示词排在工具之后，它一变，之后的一切（包括整段历史）每轮重算。上面的实测里，坏版本的增量请求只复用了 153/337 字节，好版本是 428/428。没有症状：模型答得好好的，测试全过，日志正常，只有账单在涨。

源码里怎么防的：DSH 不给这类内容留位置——它连「运行时上下文」都单独分层，并且只在文本真的变了的时候才发新消息（runtime-context.ts:155）。它还留了一句「时间敏感」的边界：系统提示词里的本地路径和端点被排到顺序表的末尾，注释说明理由是「它们在可复用的指令之后」。而 OH 与 lcc 都走了另一条路——它们都在系统提示词里放了日期或时间（system_prompt.py:71、s15/code.py:858）。OH 的日期只到「天」，所以同一天内不失效；lcc 精确到秒，等于每轮都失效。这条差别很适合当检验标准：问「这个字段改变时，模型真的需要知道吗？如果需要，它必须排在系统提示词里吗？」

坑二：JSON 键顺序不稳定

触发条件：工具 schema、消息的 extra 字段、任何进请求的结构化数据经过 dict 拼装，而且这个 dict 的字段顺序取决于并发任务的完成顺序、set 的迭代顺序、或某个中间件的实现细节。后果：内容和上一轮完全一样，序列化出来的字节不同 —— 缓存从第一个顺序不同的键起失效。这种失效比时间戳更难查，因为两次渲染在人眼里完全一样。

源码里怎么防的：本质上靠「不让顺序有机会漂移」。DSH 的 headerEquals 是把工具 schema 按位置逐个比（hx-04 讲过），也就是说位置本身被视为语义的一部分；而位置由 orderTools 的排序保证。我们的 canonical_json 用 sort_keys=True 把这件事压成一行。测试里对应的断言是「键顺序不同但内容相同，渲染必须逐字节一致」——没有这条测试，这个坑会在某次重构里悄悄回来。

坑三：把「缓存写」当成「缓存命中」

触发条件：只看 usage 里的「有缓存相关的 token」就以为命中了，不区分 cache_read_input_tokens 和 cache_creation_input_tokens。后果：你会看到非零数字、以为一切正常，实际上每次都在写新缓存——也就是把整份输入按缓存写的价格付了一遍，比不缓存还贵。DSH 把这两个字段映射成两个独立字段（translate.ts:36），就是为了让这一区分在类型上无法被抹掉。

检测的判定标准：官方文档给的说法是看 cache_read_input_tokens 是否为 0——为 0 就是没命中。DSH 的 e2e 测试把这条标准写成断言，而且要求的是「第一次之后的每一次都大于 0」（request-cache.e2e.ts:95）。这个「逐次断言」比「平均命中率」有用得多：平均值会掩盖「只有前两条命中、后面全废」这种最糟糕的情形。

坑四：前缀太短，本来就命不中

触发条件：以为「内容没变就该命中」，结果发现小会话、短提示词怎么都是 0 命中。原因：真实缓存有最小可缓存长度（不同模型不同，常见量级是 1024 token；Anthropic 官方文档给了具体门槛）。比这个长度短的前缀根本不会被缓存，不管它多稳定。

源码里的痕迹：DSH 的缓存 e2e 测试特意把系统提示词写得很长，注释直接写明理由是「长到足以覆盖 provider 的缓存块粒度（64 token）」（request-cache.e2e.ts:24-25）。也就是说：测试作者知道「短前缀必然不命中」，所以为测试造了一个足够长的前缀。这个细节值得记：如果你的回归测试在一个短提示词上断言缓存命中，它测的不是你的 harness，而是 provider 的块大小。

坑五：为了「模型看得更清楚」而重排系统提示词

触发条件：想让提示词更易读，把「工具说明」挪到「身份说明」之前，或者把某个段插到中间。后果：这是故意的前缀断裂，而且是小改动造成的大面积失效——插入点之后的全部段都要重算。在长会话里，这一次编辑的成本可能是几十次请求的差额。

源码里怎么防的：DSH 把顺序集中登记在一张常量表里（index.ts:131），每段用一个名字去取位置（getSectionOrder('HARNESS_IDENTITY') 之类），而不是在各自插件里写数字。好处是顺序的改动变成一个集中、显式、可 review 的动作，而不是几十个插件的相对位置在长期演进里慢慢漂移。这与 hx-04 讲「格式版本要显式声明」是同一个思路：把隐式的、会累积的耦合变成一张显式的表。

小结

这一章可以压成四句可执行的话：

  1. 渲染必须确定。键排序、固定分隔符、工具按名字排序、比较函数不依赖 locale。任何「取决于环境或时序」的字节，都是缓存失血的源头。
  2. 易变内容放尾部。运行时上下文作为追加消息存在，不要进系统提示词；真的变了才发新快照；作废发一句固定文本，而不是删消息。
  3. 变化要分类，不要一刀切。「工具集变了」和「历史尾巴长了一条」的成本差一个量级。工具变更写一条追加的 developer/message，系统提示词的准入交给一个集中的判定函数。
  4. 命中率要能被观测和断言。provider 的 cache_read_input_tokens 是真相；本地 diff_prefix 是原因。两个都进日志，前者进回归测试。
