第 10 章

长期记忆存储与指令文件

主线故事 · 第 10 章（虚构）

“规矩要写下来，”老唐在会议室白板上写，“写在代码旁边，跟代码一起进版本库。”

他们建了第一个 AGENTS.md，放在仓库根目录，一共六条：测试用 pytest、公开接口不许动、提交信息用中文、依赖不许多加、日志格式、目录结构。橘子第二天进这个仓库，第一轮就把六条都读到了，一整周没再问过“用 unittest 还是 pytest”。

问题出在第三个仓库。那个仓库有三层目录，根目录有一份约定，backend/ 下面还有一份更细的。橘子只读了根目录那份，于是把后端专用的命名规范漏掉了。等林舟加上“往上找、往细找”的逻辑之后，新的毛病来了：它把三个目录的约定一股脑按顺序塞进上下文，里面有两句互相矛盾的话（根目录说“依赖不许多加”，子目录写的是“需要时用 poetry 加”），模型自己挑了后面那句。

“两份都读到了，但你没有告诉它谁大谁小。”老唐说，“人写的规矩，得能排出先后。”

第二件事发生在同一天。橘子自己也需要记东西——客户的口味、踩过的坑、某个接口为什么长这样。这些东西没人会写进 AGENTS.md，可它们又必须跨会话活下来。于是他们让橘子自己开一个记忆库：一条一个文件，外加入口索引。

这一章要弄清楚两类知识怎么分开对待：人写的指令文件（怎么找、怎么合并、什么时候加载），和 agent 自己写的记忆条目（格式、命名、索引、去重、并发）。

前几章处理的都是“这一个会话里”的上下文：系统提示、运行时上下文、压缩、卸载。会话一结束，它们就没了。本章处理跨会话还活着的知识，它有两种来源，而且必须分开对待：

  • 指令文件：人写的 AGENTS.md / CLAUDE.md，跟代码一起进版本控制，按用户级、项目级、子目录级层叠。
  • 记忆条目：agent 自己（或会话结束后的后台任务）写下来的笔记，一条一个 Markdown 文件，外加一个 MEMORY.md 索引。

本章只讲“存”和“装”：文件放在哪、长什么样、谁来写、怎么防并发和注入。“下一轮该取哪几条”是检索问题，留给 hx-11；记忆的过期、替代与整理见 hx-12。

先看全貌：长期记忆与指令文件是什么、管哪些事

一句话：会话结束就消失的东西都属于上下文；跨会话还活着的知识有两种来源，一种是人在文件里写的，一种是 agent 自己记下来的，两者必须分开对待。

  • 指令文件：AGENTS.md、CLAUDE.md 这类人写的约定，跟代码一起进版本控制，按用户级、项目级、子目录级层叠。
  • 记忆条目：agent 自己写下的笔记，一条一个 Markdown 文件，外加一份索引。

这一层要管的事：

  • 查找：从当前目录往上找到哪里为止，谁先谁后。
  • 合并与排序：多份约定同时命中时，冲突怎么裁决。
  • 加载时机：每轮重新读，还是启动读一次再增量刷新。
  • 条目格式：文件名怎么定、正文放什么、索引怎么维护。
  • 写入：谁有权限写、怎么去重、并发写怎么办。

四个决定，先给结论：

决定看起来省事的做法本章的结论
指令文件的作用范围只读仓库根目录那一份从当前目录往上找，再由宽到窄排；子目录那份离得近，优先级更高
加载时机每轮都重新读一遍重读会让前缀缓存每轮失效（第 06 章），一般读一次再按需刷新
记忆条目的组织所有笔记写进一个大文件一条一个文件，稳定命名（slug），外加一份索引；索引整份重建而不是追加
索引怎么读把整个记忆库塞进上下文索引进上下文，正文按需读；索引本身也要控制长度

三个仓库在这一层分别是什么水平

DSH（TypeScript）：指令文件的层叠规则最清楚，从工作目录往上找到项目根，再由宽到窄排序。这一节的主要参考。

OpenHarness（Python）：只认 CLAUDE.md 这一个文件名，一路往上找到磁盘根。写法简单，可以看清“只认一个名字”的取舍。

amt（notebook 教程）：记忆条目的格式、索引、类型划分基本来自它的思路，用的都是示意代码。

labs（本章要写的）：labs/harness/memory_store.py，查找、排序、渲染指令文件，以及记忆条目的读写、索引重建、原子写。

本章怎么读：

  1. 第 1 节先把两类知识分开，这是全章的组织方式。
  2. 第 2 节讲指令文件：查找、合并、加载时机。四家实现各有取舍，可以只看你关心的那一家。
  3. 第 3、4 节讲 agent 自己写的记忆：格式、索引、写入路径和并发。
  4. 本章和下一章连着读：这一章管“怎么存”，第 11 章管“这一轮取哪几条”。
  5. 蓝色的 文件:行号 是源码出处，第一遍可以跳过。

两类持久知识：谁写、信多少、什么时候读

把指令文件和记忆混成一个“长期记忆”框，是最常见的设计错误。它们在三个维度上都不一样：

维度指令文件（AGENTS.md / CLAUDE.md）记忆条目（memory/*.md）
写入者人，经过代码评审模型，或后台提取任务
信任级别高于记忆，但低于系统提示和用户当轮的直接指令只是“背景知识”，不能当成新命令
加载时机会话开始时整份装入，之后按文件变化增量刷新索引常驻，正文按相关性挑几条（hx-11）
存放位置仓库里，跟代码走通常在仓库外的数据目录，按项目分桶

信任级别这一行在源码里是写成文字直接告诉模型的。DSH 给指令文件的引导语是 render.ts:217：更具体的优先，并且“不覆盖系统、开发者或用户的直接指令”。learn-claude-code 给记忆的引导语则更保守，s09_memory/code.py:346：召回的偏好和事实是上下文，不是新命令，冲突时以当前用户请求为准。

为什么要分开：指令文件是人审过的，记忆是模型自己写的。模型写的东西如果拿到和指令文件一样的地位，一次被注入的网页内容就可能变成“永久规则”。两类知识分开装、分开标注，是后面所有防御的前提（hx-17 会专门讲记忆投毒）。

指令文件：查找、合并、加载时机

DSH：从 cwd 往上找到项目根，再由宽到窄排

DSH 的查找规则全在 packages/context/agent-instructions。默认值三行就能读完：项目根标记是 .git（config.ts:11），每个目录的候选文件按顺序是 AGENTS.md、CLAUDE.md（config.ts:12），之后还有一层不进版本控制的本地覆盖 AGENTS.local.md / CLAUDE.local.md（config.ts:13）。

查找分三步：

  1. 用户级：先看 harness 自己的 home，再看共享的 agents home，两处只认一个固定文件名 AGENTS.md（files.ts:336，文件名常量在 render.ts:122）。
  2. 找项目根：从 cwd 往上，遇到含 .git 的目录就停（files.ts:241）；一路走到磁盘根都没找到，就把 cwd 本身当项目根（files.ts:244）。注意这个回退：没有项目根时不会去读 cwd 的祖先目录。
  3. 项目链：ancestorChain 生成从项目根到 cwd 的目录链，最后 files.ts:267 反转成“由宽到窄”。每个目录里先读基础候选、再读本地覆盖（files.ts:360）。

合并规则是不合并：所有文件按“用户级 → 项目根 → … → cwd”的顺序原样拼接，冲突怎么裁决交给模型，靠的就是 render.ts:217 那句“更具体的优先”。唯一的去重是同一目录里内容相同（trim 后）的候选只留第一个，配置注释写在 config.ts:27。典型场景是 CLAUDE.md 只是 AGENTS.md 的软链接，不去重就会把同一份规则塞两遍。

OpenHarness：只认 CLAUDE.md，一路找到磁盘根

OpenHarness 的查找写在 prompts/claudemd.py，规则差别很大。它从 cwd 开始遍历所有祖先（claudemd.py:14），没有项目根这个停止条件；每层只认 CLAUDE.md、.claude/CLAUDE.md 和 .claude/rules/*.md（claudemd.py:16）。在钉住的 commit 里全文搜索 AGENTS.md 没有命中，也就是说它不读 AGENTS.md。结果按发现顺序追加（claudemd.py:20），所以是由近到远，正好和 DSH 相反，而且没有任何一句告诉模型“谁优先”。

大小控制只有一条：每个文件截到 12000 字符（claudemd.py:46），没有总预算。祖先目录越多，这一段就越长。

加载时机：每轮重读，还是读一次再增量刷新

这个选择直接决定前缀缓存能不能命中（见 hx-06）。

  • OpenHarness 每轮重建系统提示。每次用户输入都会调用 runtime.py:736，指令文件放在系统提示里（context.py:146），后面跟着 MEMORY.md 和按当轮提问挑出来的相关记忆（context.py:174）。好处是改了 CLAUDE.md 下一轮立刻生效；代价是系统提示的尾部几乎每轮都可能变，变化点之后的整段历史都要重新计算前缀（作者归纳，实际命中率还取决于提供方的缓存断点）。
  • DSH 首请求前读一次，之后按文件触碰增量刷新。模块注释第一段就是这条约定（index.ts:4）：工具结果里出现的文件触碰先收集起来，到 step 结束时再重算。指令以一条消息插入在用户提问之后、运行时上下文之前（index.ts:357），不进系统提示，所以改 AGENTS.md 不会改写最前面的缓存前缀。

DSH 的总预算默认 64 KiB（cordis.patch.yml:301）。超了先从最宽泛的文件开始整份丢弃（render.ts:362），只剩最具体的一个还放不下时才截断它（render.ts:376），并在文本里写明省略和截断了什么。这个顺序的道理是：离 cwd 越近的规则越可能和当前任务相关。

注入：指令文件提前闭合外框

DSH 把整段指令包在一对 system-reminder 标签里，外框由本模块自己拼（render.ts:315）。如果某个 AGENTS.md 里写了一个字面的结束标签，后面的文字在模型看来就出了框，像是另一段系统区内容。所以正文先过一遍 render.ts:88，把结束标签变形；测试 agent-instructions.spec.ts:942 要求路径和派生作用域里的也要转义（这条坑最早记在 notes-context.md）。

注意 replaceAll 用的是精确字符串（render.ts:17），大写或带空格的变体不会被替换。模型读的是文本而不是 XML 解析器，这些变体会不会被当成结束标签没法从源码判定；labs 里的版本保守一点，用大小写不敏感、允许空白的正则。OpenHarness 只用一个 md 代码围栏包住内容（claudemd.py:47），不做任何转义，文件里一行 ``` 就能闭合围栏。指令文件和记忆被投毒的完整讨论见 hx-17。

labs：查找、排序与渲染

find_instruction_files 采用 DSH 的规则：由远到近（用户级 → 项目根 → … → start_dir），停在 stop_at 或第一个含 .git 的祖先，都没有就只看 start_dir。

def find_instruction_files(
    start_dir: str | Path,
    stop_at: str | Path | None = None,
    *,
    names: Sequence[str] = INSTRUCTION_NAMES,
    user_dir: str | Path | None = None,
    max_file_bytes: int = 1_048_576,
) -> list[InstructionFile]:
    """由远到近：用户级 → 项目根 → … → start_dir。

    合并规则：不做语义合并，全部按这个顺序拼接，越靠后越具体，冲突时以后者为准
    （渲染时把这条规则写给模型）。同一目录里内容相同的文件只保留第一个。
    停止条件：给了 stop_at 就停在它（含）；否则停在第一个含 .git 的祖先（含）；
    都没有就只看 start_dir，不会一路找到磁盘根目录。
    """
    start = Path(start_dir).resolve()
    top = Path(stop_at).resolve() if stop_at is not None else find_project_root(start) or start
    if top != start and top not in start.parents:
        raise ValueError(f"stop_at 必须是 start_dir 或它的祖先：{top}")
    chain = [start]
    while chain[-1] != top:
        chain.append(chain[-1].parent)
    scoped = [(d.relative_to(top).as_posix(), d) for d in reversed(chain)]
    if user_dir is not None:
        scoped.insert(0, ("user", Path(user_dir).resolve()))
    found: list[InstructionFile] = []
    seen_paths: set[Path] = set()
    for scope, directory in scoped:
        seen_bodies: set[str] = set()
        for name in names:
            path = directory / name
            if path in seen_paths or not path.is_file() or path.stat().st_size > max_file_bytes:
                continue
            content = path.read_text(encoding="utf-8", errors="replace")
            if content.strip() in seen_bodies:
                continue  # 典型情况：CLAUDE.md 是 AGENTS.md 的软链接或拷贝
            seen_paths.add(path)
            seen_bodies.add(content.strip())
            found.append(InstructionFile(path, scope, content))
    return found

渲染时转义结束标签，超预算先丢最宽泛的文件：

def escape_reminder(text: str) -> str:
    """把正文里的结束标签变形：指令文件就没法提前闭合外框、把后文伪装成系统区。"""
    return _CLOSE_RE.sub("<\\\\/system-reminder>", text)
def render_instructions(files: Sequence[InstructionFile], max_bytes: int = 32_000) -> str:
    """超预算时先丢最宽泛的文件，最后才截断最具体的那个（与 DSH render.ts 的顺序相同）。"""
    if not files or max_bytes <= 0:
        return ""
    kept = list(files)
    while len(kept) > 1 and len(_frame(kept, len(files) - len(kept)).encode()) > max_bytes:
        kept.pop(0)
    omitted = len(files) - len(kept)
    if len(text := _frame(kept, omitted).encode()) <= max_bytes:
        return text.decode()
    last = kept[-1]
    cut = last.content.encode()[: max_bytes].decode(errors="ignore")
    while cut and len(_frame([replace(last, content=cut)], omitted, True).encode()) > max_bytes:
        cut = cut[: len(cut) * 9 // 10]  # 每次砍掉一成：转义会让长度变化，不能一步算准
    return _frame([replace(last, content=cut)], omitted, True) if cut else ""

记忆条目：一条一个文件，外加一个索引

格式与类型

OpenHarness 和 learn-claude-code 用的是同一种格式：记忆目录里每条记忆一个 Markdown 文件，开头是 YAML frontmatter，另有一个 MEMORY.md，每行一个指向条目文件的链接。类型划分两边也完全一致，都是四类（schema.py:22，s09_memory/code.py:50）：

  • user：用户是谁、偏好什么；feedback：用户纠正过的做法；project：代码里看不出来的项目事实；reference：外部资源的指针。

OpenHarness 还多了一个正交的作用域维度 private / project / team（schema.py:23），frontmatter 字段一共 16 个（schema.py:32），包括签名、重要度、TTL、disabled、supersedes。后几个字段服务于检索和整理，见 hx-11、hx-12。

记忆目录放在仓库外的数据目录里，按 cwd 绝对路径的 sha1 前 12 位分桶（paths.py:14）。索引装进系统提示前截到 200 行、25 000 字节（schema.py:28、schema.py:29）。

为什么用文件而不是数据库：人能直接读和改，能 diff，能放进 git，坏了用编辑器就能修。代价是没有事务、没有索引查询，并发靠文件锁，一致性要自己维护。这也是为什么索引必须是“可以随时重建的缓存”，真相只在条目文件里。

labs 的 frontmatter 只支持 key: value 和字符串列表，不依赖 PyYAML（OpenHarness 用的是 PyYAML，schema.py:15）。必填字段和类型枚举在写入前校验：

def validate_meta(meta: dict[str, object]) -> None:
    for key in REQUIRED_FIELDS:
        value = meta.get(key)
        if not isinstance(value, str) or not value.strip():
            raise InvalidMemory(f"缺少必填字段：{key}")
    if meta["type"] not in MEMORY_TYPES:
        raise InvalidMemory(f"未知记忆类型：{meta['type']!r}，可选 {MEMORY_TYPES}")
    for key in ("name", "description"):
        if any(ch in str(meta[key]) for ch in "\r\n"):
            raise InvalidMemory(f"{key} 必须是单行：索引一行一条，换行会把索引拆坏")
    for key in ("created_at", "updated_at"):
        if not isinstance(meta.get(key, ""), str):
            raise InvalidMemory(f"{key} 必须是字符串")
    tags = meta.get("tags", [])
    if not isinstance(tags, list) or not all(isinstance(tag, str) for tag in tags):
        raise InvalidMemory("tags 必须是字符串列表")

文件名：slug 与路径穿越

文件名由名字派生。OpenHarness 把所有非 ASCII 字母数字换成下划线（manager.py:59），纯中文标题会全部退化成 memory，再靠 _2、_3 后缀区分。learn-claude-code 用 \w，保留 Unicode（s09_memory/code.py:91）。labs 跟 lcc 一样，并多做两件事：避开与索引同名和 Windows 保留设备名；拼出路径后再确认它仍直接位于记忆目录下。

def slugify(name: str) -> str:
    """名字 → 文件名。非单词字符一律换成 -，所以 / \\ 和 .. 都进不了文件名。"""
    slug = _SLUG_RE.sub("-", name.strip().lower()).strip("-_")[:MAX_SLUG_LEN].rstrip("-_")
    if not slug:
        raise InvalidMemory(f"名字里没有能当文件名的字符：{name!r}")
    if slug in _RESERVED_STEMS:
        slug += "-note"
    return slug
    def path_for(self, slug: str) -> Path:
        # 第二道防线：slug 已经滤掉了分隔符，这里再确认解析后仍直接位于根目录下。
        root = self.root.resolve()
        path = (root / f"{slug}.md").resolve()
        if path.parent != root:
            raise InvalidMemory(f"路径逃出了记忆目录：{slug!r}")
        return path

索引：整份重建，而不是追加

OpenHarness 写入后判断“文件名没出现在索引里就追加一行”（manager.py:118），删除时去掉“包含文件名”的行（manager.py:156）。两处都是子串判断：已经有 foo_bar.md 时，新写的 bar.md 不会进索引；删 bar.md 会连带删掉 foo_bar.md 那一行。learn-claude-code 每次写入后整份重建索引（s09_memory/code.py:168），没有这个问题。labs 用后一种做法，并把名字和描述里的方括号换掉，防止伪造第二个指针：

def render_index(entries: Sequence[MemoryEntry]) -> str:
    def plain(text: str) -> str:
        # 方括号换成圆括号：否则名字或描述里的 "](evil.md)" 能在索引里伪造出第二个指针。
        return text.replace("[", "(").replace("]", ")")

    lines = ["# Memory Index", ""]
    for entry in entries:
        lines.append(f"- [{plain(entry.name)}]({entry.slug}.md) — {plain(entry.description)}")
    return "\n".join(lines) + "\n"
    def index_drift(self) -> tuple[set[str], set[str]]:
        """（目录里有、索引里没有的文件, 索引指向、目录里没有的文件）。"""
        on_disk = {f"{e.slug}.md" for e in self.scan()[0]}
        text = self.index_path.read_text(encoding="utf-8") if self.index_path.exists() else ""
        pointed = set(_POINTER_RE.findall(text))
        return on_disk - pointed, pointed - on_disk

写入：谁写、怎么去重、怎么防并发

三条写入路径

OpenHarness 里有三种东西会写记忆目录：

  1. 模型在主循环里直接写。没有专门的记忆工具，系统提示告诉模型记忆目录在哪、建议“简短的主题文件加 MEMORY.md 里一条索引”（memdir.py:28），模型用普通的文件工具去写。这条路径绕过了 schema 校验和锁。
  2. 每轮结束后的后台提取，受开关控制（query_engine.py:189）。本轮模型已经写过记忆就跳过（memory_extract/__init__.py:97），否则发一次不带工具的请求（:108），要求返回 JSON，再逐条交给 add_memory_entry 落盘。
  3. autodream 整理：合并、改写、清理旧记忆。动手前先把整个目录拷一份备份（backup.py:45）。整理的策略属于 hx-12。

session_memory 是另一回事：它存的是当前会话的摘要，用来跨压缩边界续接，不是跨会话的长期记忆，这里不展开。

去重与原子写

OpenHarness 按正文签名去重（manager.py:72）：同样的正文写第二次会更新原文件。反过来，同一个标题配新正文会新建 foo_2.md，旧事实和新事实同时存在。labs 选的是另一种语义：同名即更新，保留 created_at 和人手工加的字段。两种都说得通，关键是写清楚“同一条记忆”按什么认定。

所有写入都走“临时文件 + replace”（manager.py:114），进程中途崩溃时文件要么是旧的、要么是新的，不会只写一半。删除是软删除，只把 disabled 置真（manager.py:147）。

    def save(
        self,
        name: str,
        *,
        memory_type: str,
        description: str,
        body: str,
        tags: Sequence[str] = (),
    ) -> MemoryEntry:
        """同名（slug 相同）就更新原文件：保留 created_at 与人手工加的字段。"""
        if not body.strip():
            raise InvalidMemory("正文不能为空")
        slug = slugify(name)
        self.root.mkdir(parents=True, exist_ok=True)
        with file_lock(self.lock_path):
            path = self.path_for(slug)
            old = parse_entry(slug, path.read_text(encoding="utf-8")) if path.exists() else None
            now = self._clock()
            meta: dict[str, object] = {
                **(old.extra if old else {}),
                "name": name.strip(),
                "description": description.strip(),
                "type": memory_type,
                "created_at": old.created_at if old and old.created_at else now,
                "updated_at": now,
                "tags": list(dict.fromkeys(tag.strip() for tag in tags if tag.strip())),
            }
            validate_meta(meta)
            atomic_write_text(path, render_memory(meta, body))
            self._write_index_locked()
        return parse_entry(slug, path.read_text(encoding="utf-8"))

并发：两种锁

主循环的写入和后台提取可能同时发生。OpenHarness 写条目时用内核文件锁（manager.py:60，POSIX 走 fcntl，Windows 走 msvcrt），进程死了锁自动释放。autodream 的整理锁是另一套：往锁文件写入自己的 pid 再回读确认（lock.py:69），持锁超过一小时视为过期（lock.py:15）。“写完再读回来看是不是自己”在两个进程几乎同时写时仍可能都以为拿到了锁（作者归纳）。labs 用 O_CREAT | O_EXCL 创建锁文件，同一时刻只有一个进程能成功，崩溃留下的锁按年龄判过期：

@contextmanager
def file_lock(path: Path, *, timeout: float = 5.0, stale_after: float = 60.0) -> Iterator[None]:
    """O_CREAT | O_EXCL 是原子的：同一时刻只有一个进程能把锁文件创建出来。"""
    deadline = time.monotonic() + timeout
    while True:
        try:
            fd = os.open(path, os.O_CREAT | os.O_EXCL | os.O_WRONLY)
            break
        except FileExistsError:
            _break_if_stale(path, stale_after)
            if time.monotonic() >= deadline:
                raise TimeoutError(f"拿不到记忆锁：{path}") from None
            time.sleep(0.05)
    try:
        try:
            os.write(fd, f"{os.getpid()}\n".encode())
        finally:
            os.close(fd)
        yield
    finally:
        path.unlink(missing_ok=True)

DSH 有没有长期记忆

没有。DSH 跨会话持久化的只有指令文件，没有 agent 自写的记忆库，跨会话检索默认关闭（沿用 dsh-00 的结论，本章没有逐包重新核对）。想让 DSH “记住”什么，只能写进 AGENTS.md，也就是经过人手。这是一种更保守的取舍：没有记忆投毒面，代价是用户每次都要自己维护文件。

坑与失败案例

  1. 索引子串匹配丢条目。触发：记忆目录里已有 foo_bar.md，再写一条 slug 为 bar 的记忆，或者删除 bar。后果：bar.md 存在但不在索引里，模型看不到它；或者删 bar 时把 foo_bar 的索引行一起删了。OpenHarness 没防（manager.py:118、:156 都是 in 判断）。labs 每次整份重建索引，index_drift 能报出目录和索引的差异，rebuild_index 以目录为准修复。
  2. 指令文件伪造系统区。触发：仓库里的 AGENTS.md（可能来自一次被污染的 PR）写了字面的 system-reminder 结束标签，后面跟一段“系统指令”。后果：模型可能把这段话当成框外的高优先级内容。DSH 用 render.ts:88 转义精确形式，大小写变体没覆盖；OpenHarness 的 md 围栏一行 ``` 就能闭合，完全没防。labs 用大小写不敏感的正则。
  3. 中文标题全部退化成 memory。触发：OpenHarness 里用中文标题写记忆。后果：文件名变成 memory.md、memory_2.md、memory_3.md，人打开目录分不清哪个是哪个，“文件可读、可 diff”的优势大打折扣。manager.py:59 只保留 ASCII；lcc 和 labs 用 \w 保留 Unicode。
  4. 移动仓库就“失忆”。触发：把项目目录改名或挪到另一块盘。后果：paths.py:14 按绝对路径哈希分桶，新路径对应一个空目录，旧记忆还在磁盘上但再也不会被加载。OpenHarness 没防；lcc 把记忆放在工作区的 .memory 里（s09_memory/code.py:37），跟着目录走，代价是容易被误提交进 git。
  5. 模型直接写文件绕过校验。触发：模型按 memdir.py:28 的提示用普通写文件工具写记忆。后果：frontmatter 缺字段、类型拼错，或者忘了更新索引，下一次扫描时这条记忆要么被跳过、要么被当成默认类型（OpenHarness 这一步的具体行为本章没有核对）。labs 的 scan 把解析失败的文件单独列出来，而不是静默丢弃：
    def scan(self) -> tuple[list[MemoryEntry], list[str]]:
        """扫目录：返回（合法条目, 解析失败的文件名）。坏文件跳过但要报出来。"""
        entries: list[MemoryEntry] = []
        broken: list[str] = []
        if not self.root.is_dir():
            return entries, broken
        for path in sorted(self.root.glob("*.md")):
            if path.name.lower() == INDEX_NAME.lower():
                continue
            try:
                entries.append(parse_entry(path.stem, path.read_text(encoding="utf-8")))
            except (InvalidMemory, OSError, UnicodeDecodeError):
                broken.append(path.name)
        return entries, broken

一句话归纳（作者归纳）：DSH 只信人写的文件，规则最严但没有自动记忆；OpenHarness 功能最全，但索引一致性和指令注入两处有洞；learn-claude-code 是教学最小实现，索引做对了，并发和原子写没管。

小结

  • 指令文件和记忆条目要分开装、分开标注信任级别。指令是人审过的，记忆只是背景。
  • 指令文件查找要有停止条件（项目根），拼接顺序要固定，并且把“谁优先”写给模型。
  • 加载时机影响前缀缓存：每轮重读最简单，读一次再增量刷新更省。
  • 记忆用“一条一个文件 + 可重建的索引”：目录是真相，索引只是缓存。
  • 写入要校验 schema、slug 防穿越、原子写、加锁；外框标签要转义。
