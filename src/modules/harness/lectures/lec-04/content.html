第 04 讲 · 把指令拆分到不同文件里

AGENTS.md 膨胀到 300 行，然后 400 行，然后 600 行。然后 agent 的表现反而变差了：关键约束被埋在文件中间，改一个小 bug 要处理无关的部署说明，三条互相矛盾的风格规则随机选一条遵循。

为什么会膨胀，为什么膨胀有害

最常见的恶性循环：agent 犯了个错，你加一条规则防止这个。然后又犯错，再加一条。累积效应是灾难性的。具体有四个问题：

  • 上下文预算被吃掉。 一个膨胀的指令文件可能占掉 10–20K tokens（128K 窗口的 8–15%）。到真正需要理解代码时，预算已经不够了。
  • 中间迷失。 Liu et al. 2023 清楚地证明：LLM 对长文本中间部分的信息利用效率显著低于两端。关键安全约束埋在第 300 行，被忽略的概率非常高。
  • 优先级冲突。 不可违反的硬约束和某个特定场景的历史教训，在文件里看起来一模一样。Agent 没有可靠信号区分哪个是红线，哪个只是建议。
  • 矛盾累积。 不同时期加的指令之间开始出现矛盾，agent 每次随机选一条遵循。

核心概念

概念说明
指令膨胀指令文件占到上下文窗口 10–15% 时，开始挤占代码阅读和任务推理的预算
指令信噪比 (SNR)文件中与当前任务相关的指令占总指令的比例。修一个 bug 被迫读 50 行部署说明，SNR 就很低
入口文件短小的引导文件，作用是把 agent 送到合适的专题文档，而不是自己包含所有内容
按需展开先给概要，需要时再给详细。好的 harness 设计不把所有选项一次性砸到 agent 脸上

拆分方案

入口文件 AGENTS.md 控制在 50–200 行，只放：项目概览（一两句话）、首次运行命令、全局硬约束（不超过 15 条不可违反的规则）、指向专题文档的链接。

# AGENTS.md（入口，控制在 80 行内）

## 项目概览
Python 3.11 FastAPI 后端，PostgreSQL 15 数据库。

## 快速开始
- 安装：make setup
- 测试：make test
- 完整验证：make check

## 硬约束
- 所有 API 必须走 OAuth 2.0 认证
- 所有数据库查询必须用 SQLAlchemy 2.0 语法
- 所有 PR 必须通过 pytest + mypy --strict + ruff check

## 专题文档
- API 设计规范 (docs/api-patterns.md) — 添加新端点时必读
- 数据库操作约束 (docs/database-rules.md) — 涉及数据库修改时必读
- 测试标准 (docs/testing-standards.md) — 编写测试时参考

每个专题文档 50–150 行，按主题放在 docs/ 目录下或对应模块目录旁。Agent 只在需要时才去读。

真实效果

一个 SaaS 团队把 AGENTS.md 从 600 行裁剪到 80 行，创建三个专题文档（API 设计规范 120 行、数据库规则 60 行、测试标准 80 行），同时把历史笔记要么转成测试用例，要么删除。

重构后：同一任务集的成功率从 45% 提升到 72%。安全约束遵循率从 60% 提升到 95%，因为规则从文件中间移到了入口文件顶部，不再被"中间迷失"了。

OpenAI 和 Anthropic 都隐性支持拆分：OpenAI 说入口文件应"短小且以路由为导向"，Anthropic 说长运行 agent 的控制信息应"简洁且高优先级"。两家说的是同一件事：别把什么都塞进一个文件里。
