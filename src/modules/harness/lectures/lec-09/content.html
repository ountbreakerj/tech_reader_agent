第 09 讲 · 防止 Agent 提前宣告完成

你让 agent 实现"密码重置"功能，它改了 schema、写了端点、加了邮件模板，跑了单元测试全部通过，然后告诉你"做完了"。实际一跑：重置链接发不出去，数据库迁移半途失败，端到端流程从来没走过一遍。

系统性过度自信

Guo 等人 2017 年在 ICML 上的经典论文证明：现代神经网络系统性地过度自信，模型自报的置信度显著高于实际准确率。AI 编码 agent 也一样——它"觉得"做完了，但实际上差得远。

Anthropic 在 2026 年的研究中发现了一个更深层的失败模式：当 agent 被要求评估自己的工作时，它系统性地过度正面评价，即使人类观察者认为质量明显不达标。在主观任务（如设计审美）上尤其严重。

解决方案不是让 agent "更客观"。同一个模型既生成又评估，内在地倾向对自己慷慨。解决方案是把"干活的人"和"检查的人"分开。

三层终止检查

harness 必须用外部化的、基于执行的验证来替代 agent 的"感觉"。三层校验缺一不可：

层级检查内容典型命令
第一层：静态分析语法正确、类型检查、lintmypy --strict / ruff check
第二层：运行时行为测试通过、应用能启动、关键路径可用pytest / npm test
第三层：系统级确认端到端流程、集成验证、用户场景Playwright E2E / curl 完整流程

在 AGENTS.md 里写清楚：

## 完成定义
- 功能完成 = 端到端验证通过，不是"代码写完了"
- 在第 1 层没通过时，不许进入第 2 层
- 在第 2 层没通过时，不许进入第 3 层
- 核心功能验证通过之前不许重构

单元测试通过 ≠ 任务完成

最常见也最危险的陷阱。单元测试的设计哲学是隔离被测单元、模拟依赖，这恰好使其无法检测跨组件问题：

  • 接口不匹配：各自的单元测试都用了 mock，都通过了。只有端到端跑通时才发现问题。
  • 状态传播错误：ORM 缓存层还持有旧结构的缓存条目，但单元测试每次都是全新 mock 环境。
  • 环境依赖性：测试环境一切 mock 行为正确，真实环境因配置差异、网络延迟、服务不可用而失败。

Claude Code 还有一个常见行为模式：在核心功能还没验证通过时就开始重构代码、优化性能。重构会改变已完成验证和未完成验证之间的边界，可能破坏之前隐式正确的代码路径。Knuth 的"过早优化是万恶之源"在 agent 场景里有了新含义。

让错误消息可自修正

OpenAI 在 Codex 实践中提出的关键模式：给 agent 写的错误消息要包含修复指导。不要只说"错了"，要说清楚哪里错了、为什么、该怎么改。

# 差
Test failed

# 好
Test failed: POST /api/reset-password returned 500.
Check that the email service config exists in environment variables.
The template file should be at templates/reset-email.html.

三 agent 架构对比数据（同一任务，同一模型 Opus 4.5）：单 agent 裸跑 20 分钟花 $9，游戏实体无法响应输入；三 agent（planner + generator + evaluator）6 小时花 $200，游戏可以正常游玩。区别只在 harness。
