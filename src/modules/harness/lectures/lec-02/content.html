第 02 讲 · Harness 到底是什么

"harness"在圈子里被用得越来越多，但大多数人说 harness 的时候，指的其实是一个 prompt 文件。一个 prompt 文件不是 harness。这一讲给它一个精确的、可操作的定义。

Harness 五子系统模型

Harness 由五个子系统组成：指令、工具、环境、状态、反馈。每个子系统都有明确的职责。

子系统职责典型工件
指令告诉 agent 这是什么项目、不可违反的约束、验证命令AGENTS.md / CLAUDE.md
工具让 agent 能读写文件、执行命令、访问外部系统shell、文件 API、测试运行器
环境可重现的运行时：依赖、版本、服务pyproject.toml、.python-version、Docker
状态跨会话的持久化进度：做了什么、为什么、下一步是什么PROGRESS.md、DECISIONS.md、git commits
反馈可执行的验证：让 agent 能自证"做完了"pytest、mypy、lint 命令

五个子系统缺一个，harness 就不完整，agent 用起来总会别扭。其中反馈子系统通常投入最少、回报最高——先把验证命令写清楚。

工具侧写：各产品的 harness 完整度

Claude Code 会读仓库里的 CLAUDE.md，能用 shell 跑命令，在本地环境执行，有会话历史，能跑测试看结果。但如果不告诉它怎么跑测试，它就没法验证自己做得对不对——反馈子系统需要你来填。

Codex（OpenAI）用 git worktree 隔离每个任务的运行环境，配合本地可观测性栈。它在有 AGENTS.md 和清晰验证命令的仓库里，表现远超在"裸"仓库里。

AutoGPT 是反面教材：缺乏结构化状态管理导致长任务上下文不断累积，缺乏精确反馈机制导致 agent 陷入循环。很多人说它"不行"，但其实是它的 harness 不行。

核心原则

  • 仓库是唯一事实来源。 Agent 看不到的东西，对它来说等于不存在。OpenAI 把仓库当作"记录系统"，所有必要的上下文都必须在仓库里。
  • 给地图，不给说明书。 AGENTS.md 应该是目录页，不是百科全书。100 行左右就够了，放不下就拆分到 docs/ 目录，让 agent 按需去读。
  • 约束而非微操。 好的 harness 用可执行的规则约束 agent，而不是在指令里逐条叮嘱。OpenAI 说"执行不变量，不要微管实现"；Anthropic 发现 agent 会自信地夸赞自己的工作，解决方案是把"干活的人"和"检查的人"分开。
  • 逐个移除看效果。 保持模型不变，逐个移除五个子系统，看哪个移除后性能下降最多，它的边际贡献就最大。

一个团队的四个阶段

用 GPT-4o 开发 TypeScript + React 前端（约 20,000 行代码），四个阶段对应依次补齐 harness 各组件：

  1. 只有 README 基本描述 → 成功率 20%（选错包管理器、命名约定错误、跑不了测试）
  2. 加了 AGENTS.md（技术栈版本、命名约定、架构决策）→ 成功率 60%
  3. AGENTS.md 里列出验证命令 yarn test && yarn lint && yarn build → 成功率 80%
  4. 引入进度文件模板，agent 每次运行记录完成和未完成的工作 → 成功率 80–100%

四次迭代，模型一个字没改，成功率从 20% 到接近 100%。
