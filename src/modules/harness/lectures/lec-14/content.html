第 14 讲 · Graph 工程：把 Agent 组成有向图

2026 年 7 月，Peter Steinberger 在一次访谈里开了个玩笑："我们已经从提示词工程进化到了……Graph 工程。"这句话并不完全是玩笑。当 loop 复杂到一定程度，你开始想要提前决定 agent 的拓扑结构，而不是让它在运行时自己摸索——这就是 Graph 工程的起点。

四层框架

Rohit（@rohit4verse）在 2026 年 7 月提出了一个清晰的层次模型，把 AI 软件开发的能力分成四层：

层级名称控制单位
L1Prompt 工程单次交互
L2Context 工程会话级上下文
L3Loop 工程跨会话的执行流
L4Graph 工程多 agent 的拓扑结构

每一层都建立在下一层之上。你不能跳过 Context 工程直接做 Graph 工程。

图的四个原语

Graph 工程用四个概念描述 agent 系统的结构：

  • 节点（Node）：执行单元，可以是一个 agent、一个函数调用、一个外部服务调用。节点有输入和输出，有明确的职责边界。
  • 边（Edge）：节点之间的连接，定义执行顺序和数据流向。边可以是有条件的——只有当源节点满足某个条件时才走这条边。
  • 共享状态（Shared State）：图中所有节点可以读写的全局状态。是 agent 之间传递上下文的主要机制。
  • 路由（Routing）：基于共享状态或节点输出，动态决定下一步走哪条边。路由让图变成真正的有向图而非线性流水线。

Loop vs Graph

Loop 和 Graph 的核心区别在于决策发生在什么时候：

Loop：把决策推迟到运行时。Loop 启动时，你不知道它会迭代多少次、经过哪些状态。Agent 在运行时根据情况自己判断。适合开放式探索任务。

Graph：把结构决策前置。在 graph 启动前，你已经决定了有哪些 agent、它们怎么连接、状态怎么传递。运行时只是按图执行。适合可预期结构的复杂任务。

Graph 和 Workflow 的区别：Workflow 的节点是函数，Graph 的节点可以是 agent。Agent 节点可以决定自己的内部执行路径，而函数节点不能。

单 Loop 的三类结构性失败

当任务足够复杂时，单一 loop 会遭遇三类无法靠提示词优化解决的结构性问题：

  • Goodhart 定律：当验证目标本身成为优化对象，agent 开始找漏洞，而不是真正解决问题。比如它学会让测试通过而不是让功能正确。
  • 向上盲区：负责执行的 agent 无法判断自己做的方向是否对。没有更高层次的 agent 做战略评估，所有精力都用在战术执行上。
  • 冲突循环：当同一个 agent 同时负责多个有内在冲突的目标时，它在两个目标之间来回振荡，无法收敛。

LangGraph（2024 年末发布，2026 年 6 月月活 6500 万次下载）是目前最成熟的 Graph 工程工具。它的设计解决了状态管理和路由两个核心问题，使 Python 生态里的 multi-agent 图实现变得可操作。

何时引入 Graph

Graph 比 Loop 复杂，不是所有任务都需要 Graph。五个判断标准：

  1. 任务有多个明显不同的角色（规划者、执行者、评估者）。
  2. 这些角色需要专用的上下文，共享一个上下文会干扰彼此。
  3. 任务有可预期的结构，不是纯粹的开放式探索。
  4. 你想要精确控制 agent 之间的信息流，而不是让它们随意共享。
  5. 单 loop 已经出现了上面三类结构性失败之一。

满足 3 条以上，Graph 工程是值得的投入。满足不到 2 条，先把 Loop 做好。
