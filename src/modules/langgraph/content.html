LangChain 速览回顾

先花 3 分钟快速回顾 LangChain 核心概念 —— 后面 LangGraph 的很多东西都建立在这些基础之上。

类比时间：如果把 LLM 应用比作做菜，LangChain 给你提供了食材（Prompt 模板）、厨具（LLM 调用）和调料（工具/Tool）。但怎么做菜（流程编排），它只提供了一种非常简单的方案 —— 链（Chain）。

LangChain 核心组件

组件作用一句话
PromptTemplate模板化提示词把变量填进模板，生成完整 prompt
ChatModel调用大模型封装 API 调用，统一接口（推荐 Claude Sonnet 5）
OutputParser解析输出把 LLM 的文本输出变成结构化数据
Tool给 LLM 接外部能力搜索、计算、读文件……
Chain (LCEL)串联组件prompt | llm | parser 管道语法
Agent自主决策 + 工具调用LLM 自己决定用什么工具、调几次
关键限制：LangChain 的 Chain 是线性管道 —— A → B → C，数据单向流动。Agent 虽然能循环调用工具，但流程控制能力有限，很难实现复杂的分支、回退、并行、人工审核等场景。

举个例子，用 LangChain LCEL 写一个简单的代码生成链：

Python 
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# 三个组件，一条链
prompt = ChatPromptTemplate.from_template(
    "请用 Python 实现以下需求：{requirement}"
)
llm = ChatAnthropic(model="claude-sonnet-5")
parser = StrOutputParser()

# LCEL 管道语法：prompt → llm → parser
chain = prompt | llm | parser

# 运行
result = chain.invoke({"requirement": "一个冒泡排序函数"})
print(result)

这就是你已经掌握的 LangChain —— 简单、线性、好用。但当需求变成：

  • 生成代码 → 如果有 bug → 修复 → 重新审查 → 循环直到通过
  • 多个 Agent 并行工作，最后汇总
  • 中间需要人类审核再继续

Chain 就力不从心了。这就是 LangGraph 登场的原因。

为什么需要 LangGraph？

⛓️ LangChain Chain

  • 线性管道 A → B → C
  • 数据单向流动
  • 没有原生循环支持
  • 难以实现分支和回退
  • 状态管理靠外部变量

🕸️ LangGraph

  • 图结构（任意连接）
  • 状态在节点间共享和修改
  • 原生支持循环和条件分支
  • 内置持久化和断点恢复
  • 原生支持 Human-in-the-Loop
类比：LangChain 的 Chain 像是流水线 —— 传送带从头到尾，工位固定顺序。LangGraph 像是乐高积木 —— 你可以用积木（节点）和连接件（边）拼出任何形状的工作流：有环的、有分支的、并行的，随你设计。

LangGraph 是什么？

一句话：LangGraph 是 LangChain 生态中的图编排框架，专门用来构建有状态的、多步骤的 AI 工作流。它由 LangChain 团队开发，是构建复杂 Agent 系统的首选方案。

特性说明
图结构用节点（Node）和边（Edge）定义任意复杂的工作流
状态管理显式的共享状态对象，在节点间传递和修改
条件路由根据状态动态决定下一步走哪条路
循环支持天然支持「审查→修复→再审查」这种循环
持久化内置 Checkpoint，可以暂停、恢复、回溯
Human-in-the-Loop在任意节点插入人类审核断点
流式输出支持逐节点流式返回中间结果
Sub-Graph将子图作为节点嵌入主图，实现模块化
并行执行多节点并行运行，支持 Map-Reduce 模式

LangGraph 核心概念全解

逐个拆解 LangGraph 的 6 大核心概念。每个概念都配类比 + 图解 + 代码，确保你真正理解。

State（状态）— 共享记忆

类比：想象一个多人协作的共享白板。每个参与者（节点）都可以在白板上写字、擦除、修改。所有人看到的都是同一块白板的最新内容。State 就是这块白板。

State 是 LangGraph 的核心中的核心。它是一个 Python 对象（通常是 TypedDict 或 Pydantic BaseModel），在整个图的执行过程中被所有节点共享。

定义 State

Python 
from typing import Annotated, TypedDict
from operator import add

class CodeGenState(TypedDict):
    # 用户需求
    requirement: str
    # 生成的代码
    code: str
    # 生成的测试
    tests: str
    # 审查意见
    review_feedback: str
    # 审查是否通过
    is_approved: bool
    # 修复轮次计数
    revision_count: int
    # 历史记录（用 Annotated + add 实现追加而非覆盖）
    history: Annotated[list[str], add]
关键语法 Annotated[list[str], add]：默认情况下，节点返回的字典会覆盖 State 中同名字段。但加上 Annotated[list, add] 后，新的列表会追加到原有列表后面，而不是替换。这在记录历史日志时非常有用。这里的 add 就是一个 reducer 函数，后面高级详解会深入讲。

Node（节点）— 干活的人

类比：如果 State 是白板，Node 就是一个个工人。每个工人走到白板前，读取上面的内容，做自己的工作，然后把结果写回白板。

Node 就是一个普通的 Python 函数，接收当前 State，处理后返回一个字典（要更新的字段）。也可以是另一个编译好的 Graph（子图）。

Python 
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate

llm = ChatAnthropic(model="claude-sonnet-5")

def generate_code(state: CodeGenState) -> dict:
    """代码生成节点：读取需求，生成代码"""
    requirement = state["requirement"]

    prompt = ChatPromptTemplate.from_template("""
    请用 Python 实现以下需求，只输出代码，不要解释：
    {requirement}
    """)
    chain = prompt | llm
    result = chain.invoke({"requirement": requirement})

    # 返回要更新的字段（不是完整 State）
    return {
        "code": result.content,
        "history": [f"✅ 生成了代码（{len(result.content)} 字符）"]
    }
要点：节点函数的返回值是一个字典，只包含要更新的 State 字段。LangGraph 会自动把它合并到当前 State 中。你不需要返回完整的 State。

Edge & 条件分支 — 流程控制

类比：Node 是工人，Edge 就是工人之间的传话规则。「做完后把结果传给下一个人」—— 这是普通边。「如果质量不合格，传给修复组；如果合格，传给发布组」—— 这是条件边。

普通边（Normal Edge）

最简单的情况：A 做完就去 B。

Python

graph = StateGraph(CodeGenState)

# 添加节点

条件边（Conditional Edge）

根据 State 的值，动态决定下一步去哪里。这是 LangGraph 最强大的特性之一。

Python 
def should_continue(state: CodeGenState) -> str:
    """路由函数：根据审查结果决定下一步"""
    if state["is_approved"]:
        return "approved"   # 通过 → 结束
    elif state["revision_count"] >= 3:
        return "max_retries" # 超过重试上限 → 结束
    else:
        return "revise"      # 不通过且未超限 → 去修复

# 添加条件边
graph.add_conditional_edges(
    "review",           # 源节点
    should_continue,    # 路由函数
    {
        "approved": "__end__",  # 通过 → 结束
        "max_retries": "__end__", # 超限 → 结束
        "revise": "revise_code",  # 需修复 → 修复节点
    }
)

路由函数的规则：
  • 接收当前 State，返回一个字符串（路由 key）
  • 返回值必须是 add_conditional_edges 映射字典中的 key 之一
  • __end__ 是 LangGraph 的内置特殊节点，表示流程结束

Graph 编排 — 把一切串起来

类比：State 是白板，Node 是工人，Edge 是传话规则 —— 那 StateGraph 就是项目经理，负责把所有人和规则组织起来，定义「谁先做、谁后做、做完给谁」。

完整的图构建流程就 4 步：

1
创建图 — 传入 State 类型
2
添加节点 — 把函数注册为有名节点
3
添加边 — 定义节点之间的连接（普通边 + 条件边）
4
编译 — 调用 .compile() 生成可执行的图

# Step 1: 创建图
graph = StateGraph(CodeGenState)

graph.add_node("generate", generate_code)
graph.add_node("test_gen", generate_tests)

# Step 4: 编译

持久化与 Checkpoint — 记忆不丢失

类比：玩游戏时的存档系统。每走一步自动存档（Checkpoint），你可以随时读档回到任意一步，也可以在游戏崩溃后从最近的存档继续。LangGraph 的持久化就是这个存档系统。

持久化的核心用途：

  • 断点恢复：流程中断后（网络错误、进程重启），从上次的 Checkpoint 继续
  • Human-in-the-Loop：在某个节点暂停，等人类审核后再继续
  • 时间回溯：查看任意一步的状态快照，方便调试
  • 长期记忆：跨会话保持 Agent 的记忆
Python 
from langgraph.checkpoint.memory import InMemorySaver

# 创建 Checkpoint 存储（内存版，生产环境可用 SQLite / PostgreSQL）
checkpointer = InMemorySaver()

# 编译时传入 checkpointer
app = graph.compile(checkpointer=checkpointer)

# 运行时指定 thread_id（标识一次会话）
config = {"configurable": {"thread_id": "session-001"}}
result = app.invoke(
    {"requirement": "实现一个 LRU Cache"},
    config=config
)

# 之后可以从这个 thread 的任意 checkpoint 恢复
history = app.get_state_history(config)
for snapshot in history:
    print(snapshot.metadata["step"], snapshot.values)
注意：InMemorySaver 是内存存储，进程结束就没了。生产环境请用 SqliteSaver 或 PostgresSaver（详见高级详解章节）。

Human-in-the-Loop — 人类介入

类比：自动驾驶汽车 —— 大部分时候自动行驶，但在复杂路口会提示「请人类接管」。LangGraph 的 Human-in-the-Loop 就是这个「请人类接管」的机制。

LangGraph 有两代写法。先看现在推荐的那一种：在节点里直接调 interrupt()，把「要问人类什么」当成数据交出去；外部想好了，再用 Command(resume=…) 把答案送回去。两边通过 Checkpoint 衔接，所以 必须配 checkpointer，否则无处存放挂起的现场。

Python 
from langgraph.types import interrupt, Command

def review_node(state: ProjectState) -> dict:
    # interrupt() 把 payload 交给外部，并在此处挂起
    # 恢复后，它的返回值就是 Command(resume=...) 传进来的东西
    decision = interrupt({
        "question": "这段代码是否通过审查？",
        "code": state["code"],
    })
    return {
        "is_approved": decision["approved"],
        "review_result": decision.get("comment", ""),
    }

# 编译时不需要再写 interrupt_before / interrupt_after，但 checkpointer 是必选
app = graph.compile(checkpointer=checkpointer)

# 第一次跑 —— 到 interrupt() 就停
result = app.invoke(initial_state, config=config)
print(result["__interrupt__"])   # 拿到上面交出的 payload

# 也可以从快照里读，适合跨进程、跨请求的场景
snapshot = app.get_state(config)
print(snapshot.tasks[0].interrupts)

# 人类决定后恢复；resume 的值会成为 interrupt() 的返回值
final = app.invoke(
    Command(resume={"approved": True, "comment": "逻辑没问题"}),
    config=config,
)
最容易踩的坑：恢复时节点是「从头重跑」的。interrupt() 不是协程挂起，不会从那一行接着往下走——LangGraph 会把整个节点函数重新执行一遍，只是这一次 interrupt() 直接返回你传的值。所以 interrupt() 之前的代码会跑两次：写数据库、发邮件、扣费这类有副作用的操作千万不要放在它前面，要么移到 interrupt() 之后，要么拆到单独的节点里。

补充：编译期的静态断点

早期的写法是在 compile() 时声明 interrupt_before 或 interrupt_after，它们仍然可用，而且在「只想在固定位置停下来看一眼」时更简单：不用改节点代码，适合调试和临时埋点。

Python 
# 在 "review" 节点后暂停，不需要改节点函数
app = graph.compile(
    checkpointer=checkpointer,
    interrupt_after=["review"],
)

result = app.invoke(initial_state, config=config)

# 静态断点靠改 State 来传递人类的意志
app.update_state(config, {"is_approved": True})

# 传 None 表示「从暂停点继续，不给新输入」
result = app.invoke(None, config=config)
两种写法怎么选：需要把「问题」和「答案」都当数据传递（审批表单、工具调用确认、多轮改写）就用 interrupt()；只是想在固定位置打个断点看看 State，编译期的 interrupt_after 更轻。两者可以共存。

Sub-Agent 模式详解

类比：一个创业公司 —— CEO（主 Agent）不亲自写代码、不做设计、不搞销售，而是把任务分配给 CTO、CFO、CMO（Sub-Agents）。每个 Sub-Agent 有自己的专业领域和工具，CEO 负责协调和决策。

Sub-Agent 模式是 LangGraph 构建多 Agent 系统的核心范式。掌握它，你就能构建任意复杂的 Agent 工作流。

Sub-Agent 的核心三要素

1
主 Agent（Orchestrator）：接收用户输入，决定调用哪个 Sub-Agent，汇总结果，控制整体流程
2
Sub-Agent（Worker）：专注做一件事，有自己的 prompt、工具和输出格式
3
共享 State：所有 Agent 通过同一个 State 对象通信。这是协作的「白板」

两种协作模式

🔄 串行流水线

A → B → C，每一步依赖前一步的输出

适合：代码生成→测试→审查 这种有明确先后顺序的场景

控制力：你可以精确控制每个 Agent 的执行顺序，观察中间 State 变化

⚡ 并行扇出/扇入

A → [B, C, D] 并行 → E 汇总

适合：多个维度同时审查（安全、性能、风格）

控制力：扇出前/扇入后都可以插入处理逻辑，控制中间产物的流转

如何控制中间流程与产物流转

这是你学完后最需要的能力。核心思路：State 就是你控制流程的抓手。

Python 
# 控制中间产物流转的三种手段：

# 1. State 字段 —— Agent 之间传递数据的通道
#    Agent A 写入 state["code"]，Agent B 读取 state["code"]
#    你可以在任何节点中添加「转换逻辑」来处理中间产物

def transform_before_review(state: State) -> dict:
    """在审查之前，对代码做预处理"""
    code = state["code"]
    # 比如：提取代码块、移除注释、格式化...
    cleaned = extract_python_code(code)
    return {"code": cleaned}

# 2. 条件边 —— 根据中间产物决定下一步
def route_by_quality(state: State) -> str:
    """根据代码质量评分路由到不同 Agent"""
    score = state.get("quality_score", 0)
    if score < class="op">>= 8:
        return "publish"    # 高质量 → 直接发布
    elif score >= 5:
        return "minor_fix"  # 中等 → 小修
    else:
        return "rewrite"    # 低质量 → 重写

# 3. interrupt —— 在关键节点暂停，让人类检查/修改中间产物

    checkpointer=checkpointer,
    interrupt_after=["generate"]  # 生成后暂停，人类检查代码再继续
)

这里容易出错：如果自己声明 messages: list 却没有消息 reducer，并行节点或连续节点可能互相覆盖历史。纯消息工作流直接使用 MessagesState；需要额外字段时继承它，不要重新定义同名 messages 字段。

Supervisor 与 handoff：由谁决定下一位执行者

Supervisor 是负责分派与验收的编排节点；handoff 是把控制权连同必要状态交给下一位 Agent。handoff 不应只是提示词里的「请转交」，而应落实为图中的路由。下面的 supervisor 根据 State 决定先研究、再写作，工作节点用 Command(update=..., goto=...) 同时提交产物并把控制权交回 supervisor：

from langchain.agents import create_agent
from langgraph.graph import StateGraph, MessagesState, START, END

class TeamState(MessagesState):
    task: str
    research_notes: str
    final_answer: str

    model="openai:gpt-5.5", tools=[search_web],
    system_prompt="只输出核实过的事实摘要。",

    model="openai:gpt-5.5", tools=[],

        return Command(goto="researcher")
    if not state.get("final_answer"):
        return Command(goto="writer")
    return Command(goto=END)

        "messages": [{"role": "user", "content": state["task"]}]
    })
    notes = result["messages"][-1].content

        update={"research_notes": notes}, goto="supervisor"

        "messages": [{"role": "user", "content": prompt}]
    })
    answer = result["messages"][-1].content
    return Command(

模式控制权适用场景
Supervisor集中在一个编排节点流程需要统一验收、预算与停止条件
直接 handoff当前 Agent 决定下一位角色切换自然、路径较少的对话系统
固定流水线由静态边决定步骤稳定、合规要求高、需要可预测执行
这里容易出错：handoff 必须传递最小但完整的上下文，并设置最大移交次数或终止条件，否则 Agent 可能互相转交形成循环。涉及副作用的工具还要配合持久化与 HITL，不能只依赖 supervisor 的自然语言判断。

6.1 Sub-Graph — 子图模块化

类比：如果一个函数太长，你会拆成多个小函数。Sub-Graph 就是把一个大图拆成多个小图 —— 每个子图负责一个独立的功能模块，然后像搭积木一样组合起来。

什么时候用 Sub-Graph？

  • 某个流程（如「审查+修复循环」）在多处复用
  • 主图太复杂，需要模块化拆分
  • 不同团队负责不同子流程
Python 
# ===== 子图：审查 + 修复循环 =====

Send API — 动态 Map-Reduce

当需要对列表数据中的每一项并行处理时，使用 Send API：

Python 
from langgraph.types import Send

class BatchState(TypedDict):
    files: list[str]            # 要处理的文件列表
    results: Annotated[list[str], add]  # 每个文件的结果（追加）
    summary: str                      # 必须声明！State 里没有的 key，节点返回了也会被静默丢弃

# Map 阶段：为每个文件创建一个并行任务
def dispatch(state: BatchState):
    """扇出：为每个文件发送一个并行任务"""
    return [
        Send("process_file", {"file": f})
        for f in state["files"]
    ]

# 处理单个文件的节点
def process_file(state):
    return {"results": [f"已处理: {state['file']}"]}

# Reduce 阶段：汇总所有结果
def summarize(state: BatchState):
    return {"summary": f"共处理 {len(state['results'])} 个文件"}

graph = StateGraph(BatchState)
graph.add_node("process_file", process_file)
graph.add_node("summarize", summarize)

# 用条件边 + Send 实现动态扇出
graph.add_conditional_edges(START, dispatch)
graph.add_edge("process_file", "summarize")
graph.add_edge("summarize", END)

6.3 自定义 State Reducer

Reducer 决定了节点返回值如何合并到 State 中。内置的 add 只是冰山一角，你可以写自己的 Reducer。

Python 
from typing import Annotated

# 自定义 Reducer：合并两个字典（而非覆盖）
def merge_dicts(old: dict, new: dict) -> dict:
    """合并字典，新值覆盖旧值中同名 key"""
    return {**old, **new}

# 自定义 Reducer：保留最新 N 条记录
def keep_last_n(n: int):
    """返回一个 Reducer，只保留最近 n 条记录"""
    def reducer(old: list, new: list) -> list:
        combined = old + new
        return combined[-n:]
    return reducer

class SmartState(TypedDict):
    # 默认：后写入覆盖前值
    code: str

    # 追加模式：新列表追加到旧列表
    logs: Annotated[list[str], add]

    # 字典合并：新字典合并到旧字典
    metadata: Annotated[dict, merge_dicts]

    # 滑动窗口：只保留最近 10 条消息
    messages: Annotated[list[str], keep_last_n(10)]
实际用途：在构建聊天 Agent 时，keep_last_n Reducer 非常有用 —— 你不想把所有历史消息都塞进 LLM 的上下文窗口，只保留最近 10 轮对话就够了。

    except Exception as e:
        return {"code": "", "error": str(e)}

# 方法二：Runnable 自带的重试。注意 langchain_core.runnables 里没有 Retry 这个类，
# 底层实现是 RunnableRetry，日常用 .with_retry() 这个便捷方法即可
reliable_llm = llm.with_retry(
    retry_if_exception_type=(Exception,),
    stop_after_attempt=3,
    wait_exponential_jitter=True,
)

# 方法二·补充：LangGraph 的节点级重试，比包装单个 LLM 覆盖面更广
from langgraph.types import RetryPolicy

graph.add_node("generate", generate_fn,
               retry_policy=RetryPolicy(max_attempts=3))
# 重试用尽后异常会继续上抛；想改流向得在节点内捕获，再返回 Command(goto=...)

# 方法三：条件边兜底
def check_error(state: State) -> str:
    if state.get("error"):
        return "handle_error"
    return "continue"

graph.add_conditional_edges("generate", check_error, {
    "handle_error": "error_handler",
    "continue": "review",
})

案例一：RAG 检索增强生成 Pipeline

场景：你有一个公司的知识库（文档、PDF、网页），用户提问时，系统先检索相关文档片段，再用 LLM 基于这些片段生成回答，并附上来源引用。

    subgraph RAG["RAG Pipeline"]
        ROUTE["意图路由"] -->|知识库问题| RETRIEVE["文档检索"]
        ROUTE -->|闲聊通用| DIRECT["直接回答"]
        RETRIEVE --> GRADE["相关性评分"]
        GRADE -->|相关| GENERATE["生成回答"]
        GRADE -->|不相关| REWRITE["改写查询"]
        REWRITE --> RETRIEVE
        GENERATE --> VERIFY["回答验证"]
        VERIFY -->|有依据| DONE(["输出回答+引用"])
        VERIFY -->|无依据| GENERATE
    end

Python 
# rag_pipeline.py
from typing import Annotated, TypedDict
from operator import add
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langgraph.graph import StateGraph, START, END

llm = ChatAnthropic(model="claude-sonnet-5")

# ===== State =====
class RAGState(TypedDict):
    question: str                     # 用户原始问题
    rewritten_query: str              # 改写后的检索查询
    documents: list[str]             # 检索到的文档片段
    is_relevant: bool                 # 文档是否相关
    answer: str                       # 生成的回答
    sources: list[str]               # 引用来源
    has_evidence: bool                # 回答是否有文档依据
    attempt: int                      # 重试次数

# ===== 节点 =====

def route_intent(state: RAGState) -> str:
    """判断是知识库问题还是闲聊"""
    # 简化：用关键词判断，生产中用 LLM 分类
    keywords = ["文档", "手册", "规定", "流程", "政策"]
    if any(kw in state["question"] for kw in keywords):
        return "retrieve"
    return "direct"

def retrieve_docs(state: RAGState) -> dict:
    """从向量数据库检索相关文档"""
    query = state.get("rewritten_query") or state["question"]
    # 实际项目中接入向量数据库
    # docs = vectorstore.similarity_search(query, k=3)
    docs = ["文档片段1...", "文档片段2...", "文档片段3..."]
    return {"documents": docs, "attempt": state.get("attempt", 0) + 1}

def grade_relevance(state: RAGState) -> dict:
    """判断检索到的文档是否与问题相关"""
    prompt = ChatPromptTemplate.from_template("""
    判断以下文档是否与问题相关。只回答 "相关" 或 "不相关"。

    问题：{question}
    文档：{documents}
    """)
    result = (prompt | llm).invoke({
        "question": state["question"],
        "documents": "\n".join(state["documents"])
    })
    is_relevant = "相关" in result.content and "不相关" not in result.content
    return {"is_relevant": is_relevant}

def rewrite_query(state: RAGState) -> dict:
    """改写查询以提高检索质量"""
    prompt = ChatPromptTemplate.from_template("""
    原始查询没有找到相关文档，请用不同的方式重新表述：
    {question}
    只输出改写后的查询，不要解释。
    """)
    result = (prompt | llm).invoke({"question": state["question"]})
    return {"rewritten_query": result.content}

def generate_answer(state: RAGState) -> dict:
    """基于检索文档生成回答"""
    prompt = ChatPromptTemplate.from_template("""
    基于以下文档回答问题。如果文档中没有相关信息，请说"无法根据现有文档回答"。

    文档：
    {documents}

    问题：{question}

    回答时请标注引用来源。
    """)
    result = (prompt | llm).invoke({
        "documents": "\n---\n".join(state["documents"]),
        "question": state["question"]
    })
    has_evidence = "无法" not in result.content
    return {
        "answer": result.content,
        "sources": [f"文档{i+1}" for i in range(len(state["documents"]))],
        "has_evidence": has_evidence
    }

def direct_answer(state: RAGState) -> dict:
    """闲聊问题直接回答"""
    result = llm.invoke(state["question"])
    return {"answer": result.content, "sources": [], "has_evidence": True}

# ===== 路由函数 =====
def check_relevance(state: RAGState) -> str:
    if state["is_relevant"]:
        return "generate"
    elif state.get("attempt", 0) >= 2:
        return "generate"  # 超过重试次数，直接生成
    return "rewrite"

def check_evidence(state: RAGState) -> str:
    if state["has_evidence"] or state.get("attempt", 0) >= 3:
        return "end"
    return "retry"

# ===== 构建图 =====
graph = StateGraph(RAGState)
graph.add_node("retrieve", retrieve_docs)
graph.add_node("grade", grade_relevance)
graph.add_node("rewrite", rewrite_query)
graph.add_node("generate", generate_answer)
graph.add_node("direct", direct_answer)

graph.add_conditional_edges(START, route_intent,
    {"retrieve": "retrieve", "direct": "direct"})
graph.add_edge("retrieve", "grade")
graph.add_conditional_edges("grade", check_relevance,
    {"generate": "generate", "rewrite": "rewrite"})
graph.add_edge("rewrite", "retrieve")
graph.add_conditional_edges("generate", check_evidence,
    {"end": END, "retry": "retrieve"})
graph.add_edge("direct", END)

app = graph.compile()
这个案例展示了：意图路由（条件边）、检索→评分→改写的循环（提高检索质量）、回答验证（确保有据可依）。这三者组合起来就是一个生产级 RAG 系统的核心骨架。

案例二：多模型协作系统

场景：不同任务分配给最擅长的模型 —— Claude Opus 5 负责深度推理和架构设计，Claude Sonnet 5 负责代码生成和审查，Claude Haiku 4.5 负责快速分类和提取。各取所长，协作完成复杂任务。

    PLAN --> CODE["Claude Sonnet 5 代码实现"]
    PLAN --> DOC["Claude Sonnet 5 文档撰写"]

    CODE --> REVIEW["Claude Haiku 4.5 代码审查"]
    REVIEW -->|不通过| CODE

    CODE --> DONE
    DOC --> DONE["汇总输出"]
    REVIEW -->|通过| DONE

Python 
# multi_model.py
from langchain_anthropic import ChatAnthropic
from typing import Annotated, TypedDict
from operator import add

# ===== 三个模型，各司其职 =====
planner = ChatAnthropic(model="claude-opus-5")     # 最强推理
coder   = ChatAnthropic(model="claude-sonnet-5")   # 最佳编程
fast_llm = ChatAnthropic(model="claude-haiku-4-5-20251001")   # 最快速度

# ===== State =====
class ProjectState(TypedDict):
    requirement: str
    architecture: str          # Opus 输出的架构设计
    code: str                   # Sonnet 输出的代码
    docs: str                   # Sonnet 输出的文档
    review_result: str
    is_approved: bool

# ===== 节点：每个节点用最合适的模型 =====

def plan_architecture(state: ProjectState) -> dict:
    """Opus 5：负责深度架构规划"""
    result = planner.invoke(f"""
    请为以下需求设计详细的技术架构：
    {state['requirement']}

    输出：模块划分、数据流、接口设计。
    """)
    return {"architecture": result.content}

def write_code(state: ProjectState) -> dict:
    """Sonnet 5：负责代码实现"""
    result = coder.invoke(f"""
    根据以下架构设计编写 Python 代码：
    {state['architecture']}
    """)
    return {"code": result.content}

def write_docs(state: ProjectState) -> dict:
    """Sonnet 5：负责文档撰写（与写代码并行）"""
    result = coder.invoke(f"""
    根据以下架构设计编写技术文档：
    {state['architecture']}
    """)
    return {"docs": result.content}

# 审查节点：用最快的模型做把关，产出 State 里声明的 review_result / is_approved
def review_code(state: ProjectState) -> dict:
    prompt = f"审查这段代码，只回 PASS 或 FAIL 加一句理由：\n{state['code']}"
    verdict = fast_llm.invoke(prompt).content
    return {
        "review_result": verdict,
        "is_approved": verdict.strip().startswith("PASS"),
    }

# ===== 构建图 =====
graph = StateGraph(ProjectState)
graph.add_node("plan", plan_architecture)
graph.add_node("code", write_code)
graph.add_node("docs", write_docs)
graph.add_node("review", review_code)

graph.add_edge(START, "plan")
# 规划后，写代码和写文档并行执行
graph.add_edge("plan", "code")
graph.add_edge("plan", "docs")
# code 先过审查；不通过就打回去重写，与图 12 的回边一致
graph.add_edge("code", "review")
graph.add_conditional_edges(
    "review",
    lambda state: "done" if state["is_approved"] else "retry",
    {"done": END, "retry": "code"},
)
graph.add_edge("docs", END)

app = graph.compile()
核心思想：不要所有任务都用同一个模型。Opus 做规划（需要最强推理能力）、Sonnet 做实现（编程能力最强）、Haiku 做分类（速度最快成本最低）。这样既保证质量又控制成本。

Python 
# data_pipeline.py
from typing import TypedDict
from langchain_anthropic import ChatAnthropic
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

llm = ChatAnthropic(model="claude-sonnet-5")

# ===== State =====
class AnalysisState(TypedDict):
    raw_data: str                # 原始数据（CSV/JSON 字符串）
    cleaned_data: str            # 清洗后的数据
    data_profile: str            # 数据画像描述
    analysis: str                # 分析结果
    human_feedback: str          # 人工审核意见
    visualization_plan: str     # 可视化方案
    report: str                  # 最终报告
    needs_revision: bool         # 是否需要修改

# ===== 节点 =====

def clean_data(state: AnalysisState) -> dict:
    """数据清洗：处理缺失值、异常值、格式统一"""
    result = llm.invoke(f"""
    请分析以下数据的清洗需求，并输出清洗后的数据：

    原始数据：
    {state['raw_data']}

    请：
    1. 处理缺失值（标记或填充）
    2. 识别异常值
    3. 统一数据格式
    4. 输出清洗后的数据摘要
    """)
    return {"cleaned_data": result.content}

def profile_data(state: AnalysisState) -> dict:
    """数据画像：描述数据的基本特征"""
    result = llm.invoke(f"""
    对清洗后的数据进行画像分析：
    {state['cleaned_data']}

    输出：
    1. 数据规模（行数、列数）
    2. 各字段类型和分布
    3. 关键统计量
    4. 数据质量评估
    """)
    return {"data_profile": result.content}

def analyze(state: AnalysisState) -> dict:
    """统计分析：发现规律和趋势"""
    feedback = state.get("human_feedback", "")
    extra = f"\n人工审核意见：{feedback}" if feedback else ""

    result = llm.invoke(f"""
    基于数据画像进行深入分析：
    {state['data_profile']}
    {extra}

    输出：
    1. 关键发现和趋势
    2. 相关性分析
    3. 异常模式识别
    4. 可操作的建议
    """)
    return {"analysis": result.content, "needs_revision": False}

def suggest_visualization(state: AnalysisState) -> dict:
    """推荐可视化方案"""
    result = llm.invoke(f"""
    根据以下分析结果，推荐最佳可视化方案：
    {state['analysis']}

    为每个图表提供：类型、数据字段、Python matplotlib 代码。
    """)
    return {"visualization_plan": result.content}

def generate_report(state: AnalysisState) -> dict:
    """生成最终分析报告"""
    result = llm.invoke(f"""
    将以下内容整合为一份专业的数据分析报告：

    数据画像：{state['data_profile']}
    分析结果：{state['analysis']}
    可视化方案：{state['visualization_plan']}

    报告格式：执行摘要 → 数据概述 → 关键发现 → 建议 → 附录
    """)
    return {"report": result.content}

# ===== 路由 =====
def check_revision(state: AnalysisState) -> str:
    if state.get("needs_revision"):
        return "revise"
    return "continue"

# ===== 构建图 =====
graph = StateGraph(AnalysisState)
graph.add_node("clean", clean_data)
graph.add_node("profile", profile_data)
graph.add_node("analyze", analyze)
graph.add_node("visualize", suggest_visualization)
graph.add_node("report", generate_report)

graph.add_edge(START, "clean")
graph.add_edge("clean", "profile")
graph.add_edge("profile", "analyze")
graph.add_edge("analyze", "visualize")
graph.add_edge("visualize", "report")
graph.add_edge("report", END)

# 编译，支持人工审核
checkpointer = InMemorySaver()
app = graph.compile(
    checkpointer=checkpointer,
    interrupt_after=["analyze"]  # 分析后暂停，人工审核
)

# ===== 使用 =====
config = {"configurable": {"thread_id": "analysis-001"}}

# 第一次运行（在 analyze 后暂停）
result = app.invoke(
    {"raw_data": "你的 CSV/JSON 数据..."},
    config=config
)

# 人工审核分析结果后，决定是否继续
# 如果需要调整：app.update_state(config, {"human_feedback": "请重点关注xxx"})
# 继续执行：app.invoke(None, config=config)
这个案例展示了：Human-in-the-Loop 在实际业务中的应用 —— 数据分析是典型的「需要人工判断」场景。你可以审核分析结果，添加额外指令，再让系统继续生成报告。这就是 LangGraph 的价值：不是全自动，而是人机协作。
