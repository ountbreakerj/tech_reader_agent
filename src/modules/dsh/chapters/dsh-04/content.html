第 4 章

会话持久化、存储与跨会话检索

Harness 的 hx-04 已经从“日志模型”的角度讲过会话日志：日志是事实来源、请求头为什么要进日志、格式 v0–v4 只允许相邻迁移、撕裂尾巴怎么识别、崩溃后怎么修。这一章换一个站位，从存储层看同一份日志：字节是怎么落到磁盘上的，日志之外还有哪些“从日志算出来”的东西，它们存在哪、什么时候失效，以及跨会话的全文检索是怎么在日志旁边搭起来的。

读完这一章，你应该能回答四个问题：一条事件从 session.append() 到磁盘上的 fsync 中间经过了哪几层；迁移包里一条迁移具体改了哪些字段；投影缓存为什么“可能过期但永远不会错”；以及为什么全文检索的包都装上了，默认却是关着的。

一张地图：一份事实，三种派生

先把这一章出场的包按“谁是权威”分成两类。只有一样东西是权威：JSONL 会话日志。其余三样都是从它折叠或索引出来的派生物，丢了可以重建，和日志不一致时以日志为准。

这个划分不是作者的归纳，DSH 在一份已实施的设计记录里写得很直白：全文检索用的 SQLite 数据库是“可丢弃的投影”，不能拿来当持久化，因为那会“把两种无关的存储合并”（jsonl-only-session-persistence.md:25）。同一份记录还交代了一段历史：仓库曾经有一个 SQLite 版的会话持久化后端，后来被删掉了，JSONL 成为 ctx.sessionPersistence 的唯一一方实现，抽象契约保持后端中立，留给仓库外的实现（同文件:15）。删掉的理由是：一个没人选的生产后端，照样要承担每一项格式、生命周期、平台和迁移义务。

和 Python 读者的对照：如果你写过 Django，可以把 JSONL 日志想成数据库里的事实表，投影是 @cached_property，投影缓存是你手动维护的一张汇总表，FTS 索引是 Elasticsearch。区别在于 DSH 把“汇总表可以随时丢”这件事写成了硬约束，而不是团队默契。

存储层的写入路径：从契约到 fsync

契约只有五个动词

session-persistence 包本身不做 IO，它只定义一个抽象服务 session-persistence/src/index.ts:137。抽象方法只有五个：create（新建一个会话）、open（按读或写模式打开，拿到一个句柄）、flush、stat（看一个会话的快照信息，不读全文）和 list。真正的读写都走句柄，hx-04 已经讲过句柄的读写两种模式和“永远不返回撕裂尾巴”的承诺。

站在存储层看，这个契约最值得注意的是它没有什么：没有“按条件查询事件”，没有“全文搜索”，没有“改写某一条”。查询是 session-query 的事，改写根本不允许（改格式要走迁移，生成新文件）。stat 和 list 返回的快照带一个 revision，后面讲检索索引时会看到它被拿来判断“这个会话自上次索引后有没有变”。

一批事件怎么落盘

hx-04 讲过前半段：实时事件先克隆进缓冲区，200 毫秒窗口到期后成批写。这里接着往下看。窗口到期或收到 session/flush 时调用的是 drainLive，它用一个很短的写法保证并发调用只排空一次：

  drainLive(): Promise<void> {
    return this.draining ??= this.drainBuffered().finally(() => {
      this.draining = undefined
    })
  }

packages/session/session-persistence-jsonl/src/storage.ts:288-292

??= 的意思是“左边是 undefined 才赋值”。第一个调用者创建排空任务并存进 this.draining，排空期间再来的调用者直接拿到同一个 Promise，排空结束后清掉。Python 里等价的写法是把一个 asyncio.Task 存在实例上，有就 await 它，没有才新建。

排空最终调用后端的 persistBatch。它在写之前做两件事：先把这个会话的“冷日志备忘”删掉（缓存的旧读结果马上就会过时），再看会话有没有物化过。DSH 的会话是惰性物化的：新建会话时磁盘上什么都没有，第一批事件落盘时才连同头记录一起创建文件。

  private async appendLines(meta: SessionHeader, events: readonly SessionEvent[]): Promise<void> {
    const content = await this.encodeEventBatch(events)
    const path = logPath(this.root, meta.cwd, meta.id, this.compression)

      closed = true
      await handle.close()

        await handle.sync()

packages/session/session-persistence-jsonl/src/index.ts:1334-1362

顺序是：先记下写之前的文件大小 before，整批编码成一段字节一次写入，再 sync()（也就是 fsync，让操作系统把数据真正刷到磁盘）。写或 sync 任何一步失败，就把文件截回 before。方法上方的注释说明了原因：游标没有前进，上层会重试同一批；如果留下半批字节，重试就会写出重复的序号（index.ts:1332）。回滚自己也失败时，两个错误用 AggregateError 一起抛出，不吞掉任何一个。

这和 hx-04 讲的“撕裂尾巴”是两道不同的防线。撕裂尾巴处理的是进程被杀，来不及执行任何清理代码，只能在下次读取时识别并截掉；这里的回滚处理的是进程还活着但 IO 报错，比如磁盘满，当场就能恢复原状。

换代发布时还要 fsync 目录

迁移会生成一个新版本的日志文件（hx-04 讲过文件名带版本）。新文件写完并 fsync 之后，还要 fsync 它所在的目录，否则断电后“这个目录里有这个文件名”这件事本身可能丢失。DSH 的实现在 Windows 上直接跳过，注释说明 Windows 的命名空间操作本身就是直写的：

迁移链怎么组织成包

一条迁移一个包，目录由脚本生成

hx-04 讲了迁移的两条规则（只许相邻、比当前新的一律拒绝）。这里看它在仓库里的形状。packages/session/ 下有一个契约包 session-format，四个迁移包 session-format-v0-to-v1 到 v3-to-v4，外加一个把它们拼起来的 session-format-catalog。每个迁移包的 package.json 描述就说明了它改什么：v0→v1 是“恒等迁移”（v0-to-v1/package.json:3），v1→v2 改助手消息的流式表示，v2→v3 改系统提示的流式表示、规范信封和 PTC（程序化工具调用）。

拼装的目录文件是脚本生成的，文件头写着“不要手改”，并且说明了为什么用直接 import：

逐字看一条迁移：v3→v4 把工具结果从 user 消息里提出来

v3 及以前，工具结果存成一条 role: 'user' 的消息，content 里放唯一一个 type: 'tool-result' 的包装块。这是很多 API 的历史写法（Anthropic Messages API 至今仍然把 tool_result 放在 user 消息里）。v4 改成一等公民的 role: 'tool'。做这件事的函数是 liftToolResult：

export function liftToolResult(event: SessionFormatEvent): SessionFormatEvent {
  if (event.type !== 'tool/result' || !isSessionFormatJsonObject(event.data)) return event
  const data = event.data
  const message = data['message']
  if (!isSessionFormatJsonObject(message) || message['role'] !== 'user') return event
  const source = message['source']
  const callId = isSessionFormatJsonObject(source) ? source['callId'] : undefined
  const content = message['content']
  const block = Array.isArray(content) && content.length === 1
    ? (content as readonly SessionFormatJsonValue[])[0]
    : undefined
  const wrapper = isSessionFormatJsonObject(block) ? block : undefined
  const id = message['id']
  if (typeof id !== 'string' || id.length === 0
    || !isSessionFormatJsonObject(source) || source['kind'] !== 'tool'
    || typeof callId !== 'string' || callId.length === 0
    || wrapper === undefined || wrapper['type'] !== 'tool-result'
    || wrapper['toolCallId'] !== callId) {
    throw new SessionFormatError(`format v3 ${event.type} at seq ${event.seq} requires exactly one tool-result wrapper matching its tool source`)
  }
  const isError = wrapper['isError']
  if (isError !== undefined && typeof isError !== 'boolean') {
    throw new SessionFormatError(`format v3 ${event.type} at seq ${event.seq} tool-result isError must be boolean`)
  }
  const targetMessage: Record<string, SessionFormatJsonValue> = {
    role: 'tool',
    source,
    toolCallId: callId,
    content: resultContent(wrapper['content'], `format v3 ${event.type} at seq ${event.seq}`),
    ...(isError === undefined ? {} : { isError }),
    id,
    ...extensionFields(message, MESSAGE_FIELDS, 'message'),
    ...extensionFields(wrapper, WRAPPER_FIELDS, 'result'),
  }
  return { ...event, data: { ...data, message: targetMessage } }
}

这个函数体现了三条迁移纪律。第一，不认识的事件原样放过：第 37、40 行，不是 tool/result 或者已经不是 user 角色，直接返回原事件。第二，看着像但不对的事件直接报错，不尽力而为：包装块多一个、call id 对不上、isError 不是布尔值，都抛 SessionFormatError。测试里专门有一条“多出一个顶层文本块就拒绝”（tool-role.spec.ts:220）。第三，未知字段改名保留，而不是丢掉：迁移的作者不知道某个插件往消息上挂了什么，所以不替它做决定。

v3→v4 还有一个特殊之处：它需要知道父会话有哪些子会话（fork 关系），这是单条事件看不出来的。目录包为此提供了一个变体工厂，用带子会话证据的迁移替换掉默认那条边，其余边不变（children.ts:13-19）。

投影：从日志折叠出来的派生状态

一个投影单元就是一个 reduce

侧边栏要显示每个会话“一共几轮、花了多久、标题是什么”。最笨的办法是每次都把整份日志读一遍。DSH 的办法是投影：注册一个纯函数 apply(state, event) → state，每提交一条事件就推进一次。Python 读者可以直接想成 functools.reduce(apply, events, init(header))，只不过这个 reduce 是增量跑的。

   * rows from an older unit are discarded instead of being forward-applied
   * into garbage. Non-negative integer.
   */
  stateVersion: number

packages/session/session-projection/src/index.ts:86-92

投影定义里除了 init、apply、可选的 wire.view，就是这个 stateVersion。它是投影缓存失效的唯一开关。顺带澄清一个容易混的名字：core 里还有一个 contentGeneration（surface.ts:251），那是消息表面被替换或被插件改写的计数，用来让 messages() 的内存缓存重建，和这里的投影缓存没有关系。

apply 的注释还有一条硬规定：对不关心的事件必须返回同一个引用，这样 Object.is 一比就知道没变，下游零开销（index.ts:64-66）。这是 React 不可变更新的同一套路数。

投影缓存：可能过期，但永远不会错

投影本身在内存里，重启就没了。冷启动列出 200 个历史会话时，总不能把 200 份日志从头折一遍。于是有了 session-projection-cache：把每个投影的状态存成一行 (ver, seq, val)，下次从这一行接着折。包的开头把定位说得很清楚，缓存是“折叠的捷径，不是权威”，一行“可能过期（seq 说明多过期），但永远不会错”（index.ts:10-14）。

“永远不会错”靠的是恢复时的三道检查：

        && row.ver === def.stateVersion

packages/session/session-projection/src/index.ts:511-520

  • ver === stateVersion：投影的折叠逻辑改过，老行直接丢，不尝试迁移。
  • seq >= beforeBase：这一行确实覆盖到了尾部读取的起点。
  • seq <= endSeq：这一行没有声称见过日志里根本不存在的事件。这一条防的是 hx-04 讲过的崩溃修复：日志被截短之后，缓存行的水位可能比日志还长。

为了让第三条检查可靠，读尾部时故意从最低水位再往前一条开始读（index.ts:426-436）。这样哪怕尾部是空的，也能知道日志到底延伸到哪一条，而不是把“读到零条”误当成“没有新事件”。

为什么不把派生状态写回日志

最直接的替代方案是：每轮结束往日志里追加一条 stats/snapshot 事件，冷启动时找最后一条快照。DSH 没这么做，从代码里能看出三个理由。第一，投影是插件注册的，日志格式是全局冻结的；把插件状态写进日志，就等于每改一次投影逻辑都要发一版日志格式。第二，stateVersion 不匹配时缓存行直接丢弃（spec.ts:24-27），可日志里的东西不能丢，只能迁移。第三，缓存的写入路径全部“软失败”，丢一次写只是下次冷读多回放一段；日志写失败则是数据丢失。两种东西的失败语义完全不同，所以放在两种存储里。（最后这一句是作者的归纳。）

缓存什么时候写？三个必写点（会话创建、turn/end、会话释放）加两个节流触发：
