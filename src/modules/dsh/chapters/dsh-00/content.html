导读：DSH 的整体架构（d743267388）

这一章写给主语言是 Python、不熟 TypeScript、但在 agent / LLM 领域工作的读者。读完你应该能回答四个问题：DeepSeek Harness（下文简称 DSH）这个仓库里有什么；335 个包按什么方向互相依赖；用户输入一句话以后，代码依次经过哪些包、哪些函数；常见的 harness 学习主题在 DSH 里分别对应哪些包、实现到什么程度。

全部结论基于 commit d743267388641bc76f17c45ce8b4c231aed1d32c，每个结论都附上 文件:行号。规模和依赖数字由脚本遍历各包的 package.json 和 src/ 得到，原始数据在 dsh-packages.json。

三个比喻：沿用旧版 DSH 模块的三个比喻，在这个 commit 上依然成立。① ctx 相当于依赖注入容器，服务挂在 ctx.xxx 上；② waterfall 相当于 ASGI 中间件，监听者调用 next() 就把请求交给下一层，不调用就截断后面的处理（见 events.ts:228）；③ 会话日志相当于只追加、不改写的 git 历史，其他视图都从它推导出来（见 session/index.ts:515）。

仓库是什么

DSH 是一个 pnpm monorepo，用 TypeScript 写成，通过插件组合出 agent 运行时。packages/ 下按领域分目录（core、llm、session、sandbox……），每个领域里有若干叶子包；apps/ 放的是装配好的产品入口（CLI、桌面端、Web 前端）。底层的插件框架 Cordis 不在 packages/ 里，而是作为第三方代码放在 vendor/cordis（vendor/cordis/package.json:3）。

入口：从 dsh 命令到插件树

所有界面（命令行、Web、桌面端）共用同一条启动链。下面以 dsh headless "run the tests" 为例逐跳列出（这种写法是 dsh --profile headless 的简写，见 args.ts:95）。

  1. 可执行入口：安装后的 dsh 命令指向 apps/cli 的 lib/bin.js（apps/cli/package.json:15）；在仓库里开发时，pnpm dsh 直接用 tsx 跑源码（package.json:204）。pnpm-workspace.yaml 里也写明 apps/cli 负责这个 bin（pnpm-workspace.yaml:8）。
  2. 参数解析：runCli 调用 parseDshArgs（bin.ts:29）。启动器只解析自己负责的参数（选哪个 profile、叠加哪些 patch、是否 dump 配置），其余参数原样交给插件树（args.ts:4）。
  3. 进入 profile 启动：profile 模式下按需加载 profile-boot.ts（bin.ts:33），调用 runProfile（profile-boot.ts:244）。它依次做四件事：根据启动环境安装 HTTP 代理（:249）；合成补丁栈，顺序是 bundle 层、用户层、--patch 覆盖层（:265）；注册信号处理（:280）；最后调用 boot（:296）。根配置本身只是一个空列表 []，整棵插件树都由补丁叠出来（:81-85）。
  4. 宿主准备：boot 的 prepare 回调先挂载 PluginPackages（:302），再通过 provideCmdline 把内层参数和退出函数提供给插件（:307）。
  5. 装载插件树：app-boot 里的 boot（app-boot/index.ts:975）先新建根 Context（:982），然后挂载 Loader（:1004），执行 prepare（:1005），挂载根 include（:1007），等全部条目就绪（:1013），最后检查必需的启动条目（:1015）。
  6. 插件按依赖激活：bundle 补丁里每一行是一个插件，例如 llm（base/cordis.patch.yml:34）、agent-loop（:499），以及 DeepSeek 适配器 dsh-llm-deepseek-api-key（:514）。行的先后顺序不决定加载顺序，插件在它依赖的服务可用时才激活（:12）。headless bundle 在此基础上加了一行 headless-runner（headless/cordis.patch.yml:24），它要等 agentDefaultModel、agents、sessions 三个服务都就绪才运行（headless/index.ts:40）。
  7. 其他界面走同一条路：桌面端的宿主进程同样调用 runProfile，只是把 profile 固定为 desktop（desktop-host/index.ts:25、:27）；dsh web 启动 web profile（args.ts:92）。

白话：可以把它想成 python -m dsh --profile headless：启动器读入一组 YAML 补丁，合成一份“插件清单”，然后像 importlib 那样逐个导入，把它们注册进同一个依赖注入容器。容器会等每个插件声明的依赖都到齐后才激活它，所以清单里的书写顺序不重要。main 函数里没有写死“先初始化 A 再初始化 B”。

profile 与 bundle

profile 是一组 bundle 的有序叠加。仓库自带 5 个 profile 模板（profile.ts:179）：

profilebundle 叠加用途
headlessbase + headless（profile.ts:187）一次性任务：结果打印到 stdout 后退出
webbase + web-app浏览器界面
acpbase + acp-app通过 stdio 上的 JSON-RPC（Agent Client Protocol）驱动
sdkbase + sdk-app通过 stdio 上的 JSON-RPC 为 SDK 客户端提供服务
sdk-minimal只有 sdk-minimal不叠加 base 的最小组合

核心服务都集中在 base bundle 里：llm、session、agent、llm-retry、JSONL 持久化、沙箱、审批、工具、压缩、子代理等，绝大多数插件都在这里装配。后文提到的“默认装配”，指的就是 base bundle。

与旧版 DSH 模块的差异：① 旧稿说模型流式输出时会写 assistant/chunk 事件。在这个 commit 里，测试明确断言日志中没有这种事件（loop.spec.ts:107）；流式帧改走 agent/assistant-stream 事件，日志里只保留 assistant/attempt 和 assistant/message。② 旧稿引用的 examples/ 目录已经不存在，看装配示例要读 packages/bundle/*/cordis.patch.yml。③ core/ 下现在有 8 个包，没有旧稿提到的 agent-spine。

分层架构

统计口径

  • 依赖边：取 dependencies、peerDependencies、optionalDependencies 中以 workspace: 开头的条目；不算 devDependencies（其中多为测试用）。DSH 的包大多用 peerDependencies 声明自己依赖的服务接口，例如 core/tools 用 peer 方式依赖 agent、llm、session、sandbox、user-approval 等包。
  • Cordis 不计入领域表：335 个包里有 334 个依赖 @deepseek-ai/cordis（唯一的例外是 apps/web）。它在 vendor 目录里，不属于任何 packages/ 领域，计入表格只会让每一行都多一列同样的内容。
  • client 包被低估：界面包的运行时依赖主要写在 package.json 的 dsh.client.inject 和 devDependencies 里（例如 ui-chat/package.json:30），peer 只写了 Cordis（:51）。因此按本口径，client 领域对外依赖很少，这是统计方式造成的，不能说明界面包真的依赖少。

从表中能读出的四个结论

  1. 四个领域是汇聚点：被依赖最多的是 util（47 个领域依赖它）、core（42）、llm（33）、session（29）。1,367 条跨领域边中，指向 core、util、llm、session 的分别有 299、219、112、105 条，四项合计约占 54%。要读懂 DSH，先读这四块。
  2. 领域之间有双向依赖，包之间没有环：在领域层面能找到 18 对互相依赖的领域，比如 core 和 llm、core 和 session、llm 和 session。但在包层面做强连通分量检查，结果是 0 个环。原因是“领域”只是目录分组，同一个目录里既有底层的接口包，也有上层的策略插件。例如 core/tools 依赖底层的 dsh-llm（tools/index.ts:13），而 llm 目录里的重试插件 llm-retry 反过来依赖 dsh-agent（llm-retry/index.ts:12）。所以判断依赖方向要看包，不能只看目录。
  3. 具体实现藏在接口后面：core/agent-loop 是真正驱动 turn 循环的包，却只有 bundle（base、sdk-minimal）和一个测试工具包依赖它。其他包都面向 core/agent 提供的 ctx.agents 接口编程，这一点在源码注释里写得很清楚（agent/index.ts:167）。agent-loop 在构造时把自己注册为工厂（agent-loop/index.ts:388）。llm-retry 也一样，只有 bundle 和 token-meter 依赖它。
  4. 依赖链很长，而且有一处是包依赖应用：把“深度”定义为从某个包出发、沿依赖走到底的最长路径。util/values 的深度是 0，llm/llm 是 2，core/session 是 3，core/agent 是 6，core/tools 是 8，core/agent-loop 是 9，bundle/base 是 14，apps/cli 是 17。最深的是 subagent/subagent-dsh-sdk（19），因为它经由 sdk/client 依赖了 apps/cli：SDK 客户端要把整个 dsh 当作子进程来驱动（sdk/client/package.json:3）。这是全仓库唯一一处包依赖应用的反向边。
  waterfall(...args: any[]) {
    const cbs = this.dispatch('waterfall', args)
    const inner = args.pop()
    const next = () => {
      const cb = cbs.shift() ?? inner
      return cb(...args)
    }
    args.push(next)
    return next()
  }

上面是 Cordis 的 waterfall 实现（events.ts:234-243）。后文出现的 agent/pre-step、llm/stream、tools/execute 等扩展点都用这种机制：监听者按注册顺序层层包裹，最里层是内置的默认行为。

白话：底座层相当于 Python 项目里的 utils/ 和类型定义；核心层相当于“定义抽象基类的那几个模块”，例如 llm/llm 定义 LlmAdapter，core/session 定义会话日志，sandbox/sandbox 定义 SandboxProvider；能力层是各种“接口 + 实现 + 给模型用的工具”三件套；外围层是 Web 后端、界面和协议桥；装配层只负责“这次启动用哪些插件”。依赖只能从外层指向内层，内层不知道外层的存在。

下面用 headless profile 走一遍完整链路，因为这条链路中间没有 HTTP、界面和协议转换。换成其他入口时，只是调用 agent.followup 的地方不同：Web 端在 session-controller/commands.ts:365，ACP 在 acp/session.ts:303，SDK 在 sdk/server.ts:210。从 followup 往下，各入口走的代码完全相同。

重试：策略归 provider，执行归插件

重试策略由各 provider 自己声明，适配器注册时就带上了（llm-deepseek/adapter.ts:33）。llm-retry 本身没有任何配置项，它只负责在 agent/request-error 上执行 provider 给出的策略。策略分两种：normal 只重试列入名单的错误码，次数有上限（llm-retry:223）；always 对任何失败都无限重试，直到成功、被取消或插件卸载（retry-policy.ts:50）。如果服务端返回了 Retry-After，就按服务端给的时间等待（:227）；否则用下面的退避公式：

function localDelay(config: ResolvedRetryPolicy, retry: number, random: () => number): number {
  const exponent = Math.min(retry - 1, 1024)
  const exponential = Math.min(config.initialDelayMs * 2 ** exponent, config.maxDelayMs)
  const jitter = 1 - config.jitterRatio + 2 * config.jitterRatio * random()
  return Math.min(exponential * jitter, config.maxDelayMs)
}

出处：llm-retry:59-64。默认参数是初始 500 ms、上限 10 s、抖动比例 0.1（retry-policy.ts:15-17）。每次重试前先写一条 llm/retry 事件，然后进入可取消的等待（llm-retry:188）。已经重试了几次也是从日志里统计出来的，所以进程重启后计数不会丢。

熔断：没有

在非 client 包里搜索 circuit、breaker、half-open、cooldown，结果都与熔断无关（例如注释里的 short-circuit、half-open range）。有三个机制看起来与熔断相近，但都不是熔断，不要混为一谈：

  • llm-retry 的重试计数在每个 step/start 和 turn/end 时清零（llm-retry:131）。所以它限制的是“单个 step 内最多重试几次”，不会在多次请求之间累积失败率，也不会把某个 provider 暂时摘掉。
  • compaction-basic 的 maxOverflowRetries 默认为 1（config.ts:106），只限制上下文超长后的恢复次数。
  • repeat-tool-reminder 在模型连续重复同一个工具调用 3、5、8 次时提醒模型（base yml:446），但它明确只提醒、从不拦截（repeat-tool-reminder:216）。

白话：Python 里的 pybreaker 会记录“最近 N 次调用失败了几次”，失败多了就在一段时间内直接拒绝调用，过一阵再放少量请求试探。DSH 里没有这种跨请求的状态机。如果要做，按 DSH 的设计应该写一个插件挂在 agent/request-error 或 llm/stream 上，把熔断状态作为事件写进会话日志，这样回放时状态也能还原。

记忆：为什么只评“部分”

DSH 让“记忆”落在三个地方：工作区里的文件（AGENTS.md 由 agent-instructions 自动注入上下文）、会话日志本身（按 id 续跑，或通过 session-reference 引用另一个会话的快照，session-reference:2），以及同一会话内持久化的目标（goal）和待办（todo）。实验性的 Ralph 工具甚至在提示词里直接写明“工作区就是长期记忆”（tool-ralph:157）。缺少的是一般意义上的 memory 模块：没有在对话中自动提炼出值得记住的事实并写入记忆库的流程，也没有按语义检索召回记忆、注入上下文的流程。跨会话检索在默认装配里也是关闭的。
