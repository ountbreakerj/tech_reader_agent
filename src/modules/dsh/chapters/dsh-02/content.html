第 2 章

LLM 层：provider 适配、流式组装与重试

前两章讲了 DSH 的整体形状（导读）和插件怎么接成运行时（Cordis 与装配）。这一章下沉一层，讲一条请求真正离开进程之前经过的那三个包：provider 无关的接口（llm/llm）、一个具体 provider 的翻译层（llm/llm-deepseek）、以及挂在循环扩展点上的重试执行器（llm/llm-retry）。全部结论基于 commit d743267388641bc76f17c45ce8b4c231aed1d32c。

对写 Python 的人，这一章有一个统一的对照物：你在 openai / anthropic SDK 上包过的那一层 class LLMClient。DSH 做的事差不多，但把三件通常混在一起的事拆开了——协议翻译（适配器）、协议之上的统一词汇（llm 服务）、失败之后怎么办（重试策略与重试执行器分属两个包）。拆开的代价是文件更多；好处是同一个重试执行器能给所有 provider 用，而每家 provider 的超时判定、错误分类、退避偏好仍然是它自己的事。

provider 无关的词汇表：请求、块、结束原因、用量

packages/llm/llm/src/types.ts 开头的注释把这一层的职责写死了：它是一份"循环、会话日志和插件共用的 provider 无关词汇"，只有适配器负责翻译 provider 的线上消息（llm/src/types.ts:2）。这句话值得停一下：它意味着循环、压缩、token 计量、UI 全都不该 if provider === 'deepseek'，任何 provider 差异必须在适配器里被消化掉。

llm 服务：注册表 + 唯一入口

ctx.llm 就是 LlmRuntime，官方对它的描述是"一个适配器注册表加一次流式模型调用"（llm/src/index.ts:339，类定义在 llm/src/index.ts:342）。它内部就是一张 Map<provider, AdapterRegistration>。

两侧的兜底：适配器抛错变成 finish，消费者抛错照旧往外扔

这一层最值得抄的一条设计在 adapterStream 的边界上。整个适配器调用被包在两次 try 里，任何一个环节抛错都被转成一个终态 finish 块而不是异常：

    type: 'finish',
    reason: signal?.aborted || failure.code === 'ABORTED'
      ? { kind: 'aborted', failure }
      : { kind: 'error', failure },
  }
}

llm/src/index.ts:1160-1169

边界划在哪，注释写着：适配器选择、分发、迭代失败 → 变成终态失败块；中间件和下游消费者的失败 → 仍然抛出（llm/src/index.ts:1037-1040）。理由是这样一条流在任何位置中断都有确定的终点：只要迭代器正常结束或吐出一个 finish，上层就有一份完整协议；异常只用来标记"这不是 provider 的问题"。

这条分界线让重试逻辑能写得非常笨：循环里只判 finish.kind，不需要同时捕异常（agent-loop/src/agent.ts:506）。

顺便记一下 llm/stream 这个扩展点：它是包住每一次流式调用的 waterfall，设计用途写的是"重试、回放、路由"（llm/src/index.ts:64）。实际的 llm-retry 没有挂在这里（原因见 4.2）——所以"设计时留的扩展点"和"实现时选的扩展点"可以不是同一个，读源码时要以 ctx.on 的实际调用为准。

一个具体适配器：从内部消息到 Messages 请求，再翻回来

DeepSeek 适配器（llm/llm-deepseek，20 多个文件）除了网络之外只做两件事：出去的时候序列化（serialize.ts）、回来的时候翻译（translate.ts）。协议是 Anthropic 兼容的 Messages 接口，这一点从请求头就能看出来（llm-deepseek/src/adapter.ts:130）。

三条：① 内部 role 有五种（system / developer / user / assistant / tool），线上只有三种——tool 结果被翻译成 user 角色的 tool_result 块，因为 Messages 协议里工具结果就是用户侧内容。② 相邻同角色消息合并成一条，这既符合协议要求（连续同角色消息有些 provider 会拒绝），也让"一批工具结果"落进同一条 user 消息。③ 空的 user 消息直接跳过。

退避怎么算。 三行纯函数：

function localDelay(config: ResolvedRetryPolicy, retry: number, random: () => number): number {
  const exponent = Math.min(retry - 1, 1024)
  const exponential = Math.min(config.initialDelayMs * 2 ** exponent, config.maxDelayMs)
  const jitter = 1 - config.jitterRatio + 2 * config.jitterRatio * random()
  return Math.min(exponential * jitter, config.maxDelayMs)
}

llm-retry/src/index.ts:59-64

逐项：指数是 2 ** (retry - 1)，第一次重试就是初始值（500 ms）而不是它的两倍；指数本身夹到 1024，防止 2 ** n 变成 Infinity；先夹一次上限，再乘抖动系数 [1 - r, 1 + r]（r=0.1 时是 0.9–1.1 倍的对称抖动），乘完再夹一次上限。第二次夹的意义是：抖动不能把延迟推出上限。测试里用固定随机数把这个算式钉死了——random() 依次返回 0 和 1 时，第一次退避是 450 ms（500 × 0.9），第二次是 1100 ms（1000 × 1.1）（llm-retry/tests/retry.spec.ts:353、retry.spec.ts:357）。自己验算一遍比读文档可靠：500 * 2**0 * 0.9 = 450、500 * 2**1 * 1.1 = 1100。

没有真实用量时，一切都靠一个常数：4 个字符算 1 个 token（estimate.ts:13），外加每个块 4 个 token 的结构开销、每条消息 4 个 token 的角色开销（estimate.ts:16）。图像不按这个方法算——它的价格由路由声明（适配器的 imageRequestPricing），没有声明的路由退回结构 JSON 价格（estimate.ts:29）。

注意这里的 4 字符 = 1 token 是源码里的固定启发式，不是我编的教学示意数——它写在常量注释里（"固定文本密度估计，直到需要精确分词为止"）。对中文内容这个估算会明显偏低，这也是它只用来触发压缩、不用来计费的原因。

凭据：只引用值，不搬运值

凭据子系统只要知道三件事就能读懂接口（packages/credentials/），细节留给专门章节。

① 配置里存的是引用，不是密钥。 引用就是一个 POSIX 环境变量名（DEEPSEEK_API_KEY），有严格的命名文法校验（credentials/src/index.ts:19）。模块注释说明了动机：消费者每次操作重新解析一次引用，所以换了密钥下一个操作就生效，不用重启插件，而配置界面描述一个引用时永远看不到它的值（credentials/src/index.ts:5-7）。

取舍与坑

四条路线的对比

做法退避与重试次数归谁代价适用场景
DSH：provider 插件出策略 + 独立重试插件执行策略随 provider 注册冻结；执行器只有一个（llm-retry）多两个包、一次注册；改策略要重注册；agent/request-error 这个扩展点必须存在provider 多、且各家对"什么算可重试"和"该怎么等"意见不同；需要把重试计数当持久事实
重试写进客户端 SDK（max_retries=5）SDK 内部，调用方看不到重试对上层不可见——超长上下文、换模型、压缩这些都接不进来；重试次数重启即失忆；日志里只有一条结果，排障时看不到"它试了几次"脚本、一次性任务；不要求把过程落进日志的系统
客户端完全不重试，错误直接抛没人管一次 429 或一条断流就毁掉整个 turn；长任务失败率随步数线性上升调用方自己包一层重试，或者本来就是交互式、失败会被用户看到
always 模式（无限重试到成功/取消/卸载）本地退避，没有次数上限真正终局的错误（配额耗尽、账号被禁）会一直转；必须有取消信号和卸载清理兜底无人值守的长任务，且取消路径可靠

这四条里最容易被低估的是第二条的隐性成本。SDK 里重试有一个安静的问题：它把"一次尝试"和"一次调用"合并成了一个概念。一旦上层需要区分它们——要在重试时重新压缩上下文、要换模型、要把失败计数写进日志、要在界面上显示"正在重试第 2 次"——那道缝就没了。DSH 那条看起来啰嗦的链路（策略定义 → 注册冻结 → 循环派发 → 事件日志 → 投影计数）换来的正是这道缝的存在。

坑 1：错误码没分类清楚，重试策略就永远不起作用

触发条件：写一个新适配器时，把所有异常都兜底成同一个码，或者把 failures 里的错误码随手写成了 'UNKNOWN'。

后果：默认可重试集合是五个具体的码（EMPTY_RESPONSE / RATE_LIMIT / SERVER / TIMEOUT / TRANSPORT）。一个码没落在集合里，normal 策略就直接 return next()，一次都不会重试，而且不报错、不警告——现象只是"偶发失败率偏高"。

源码里怎么防的：分类集中在 providerError() 一处，且保证一定返回一个具体码——最后那个 else 分支即使 status 是 undefined 也返回 'SERVER'，而不是留空（5.4 引的那一段）。也就是说"没识别出来"被归到可重试的一侧而不是不可重试的一侧，这是对的默认方向。反面例子在别处：agent-loop 里非 LlmError 的意外错误会被压平成 UNKNOWN 写进 turn/end（agent-loop/src/agent.ts:381）——那种错误确实不该重试，所以这个压平是有意的。

坑 2：流"干净地断在半路"和"超时"是两种错，只重试其中一种

触发条件：代理或网关把连接正常关掉，但没发 message_stop。

后果：translate.ts 的事件循环自然结束，抛出 STREAM_CLOSED。这个码不在默认可重试集合里，所以默认配置下整个 turn 直接以 error 结束，一次重试都不做。

为什么这么设计：HTTP 层完全正常（状态 200、SSE 头也在），"断在半路"在协议上无法与"服务端有意提前结束"区分。把它默认算作可重试，会让一类真实的协议错误被无限重试。测试把这个行为固定下来了：断言请求数恰好为 1、日志里没有 llm/retry、turn/end 的原因是 STREAM_CLOSED，而且那份残缺的流仍然被完整存进了 assistant/attempt（llm-retry/tests/transport-recovery.spec.ts:192）。

想让它可重试：在 provider 的 retryPolicy 里把 STREAM_CLOSED 加进 retryableCodes，或者切到 always。这就是"策略归 provider"的实用之处——这是一个纯配置决定，不用改代码。

对照一下真正的停滞：连上了但一段数据都不来，由空闲看门狗判成 TIMEOUT（默认 300 秒，llm-deepseek/src/defaults.ts:4），这个默认可重试，测试描述的就是"停住的响应体变成 TIMEOUT 并在下一次请求成功"（transport-recovery.spec.ts:217）。两种"没走完"的默认待遇完全相反，值得记。

坑 3：截断的 tool-call 有两个"看起来都合理"的处理，只有一个是对的

触发条件：模型输出被 max_tokens 截断，恰好停在工具参数中间。

两种直觉做法：① 解析参数时失败就报错——结果把一次可恢复的截断变成协议错误，用户看到的是"provider 返回了非法 JSON"；② 报错前先按"尽力解析"把半个 JSON 补成合法的——结果是模型拿到了工具名正确、参数错误的调用，工具照常执行，副作用已经产生且不可撤销。

源码里的做法：都不做。翻译层看见 max-tokens 就跳过 JSON 校验（5.3 引的第 151 行），组装层只丢工具调用、保留文本（5.2 引的 assembled()），循环层看到 max-tokens 就不执行工具并让这个结束原因在本 turn 内粘滞。三层各做一件小事，合起来的效果是：截断的工具调用根本没到过工具运行时，同时它前面那段文本仍然被保存下来给用户看。

代价：默认行为是"截断即停"，用户得再说一句话才能继续。想自动续写需要在 agent/turn-stopping 上挂一个插件把 turn 拖住（测试 agent-loop/tests/loop.spec.ts:1459 描述的就是这个场景：续写过了，结局仍然是 max-tokens）。这个设计把"要不要续写"外置成了插件。

坑 4：失败的尝试会留在日志里，但绝不能进上下文

触发条件：一次请求失败后重试成功。

后果（如果不处理）：失败那次已经吐出了一部分文本、也可能吐出了半截工具调用。如果它被当成 assistant 消息写进历史，下一次请求的上下文里就有了一段"作者不明"的文本，而那条半截工具调用还会触发配对校验失败（tool calls need immediate results）——整个会话从此发不出请求。

源码里怎么防的：三重。① 失败写 assistant/attempt，成功才写 assistant/message，而 deriveMessages() 只读后者。② 序列化前的配对校验会拦住悬空调用（5.2）。③ 循环在 step 异常时给未答的调用补一对 call/result，理由写在注释里——provider 拒绝悬空的 assistant 调用（core/session/src/repair.ts:164）。

测试同时验证了三件事：失败尝试有 7 条 chunk 被完整留存、assistant/message 只有一条、工具执行次数为 0（llm-retry/tests/retry.spec.ts:287）。这里有一处 API 细节值得注意：preparedCall.stream() 只能发一次（INVALID_PREPARED_CALL），所以重试走的是 continue 回到 step 循环开头、重新 prepareCall，而不是复用同一个 prepared call 再发一次。重试之所以能顺带换模型、重新压缩上下文，根子就在这条"只能发一次"的约束上。
