第 1 章

Cordis 与装配：插件怎么接成运行时

上一章（导读：DSH 的整体架构）把 DSH 当成一个黑盒看了个全景：335 个包、一次请求的 8 步。这一章把盒子拆开，看这些包是怎么被接成一个运行时的。全部内容基于 commit d743267388641bc76f17c45ce8b4c231aed1d32c，每个结论都带 文件:行号。

如果你写 Python，可以先在心里做一次替换：DSH 里没有 main.py 里那一串 db = Database(); agent = Agent(db, tools)。取而代之的是一份 YAML 行列表（每行是一个插件），加上一个叫 Cordis 的插件框架负责"按声明的依赖顺序把它们点着"。这一章要讲清楚三件事：插件之间怎么找到对方（服务与依赖注入）、一棵插件树从哪来（profile / bundle / patch / Loader）、插件之间怎么在一件事上接力（事件派发与扩展点）。

Cordis 是什么，为什么放在 vendor 里

Cordis 不在 packages/ 里，它和 cosmokit、schemastery、loader、include、group、hmr、timer 一起放在 vendor/——是随仓库一起走的第三方代码（pnpm-workspace.yaml:2）。它自称 "Meta-Framework for Modern JavaScript Applications"，版本 4.0.5-alpha.1（vendor/cordis/package.json:3、vendor/cordis/package.json:4）。

它的全部内核只有 9 个源文件、约 2,700 行：context.ts（146 行）、events.ts（352）、fiber.ts（754）、reflect.ts（418）、registry.ts（337）、service.ts（115）、logger.ts（271）、utils.ts（287）、index.ts（16）。index.ts 就是一张目录，把每个文件用一句注释说明白：

Cordis 对 Python 读者来说是一个陌生的形态，用四个词就能框住：Context（代理对象）、Service（挂在 ctx 上的服务）、Plugin（一个会注册服务的函数或类）、Fiber（一次插件加载的运行时实例）。下面四节分别讲。

ctx 不是字典，是一个代理

文档写得很直白："The concrete Context class is proxied at runtime"——Context 类在运行时被 Proxy 包了一层，所以文档上看到的 ctx.xxx 是由各个插件"事后增强"出来的（context.ts:12）。根 Context 构造时就把代理装好：

  constructor() {

    this[symbols.intercept] = Object.create(null)
    const self = new Proxy<this>(this, ReflectService.handler)
    this.root = self
    this.baseUrl = undefined
    this.fiber = new Fiber(self, {}, Object.create(null), null, () => [])
    this.reflect = new ReflectService(self)
    this.registry = new RegistryService(self)
    this.events = new EventsService(self)
    this.logger = new LoggerService(self)
    this.fiber._disposables.clear()
    return self
  }

vendor/cordis/src/context.ts:71

所以 ctx 上能读到什么是运行时决定的，不是类型决定的。读一个属性时，代理会交给 ReflectService.handler.get，那里做的是：先直接取（reflect、registry、events、logger 这些是真实字段），取不到就当成服务名去服务表里查。查不到就抛 cannot get property ... without inject（reflect.ts:144）。

服务查询不是查一张全局表，而是沿 fiber 链往上走：

三个细节值得记住。第一，fiber.store 是"这个 fiber 当时看得见的服务快照"，不是全局表——所以同名服务在不同层级可以不同。第二，if (prop in fiber.inject) 那一行把错误信息改写成 "in inactive context"（reflect.ts:160）：你声明了依赖但这个插件还没被激活，和你压根没声明依赖，是两种不同的错误，报错文本会区分。第三，ctx.on、ctx.plugin、ctx.waterfall 这些并没有写在 Context 类上，它们是 ReflectService 构造时用 mixin 转发出来的：

fiber 的状态机：依赖齐了才跑

fiber 有六个状态（fiber.ts:147）：PENDING（等依赖）、LOADING、ACTIVE、FAILED、UNLOADING、DISPOSED。

核心机制藏在一个叫 epoch 的字符串里。_refresh() 遍历 inject 的每个名字，从 fiber.store 里取实现，把它们的 fiber 序号拼成一个字符串；任何一个缺失，epoch 就是 INACTIVE（fiber.ts:611）：

  _refresh() {
    let epoch: string | boolean = false
    epoch = ''
    for (const name of Object.keys(this.inject)) {
      const impl = this._store[name]
      if (!impl) {
        epoch = INACTIVE
        break
      }
      epoch += ':' + impl.fiber.uid
    }
    this._setEpoch(epoch)
  }

vendor/cordis/src/fiber.ts:611-623

然后 _setEpoch 比较新旧 epoch：从 INACTIVE 变成有值就跑 _reload()，反过来跑 _unload()（fiber.ts:625-637）。注意 epoch 里拼的是提供者 fiber 的 uid，所以"同一个名字换了一个提供者"也算变化，插件会被卸载再加载一次——这是 hot reload 与"服务被替换"能工作的原因。

这一条对读配置很关键。packages/bundle/base/cordis.patch.yml 开头自己写了：

# Row order carries no load semantics (activation is service-availability
# driven); the grouping is for readers.

packages/bundle/base/cordis.patch.yml:12-13

换句话说，那份 500 多行的 YAML 不是按顺序执行的脚本。行序只影响可读性；真正决定"谁先跑"的是服务依赖：llm 服务没人提供时，所有 inject 了 llm 的插件都停在 PENDING。

dispose 与 effect：所有资源都挂在一个列表上

插件要注册任何有生命周期的东西，都得包在 ctx.effect(() => { ...; return () => 清理 }) 里（fiber.ts:418）。ctx.on 就是这么实现的——注册监听者时顺手记一条 effect，标签写成 ctx.on("事件名")（events.ts:300）。卸载时并行跑完所有 disposer（fiber.ts:676）。

一个插件"没 clean 干净"在 Cordis 里几乎没有借口：ctx.on、ctx.provide、ctx.accessor、ctx.mixin 全都是 effect。真正会泄漏的是逃出这套机制的持有物——比如一个定时器、一个长连接、一个自己在外面保存的闭包。这就是"坑 5"。

装配：从 dsh 命令到一棵插件树

这一节回答"那 500 行 YAML 是从哪来的"。分工是：profile 决定用哪些 bundle，bundle 提供 patch 文件，patch 叠加成一棵条目树，Loader 把每个条目变成一次 ctx.plugin。

profile 是一个目录，不是一段代码

profile 位于 $DSH_HOME/profiles/<name>（app-boot/src/profile.ts:169），目录里有 package.json（写明这个 profile 用哪些 bundle）和 cordis.patch.yml（用户自己的补丁层）。仓库自带 5 个模板（profile.ts:179）：

sdkdsh-base + dsh-sdk-appprofile.ts:190

bundle 是 npm 包，包清单里声明自己的补丁文件："dsh": { "bundle": { "patch": "./cordis.patch.yml" } }（bundle/base/package.json:34）。

而且每次启动都会重写它，理由写在注释里（profile-boot.ts:171）：Loader 在插件自我卸载时会把当前树回写进这个文件，一旦被回写，下一次启动就会把每个 bundle 的 insert 重复叠一遍。所以"空根"是个不变量，靠每次启动重写来维持。这个文件之所以还存在于磁盘上，只是因为它给 Loader 提供了一个真实的 include 锚点来定 baseUrl。

补丁栈的合成顺序写在 composeProfile（profile-boot.ts:197），注释里写全了：bundle 层（按 dsh.profile.bundles 顺序）→ profile 自己的用户层 → $DSH_HOME/cordis.patch.yml（机器级偏好，所以盖过 per-profile 层）→ --patch 覆盖层 → 遥测开关。还有一个值得注意的顺序：在导入任何插件之前就先算好模块解析结果（profile-boot.ts:206）。

两种 insert：带 id 的是往某个 group 行的子列表里追加（include/index.ts:91），不带 id 的是追加到顶层（include/index.ts:93）。不带 insert 的补丁则是按 id 覆盖已有行的字段（include/index.ts:120），而 config 是整块替换而不是深合并——base 的注释专门强调了这一点（cordis.patch.yml:6），所以任一模式 bundle 覆盖一行时必须把这一行的每个键都重述一遍。匹配不到 id、或 name 不一致时，补丁只是告警并跳过（include/index.ts:116）——这是"坑 1"。

装配时怎么"选实现"

这是本节最有用的部分。同一个接口在 DSH 里有多种实现，切换方式一共四种，按粗暴程度递增：

手法怎么做例子
注册表服务本身不变，实现往它里面注册ctx.llm.registerAdapter(['deepseek-official'], adapter)（llm-deepseek/src/host.ts:55）
平台开关同一功能的两行，用 disabled: !!js 互斥bash-sandbox / pwsh-sandbox（cordis.patch.yml:246、:250）

这里的 cordis:group 是一个 Loader 内置的假插件，作用只是提供一个嵌套的子条目列表（vendor/group/src/index.ts:3，整个文件三行，转发 Loader 里的 Group）。isolate.sessionQuery: true 让这个 group 下面的 sessionQuery 解析到一个新的隔离标签上——于是两份实现并存，各看各的（context.ts:121）。

再看 LLM provider 这一层。base 里默认装了两个 provider 插件——一个是 API key 方式（cordis.patch.yml:514），一个是账号方式（:517）——它们不是互相替换，而是各注册各的 provider 名。默认用哪个，由另一行的配置决定（cordis.patch.yml:88）。

与 Python 的对照：如果自己用 Python 写，这一步通常是一个 config.py 里的字典加上 if settings.provider == "..."。DSH 把它拆成了"服务接口 + 多个注册方 + 配置行叠加"，好处是新增一个 provider 不用改任何现有代码；代价是默认值散落在 YAML 的不同层里，要回答"这个 provider 现在到底跑没跑"得把补丁栈读完。

插件之间怎么通信：事件与扩展点

服务解决"我要用别人"的问题；事件解决"我要在别人的流程里插一脚"。Cordis 的事件总线有五种派发模式（events.ts:26），DSH 实际主要用其中三种。

waterfall：串成链条，不调 next() 就是否决

实现只有 10 行，读懂了就没有魔法：

  waterfall(...args: any[]) {
    const cbs = this.dispatch('waterfall', args)
    const inner = args.pop()
    const next = () => {
      const cb = cbs.shift() ?? inner
      return cb(...args)
    }
    args.push(next)
    return next()
  }

三种派发怎么选

模式语义返回值怎么用DSH 里的用例
emit同步调用，不看返回值、不等 Promise（events.ts:194）忽略agent/assistant-stream（agent.ts:449）、tools/result（tools/index.ts:1710）

waterfall外面包里面，靠 next() 接力最外层监听者的返回值agent/pre-step、agent/request、tools/pre-execute 等

判定"截断"的规则在 isBailed：只有 null、false、undefined 三个值不算 bail，其余任何返回值都算（events.ts:13-15）。这条规则意味着 serial 的监听者必须显式 return 才算"我处理了"，漏写 return 等于什么都没说。

再看一个"包装层"的例子，超时策略（完整实现不到 40 行）：

export function apply(ctx: Context): void {
  ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {
    const timeoutMs = ctx.tools.get(exec.name, exec.agent)?.timeoutMs
    // A tool that declares no budget: no deadline, delegate unchanged.
    if (timeoutMs === undefined) return next()

    using d = deadline(exec.signal, timeoutMs, TOOL_TIMEOUT)
    // Swap the derived deadline onto exec for dispatch, then restore the
    // caller's own signal so post-execute listeners never see this plugin's
    // (possibly already-aborted) timeout signal.
    const upstream = exec.signal
    exec.signal = d.signal
    try {
      const result = await next()
      // If OUR timer fired (scoped by code — a nested outer deadline reads as
      // undefined here), the tool/capability saw the abort and reached
      // quiescence; replace whatever it returned (its own abort result) with the
      // structured TOOL_TIMEOUT the model sees.
      if (timeoutOf(d.signal, TOOL_TIMEOUT) !== undefined) {
        return toolTimeoutResult(timeoutMs)
      }
      return result
    } finally {
      exec.signal = upstream
    }
  })
}

packages/guard/timeout-policy/src/index.ts:55-85

它临时把 exec.signal 换成带 deadline 的 signal，调 next()，然后无论如何都换回来。三个细节都值得学：① 没用 timeoutMs 的工具直接 return next()，不做任何事也不改变行为（timeout-policy/index.ts:59）；② 只有自己这个计时器触发时才改写结果，嵌套的外层 deadline 不会误判（:73）；③ 用 finally 恢复 signal，包出去的必须包回来。

按作用域过滤：同一事件只发给相关的 Agent

DSH 在一个多 Agent 进程里跑，tools/pre-execute 这类事件不能广播给所有人。EventsService.dispatch 里有一段过滤器逻辑，每个监听者记录自己属于哪个 ctx，派发时逐个比对（events.ts:163）。DSH 侧对应的写法是 scopeTarget(this, exec.agent)——把当前 Agent 作为派发目标，只有这个作用域下的监听者收到（tools/index.ts:1511）。扩展点的类型注释里反复出现的那句 "Scope-filtered dispatch" 说的就是这件事。

取舍与坑

三条路线对比

维度Cordis 插件化（DSH 的做法）直接 import 组装钩子函数表
新增一个功能写一个包 + 在 YAML 加一行改组装代码改组装代码并挂钩子
替换实现加一行 disabled 或按 id 覆盖 config改 import改钩子的挂钩点
依赖顺序由服务可用性决定，不用手排（fiber.ts:611）手写顺序，错了就崩手写顺序
卸载/热重载disposer 自动跑，服务自动注销多半没有手动维护反注册
调试成本高：要知道最终跑的是哪几个插件，得把补丁栈读完低：读一个文件中：读钩子注册处
失败模式静默 PENDING（插件没激活但也不报错）启动时直接异常钩子没被调用，静默
适用场景多产品线共用一套内核（CLI / Web / 桌面 / SDK）单一产品单一产品但需要少量扩展点

最后一行的失败模式是这套设计的真正代价，也是下面"坑 3"要展开的。auditStartupEntries 只在条目落在"必需"名单里时才判死，其余只是 warning；非必需的插件静默不激活是允许的（app-boot/index.ts:939）。

坑 1：补丁按 id 覆盖，行序完全不保证谁生效

触发条件：你在 profile 的 cordis.patch.yml 里写一行想改 base 某个插件的配置，但 id 写错了，或者 name 与目标行不一致。

后果：补丁被静默跳过（只打一行 warning），启动照常成功，你以为改了但没改。applyEntryPatches 对三种情况都是 warn + continue：找不到 id（include/index.ts:83）、目标不是 group（:87）、name 不匹配（:116）。

源码里怎么防的：部分防住。插入的行会被立刻建索引，所以同一份补丁列表里后面的补丁可以改前面刚插入的行（include/index.ts:100，注释解释了不这么做的话"inserted rows were silently unpatchable"）。但跨层写错 id 依然只是 warning。要确认生效了，得用 dsh --dump-config 把最终树打出来看。

坑 2：同名服务在同一作用域注册第二次，直接抛错

触发条件：两个插件在同一层（没有 isolate）都提供同一个服务名。

后果：后注册者抛 service "X" has been registered at <先注册者的插件名>（reflect.ts:290），该插件变成 FAILED。

设计判断：这是故意的 fail-loud。Cordis 没有"后写的覆盖先写的"这种静默语义——因为同一层出现两个提供者，多半是配置写错了（比如你既装了 sandbox-local 又想装一个自己的沙箱，忘了把前者 disabled）。要真正做到"并存"必须显式隔离：ctx.isolate(name)（context.ts:119）或组补丁里的 isolate: { sessionQuery: true }（session-search/cordis.patch.yml:5）。这里的坑是：报错信息只写了"谁先注册的"，没写"你该去 disable 谁"，排查时得自己回去翻补丁栈。

坑 3：inject 写错名字 → 插件静默不激活

触发条件：插件的 inject 里有一个服务名，整个树里没有任何插件提供它（打错字、或者对应的插件被 disabled: true 关掉了）。

后果：fiber 永远停在 PENDING。_refresh() 发现某个名字没实现，epoch 就是 INACTIVE，插件体一行都不跑（fiber.ts:611-623）。如果它不在必需名单里，启动只是打一行 warning。

源码里怎么防的：这是 DSH 明确设计过的诊断路径。auditStartupEntries 对 PENDING 条目会算出缺哪些服务并打印（app-boot/index.ts:873），最终文本形如 pending (waiting for service: X)（:883）。另外，运行期如果真去读一个"声明了但没激活"的服务，错误文本会被改写成 cannot get required service "X" in inactive context（reflect.ts:160），和"没声明就直接用"区分开。读启动日志里那几行 warning 是排查这类问题的唯一入口。

坑 4：waterfall 监听者漏写 return，链条退化成"谁都没处理"

触发条件：在 agent/request-error 之类的 waterfall 里做异步判断，写成 if (canRetry) { return { kind: 'retry' } } 但外层忘了 return await next()，或者反过来该调 next() 却没调。

后果：两种都糟糕。漏调 next() 会否决整条链，包括内置行为（events.ts:228）；调了 next() 但把结果丢掉、自己返回 undefined，则下游的决策全部丢失，调用方看到的是"没人处理"。在 agent/request-error 上表现为：请求失败但不重试、直接抛 LlmError（agent.ts:523）。

源码里的写法：看 llm-retry 怎么处理的——超过上限时显式把控制权交出去：return next()（llm-retry/index.ts:223）。serial 那边同理：判定"我处理了"用的是 isBailed，返回 undefined 等于没处理（events.ts:13）。规则可以一句话记：waterfall 必须二选一——要么 return next()，要么自己 return 一个决策；serial 必须显式 return 一个真值。

坑 5：注册顺序能改变行为，而顺序由 YAML 行序决定

触发条件：两个插件监听同一个 waterfall 事件，行为取决于谁在外面。

后果：调换 YAML 的行序就能改变结果——尽管文件开头写着"行序不带加载语义"（cordis.patch.yml:12）。那句话只说对了激活时机：谁先激活由服务可用性决定，但监听者的排队顺序仍按注册顺序，prepend 还能再往前插。

源码里的实例：spill-policy 用 prepend: true 把自己放到 post-execute 队首（spill-policy/index.ts:133），先 await next() 拿全部下游结论再决定要不要转存。它对 read 工具的结果特意不转存（:135）——如果它排在别的监听者后面，别人已经改了 content，这个判断的前提就不一样了。防的方式：需要"包住所有人"的监听者显式写 prepend: true，不要指望 YAML 行序。

坑 6：热重载与配置回写

触发条件：改了 profile 的 cordis.patch.yml，或让某个插件自我卸载。

后果 A（配置被污染）：Loader 提供 write() 持久化，插件自我卸载时会把当前树回写到 cordis.yml（loader/index.ts:165）。因为根配置是"空列表 + 全靠补丁叠"的结构，一旦被回写，下一次启动会把每个 bundle 的 insert 重复叠一遍。profile-boot 的防法是每次启动都重写空根（profile-boot.ts:171），注释里直接点明了这个原因。

后果 B（卸载时不清理）：fiber 卸载会并行跑完所有 effect 的 disposer（fiber.ts:676）。但但如果插件持有的是没被包进 effect 的资源——自己写的定时器、外部连接、挂在模块级变量上的状态——Cordis 不知道它的存在，热重载会让它累积。真实代码里怎么防的：llm-retry 在插件卸载时主动中止所有正在等待的重试（llm-retry/index.ts:256），也就是自己把"等待中的 Promise"登记进 effect 的清理链。这是写插件时的标准动作：凡是有"还在等"的东西，卸载时必须显式 abort。

另外注意 headless 直接关掉了热重载：headless bundle 里 disabled: true（bundle/headless/cordis.patch.yml:33）就是那条 HMR 行。一次性任务不需要为重载付出复杂度。
