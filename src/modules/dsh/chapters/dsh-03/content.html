第 3 章

上下文工程：系统提示、运行时上下文、压缩与 spill

前两章讲了骨架：DSH 的整体架构和Cordis 与装配。这一章讲一件更贴肉的事：每一次模型请求，喂进去的那坨东西是怎么拼出来的。把这一章读完，你应该能回答三个具体问题：为什么 DSH 的提示词每步都重新组装却还能命中前缀缓存；为什么运行时上下文（"现在是几点""沙箱是什么模式"）是一条 user 消息而不是系统提示的一部分；以及当一个会话长到快撑爆上下文窗口时，系统做了哪些事、按什么顺序做。

整体一句话：DSH 把"上下文"拆成了三层，分别有不同的生命周期和不同的稳定性，然后在请求边界上按需拼接。稳定层是系统提示（system/message，只在内容真的变了时才动）；刷新层是运行时上下文快照（user/message，每步重新渲染，但只有变了才写日志）；裁剪层是压缩与 spill（把历史里太长的部分替换成摘要或落盘引用）。三层都在会话日志里留下事件，所以整条历史可回放。

一次请求的上下文由谁拼成

拼装这件事有一个唯一的服务负责：ctx.systemPrompt（core/system-prompt/src/index.ts:425）。它本身不写任何提示词内容，它是一张登记表：谁想往提示词里加一段，就在这张表上登记一段，并给一个 order 数字。真正的文本由各个插件提供。

登记表上有四类东西，这是理解这一章的关键：

类别登记方法去处典型贡献者
section（提示词段）ctx.systemPrompt.section()拼进系统提示，用 join('\n\n') 连工具说明、persona、plan mode
context（运行时上下文）ctx.systemPrompt.context()拼成一条 user 消息快照工作目录、沙箱策略、审批策略
variable（变量）ctx.systemPrompt.variable(){{name}} 占位符的取值provider / model
tool provider（工具 schema）ctx.systemPrompt.tools()请求的 tools 字段工具注册表（自动登记）

工具注册表在构造时就把自己挂上去了，所以业务包不需要手写这一步（core/tools/src/index.ts:855）。

这张表短得可疑，值得停一下：运行时上下文的槽位只有四个。这不是没写完，而是一个设计约束——运行时上下文是每步都要重新渲染、而且要尽量少变的东西，所以 DSH 只允许少数几个“真正随时会变的状态”进来（工作目录、沙箱模式、审批策略、子代理委托）。想加第五个，得先在这张表上加号，也就是得改 core 的代码。

为什么用 Central 编号：前缀缓存（KV cache）只认逐字节相同的前缀。如果每个插件用自己觉得合理的 order，两个插件的相对顺序就依赖于加载顺序或名字排序，前端一变顺序，整段前缀就失效。中央编号让"提示词长什么样"成为一个可以静态审阅的常量表。

assemble：一次模型调用前的流水线

拼装入口是 assemble()，每个 step 都会调一次（index.ts:610）。它做的事可以拆成六步：

  1. 合并作用域：全局层 + 该 Agent 的 scope 链，近的作用域覆盖远的（注释原文 "Scoped variables shadow globals."，index.ts:615）。
  2. 按 name 去重：同名的段/上下文后注册的覆盖先注册的（index.ts:627）。
  3. 按 order 排序（index.ts:648）；order 相同时按名字排（index.ts:245），所以同样一组插件，不管以什么顺序注册，拼出来的系统提示都逐字相同，这是前缀缓存能命中的前提。
  4. 上下文按 order 排序，required 的即使被 suppress 也保留（index.ts:668）。
  5. 跑 waterfall system-prompt/assemble，让插件在最后一刻改装配结果（index.ts:673）。
  6. 强制修正：如果有 complete 段，返回的 sections 只剩它一个（index.ts:681）。

第 5 步是个很有 DSH 特色的设计：每次装配都是一个 waterfall。工作目录插件正是靠这个在水位线上"补一刀"——它注册的 context 是一个纯函数，但真正的目录读取是异步的，所以它挂在 assemble 上先 await 目录就绪，再修装配结果（session/working-directory/src/index.ts:97）。

注意那句开场白："This snapshot supersedes earlier runtime-context snapshots."——这是运行时上下文的设计核心。它不是增量追加，而是"以最新一份为准"。历史里那些旧的快照仍然留在日志里，但模型被明确告知忽略它们。这样做的代价是浪费 token，收益是每步只需要写一条新消息，不用去改历史。

还有一个特殊标记值得知道：renderPrompt 里的 interpolate === false 分支表示"这段文本里的 {{...}} 是字面量，不要去解析"。工具生成的文档、包含花括号的目录名都需要这个开关，否则会在装配时报"未知变量"。

两次装配（pre-step 一次、请求前一次）不是冗余。第一次是为了让 agent/pre-step 的监听者能拿到 prompt 信息做决策（比如压缩插件要判断当前提示词占多少 token）；第二次是为了让"只有到准备请求才知道的事"（路由到哪个 provider/model、模型是否支持图片）能反映进上下文。refreshContext 只重算 context 部分，不重跑 sections（index.ts:578），并且会把 waterfall 里刚补上的 required 条目按 order 插回正确位置（index.ts:595）。

稳定层与刷新层：为什么系统提示不走普通的"每步重写"

这是全章最重要的一节。如果你只记住一件事，记这个。

系统提示的三种去向

系统提示渲染出来之后，去向不是唯一的。决定去向的是路由能力和序列状态，代码在 SystemPromptProjection.project() 里（core/agent-loop/src/runtime-context.ts:65）：

  project(rendered: string, input: SystemPromptDecisionInput): SystemPromptCommit[] {

    const nodes = this.systemNodes()

    const head = nodes[0]

    if (head === undefined) {

      return [{ message: createSystemMessage(rendered), intent: { surfaceOp: 'append' } }]

    }

    const latest = nodes.findLast(node => node.text !== '') ?? head

    if (!input.inHistory || input.startsSeries || rendered.length === 0) {

      const updates = nodes.slice(1).filter(node => node.text !== '')

        .map(node => this.replace(node.seq, ''))

      if (head.text !== rendered) updates.push(this.replace(head.seq, rendered))

      return updates

    }

    if (latest.text === rendered) return []

    return [{ message: createSystemMessage(rendered), intent: { surfaceOp: 'append' } }]

  }

core/agent-loop/src/runtime-context.ts:88-103

读这段代码要抓住一件事：它返回的不是"要写什么"，而是"相对于已有历史要改哪里"。三种情形：

  1. 还没有系统提示（head === undefined）→ append 一条新事件。注释特别强调："The first prompt, even empty, reserves surface node 0."（runtime-context.ts:59）——哪怕提示词是空的也要占住第 0 号位置。
  2. 路由不支持在历史里更新提示词，或者这是一个新序列，或者提示词被清空了（第 95 行的三个条件）→ 把第 0 号节点替换成新内容，同时把后面所有非空的系统节点替换成空串。
  3. 路由支持在历史里更新，且序列继续 → 内容没变就什么都不做（返回 []）；变了就 append 一条新的系统消息在历史末尾。

第 3 种情形是理解"前缀缓存"的关键。DeepSeek 的模型声明了 systemPromptUpdate: 'in-history'（llm/llm-deepseek/src/models.ts:12），意思是这个模型接受在对话中途出现一条新的 system 消息。于是提示词变了的时候，DSH 不去动最前面的那条（动了就整段前缀缓存全废），而是在末尾追加。前面的所有历史保持逐字节不变，缓存全部命中，只有新追加的那一条需要重新算。

反过来，如果路由不支持中途换提示词（比如某些只认开头一个 system 字段的协议），那就只能改第 0 号节点。代码此时会顺手把第 0 号变成"唯一有效的系统提示"，把后面所有非空节点清空——这样历史里不会留一堆互相矛盾的旧提示词等着模型自己去猜哪个算数。

"序列"是什么

startsSeries 这个入参来自调用方，判断条件有三条或的关系（core/agent-loop/src/agent.ts:416-421）：pre-step 监听者显式声明了新序列、surface 自上次请求以来被改过（requestSurfaceGeneration !== surface.contentGeneration，agent.ts:419）、或者工具 schema 变了而路由不支持工具热更新。

为什么"surface 被改过"要重新起一个序列？因为已经有别的东西破坏了前缀（最典型的就是压缩：它把中段的历史换成了一条摘要）。既然缓存注定要全废，那不如顺手把提示词也折叠回第 0 号，让历史更短更干净。这是一条很务实的规则：缓存已经付过的代价，不要让它白付第二次。

运行时上下文为什么是 user 消息

运行时上下文走的是完全不同的机制，代码在 RuntimeContextProjection（runtime-context.ts:114）：

  project(current: string, sections: readonly ContextSnapshotSection[]): UserMessage | undefined {

    if (this.retained === undefined && current.length === 0) return

    const snapshot = current.length === 0 ? CLEARED : current

    if (this.retained?.text === snapshot) return

    return createUserMessage({

      content: [{ type: 'text', text: snapshot }],

      // The cleared marker has no contributions left to attribute.

      source: sections.length === 0

        ? { kind: SOURCE }

        : { kind: SOURCE, form: 'snapshot', sections },

    })

  }

core/agent-loop/src/runtime-context.ts:152-163

三个设计点：

  • 它是 user 角色，不是 system。为什么？因为 system 消息在多数协议里只有开头那一条是"权威"的，中途出现会被当成补充说明；而 user 消息天然就是"对话的一部分"，追加一条不改变前面任何字节。把会变的东西放进 user 消息，就是保证 system 那一层（缓存前缀里最值钱的一段）永远不动。
  • retained 的三态：注释写得很清楚，undefined 表示"从来没有过快照"，null 表示"曾经有过但现在没有了"（runtime-context.ts:115）。这个区分是为了让"第一份快照是空的"和"快照被清掉了"有不同行为：前者什么都不写（if (this.retained === undefined && current.length === 0) return），后者要写一条"已清空"的墓碑消息，否则模型会一直以为旧快照还有效。
  • 内容没变就完全不写。返回值是 undefined 时调用方什么都不 append。步与步之间大部分上下文是一样的，"没变"是常态，所以这条早返回省掉了大量日志写入和 token。

墓碑文案是一条常量（runtime-context.ts:20），正面文案则是 joinContextSections 里那两行开头。

写日志时用的是 surfaceOp: 'append'（agent.ts:430），系统提示则带着 intent（可能是 append 也可能是 replace，agent.ts:423）。这就是"surface 操作"的用法：一条日志事件既记录了内容，也记录了它如何改变"模型可见历史"。replace 不会删掉被替换的事件，事件仍在日志里，只是不再出现在推导出的消息列表里。

坑 1：多段、非文本的系统消息会被当成"无效"整条清掉。回放逻辑用 systemNodes() 扫描存活节点，判定文本用的是 textOf()——它要求 content.length === 1 且那一个块是 text（runtime-context.ts:28-29）。一段由两个 text 块拼成的系统消息，或者带 reasoning 块的系统消息，textOf 返回 undefined，而 content.length === 0 ? '' : textOf(...) 的写法会把它记成"空文本"。测试专门钉住了这个行为（tests/system-prompt-projection.spec.ts:43）。后果不是崩溃，是你以为写进去的提示词在下一轮就静默消失了。写自定义系统消息时，保持"一条消息、一个 text 块"。

context/ 这一组插件：谁往上下文里放了什么

packages/context/ 这一组插件的共同点是：只贡献上下文，不定义工具。而且它们贡献的位置分两种截然不同的方式——有的往系统提示的 section 里加，有的往运行时上下文里加，有的干脆自己写一条独立消息。逐个说。

注释把顺序讲明白了：用户的直接提问在前，指令上下文紧跟其后，驱动追加的运行时上下文最后。这不是审美问题——它决定了模型看到的三条消息的相对位置，也是缓存稳定性的要求（每次位置一样，前缀才一样）。

time-context：唯一一个"每次都可能不同"的

时间是最典型的运行时上下文，也是最容易被写错的。DSH 的实现有意思的地方全在"什么时候真的写进去"上。

它不注册 context 提供者，而是自己在 agent/pre-step 上追加一条消息（context/time-context/src/index.ts:185）——和 agent-instructions 同一套路。原因也一样：时间不需要每步都刷。

频率控制靠一个可配置的下限，默认 10 分钟：

  const refreshIntervalMs = config.refreshIntervalMs ?? 600_000

压缩：三种触发、四种插件、一个替换

会话长了以后历史会超过上下文窗口。DSH 的应对不止"压缩"一种，而是一整套按代价递增的工具。先看全貌：

服务契约：一个抽象类，三个抽象方法

压缩的可插拔点是一个抽象服务 CompactionEngine（compaction/compaction/src/index.ts:119），注册为 ctx.compaction。它定义了三种操作：

  • compactIfNeeded(agent, trigger, signal)——自动压缩入口，trigger 只有两种取值（compaction/src/index.ts:32）。
  • compactNow(agent, signal, sourceCommandId?)——手动压缩，必须在 Agent 空闲时跑（compaction/src/index.ts:162）。
  • compactRegion(start, end, agent, signal?)——按 surface 位置区间强压。注释里有一句很容易被忽略但非常重要的话："start and end name an inclusive span by surface position, not numeric seq order; replacements can make visible seqs non-monotonic."（compaction/src/index.ts:169-171）——因为 replace 会让可见的 seq 不再单调递增，所以区间是位置不是序号。这是个真实的坑（见下文）。

契约还规定了一件事：压缩成功后，代表摘要的那条 user 消息必须带 compact-checkpoint 标记（compaction/compaction/src/checkpoint.ts:49）。下游（比如运行时上下文投影）靠这个标记识别"这里发生过一次压缩"，从而知道自己那条快照可能被折叠掉了。

  • user/message + op: 'replace' 是真正的改写：一条新的用户消息占据 start 到 end 这个区间的位置，区间里的所有历史节点不再出现在推导出的消息列表里。
  • sourceEventSeqs 把这次替换指向"起止标记 + 摘要事件 + 所有被遮蔽的事件"。这是显式引用，不是靠位置推断。运行时上下文投影正是靠它知道自己那条快照被折叠了（runtime-context.ts:138-142）——注意源引用是必需的，没有它，一个装了运行时上下文插件的会话压缩之后会永远以为旧快照还在，再也不刷新。

生成摘要时还有一个面向缓存的优化：摘要请求复用了原对话的系统提示和工具定义作为前缀，这样 provider 那边的 KV cache 仍然能命中（index.ts:237-241）。换句话说，连"为了省上下文而做的压缩"这个动作本身，都在想办法省钱。

图片被挤出去的时候

图片占了 token 预算但模型发不出去时，provider 返回 IMAGE_OFFLOAD_REQUIRED_CODE。这个插件挂在同一个 agent/request-error 上（compaction-image-offload/src/index.ts:27），做法是在 surface 上记一条"这些图片以后的请求都不再发送"（image-offload.ts:44），然后重试。

注释里那句话是全章最值得抄的一句设计说明："A durable surface repair, not a provider retry: it spends no retry budget and logs no retry event."（compaction-image-offload/src/index.ts:29）——它是修历史，不是重试请求，所以不消耗重试预算。这个区分非常 DSH：一个动作到底是"又一次尝试"还是"改了要发的东西"，在日志和配额上是两回事，不能混。

它挑的是最旧的、还留在上下文里的图片出现（image-offload.ts:8-10），理由和 pruner 保守留尾一样：最近的东西更可能还在被用。它还单独注册了一个消息投影（projection.ts:1），让"被卸载的图片"在推导消息时变成一段占位文本。

存到哪、怎么防路径穿越

默认根目录是操作系统临时目录下的一个现场创建的私有目录（store.ts:36-39），会话目录名是 session id 的 sha256 前 12 位（store.ts:79-80），文件以 0o600（只有自己能读写）独占创建（store.ts:115），目录以 0o700 创建。

路径穿越的防护是一段独立的、可单测的纯函数 encodeSegment。它的做法很朴素但很严密：

export function encodeSegment(raw: string): string {

  if (raw.length === 0) return '~'

  if (raw === '.') return '~002E'

  if (raw === '..') return '~002E~002E'

  let out = ''

  for (let i = 0; i < raw.length; i++) {

    const code = raw.charCodeAt(i)

    const ch = String.fromCharCode(code)

    out += ch !== '~' && /^[A-Za-z0-9._-]$/.test(ch)

      ? ch

      : '~' + code.toString(16).toUpperCase().padStart(4, '0')

  }

  return out

}

spill-local/src/store.ts:55-68

关键性质是单射：因为 ~ 自己也被转义成 ~007E，所以不存在两个不同输入编码成同一个输出。注释把这条性质说得很清楚："Each code unit is kept literal ... or escaped as ~XXXX; ~ is itself escaped, so the mapping is reversible and distinct inputs never collide."（store.ts:41-54）。为什么单射重要？因为如果两个不同名字可能撞到同一个文件，一个会话就可能覆盖另一个的内容。而 . 和 .. 两个整段 token 被特殊处理成 ~002E / ~002E~002E，就永远不可能穿越目录。

清理策略是"启动时扫一遍，删掉超过 cleanupPeriodDays（默认 30 天）的文件"（spill-local/src/index.ts:68），设成 0 就完全关掉。为什么要保留 30 天而不是用完就删？注释回答了：一个恢复或分叉出来的会话可能还在引用旧地址（index.ts:42-47）。这是"地址的持久性"和"磁盘占用"之间的一个明确取舍。

返回给模型的东西长什么样

通知的格式是一个模板拼字符串（spill-policy/src/notice.ts:21-24），拼出来大致是：

(N bytes omitted. Omitted K images. Full formatted result stored at: <路径>. <检索指引>)

（括号内的具体措辞由 describeOmitted 与后端的 retrievalHint 提供；LOCATION 常量是 " Full formatted result stored at: "，notice.ts:7。此处措辞为教学示意，实际字节数与省略图片数由运行时决定。）

模型拿到的不是"什么都没有"，而是一段有损预览：保留头尾、中段换成 [...]、末尾接上面那条通知。构造过程有一处细节可以看出实现者的谨慎：通知本身占 token，所以预算是先扣掉通知再算能保留多少（spill-policy/src/index.ts:112），而且如果通知自己就超预算，直接抛错——外层兜住后结果是"不转存"（spill-policy/src/index.ts:113）。测试覆盖了这个边界（tests/spill-policy.spec.ts:185）。

相邻的文本块会被合并（spill-policy/src/index.ts:120-125），注释解释是为了"在 wire 上和预览里只付一次框架开销"。这类小优化在提示词工程里是复利：每次请求都省一点。

为什么挂在 tools/post-execute，而且 prepend

两个问题，两个答案。

为什么是 post-execute 而不是 execute？因为 spill 要处理的是"最终给模型的展示结果"，而不是工具的程序返回值。工具流水线把这两件事分开了：tools/execute 包住工具本体，tools/post-execute 决定最终展示结果（core/tools/src/index.ts:167）。挂在 post-execute 意味着 spill 不会影响工具代码本身看到的返回值——这一点在 PTC（模型写代码调用工具）模式下很重要，因为程序里的值必须保持完整，只有给模型看的副本才受限。测试名直接写了这条："bounds the tool/ptc-dispatch copy of an oversized sub-result while the program value stays whole"（tests/spill-policy.spec.ts:288）。

为什么 prepend？因为 post-execute 是 waterfall，而 spill 想在别人都算完之后做最后一道裁剪：它先 await next() 拿到下游决策，再决定是否替换（spill-policy/src/index.ts:133-136）。prepend 把它放在链头，于是它是"最后看到结果的人"。测试里有两条正是验证这个顺序的："wraps an earlier tool-owned projection before applying the generic cap" 和 "bounds content a downstream post-execute listener replaced"（tests/spill-policy.spec.ts:549）。

另外两个细节：

它只处理 accept 决策、且决策里没有 value 的结果（spill-policy/src/index.ts:135）。有 value 表示下游做了"程序值替换"，那种结果不该被 spill 动。

read 工具的结果永远不 spill。这是最直白的一条防循环：read 的作用就是读文件，如果它读一个大文件时被 spill 成"预览 + 一个路径"，模型看到路径会再去 read 那个路径——读到的又是预览。测试名就是这条规则本身："never spills the read tool result (avoids a read → spill → read loop)"（tests/spill-policy.spec.ts:255）。

坑 3：spill 的失败模式全部是"静默降级"，你得主动去看日志。存储失败、没有可读的附件路径、当前模型没有图片计价器、通知本身超预算——这四种情况走的是同一个 catch：spill-policy/src/index.ts:127-130，结果是 ctx.logger.warn(`spill-policy: ...; keeping the inline content`) 然后返回 undefined（不替换）。对用户来说，表现是"这次上下文特别长，但我没做错什么"。契约把这个选择写在了 saveText 的说明里：存储失败时调用方决定怎么降级，而策略选择"保留内联内容"——因为丢掉工具结果比浪费 token 糟得多。测试分别钉住了"没有后端"和"保存失败"两种情况（tests/spill-policy.spec.ts:508、:497）。排查方向：搜一下 spill-policy: 开头的警告。

坑清单

前面散在各节的问题集中在这里，每条都落到代码或测试。

坑 A：压缩把运行时上下文折掉了，插件却不知道

触发条件：一个装了运行时上下文插件的会话（时间上下文、或任何走 RuntimeContextProjection 的贡献）发生压缩，而被折进摘要的那段历史里正好包含最新的那份上下文快照。

后果：投影层以为"我已经有 retained 快照了"，于是下一步内容没变时返回 undefined——什么都不写。但那份快照实际上已经被摘要取代，模型再也看不到它。

源码怎么防的：投影构造时订阅 session/event，遇到一个带 sourceEventSeqs 且包含自己 seq 的替换事件，就把 retained 清成 null（core/agent-loop/src/runtime-context.ts:138-142）。null 这个态存在的唯一理由就在这里：它让 project() 的早返回条件失败（retained === undefined 才早返回），于是下一条快照会被重新写出。测试覆盖了这条路径（tests/runtime-context.spec.ts:24）。

教训：如果你写一个"记住自己最后写了什么"的上下文贡献者，必须同时能识别"我写的东西被别的东西替换掉了"。DSH 靠的是 replace 事件带 sourceEventSeqs，所以这个识别是精确的、不靠猜。

坑 B：区间用位置而不是序号

触发条件：想手动调 compactRegion(start, end)，参数从日志里的 seq 拷过来。

后果：压缩到错误的区间，或者直接因为"区间反转/不平衡"被拒。

源码怎么说的：契约注释明写 "start and end name an inclusive span by surface position, not numeric seq order; replacements can make visible seqs non-monotonic."（compaction/src/index.ts:169-171）。原因在 replace 的语义：一条新事件的 seq 比被它替换掉的老事件更大，但它占据的位置更靠前。所以 surface.nodes 这个数组的下标才是位置，seq 只是标识。测试里有一条专门检查区间覆盖系统提示头时会被拒（tests/compaction-basic.spec.ts:1099）。

教训：任何"记住一个位置"的代码，在系统支持"替换"之后都要区分"身份"和"位置"。这和日志系统里的 seq / 数组下标的关系是同一个问题。

坑 C：压缩正常失败，但 warning 长得像噪音

触发条件：主动压缩因为任何原因失败（模型没配 contextWindow、pruner 配置的保留量比阈值还大、摘要生成出错等等）。

后果：turn 继续跑，用户完全无感；下次仍然在同一个点上失败。如果不看日志，会以为"压缩没生效"是随机现象。

源码怎么处理的：两个不同层次的降级。TargetPressureConfigError 这种"配置错"会每个路由目标只警告一次（index.ts:166-170，避免每步刷屏）；其它错误每次警告。测试分别覆盖了"操作失败继续跑"和"每个目标只警告一次"（tests/compaction-basic.spec.ts:1739）。

教训：自动压缩这类"后台优化"必须设计成不影响主流程 + 可诊断两条同时成立。"降级为 warning"是正确的，但必须保证这条 warning 真的能被人找到——这也是为什么 DSH 里的失败都分类成了具体的 code（compaction/src/index.ts:35-41）。

坑 D：spill 与 read 的循环

触发条件：不加区分地对所有工具结果做 spill，包括 read。

后果：模型 read 一个大文件 → 拿到"预览 + 路径" → 为看全内容再 read 那个路径 → 又拿到预览 → 无限循环，每一步都烧 token。

源码怎么防的：写死在判断里（spill-policy/src/index.ts:135），并且有专门的回归测试（tests/spill-policy.spec.ts:255）。

教训：这是一种反馈环类的坑——一个"为了减轻上下文压力"的机制，可能制造出"更多上下文压力"。识别方法是问一句：这个工具的输入是不是可能指向它自己的输出？任何"压缩/转存/摘要"机制都要过一遍这个检查。

坑 E：agent-instructions 在空 turn 上丢了 pending 上下文

触发条件：指令刷新排到了一个 step 上，而这个 step 的 claimed 消息为空（比如一次纯粹的唤醒）。

后果：如果不管，这段指令上下文会被当成本轮唯一的内容发出去，白烧一次模型调用。

源码怎么防的：显式判断"这个 step 会不会真的走到模型"，不会的话就把上下文留在 inbox 里等下一步，而不是塞进 messages：
